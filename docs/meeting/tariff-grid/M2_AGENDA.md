# M2 — отношение сетки к существующему рельсу прав сценариев

**P1 —** Как тарифная сетка соотносится с уже работающим рельсом прав сценариев (`Tariff.entitledTariffSkus` → сервер → wire → конфиг клиента → бейджи `bundled/community/entitled/locked`): поглощает его, надстраивается над ним или он становится её проекцией? Единственный вердикт M2 — выбранное отношение с названными основаниями, точка единственного источника истины о правах и судьба поля `entitledTariffSkus` (остаётся как есть · становится проекцией · выводится из матрицы · иное). **Список посылок обязателен.**

# Заседание tariff-grid — общее задание

> Слово капитана 29.07: заседание по **тарифной сетке**, вердикт обязан включать **план её интеграции**.
> M0 ратифицирован владельцем; M1 вынес форму — сетка есть versioned контракт.

## Задание (одно на все вопросы)

Спроектировать тарифную сетку как машинный носитель прав (три тарифа, разнородные права
внутри) и план её интеграции в работающие контуры — кабинет, борд, клиент, детекторы — с
честным разделением: что сетка включает сегодня, а что лишь ВЫРАЗИМО ею и строится отдельно.

## Вердикт M1 (вход этой комнаты, не пересматривается)

- Объект — **versioned декларативный контракт** `TariffGridDocument`: `EntitlementRegistry`
  (определения прав) + матрица **SKU × entitlementId → EntitlementValue**.
- Пять родов права — **закрытый kind-union**: `quota{limit,unit}`, `catalog{catalogId}`,
  `instrument{enabled}`, `gated{enabled}+preconditionId`, `produce{enabled,scope?}`.
- **Home истины — сервер** (канон контура office). Клиент получает **wire DTO** и пользуется
  **pure resolve**: `resolveEntitlement(grid, sku, id)` → entitled/not_entitled + payload +
  `unmetPreconditions[]`. Плагины, борд и UI — потребители проекции, не авторы сетки.
- **Deny-by-default**: нет ячейки / mismatch kind / неизвестный id → not_entitled.
  Полнота: для каждого SKU и каждого id реестра — ячейка.
- Отдельно записано: **рельс `entitledTariffSkus` не ломается**; стыковка — предмет M2.
  `AdminGuard` и тарифные права — разные оси.

## Материал вопроса M2 (вещдоки дерева)

Рельс прав сценариев замкнут от базы до экрана:
`Tariff.entitledTariffSkus` (Prisma) → `node-realtime.service` читает права мембраны →
`node-realtime-wire` валидирует → `device-board-module-config.entitledTariffSkus` у клиента →
`ClientUserCaseCatalogService` фильтрует каталог → бейджи `bundled/community/entitled/locked`
(`user-case-settings-gate`). Ключ прав — `tariffSku` на карточке каталога; класс —
`UserCaseTier = 'bundled' | 'tariff' | 'community'`.

Смежное: `maxUserWorkspaces` (=3) и `maxNodesPerMembrane` (=1) — числовые потолки, живущие
на том же `Tariff`, но вне списка SKU. У узлов палитры прав нет вовсе.

## Границы вопроса M2

- **Не решается здесь:** троичность исхода на экране (M3), устройство двух памятей (M4),
  производство своего (M5), смена тарифа и промокод (M6), зубы (M7), план интеграции (M8).
- Форма сетки из M1 не пересматривается — M2 отвечает только за ОТНОШЕНИЕ к рельсу.
- Ядро процедур не переписывается; пользователей нет — миграционных ветвей не проектировать.
- Запрет двух источников истины о правах — ограничение задания, а не предмет спора.
