# Повестка M5 — заседание server-plugin-foundation

**Q5 — Какова форма самоописания плагина для витрины: что объявляет плагин о себе, чтобы клиентская страница показала и включила его, не зная заранее?**

Единственный вопрос комнаты. По ратифицированному DAG M5 ждёт M1 (сыгран) и M2 (сыгран);
задаёт форму видимости для M6 («живой плагин должен быть виден на витрине», Т3.11).

Что комната обязана решить (грани одного вопроса):

- Состав самоописания: M1 отдал `ShowcaseManifest extends PluginManifest` с полями на
  этой комнате; со шторма даны Т3.6 (сервер отдаёт данные для картины, не картину;
  форма показа объявлена в самоописании) и Т1 (переключаемость на уровне модуля).
  Что именно объявляется: человекочитаемое имя? описание? форма показа? схема данных
  результата?
- Словарь форм показа: клиентская страница рисует по объявленной форме — закрытый
  список форм первой волны (ряд? таблица? разметка зон? гистограмма?) с гейтом
  расширения; произвольный простор — против Т3.6.
- Канал чтения: как клиентская страница узнаёт список плагинов дома и их самоописания
  (метод IPluginHost? HTTP-эндпоинт дома? — именовать канал, не проектировать роуты).
- Канал включения: Т1 даёт переключаемость — как страница включает/выключает плагин
  (тот же канал? отдельный? кто вправе) — именование и границы прав, детали UI — вне
  предмета.
- Самоописание НЕ-витринных родов: обработчик и отчёт видимы ли странице (для
  включения по Т1) — и чем их самоописание беднее витринного.

Посылки комнаты (даны, не обсуждаются): вердикт M1 (ShowcaseManifest extends
PluginManifest, поля определяет M5; пять базовых полей манифеста; PluginId); вердикт M2
(два дома, IPluginHost с getRegisteredPlugins(): ReadonlyArray<PluginManifest>); вердикт
M3 (RunRecordView — ответ чтения результатов со stale-пометкой); вердикт M4 (канал
request для постфактум-запуска; словарь PLUGIN_TRIGGERS закрыт); конспект шторма (Т1
переключаемость; Т2 пример владельца: сортировка по громкости, пиковые зоны, аномалии,
тренды в реальном режиме; Т3.6 данные для картины, не картина); границы MEETING_BRIEF.md
(код — только после вердиктов; клиентская страница и её вёрстка — ВНЕ предмета собрания,
здесь только серверная сторона самоописания).

Требование к вердикту: назвать форму самоописания по всем граням с обоснованием против
альтернатив И полный список посылок вердикта (факт/норма) в том же прогоне. Список
посылок обязателен; лишняя посылка — тоже нарушение. Не проектировать: приёмку (M6),
клиентский UI, HTTP-роуты — только контракты и именование каналов.
