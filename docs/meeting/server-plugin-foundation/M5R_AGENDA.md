# Повестка M5′ — заседание server-plugin-foundation (переигрывание по вердикту аудита)

**Q5′ — Какова форма самоописания плагина для витрины, при том что базовый `PluginManifest` несёт РОВНО пять полей — `id` · `version` · `kind` · `mountTarget` · `triggers` — шестого нет, `enabled`/`label` в манифесте НЕ существуют (включённость — операция реестра, не поле манифеста), а расширять состав вправе только расширяющие типы родов (`ShowcaseManifest` и т.п.)?**

Единственный вопрос комнаты. Это переигрывание M5 по вердикту аудита 17.08: прежний
вердикт стоял на сочинённом составе базового манифеста («предположу рабочий состав»:
id, version, enabled, kind, label — находки A5-1/A5-2/A5-3). Состав базы дан в строке
вопроса поимённо и НЕ обсуждается; своя база не вводится.

Что комната обязана решить (грани одного вопроса):

- Состав `ShowcaseManifest`: какие поля добавляются ПОВЕРХ пяти базовых (со шторма
  Т3.6: форма показа объявлена в самоописании; прежний вердикт предлагал
  `displayForm: DisplayForm` обязательным и `description?: string` — переподтвердить
  или изменить, теперь на честной базе).
- Словарь форм показа `DisplayForm`: закрытый список первой волны (прежний вердикт:
  row · table · zone-map · histogram · time-series с лазейкой `x-${string}` и
  обязательной fallback-веткой страницы) — переподтвердить или изменить.
- Канал чтения: как страница узнаёт список плагинов дома и самоописания (прежний
  вердикт: единственный канал `IPluginHost.getRegisteredPlugins()`, narrowing по kind).
- Канал включения: прежний вердикт — отдельный метод `setPluginEnabled(id: PluginId,
  enabled: boolean)`, не канал request; границы авторизации — вне предмета.
- Самоописание не-витринных родов: видимы ли handler/report странице для
  Т1-переключения, и чем их манифесты беднее витринного (прежний вердикт: витринных
  полей у них физически нет в типе — переподтвердить или изменить).

Посылки комнаты (даны, не обсуждаются): M1_VERDICT.md — АВТОРИТЕТ словаря (пять полей
поимённо как в строке вопроса; PluginId branded `<org>.<kind>.<slug>`; включённость —
операции реестра enable/disable, НЕ поле манифеста; расширения — только через
HandlerManifest/ReportManifest/ShowcaseManifest; владелец словаря и гейты классов);
M2_VERDICT.md (два дома; IPluginHost.getRegisteredPlugins(): ReadonlyArray<PluginManifest>);
M4_VERDICT.md (канал request для постфактум; PLUGIN_TRIGGERS закрыт; сигнатуры с
PluginId, не сырыми строками); Т1 шторма (переключаемость на уровне модуля — норма);
Т3.6 шторма (данные для картины, не картина; форма показа в самоописании — норма);
Т2 шторма (примеры витрин владельца: сортировка по громкости, пиковые зоны, аномалии,
тренды — факт); вердикт аудита 17.08 (A5-1…A5-5); границы MEETING_BRIEF.md (клиентский
UI вне предмета; код после вердиктов).

Требование к вердикту: назвать форму самоописания по всем граням с обоснованием против
альтернатив И полный список посылок вердикта (факт/норма) в том же прогоне. Список
посылок обязателен; лишняя посылка — тоже нарушение. Базовый состав манифеста НЕ
переоткрывать — он в строке вопроса; `enabled`/`label` не вводить; вопросы прав вызова
в чужие комнаты не передавать (находка A5-5 — границы авторизации просто вне предмета
собрания).
