# Заседание «Регистрация в кабинете по промокоду панели» — M3 (К3) Порядок гашения и режим отказа

**Объединяющее задание (одно на всё заседание):** спроектировать контракт «кабинет ↔ панель офиса» для регистрации по промокоду панели так, чтобы сессии A, B, C, D исполнили его параллельно в своих файловых границах, а владелец завёл второй кабинет на бесплатном тарифе.

**Порядок M0 (ратифицирован владельцем 21.09):** M1 грант и дверь → M2 связь и ключ → **M3 порядок и отказ** → M4 форма; лендинг — сразу.

**M1 и M2 ратифицированы владельцем 21.09 — данности этой комнаты.** M1: дверь офиса `POST /v1/internal/cabinet/registration-codes/consume`, `mode: "check" | "redeem"`, 200 `{ ok: true, code, grant: "cabinet-register", uses: { used, max } }`, 409 `{ ok: false, reason }`, reason ∈ `not_found | revoked | expired | grant_mismatch | exhausted`; продуктовый путь зовёт только `redeem`, `check` не для формы (TOCTOU). M2: в сервере кабинета модуль `modules/office-registration/` с одним методом для C — `redeemRegistrationCode(code): Promise<RegistrationOutcome>`, исход `{ kind: 'ok'; payload } | { kind: 'refused'; reason } | { kind: 'office-unavailable'; detail } | { kind: 'config-invalid'; detail }`; таймаут 5000 мс; пара `OFFICE_URL`/`OFFICE_API_TOKEN` необязательна, без пары `APP_CONFIG.office === null`. Протоколы: `docs/seanses/cabinet-registration-promo-m1-grant-door-2026-09-21.md` (стр. 162–192), `…-m2-link-key-2026-09-21.md` (стр. 140–190).

## Вопрос M3 (ровно один)

**Q3 — В каком порядке сервер кабинета гасит код в офисе и создаёт пользователя, и что отвечает дверь регистрации при каждом исходе клиента, чтобы код не сгорал без пользователя, пользователь не появлялся без кода, а наружу уходила одна фраза?**

Вердикт обязан назвать: **порядок шагов** — проверки без побочных эффектов (флаги, длины, занятость логина, хеш) → удалённое гашение → локальное создание пользователя, или иной, и почему; **компенсацию** для каждой из двух полуудач: гашение прошло, `user.create` упал (логин занят гонкой, база) — что с кодом (сгорел; повторная попытка с тем же кодом невозможна — `exhausted`), что говорим владельцу кода, что пишем в лог; создание прошло, а исход гашения неизвестен (таймаут после отправки) — допускается ли по M2 (клиент не ретраит) и что делаем; **ответ двери `POST /v1/auth/register`** для каждого исхода клиента: `ok` → как сегодня (сессия); `refused` (все пять `reason`) → один HTTP-код и одна фраза наружу, `reason` — только в серверный лог; `office-unavailable` → код и фраза «попробуйте позже», пользователь не создан, код не погашен; `config-invalid` → код и фраза, и запись в лог как инцидент конфигурации; регистрация выключена (`ALLOW_REGISTRATION=false` **или** `office === null`) → как складываются два условия и что отвечает дверь; **ограничитель частоты** — нужен ли по образцу панели, ключ ограничения (адрес, логин), окно и порог числом, ответ 429; **DTO** — поле кода в `RegisterDto` (имя, обязательность, нормализация — трим, регистр, как в панели `codePrefix`/`normalize`); **подключение клиента** — как `AuthService` получает `OfficeRegistrationBridgeService` (импорт модуля M2 в `auth.module.ts`) и в чьих это границах; **зубы C** — каждый исход клиента с подменным клиентом (не сетью), гонка двух регистраций одним кодом с `maxUses=1` (одна проходит), гонка одним логином, регистрация выключена по каждому из двух условий, ограничитель; **что НЕ строить**.

**Чего M3 НЕ решает:** тексты и форму браузера (M4); контракт двери (M1) и клиента (M2) — их не менять; тарифные промокоды кабинета — не трогать.

**Список посылок** — вердикт обязан нести секцию с этим заголовком, где каждая посылка помечена типом (норма / факт / план) и опирается на **дословную** цитату реплики с ролью (реплики не нумеруются — цитировать дословно, не пересказом; строка таблицы вердикта — не реплика); посылка «из фактуры повестки» без реплики — не посылка. Вердикт без секции — заседание не состоялось (S-M2).
