# ADR-0029 — Регистрация в кабинете по промокоду панели: панель — правда, офис — мост, кабинет — потребитель

> **Статус:** ACCEPTED · 2026-09-23 — слово владельца на сам документ получено в чате ведущей 23.09 («ADR принят»); по канону каталога (`docs/adr/README.md`, шаг 4: после LGTM — ACCEPTED).
> **Внимание:** статус записи и сила решений — разные вещи. Сами решения **уже действовали** до принятия этой записи: комнаты M0–M4 ратифицированы владельцем 21.09 покомнатно (цепочка «протокол → аудит → сборка председателя → аудит сборки → слово владельца» — `docs/meeting/cabinet-registration-promo/MEETING_ACTIVE.md:9`), исполнение влито в ствол 22.09. Документ ничего не решает заново: он фиксирует уже ратифицированное и уже лежащее в стволе. Изменение любого пункта — новое заседание, не правка этого файла.

## Контекст

Слово владельца 21.09 (вход заседания, билет #2369): регистрация в кабинете открывается **условно** — по промокоду; промокоды **те же**, что у партнёров панели офиса; выдаёт и отзывает панель под ролью владельца; **новой системы промокодов в кабинете не заводить**; правда о коде — в панели. Цель — второй кабинет владельца для сценария тарифов
(`docs/meeting/cabinet-registration-promo/MEETING_ACTIVE.md:19`).

Контур из четырёх частей и трёх границ спроектирован заседанием `cabinet-registration-promo` за один день (21.09) и построен за следующий (22.09). Решение живёт в шести протоколах и карточке контейнера; в стволе — четыре части: A `ad9abd13`, B `03e61bb5`, C `2dbc1ae2`, D `3f338b21`, лендинг `b5a6a147` (`MEETING_ACTIVE.md:9`).

ADR записан по предложению команды в вечернем фидбеке 22.09, принятому владельцем утром 23.09, по одной причине: **ревью и будущие сессии читают код и ADR, а не протоколы заседания** — за 22.09 ревью четырежды выдало P1 на уже ратифицированное, включая требование `trim` пароля, прямо запрещённое M4 (`MEETING_ACTIVE.md:68`, билет #2403). Пока альтернатив не появилось, выбор надо зафиксировать одним документом.

Порядок комнат ратифицирован как DAG (`MEETING_ACTIVE.md:26–33`): лендинг вне графа → M1 (грант и дверь офиса) → M2 (связь и ключ) → M3 (порядок гашения и режим отказа) → M4 (форма, фраза, частота, лендинг).

## Решение

### Р1 — Панель офиса остаётся единственной правдой о коде

Тот же панельный `PromoCode` несёт грант-строку `cabinet-register`; отдельного вида кода и второй системы кодов в кабинете нет (M1, стр. 168). Грант — не раздел панели: он проходит нормализацию списка грантов, но мимо проверки доступа к разделу (M1, стр. 170).

Дверь — `POST /v1/internal/cabinet/registration-codes/consume` (M1, стр. 171) под внутренней охраной офиса, не под сессией панели и не под ролью владельца (M1, стр. 172). Запрос — `{ code, mode }`, оба поля обязательны, иной режим → 400 (M1, стр. 173). Успех `check` — без приращения, успех `redeem` — после (M1, стр. 174–175). Отказ — 409 `{ ok: false, reason }` с пятью причинами (M1, стр. 176) в ратифицированном порядке `not_found → revoked → expired → grant_mismatch → exhausted` (M1, стр. 177). Причина отдаётся **сервису** кабинета, но не пользователю (M1, стр. 178).

Атомарность — сериализованный участок «прочитать → проверить → приростить → записать» с инвариантом «успешных `redeem` не больше `maxUses`» (M1, стр. 179). Аудит-запись `redeem-cabinet-code` — только на `redeem`, на успех и на каждый отказ; `check` следа не оставляет (M1, стр. 180 + разъяснение Р1 ведущей, `MEETING_ACTIVE.md:56`). Деградация хранилища панели — 503 на обоих режимах, без тела отказа: это недоступность, а не одна из пяти причин (разъяснение Р2, `MEETING_ACTIVE.md:57`). Отзыв кода не откатывает погашенное, дальнейшее обращение отвечает `revoked` (M1, стр. 181). Дверь **не создаёт** пользователя панели и не копирует его гранты разделов (M1, стр. 182).

**Границы:** офис, каталог `modules/panel-users/`. Дверь живёт в отдельном контроллере: существующий объявлен под префиксом панели и классовым стражем сессии, и дверь туда не помещается (ратификация M1 с расширением границ A, `MEETING_ACTIVE.md:43`).

### Р2 — Офис для кабинета — мост с одним выходом наружу

Кабинет ходит к офису по паре `OFFICE_URL` / `OFFICE_API_TOKEN`; обе переменные необязательны, без любой из них регистрация выключена (M2, стр. 144–145). Схема пары — собственный файл кабинета, поле `office` попадает в конфиг приложения (M2, стр. 146–147).

Ключ — **общий** `API_INTERNAL_TOKEN` офиса, тот же, что у пусковика ночной охоты; отдельный ключ гостя-кабинета не вводится, потому что страж офиса знает ровно один ключ, а расширение стража — предмет закрытой комнаты M1 (M2, стр. 148). Носители у кабинета и пусковика разные, значение одно: смена ключа офиса ломает оба сразу (M2, стр. 150). Доставка — переносом значения на хост кабинета, не генерацией: генератор окружения пишет случайное и для ключа офиса не годится (M2, стр. 149).

Клиент — `OfficeRegistrationBridgeService` с **единственным** выходом наружу `officeFetch` и таймаутом 5000 мс (M2, стр. 151, 154). Поверхность для кабинета — один метод гашения, исход из четырёх ветвей (M2, стр. 152). Карта HTTP → исход: 200 → успех; 409 → отказ с причиной; 401/403 → неверная настройка; прочее, таймаут и сетевой сбой → офис недоступен (M2, стр. 153). Живость пары проверяется отдельным методом из глубокой проверки здоровья, а не на старте кабинета (M2, стр. 155) — урок 18.09: ротация ключа без двери проверки невидима, пусковик три недели молчал с 401 (M2, стр. 172).

**Границы:** сервер кабинета, новый модуль `modules/office-registration/` и файл-схема пары; общий файл схемы окружения не трогается — он принадлежит другой части (M2, стр. 147).

### Р3 — Кабинет: сначала все проверки без последствий, гашение — последним

Порядок двери регистрации ратифицирован (M3, стр. 181): выключено (флаг **или** пары нет) → ограничитель частоты → длины → код после обрезки пробелов → логин занят → хеш пароля → гашение кода → и **только** при успехе создание пользователя и сессии.

Обоснование — в самом решении (M3, стр. 182): общей транзакции двух хранилищ нет; создание до гашения даёт пользователя без кода, гашение до проверок сжигает код на валидации, а проверка кода перед гашением запрещена M1.

Полуудачи названы поимённо, а не оставлены на усмотрение: код сгорел, а создание упало → 403 и запись в лог, возврата гашения нет (M3, стр. 183); исход гашения неизвестен (таймаут) → создание не зовётся вовсе, 503 и запись в лог (M3, стр. 184).

Карта двери наружу (M3, стр. 210–215): выключено → 401; лимит → 429; отказ кода, локальный отказ и осиротевшее гашение → 403 одной фразой; офис недоступен или настроен неверно → 503. Причина отказа наружу не выходит — только в лог (M3, стр. 186). Ограничитель: ключ — адрес клиента, окно 600000 мс, порог 10, удар в контроллере до сервиса (M3, стр. 191). За обратным прокси адресом клиента считается **последний** элемент `X-Forwarded-For` — тот, что дописал прокси; первый элемент клиент может подделать (разъяснение Р6, `MEETING_ACTIVE.md:61`).

**Границы:** сервер кабинета, каталог `modules/auth/`; файл-помощник ограничителя заведён отдельно, потому что скользящее окно было только в офисе (ратификация M3 с расширением границ C, `MEETING_ACTIVE.md:45`).

### Р4 — Веб-кабинет: та же страница входа, фраза по статусу

Форма живёт на той же странице входа в двух режимах с переключателем; отдельного экрана и маршрутизатора нет, потому что маршрутизатора нет и в стволе (M4, стр. 130). Поля — логин, пароль, код приглашения, без повтора пароля; логин и код обрезаются по краям, **пароль не обрезается** — пробелы в нём часть секрета (M4, стр. 131, посылка 17 на стр. 174).

Фраза выбирается **только по HTTP-статусу**, английское сообщение сервера в интерфейс не попадает (M4, стр. 134–135): 401 — «Регистрация сейчас закрыта.», 403 — «Регистрация не принята.», 429 — «Слишком много попыток. Подождите 10 минут.», 503 — «Сервис временно недоступен. Попробуйте ещё раз.», иной статус и сеть — свои фразы. Все отказы 403 несут одну фразу: причина не различается (M4, стр. 134).

После 429 кнопка блокируется на 600 секунд; автоповторов нет; после 503 и сетевой ошибки повтор сразу (M4, стр. 136). Сессия после успеха берётся через контекст приложения, запись токена со страницы запрещена (M4, стр. 133). Лендинг несёт «Кабинет — вход по приглашению» и меняется на «регистрацию по приглашению» после выкатки формы (M4, стр. 138–139).

**Границы:** веб-кабинет, страница входа, слой обращения к серверу, контекст; тестовое окружение DOM заведено ровно под зубы формы (ратификация M4 с расширением границ D, `MEETING_ACTIVE.md:46`).

## Приёмка эпика (проверка решения, не его часть)

Критерий закрытия #2369 — второй кабинет владельца на `free-v1` через код из панели (`MEETING_ACTIVE.md:80`): владелец чеканит в панели код с грантом `cabinet-register` на одно использование → в кабинете переключается на создание учётной записи → логин, пароль, код → вход и мембрана нового пользователя на `free-v1` → повтор того же кода отвечает «Регистрация не принята.» → отзыв кода в панели, снова «Регистрация не принята.» → дверь без пары в окружении отвечает «Регистрация сейчас закрыта.».

Порядок выкатки и откат — `MEETING_ACTIVE.md:77–81`; выкатка идёт только по слову владельца, секреты переносит он сам. Живая проверка на стороне кабинета — поле `office_registration` в глубокой проверке здоровья, а не общий ответ о живости.
