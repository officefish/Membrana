# ADR-0028 — Парринг не раздаёт служебный токен: per-device ключ media по образцу NodeKey

> **Статус:** PROPOSED · 2026-08-20 (блок b5 спринта `studio-firebat-user-pairing`;
> автор формы — vesnin, конспект резчика
> [`../discussions/cut-studio-firebat-user-pairing.md`](../discussions/cut-studio-firebat-user-pairing.md);
> реализация — ОТДЕЛЬНЫЙ спринт `media-per-device-token`, не этот)

## Контекст

Наблюдаемое 20.08 (кодом): `PairService.pair` кабинета возвращает клиенту
`mediaToken: this.config.MEDIA_API_TOKEN` — **служебный токен всего media-сервиса**
(`packages/background-cabinet/src/modules/pair/pair.service.ts:107`). Клиент кладёт его
в `localStorage` (до b2 — напрямую; после b2 — через порт, но web-адаптер тот же
localStorage) — на узле это плоский файл на диске. Итого: **каждый спаренный клиент
каждого пользователя носит полный служебный ключ media**; отзыв невозможен иначе как
ротацией токена сервиса (положит всех клиентов разом).

Это тот же класс риска, что снят с фонового поллера узла вчера (ADR-0027 Р3): там
введён `NodeKey` — отзываемый ключ одного устройства, sha256-хеш в таблице, guard
только на ручки узла. Прецедент показал: потеря устройства = отзыв одного ключа.

## Два словаря на один смысл — сверка (поручение владельца 20.08)

| | `NodeKey` (ADR-0027) | Ключ парринга кабинета |
|---|---|---|
| Кто выдаёт | оператор сервера (служебным токеном) | **пользователь в кабинете** (accessKey → pair) |
| Что даёт | ручки узла одного устройства (очередь/результат/пульс/загрузка) | сессию клиента + `mediaToken` (сегодня — весь media) |
| Отзыв | `revokedAt`, одна строка | `pairedKeyId` отзываем в кабинете, но `mediaToken` он НЕ отзывает |
| Хеш на сервере | да (sha256, timingSafeEqual) | pairedKey — да (кабинет); mediaToken — это сам секрет сервиса |

Вывод сверки: словари **не дублируют друг друга** — это два лица одного устройства
(фоновый сборщик ↔ интерактивный клиент), но право на media у обоих должно быть
**per-device отзываемым**. Сегодня оно таково только у NodeKey.

## Решения

**Р1. Media выдаёт per-device ключ при регистрации устройства через мост кабинета.**
`MediaBridgeService.registerDevice` получает в ответ (или отдельным вызовом под
служебным токеном) device-scoped ключ; `PairResponse.mediaToken` начинает нести ЕГО,
а не `MEDIA_API_TOKEN`. Форма поля не меняется (строка) — меняется содержимое, поэтому
клиент не трогается контрактно. Носитель на media — **та же таблица `NodeKey`** (один
словарь ключей устройства; NodeKeyGuard уже умеет), либо расширение её полем `audience:
node | client` — решит резчик спринта реализации.

**Р2. Отзыв связки в кабинете отзывает и media-ключ.** Ревок `pairedKey` →
мост зовёт `DELETE /v1/devices/:id/node-key` (или его client-аналог). Потеря узла =
два отзыва одним действием пользователя.

**Р3. Ротация служебного `MEDIA_API_TOKEN` — после раскатки Р1**, когда клиенты
перестанут его носить. До того ротация запрещена как ломающая всех.

**Р4. Хранение на клиенте — включение safeStorage** (провод b4 уже стоит:
канал `membrana:secure-storage`, мост `membranaSecureStorage`, `@stage ADR-0028`
в `pairing-credentials-store`). Включение = миграция localStorage → шифртекст одним
стартом + политика «расшифровка не удалась → чистый ре-парринг, не крах». Контракт
порта b2 (три глагола, sync) не размывается асинхронностью: либо `AsyncPairingCredentialsStore`
отдельным именем, либо кэш при старте (наблюдение Ожегова, b2).

## Последствия

- Спринт `media-per-device-token`: Р1+Р2 (media+cabinet), затем Р4 (клиент), затем Р3.
- До него: служебный токен у клиентов — **названный** техдолг, не молчание; новые
  клиентские поверхности не читают `mediaToken` напрямую из localStorage — только порт b2.
- Приёмка спринта реализации: журнал запросов media не видит `MEDIA_API_TOKEN` от
  клиентов; отзыв в кабинете реально закрывает загрузку с устройства.
