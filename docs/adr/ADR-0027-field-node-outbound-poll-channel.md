# ADR-0027 — Полевой узел держит канал к серверу сам: опрос очереди заданий, дом — media, ключ узла

> [`../discussions/cut-firebat-node-device-20260819-ozhegov-run.md`](../discussions/cut-firebat-node-device-20260819-ozhegov-run.md);
> автор формы — ozhegov, [`../discussions/firebat-node-device-b1.md`](../discussions/firebat-node-device-b1.md))

## Леммы

Одним списком, чтобы спринт говорил одними словами (оговорка резчика №1):

- **Узел** — физический хост в поле (сегодня Firebat T6, Windows Home, за чужими роутерами),
  на котором стоит наше приложение.
- **Устройство** — логическая запись приёмника (`devices` в `background-media`,
  `field-node-2026-08`), от имени которой принимаются записи. Узел *несёт* устройство;
  один узел может нести одно устройство, устройство может переехать на другой узел.
- **Исходящий канал** — направление инициативы: соединение всегда открывает узел.
  Это не транспорт, а свойство любого транспорта, которым узел пользуется.
- **Транспорт** — носитель канала (здесь: HTTP-опрос; альтернативы — WebSocket, обратный
  туннель).
- **Наблюдение** — то, что уезжает по каналу наружу: запись (WAV) и состояние узла (пульс).
- **Задание** — то, что приезжает по каналу внутрь: «снять пробу N секунд», «отдать
  диагностику». Задание адресовано устройству, исполняется узлом.
- **Очередь заданий** — упорядоченный список заданий на одно устройство, который держит
  сервер; узел забирает из головы очереди, сервер помечает выдачу и исполнение.
- **Пульс** — отдельный тип наблюдения: «узел жив, время, версия, последний исход опроса».
  Не задание и не запись; синонимы (heartbeat, keepalive, статус) в тракте не употребляются.

### Ключ узла ≠ nodeId наблюдения

Ключ узла — секрет, которым узел *подписывает* обращения к серверу; он отзываем и не
хранится в наблюдении. Идентификатор узла в наблюдении — имя, по которому запись
атрибутируется; он публичен, не отзываем и не даёт прав. Смешать их — значит положить
секрет в данные либо сделать атрибуцию отзываемой.

## Контекст

Узел ожил 18.08: пишет 48 кГц в заводском режиме карты и отправляет записи сам, но
(а) по ручному запуску `yarn field:capture`, (б) со служебным токеном всего медиа-сервиса
в `.env` и (в) без способа получить задание с сервера — SSH-сервер на узле стоит, вход
снаружи закрыт каскадом роутеров, и это норма поля (полигон и улица — чужая сеть).

Слово владельца 18.08: **права узел получает установкой нашего приложения; SSH — для
отладки лабораторных работ.** Значит форма канала — не обход сети, а свойство приложения.

Рассмотрены три транспорта исходящего канала (контекст резчика, заход 2):

| Транспорт | За | Против |
|---|---|---|
| **Опрос очереди (HTTP poll)** | прозрачен для любого NAT и прокси; без состояния на сервере между запросами; ретрай тривиален; поверх уже живого `POST …/samples` | задержка = период опроса |
| WebSocket | near-realtime; сервер сам толкает задание | reconnect и состояние сокетов на сервере; второй путь рядом с HTTP-приёмом записей |
| Обратный SSH-туннель | полный доступ к узлу | это **обслуживание, а не данные**: туннель даёт консоль, а не канал наблюдений; служебный ключ на узле |

## Решения

**Р1. Транспорт — опрос очереди заданий.** Узел периодически спрашивает сервер «есть
задание для моего устройства?», исполняет, отвечает результатом и между заданиями
отправляет пульс. Выбор — по бюджету задержки этого спринта: узел сегодня — *сборщик
записей для калибровки*, команда «снять пробу» терпит секунды; для такого бюджета
WebSocket — лишнее состояние, туннель — не про данные. Переход на WebSocket при
появлении near-realtime требования — **новая ADR**, не правка этой: меняется не
транспорт, а класс нагрузки на сервер.

**Р2. Дом канала — `background-media`, модуль `firebat-node/`.** Там живут устройства,
коллекции и приём WAV; задание адресовано устройству — значит очередь заданий стоит рядом
с устройством, а не в office. Граница дома: `packages/background-media/src/modules/firebat-node/`
с экспортом через `index.ts`; внутренности `devices` наружу не просачиваются (оговорка
резчика №3). `index.ts` экспортирует **только** Nest-модуль и типы заданий/исходов;
репозитории `devices`, HTTP-контроллеры приёма WAV и хранилище ключей — internal, через
`firebat-node` не достижимы. Из клиента и из детекторов модуль не импортируется.

**Р3. Ключ узла — отдельный отзываемый секрет только на загрузку в своё устройство.**
Служебный токен медиа-сервиса с узла уходит; узел получает ключ при установке и может
только: опросить очередь своего устройства, вернуть результат, отправить пульс, загрузить
запись в коллекции своего устройства. Потеря узла без присмотра = отзыв одного ключа,
не ротация токена сервиса.

**Р4. Исходы опроса — закрытый словарь `ok | stale_key | backoff`,** единый на весь тракт
(сервер → poller → лог узла → приёмка), без синонимов (оговорка резчика №2). `ok` —
задание выдано или очередь пуста; `stale_key` — ключ отозван или неизвестен, узел
прекращает опрос до переустановки ключа; `backoff` — сервер просит увеличить период
(перегрузка, обслуживание). Любое иное состояние — ошибка транспорта, не исход. Тип-объединение
исходов живёт в `firebat-node/index.ts`; расширение словаря — **через новую ADR, не через
PR**: `retry`, `wait`, `unauthorized` и прочие «почти синонимы» не заводятся.

**Р5. Узел исполняет задание существующим трактом записи.** Poller не дублирует
`field-capture`: съёмка, измерение, запрет measured-полей в объявленном (#1950) — те же
функции того же файла. Poller — однофайловый скрипт без зависимостей (класс
`field-capture.mjs`), чтобы переноситься на узел как файл.

## Последствия

- Сервер получает очередь заданий на устройство и два новых входа (взять задание · вернуть
  результат/пульс) под ключом узла; служебный токен узлу больше не выдаётся.
- Установщик (b5) несёт ключ узла как параметр установки, не как значение в сборке.
- Усиление карты (b6) — параметр *узла*, записывается в файл-спутник записи словом, не
  в измеренные поля (#1950 в этом спринте не трогается).
- Приёмка (b7) именует исходы тем же словарём Р4.
- Вне этой ADR: WebSocket-канал, парринг через device-board, мультиузел/TDOA, LoRa —
  каждое при появлении требования получает свою запись.
