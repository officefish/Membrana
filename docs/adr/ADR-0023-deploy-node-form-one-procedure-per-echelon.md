# ADR-0023 — Узел разворачивания: процедура на сервер (эшелон) с посервисной параметризацией, прогоном в журнале и owner-gate на выкладку

> **Статус:** ACCEPTED · 2026-08-04 (LGTM владельца, два акта одного дня: «Я даю lgtm
> по adr-23» — сессия-сосед; подтверждение амандмента — ратификация спринта `deploy-procedures`)
> **Амандмент 04.08 (слово владельца):** Р1 черновика звал ОДНУ процедуру `deploy` с
> параметром-сервисом. Владелец решил иначе: «У нас два сервера. Значит и процедуры
> будет две. Пока две. Некоторые деплои будем со временем ещё больше конкретизировать» —
> процедура заводится **на сервер** (эшелон), сервис остаётся параметром прогона,
> посервисные специализации — позже, словом владельца. Р1 ниже переписан; Р2–Р5 не тронуты.

## Контекст

Обзор узла разворачивания ([`deploy-survey-2026-08-03.md`](../deploy-survey-2026-08-03.md),
магистраль 03.08) показал: узел вдвое больше, чем значился (52 глагола + 56 ssh-скриптов
против «41»), при **нуле** процедур разворачивания в реестре из пятнадцати. Связка
«сборка → подъём → smoke → конфиг» скопирована у четырёх+ сервисов; каждый новый сервис —
пятая копия, каждый деплой задачи рождал новый датированный ssh-скрипт (~20 из 56 —
осадок). Веснин в вечернем фидбеке 03.08 просил оформить ≥1 пробел как ADR-кандидат:
«архитектурное решение о форме узла разворачивания не зафиксировано».

Развилка: **какой формой** узел перестаёт быть россыпью — один оркестратор-скрипт,
пять посервисных процедур или одна процедура с параметризацией. Решение ниже
консилиум-гейта: новых core-контрактов/пакетов не вводится, форма манифестов процедур
и журнал прогонов уже канон (ADR-0021, ADR-0022); фиксируется выбор реализации.

## Решение

### Р1 — Процедура на сервер (эшелон); сервис — параметр, не копия
- Заводится процедура **на каждый сервер** (MANIFEST.json по форме ADR-0021, фреймы
  `build → rollout → smoke → record`). Пока серверов два — процедур две:
  **`deploy-office-vds`** (office.mmbrn.tech, `getOfficeSshConfig`: office + panel) и
  **`deploy-media-vps`** (`BACKGROUND_MEDIA_IPV4`: media, cabinet, device-board,
  root-site). Сервис — параметр прогона, не пятая копия связки; существующие глаголы
  остаются исполнителями шагов: процедура — рамка поверх них.
- Посервисная конкретизация («некоторые деплои со временем ещё больше
  конкретизировать» — слово владельца 04.08) — будущими специализациями этих
  процедур, не третьей абстракцией «деплой вообще».
- **Границы:** `@membrana/core` не трогается; сами compose/Caddy/env-скрипты не
  переписываются этим решением; серверная специфика (хост, конфиг) живёт в
  ssh-конфиге кода, декларация процедуры её не дублирует.

### Р2 — Выкладка только через owner-gate, и он уже существует
- Фрейм `rollout` несёт гейт `owner-rollout` (kind: gate, blocksOn: owner) — механика
  «`deploy:when-green` печатает, владелец запускает» объявляется каноном процедуры,
  а не привычкой. Автозапуск выкладки в прод запрещён конструкцией манифеста.
- **Границы:** локальные/dev-подъёмы (`*:docker:up`, `*:db:up`) гейтом не обкладываются —
  гейт только на прод-выкладку.

### Р3 — Деплой пишет прогон в общий журнал (П2 обзора)
- Фрейм `record` — не новый носитель: `procedure-run-record open/close` вокруг выкладки
  (procedureId `deploy`, subject = сервис + ревизия), лента общая
  `docs/procedure-runs/trail/`. «Что, когда и на какой ревизии выкатывалось» становится
  записью с leafHash, а не археологией по датированным хвостам.
- **Границы:** evidence прогона — ревизия и сервис; секреты и env-значения в журнал
  не пишутся никогда (резак/маска — соседний контур).

### Р4 — Датированные одноразовые ssh-скрипты — осадок, им объявляется правило
- Новый одноразовый деплой-скрипт заводится только с датой в имени и попадает под
  ежемесячную ревизию (кандидат в `weekly-dead-wire-audit`); знание из хвостов
  (`mp2…mp6-prod`, `quota-refactor-prod`, …) при взятии процедуры в работу либо
  поднимается в шаги процедуры, либо скрипт архивируется.
- **Границы:** сами 56 скриптов этим ADR не удаляются — правило действует вперёд,
  разбор осадка — отдельная санитарная работа.

### Р5 — Дрейф прод↔ствол — шаг smoke, для всех сервисов
- Механика `office-drift-code-cron` (сравнение развёрнутой ревизии со стволом)
  обобщается параметром сервиса и объявляется частью фрейма `smoke`; «что сейчас
  в проде» — замер, не вера. Питает витрину состояния в панели.
- **Границы:** cron-расписание и алёрты — вне этого решения; здесь только форма
  «дрейф — шаг процедуры».

## Out of scope / открытые задачи

- Разбор осадка 56 ssh-скриптов (Р4 действует вперёд) — санитарная работа отдельным заходом.
- Сшивка env-генерации с ротацией секретов (П5) — упирается в предикат `amnestyLifted`,
  рука владельца.
- Cron/алёрты дрейфа, панель состояния — после первого прогона процедуры.
- Server-only прогон ритуалов и сервис корпуса — потребители процедуры, не её части.
