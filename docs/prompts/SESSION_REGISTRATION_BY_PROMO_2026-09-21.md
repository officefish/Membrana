# Задание: регистрация в кабинете по промокоду из панели администратора (21.09)

**Слово владельца 21.09:** «Мы сделаем условно открытую регистрацию: условной она будет потому, что доступна пока только с промокодом, который генерируется в панели администратора».
**Зачем прямо сейчас:** сценарий тарифной лестницы (free → checkpoint → observatory и обратно) требует второй кабинет на бесплатном тарифе, а завести его на проде нечем: `POST /v1/auth/register` заперт флагом `ALLOW_REGISTRATION=false` (`deploy/generate-cabinet-env.sh:34`), формы регистрации в веб-кабинете нет, админского пути «выдать учётку» нет. Лендинг при этом обещает «Кабинет — регистрация» (`deploy/root-site/index.html:154`).
**Дерево:** своё, отдельное, от свежего `origin/main`.

## Развилка закрыта словом владельца 21.09 — путь Б

«Мы уже делали подобную систему для партнёров в офисе, мы можем не создавать новых систем, а распространить те же промокоды и для регистрации в кабинете».

Значит: промокоды регистрации **живут в панели офиса** (: модель  с , , , ; минт/отзыв под ), а кабинет при регистрации **спрашивает офис**. Новой системы промокодов в кабинете не заводить.

**Что остаётся решить — это контракт между сервисами, и по норме он идёт через короткий консилиум ДО кода:**
1. **Вид кода.** У панельного кода есть  — регистрация в кабинете становится новым грантом (например ), а не отдельной таблицей. Код с этим грантом минтится тем же маршрутом .
2. **Дверь офиса для кабинета.** Кабинету нужен внутренний маршрут «проверить и погасить код под грант cabinet:register» — атомарно, чтобы два запроса на один код не прошли оба ( против ). Существующий  заводит партнёра панели — он не подходит, нужен отдельный или параметризованный.
3. **Авторизация кабинет → офис.** В кабинете сегодня НЕТ  ( по  и  пуст) — это новая межсервисная связь, её окружение и ключ надо завести в  (ключ — слово владельца).
4. **Режим отказа.** Офис недоступен → регистрация отвечает «попробуйте позже», код не гасится, пользователь не создаётся; полусостояние «пользователь есть, код не погашен» недопустимо — порядок: сначала погасить у офиса, потом создать пользователя, при ошибке создания — компенсирующий возврат кода (или наоборот, решить на консилиуме).
5. **Ошибки наружу** не различают причину (Q3 ADR-0005); rate-limit на регистрацию как в панели.

## Задача (после консилиума по контракту)

1. Сервер: `register(login, password, promoCode)` — флаг `ALLOW_REGISTRATION` заменяется на проверку кода: код существует, активен, не исчерпан, не истёк → создать пользователя, погасить код (атомарно, гонка «два запроса на один код» — тем же приёмом, что #2313: `P2002` → повтор чтения). Ошибки регистрации наружу не различать (Q3 из ADR-0005). Rate-limit как в панели.
2. Панель офиса: грант `cabinet:register` в минте кода (срок, число погашений, отзыв — уже есть); внутренняя дверь «проверить и погасить» для кабинета.
3. Веб-кабинет: форма регистрации на `LoginPage` (логин, пароль, промокод), убрать строку «выдаётся администратором», ошибки — одной фразой.
4. Лендинг: карточка «Кабинет — регистрация» становится правдой; пока формы нет — текст «по приглашению».
5. Зубы: сервис — код истёк / исчерпан / отозван / гонка двух регистраций на один код (красный вход до правки существует: сейчас `register` не принимает код вовсе); guard — не-admin не минтит; веб — форма отправляет код.
6. Прод: после выкатки владелец минтит первый код и регистрирует второй кабинет — это и есть приёмка. Тариф новой мембраны обязан быть `free-v1`, предел буфера по `GET /v1/devices/:deviceId/quota` — 536870912.
