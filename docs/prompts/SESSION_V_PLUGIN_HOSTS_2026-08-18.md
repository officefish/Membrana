## Задача — PR-2 (можно двумя PR: хосты / дом результатов)

**Хосты (по M2 + M4/M5′):**
1. `IPluginHost` реализуется в `background-media/collections`: `mountTargetId =
   'background-media/collections'`, `registerPlugin`, `getRegisteredPlugins`,
   `setPluginEnabled`, `notify`, `request`. Реестр плагинов — в памяти процесса,
   включённость — состояние реестра (НЕ поле манифеста).
2. Валидация при регистрации: `mountTarget ∉ HOME_REGISTRY` → отказ до рантайма;
   `mountTarget ≠ mountTargetId` хоста → отказ; `isPluginId` обязателен.
3. `notify(event)` — fire-and-forget: рассылка включённым плагинам с подходящим
   `trigger`; выключенный сигнал теряет (буфера нет — M4). `request(pluginId, trigger, ctx)`
   — постфактум-запуск одного плагина. Плагин канала не знает.
4. Дом `journal` — по остаточному принципу (см. находку).

**Дом результатов (по M3/M3′):**
5. В `background-office` — коллекция Mongo `plugin-results` (та же Mongo, что у
   архивариуса) с двумя индексами: уникальный `{pluginId, version, collectionId, runId}`;
   `{pluginId, version, collectionId, kind, completedAt: -1}` для последнего состояния.
6. Сервис записи/чтения: `writeRun(RunRecord)`, `readRuns(address-фильтр) → RunRecordView[]`
   — `stale` вычисляется чтением (`inputHash_stored ≠ hash(текущего состава коллекции)`),
   в БД не хранится. Кто считает `inputHash` состава коллекции — этот сервис по запросу
   к media (или принимает от вызывающего) — решить и назвать в отчёте.
7. Граница окна — `RunRecord` + новый `StateRecord` в одной транзакции (M3).

**Норма #1950 — структурное условие PR:** ни один write-путь из плагинного контура
в `samples`/`collections` media; плагины пишут только в `plugin-results`.
