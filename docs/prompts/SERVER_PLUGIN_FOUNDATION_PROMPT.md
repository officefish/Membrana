## Контекст

Клиент несёт модульно-плагинную архитектуру — серверу нужна такая же основа, чтобы
писать **плагины серверного журнала**, дополнительно анализирующие и визуализирующие
коллекции звуков через серверные модули (замысел — слово владельца 17.08, магистраль дня).

Шторм по предмету: [`docs/storm/storm-server-plugin-foundation-2026-08-17/`](../storm/storm-server-plugin-foundation-2026-08-17/THESES.md) —
живой конспект, тезисы Т1/Т2 подтверждены владельцем.

**Определение плагина (Т1, слово владельца):** дополнительная возможность модуля/страницы;
изолированный блок программы **под версией**; включается и выключается на уровне своего
модуля. Общие библиотеки у плагинов разных модулей изоляцию не нарушают.

**Пример и режимы (Т2, слово владельца):** за день в журнал внесено 400 записей — плагин
журнала сортирует звуки по громкости или отрисовывает пиковые зоны и аномалии,
**постфактум**; при этом серверный плагин может **копить состояние и рендерить тренды
в реальном режиме**. Оба темпоральных режима — часть предмета.

**Что уже есть (разведка 17.08, факты, не решения):**

- Контракт плагина живёт в `packages/agenda/src/core` (plugin-lifecycle / registry /
  types), несёт **21 клиентский плагин**; канон — `docs/MODULE_AND_PLUGIN_UI.md`.
  Реализация привязана к Zustand/persist: контракт переносим, воплощение — нет.
- Сервер (Nest) модульность имеет; нехватка в четырёх местах: включение на ходу ·
  самоописание для UI · привязка плагина к модулю/коллекции · след работы.
- Кандидаты шторма (НЕ решения, ждут собрания): дом результатов с адресацией
  «модуль → плагин → версия → коллекция → прогон»; отпечатки входа И конфигурации в
  каждом результате; первая волна — шесть детекторов измерителя; сервер отдаёт данные
  для картины, не картину; серверному плагину нужен повод (событие/запрос).
