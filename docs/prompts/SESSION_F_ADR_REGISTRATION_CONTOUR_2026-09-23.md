# Задание сессии F: ADR по контуру регистрации «панель → офис → кабинет» (23.09)

**Основание:** предложение команды в вечернем фидбеке 22.09 (Архитектор), принято владельцем утром 23.09: «предложения команды принимаются». Подкрепление магистрали дня `cabinet-registration-rollout`, не магистраль.

**Зачем:** контур из четырёх модулей и трёх границ построен за один день и лежит в стволе; решение о его форме принято на заседании и живёт в шести протоколах и карточке. ADR фиксирует выбор одним документом до того, как появятся альтернативы, и становится тем, что читают ревью и будущие сессии (см. #2403: ревью не читает ратифицированные решения).

**Дерево:** своё, отдельное, от свежего `origin/main`. Ветка вида `docs/adr-registration-contour`. Только документы; кода не трогать.

## Что должен нести ADR

1. **Контекст:** слово владельца 21.09 (условно открытая регистрация по промокоду панели; те же коды, что у партнёров; новой системы не заводить), цель — второй кабинет для сценария тарифов.
2. **Решение** по четырём границам, каждое с опорой на протокол и на файл ствола:
   - панель — источник правды о коде: тот же `PromoCode`, грант `cabinet-register`, дверь `POST /v1/internal/cabinet/registration-codes/consume` под `ApiTokenGuard`, `mode: check | redeem`, 409 с пятью причинами в ратифицированном порядке, аудит только на redeem, 503 при деградации хранилища;
   - офис — мост: кабинет ходит к офису по паре `OFFICE_URL`/`OFFICE_API_TOKEN` (общий `API_INTERNAL_TOKEN` офиса, носитель — файл окружения кабинета), клиент `OfficeRegistrationBridgeService` с одним выходом наружу, таймаут 5000 мс, исход из четырёх ветвей, проверка живости из `health-deep`;
   - кабинет — потребитель: порядок «проверки без побочных эффектов → гашение → создание», карта двери 401/429/403/503, одна фраза наружу (Q3, ADR-0005), ограничитель 10/600000 мс по последнему адресу `X-Forwarded-For`, два условия включения (флаг И пара);
   - веб-кабинет — форма на странице входа, фразы по HTTP-статусу, блок 600 с после 429, лендинг «вход по приглашению».
3. **Отвергнутые альтернативы** — из протоколов, с цитатой: отдельный вид кода / вторая система кодов в кабинете (M1); отдельный ключ гостя-кабинета (M2); `check` перед `redeem` на продуктовом пути (M1 П12); отдельный экран регистрации и маршрутизатор (M4); trim пароля (M4).
4. **Последствия и долги** с номерами: замок двери в одном процессе офиса — реплики офиса требуют отдельного ADR (Р3); дубль `fetchMe` (#2402); a11y меток; рост карты ключей ограничителя без чистки по времени; плавающий тест журнала; ревью не читает ратифицированные решения (#2403).
5. **Приёмка эпика** (не часть ADR-решения, а его проверка): второй кабинет владельца на `free-v1` через код из панели — порядок в карточке заседания, раздел «Выкатка».

## Нормы записи

- Каждое утверждение о коде — с путём и строкой, сверенными по `origin/main` (`git show origin/main:<путь> | sed -n '<строка>p'`); чего нет в стволе — не факт.
- Каждое решение — со ссылкой на протокол и строку. «Примерно так» не принимается.
- Словарь: панель, офис, кабинет, код, грант, дверь, гашение, отзыв, пара, клиент, форма; латиница — имена файлов, полей, значений, статусов.
- Решения не переоткрывать: ADR фиксирует, что ратифицировано, а не предлагает лучше. «А лучше бы» — в чат ведущей отдельным вопросом.

## Сдача

`yarn pr:ship --type docs --scope adr --execute`; PR без слияния; в теле — список источников с номерами строк и команда сверки фактов. Слияние — по приёмке ведущей: сверка каждого утверждения о коде и каждой ссылки на протокол выборочно, не менее десяти.
