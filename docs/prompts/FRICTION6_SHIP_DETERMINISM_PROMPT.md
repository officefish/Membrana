## Контекст

За одну сессию 26.07 контур ship **дважды соврал зелёным** и **трижды проиграл гонку** с общей
веткой. Четыре дефекта лежат в трёх файлах и чинятся вместе, потому что проявляются одной
последовательностью: `pr:wait` → `gh pr merge` → cleanup → sync.

**Эпизоды-вещдоки:**

| № | Дефект | Эпизод |
|---|--------|--------|
| 1 | `pr:wait` умирает на трёх подряд транзиентах | PR #1243: `spawnSync … ETIMEDOUT` ×3 + `TLS handshake timeout` → ожидание умерло, **merge не выполнился**. PR #1253: то же |
| 2 | `task:pr-land` не доводит мердж на Windows | PR #1256: базу слил, запушил, шаг `ship-merge` упал `spawnSync yarn ENOENT` |
| 3 | Нет серверного автослияния | PR #1248, #1253, #1256 подряд стали CONFLICTING; #1256 — уже **после** зелёного CI |
| 4 | Гард «base занят соседним деревом» стар на момент исполнения | PR #1256: мердж состоялся, ветка снесена, затем `fatal: 'main' is already used by worktree at Membrana-codex` |

**Корень №4 точнее, чем «предикат сломан»:** `planPrShip` строит план ОДИН раз, а между планом
и хвостом стоит `ci-wait` на минуты. Соседняя сессия заняла `main` за это время. Предикат был
верен в момент плана и устарел в момент исполнения.

**Связанные документы:**

| Документ | Зачем |
|----------|--------|
| [`scripts/pr-wait.mjs`](../../scripts/pr-wait.mjs) | цикл ожидания, бюджет неудач `gh` |

### Что построить

1. **Класс сбоя `gh` вместо одного бюджета.** `classifyGhFailure(message)` → `network` /
   `notfound` / `auth` / `unknown`; бюджет подряд идущих неудач зависит от класса (сеть терпим
   долго — всё равно ограничены дедлайном; «нет PR» и «нет auth» — сразу). Классифицировать по
   **полному** тексту: причина у `gh` лежит в stderr, то есть не в первой строке — а лог печатал
   ровно первую. Плюс экспоненциальный бэкофф с потолком: раньше пауза равнялась интервалу, и
   три таймаута укладывались в секунды.
2. **`yarnBin(platform)`** в плане `task:pr-land`: на win32 — `yarn.cmd`, иначе `yarn`.
3. **`pr:ship --auto`** → `gh pr merge --squash --auto`. Локальные `ci-wait`/`verify` в этом
   режиме не планируются: слияние делает сервер по зелёному. В `skippedSync` — честная строка,
   что подтверждение мерджа переносится на следующий заход.
4. **Гард времени исполнения.** Шаги `sync-checkout`/`sync-ff` помечаются `guard: 'base-free'`;
   перед исполнением такого шага предикат занятости base перечитывается по состоянию **сейчас**,
   и шаг пропускается сообщением, а не падает.

---

### Запрещено

- Ронять ship после **состоявшегося** мерджа (инвариант #1166): любой шаг после `merge`,
  который может законно не выполниться, либо `optional`, либо под guard.
- Отдавать ноль при несостоявшемся мердже.
- Лечить «нет PR» и «нет auth» ожиданием — они ожиданием не лечатся.
- Убирать плановый расчёт занятости base: он даёт честный `dry-run`. Гард времени исполнения
  **добавляется**, а не заменяет.
- Трогать запрет `--delete-branch` (#653) и порядок merge → cleanup → sync.

### Тесты

| Область | Минимум |
|---------|---------|
| Класс сбоя | ETIMEDOUT / TLS timeout / 503 → `network`; «no pull requests found», «Could not resolve» → `notfound`; auth → `auth`; «Command failed: gh pr view» → `unknown` |
| Полный текст | многострочная ошибка классифицируется по stderr, её первая строка — `unknown` (регресс на лог 26.07) |
| Бюджет | сеть ≥ 8; `notfound`/`auth` = 1; `unknown` между ними |
| Бэкофф | экспонента от интервала, потолок обязателен, нулевой интервал не даёт нулевой паузы |
| `--auto` | план = один шаг `merge-auto`; `ci-wait` отсутствует; без флага хвост прежний |
| guard | `sync-checkout` и `sync-ff` несут `guard: 'base-free'`; base занят на этапе плана → шаги не планируются вовсе |
| yarnBin | win32 → `yarn.cmd`; шаг `ship-merge` берёт бинарь по платформе |
