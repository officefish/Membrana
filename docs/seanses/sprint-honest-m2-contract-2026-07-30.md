[Математик]: Фиксирую область. M1 дал: `assigned(S,p)`, `participated(S,p)`, `SprintExecution(S)` = проекция Assignments × Evidence. Вопрос 2 вводит новую переменную до окна: контракт C, который p принимает *до* работы. Без C нет области «принял / не принял», а без них `assigned` в M1 — назначение без согласия. Определяю: `Contract(S) = (subject, bounds, donePred)` — три обязательных поля; `accept(S,p,C)` и `reject(S,p,C,reason)` — события ленты *до* Evidence исполнения.

[Верстальщик]: С витрины капитана и агента: если «принял» — галочка в чате без адреса, это фальшь, как бейдж «исполнитель» без следа. Нужны два честных состояния рядом с планом: `contract: pending | accepted | rejected`, не «—». Rejected читается: reason одной строкой, не пустой красный. Layout карточек registry не рисую — только требование к данным, которые потом можно показать без легенды.

[Структурщик]: Леммы, иначе синонимы. **Контракт спринта (SprintContract)** — именованный артефакт окна S: предмет + границы + предикат сделанного; не Issue, не task-prompt, не зона leadPersona. **Формулировщик** — роль/слот, который *создаёт* C до назначения accept. **Принятие** — вещдок-запись `Acceptance(S,p,Cref)`, не emoji и не «ок» в ленте без ref. **Непринятие** — `Rejection(S,p,Cref,reasonCode)`. Home контракта и home acceptance — разные леммы; смешивать нельзя.

[Музыкант]: На слух это count-in до take, не сам take. Партитура (C) кладётся на пюпитр *до* первого такта; исполнитель говорит «слышу / не играю». M1 уже отделил имя на пюпитре от звука на ленте — здесь нужен третий жест: согласие с партитурой. Без count-in снова mono: назначили Курёхина, а он играл другую пьесу и «закрыл» чужой done. Границы C — что *не* в партии этого окна, иначе клиппинг scope.

[Teamlead]: Планка матча узкая. Не вердиктим API вызовов, не разметку 213 карточек, не ревью исполнителем, не вызовы, не аудитора. Связка: Математик — предикаты accept/reject и donePred; Структурщик — леммы и homes; Архитектор — форма C и граница «кто формулирует»; Верстальщик — честность статусов в данных; Музыкант — count-in vs take. Матч — закрытый состав C + вещдок «принял» + ветка непринятия. «Почти контракт» = BLOCK.

[Архитектор]: Конструкция: C — документ окна, не код. Три несущих поля: (1) **предмет** — что строится/решается в S одним абзацем; (2) **границы** — in/out: что сознательно вне S; (3) **сделано** — проверяемый donePred, не «улучшили». Кто формулирует: не исполнитель единолично и не «система молча» — формулировщик плана окна (капитан или Teamlead-слот по канону дня) *до* accept. Цена альтернативы «исполнитель сам пишет C» — self-grade, M1 честность рушится.

[Математик]: Предикат принятия: `accepted(S,p,C) ⇔ ∃ e ∈ PreEvidence(S): kind=contract_accept ∧ subject(e)=p ∧ ref(e)=id(C) ∧ ts(e) ≤ t_start(S)`. Симметрично reject с reason ∈ закрытого алфавита (хотя бы: `scope_unclear`, `bounds_missing`, `done_untestable`, `capacity`, `conflict_other`). Инвариант: `assigned(S,p) ∧ ¬accepted ∧ ¬rejected` = состояние `pending_accept` — не no-show M1; no-show начинается после t_start при accepted|assigned без participate. donePred — предикат на Evidence/артефактах, не на настроении.

[Верстальщик]: Три поля C на витрине будущего читателя: «Что», «Не входит», «Считается сделанным» — три блока, не простыня. Статус accept: `pending` (жёлтый смысл) / `accepted` / `rejected` + reason-code текстом из словаря, не free-form роман. Фальшь: «в работе» при `pending_accept`. Пустой bounds — видна дыра: `bounds: unset`, не молчаливый прочерк.

[Структурщик]: Словарь полей C (публичные имена): `subject` (1–2 предложения), `inScope[]` / `outOfScope[]` (списки лемм, не файловые пути как обязаловка), `doneWhen` (текстовый предикат + опц. checklist id). **Не** входят в C: список зон персонажей, diff кода, оценка часов как замена doneWhen. Acceptance-запись: `{sprintId, personaId, contractId, decision: accept|reject, reasonCode?, at, authorRef}`. Home: артефакт плана окна (тот же контур, что Assignments M1), не git-commit message.

[Музыкант]: doneWhen на слух — критерий final bounce, не «играли долго». Если doneWhen = «пощупали» — это не метр, а шум; reject с `done_untestable` честнее фейкового accept. Непринятие — не срыв концерта навсегда: либо правят партитуру и новый C' (supersede, как plan M1), либо окно без этого p, либо стоп окна. Тишина вместо reject — хуже: assigned висит, participate пусто, снова only_assigned.

[Teamlead]: Кто формулирует — фиксирую по устройству, не по вкусу: **владелец окна** (капитан или его делегат Teamlead) формулирует C; исполнитель **не** автор C в v1. Исполнитель может вернуть reject с reason — это пас назад в комбинацию, не право переписать doneWhen в свою пользу. При reject: связка «формулировщик правит C → C' supersede → повтор accept» или снятие p с Assignments. Без C' и без снятия — BLOCK на старт окна.

[Архитектор]: Граница формы: SprintContract **ждёт** M1 (без assigned/participated нет смысла accept), но **не** тащит вопросы 3–9. C не заменяет task-prompt и не дробит registry по зонам. Вариант «C = текст Issue» — дешево, но Issue часто смешивает scope и надежды: цена — нетестируемый doneWhen. Рекомендация: C — короткий структурированный блок *внутри* плана окна рядом с Assignments; Issue/PR — ссылки в inScope по желанию, не тело контракта.

[Математик]: Связь с M1 без расширения M1. `honest_pair` по-прежнему assigned∧participated. Добавляем слой Pre: `ready(S,p) ⇔ assigned(S,p) ∧ accepted(S,p,C_current)`. Старт исполнения p в S допускается только при ready (инвариант процесса, не runtime-код сегодня). Если p participated без ready — это либо shadow с нарушением процесса, либо C был, но ref потерян: qualifies Evidence не отменяем, но status окна помечает `contract_gap`. Число полей C = 3 несущих; остальное — опциональные annotations.

[Верстальщик]: Для капитана в конце окна: сверка «принял C₀ / сдан doneWhen» должна читаться без следственного романа. Если supersede C₀→C₁ — видна версия contractId, не «как-то обновили». Не рисую UI; требую в вещдоке `contractId` стабильный и `supersedes` optional. Иначе витрина «принял» указывает в воздух.

[Структурщик]: Supersede — отдельная лемма. `C' supersedes C` ⇒ accept(C) не действует; нужен новый accept(C') или explicit carry-forward rule. v1: **carry-forward запрещён** — любое изменение subject/bounds/doneWhen = новый contractId + новый accept. Иначе «принял» становится дырявым словом. Rejection не создаёт participated. Acceptance не создаёт participated. Оба — PreEvidence, kind ∉ K_exec M1.

[Музыкант]: Ещё раз по шине: Assignments = кого позвали; Contract+accept = согласие с партитурой; Evidence exec = take. Три разных разъёма. Склеить accept с первым коммитом — нельзя: коммит может быть off-score. Склеить accept с leadPersona карточки — нельзя: M1 уже запретил. Count-in слышен отдельно.

[Teamlead]: Непринятие — не драма, а упражнение. Ветки: (1) revise C → C'; (2) unassign p; (3) abort/defer sprint S. Запрет: старт «пока так» без accept. Запрет: accept задним числом после participate, маскирующий contract_gap (кроме явного grace-правила капитана с отдельной записью — не v1 default). Планка: до t_start у каждого assigned есть terminal decision accept|reject|unassigned.

[Архитектор]: «Принял» как вещдок: не сообщение, а **адресуемая запись** с полями Структурщика, ref на contractId, timestamp, subject=personaId. Где лежит: тот же home, что plan/Assignments окна (memo/plan artifact / execution registry — имя home не раздуваем до отдельного пакета). Не в git trail alone, не только в Linear comment без id. Цена «только чат» — через неделю ref не резолвится, M1 Evidence qualifies падает на том же классе дыр.

[Математик]: Минимальная алгебра решений для комнаты 2:

`PreEvent = {sprintId, personaId, contractId, decide, reason?, at}`

[Верстальщик]: Конкретика doneWhen для глаза: запрещены формулы «сделать лучше», «по возможности», «начать». Допустимы: «вердикт комнаты записан в seanses/…», «предикат X специфицирован», «DoD списка из N пунктов закрыт записью». Это не UI — это анти-декор в тексте поля, чтобы витрина закрытия не врала зелёным.

[Структурщик]: Кто формулирует — словарно: **ContractAuthor** = субъект, создающий C; в v1 = owner/delegate окна, ≠ executor. Executor = candidate из Assignments, проходящий accept. Не вводим пятую persona: author — роль акта, не новый label канона. Связь: Assignments могут существовать draft до C; **финальный** plan к t_start: ∀p∈assigned: accept на current C ∨ p снят. [Музыкант]: При reject с `capacity` — честный «не беру партию», не «тихий no-show». При `scope_unclear` — партитура грязная, правит author. ## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Из чего состоит контракт спринта C | **Три несущих поля:** `subject` (предмет, 1–2 предл.), `inScope` / `outOfScope` (границы), `doneWhen` (проверяемый критерий сделанного). Служебно: `id`, `sprintId`, `version`; опц. `supersedes`. **Не** входит: код, разметка задач по зонам, leadPersona, оценка «часов вместо done». |

| Что значит «принял» | Адресуемая **вещдок-запись** PreEvent: `{sprintId, personaId, contractId, decision: accept, at, …}` с ref на **current** C (не superseded). Не emoji, не «ок» в чате без id, не первый коммит, не label. Home — **тот же контур плана/Assignments**, не новый пакет. Accept **не** создаёт `participated` (M1). |

| Связь с M1 | M1 вход: исполнитель = проекция Assignments × Evidence. Добавляется Pre-слой: `ready(S,p) ⇔ assigned(S,p) ∧ accepted(S,p, current C)`. Старт p только при ready (процессный инвариант). accept/reject ∉ K_exec. |
| Чужие вопросы 3–9 / код / зоны | **Не решались.** Enforce-зубы CI, UI registry, ревью исполнителем, аудитор — вне комнаты. |
| Вердикт комнаты | **Принято** единогласно шестью ролями. |

**Definition of Done (фиксация решения, не продуктовый код):**
1. Протокол seanses с этой рамкой C / accept / reject / ready.
2. При следующем process-update sprint-honest: секция SprintContract + PreEvent рядом с Assignments (без нового npm-пакета).
3. Любой план окна S после t_start: ∀p∈assigned → accept(current C) или p снят; иначе plan не final.
4. Тексты `doneWhen` falsifiable; пустые bounds / done — повод reject, не «пока так».
