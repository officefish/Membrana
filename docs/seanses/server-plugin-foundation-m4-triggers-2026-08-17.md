# Консилиум: Форма повода — типизация triggers, словарь событий, механика испускания

**Повестка:** Q4 — Какова форма повода: типизация triggers манифеста и испускание событий домами?

**Участники:** Teamlead (Тарасов), Архитектор (Веснин), Структурщик (Ожегов), Математик (Дынин), Музыкант (Курёхин), Верстальщик (Родченко).

**Порядок реплик:** Музыкант → Архитектор → Математик → Структурщик → Верстальщик → Teamlead

---

[Музыкант]: Начну с практического вопроса, который задаёт тон всему остальному. Плагин — это слушатель события. Мне важно понять: событие — это нота в партитуре или сигнал на шине? Если нота — у неё есть высота (имя) и длительность (момент). Если сигнал — у неё есть источник и потребитель. Пока мы не решим форму имени, я не смогу описать, что именно плагин ждёт. Предлагаю начать с имени: `<дом>.<событие>` звучит как нота с октавой — источник известен из префикса, событие — из суффикса. Это чище, чем плоская строка `journal_entry_added`.

[Архитектор]: Конструкция `<дом>.<событие>` верна архитектурно: пространство имён жёстко связывает событие с его источником, убирает неоднозначность при росте системы. Альтернатива — глобальный плоский словарь — рассыпается, как только появится третий дом: коллизии имён, неясное владение. Альтернатива два — произвольные строки без схемы — противоречит М1: `triggers: string[]` ждёт типизации, а не произвола. Фиксирую форму: `journal.entry_created`, `collections.collection_created`, `collections.sample_added`. Закрытый словарь — в `plugin-contracts`, не в каждом доме по отдельности.

[Математик]: Формализую вопрос о двух режимах. Пусть `T` — множество триггеров плагина. Режим «подписка» (живой): плагин получает событие `e` в момент `t(e)`, если он активен в `t(e)`. Режим «запрос» (постфактум): плагин вызывается внешним агентом с явным `ctx`, независимо от момента события. Это два разных отношения между плагином и событием. Если мы сделаем их одним именем с каким-то «родом», мы смешиваем предикаты. Правильнее: одно имя события, два разных канала доставки. `triggers` в манифесте называет события-интересы; канал доставки — отдельное поле или отдельный механизм, не примешанный в строку.

[Структурщик]: Уточняю терминологию, чтобы не расходились потом. «Канал» — это не поле манифеста, это контракт в `plugin-contracts`. Если `triggers` — закрытый словарь из `plugin-contracts`, то тип должен быть `PluginTrigger[]`, а не `string[]` — M1 оставил место именно для этого. Словарь объявляется как `const enum` или `as const` объект с типом-юнионом; плагин ссылается на него по имени, не пишет строку вручную. Это единственный способ поймать ошибку типизации до runtime. Произвольная строка — это «нарушена слабая связанность»: два дома могут называть одно разными именами и никто не узнает.

[Верстальщик]: Я смотрю на это с витрины будущего M5: пользователь настраивает плагин и видит список «на что реагирует». Если словарь закрытый и типизированный — витрина может показать человекочитаемые метки без дополнительной таблицы переводов. Если строки произвольные — витрина показывает сырые технические имена. Для читаемости критично, чтобы каждый элемент словаря нёс `label` (человеческое имя) рядом с `key`. Это не моё решение сегодня — M5 его примет — но форма словаря должна это допускать. Закрытый `as const` объект с полями `key` и, опционально, `label` — правильная форма.

[Teamlead]: Слышу консенсус по имени и типу. Фиксирую: `PluginTrigger` — юнион из закрытого словаря в `plugin-contracts`, форма `<дом>.<событие>`. Это не обсуждается дальше. Теперь нужно решить три оставшихся куска: минимальный словарь событий двух домов, механика испускания через процессную границу, и что происходит с пропущенным событием. Пошли дальше — не задерживаемся на том, что уже ясно.

[Музыкант]: По словарю первой очереди. Журнал — один глагол: запись внесена. Это `journal.entry_created`. Других событий у журнала первой волны нет — он не удаляет и не изменяет. Коллекции — два глагола: коллекция создана (`collections.collection_created`) и сэмпл добавлен (`collections.sample_added`). Это минимум, достаточный для M6: плагин, слушающий `journal.entry_created`, запускается при каждой записи в журнале. Добавлять `journal.entry_updated` или `collections.sample_removed` сейчас — это открытый простор, который повестка запрещает.

[Архитектор]: Поддерживаю минимальный список. Три события: `journal.entry_created`, `collections.collection_created`, `collections.sample_added`. Но нужно зафиксировать одно структурное свойство: каждое событие несёт `payload` с минимальным контекстом — идентификатор объекта и временная метка. Это не детали витрины, это контракт в `plugin-contracts`: `IPluginEvent<T>` с полем `trigger: PluginTrigger`, `occurredAt: Date`, `payload: T`. Тип payload для каждого события — отдельный тип в `plugin-contracts`. Без этого `PluginExecutor.execute(ctx)` не знает, что в `ctx` при живом событии.

[Математик]: Теперь механика через процессную границу — здесь есть точная проблема. Nest EventEmitter живёт в одном процессе. Если `background-office` и `background-media` — разные процессы, встроенный `EventEmitter` Nest не работает как шина между ними: он локален процессу. Три альтернативы: (1) Nest CQRS / EventEmitter — только если гарантирован один процесс; (2) Redis Pub/Sub или аналог — межпроцессная шина, но внешняя зависимость; (3) HTTP/gRPC-вызов от дома к PluginExecutor напрямую — без шины, зато без дополнительной инфры. Повестка говорит «общий процесс не гарантирован» — значит вариант (1) исключается.

[Структурщик]: Вариант (3) — HTTP/gRPC от дома к PluginHost — технически чище всего с точки зрения связанности: дом вызывает контракт `IPluginHost.notify(event)`, не зная ничего о плагинах. `IPluginHost` уже есть в `plugin-contracts` по вердикту M2. Это не шина — это вызов через контракт. Дом не знает, кто подписан; он просто уведомляет `IPluginHost`. `IPluginHost` уже знает реестр плагинов и диспетчирует. Альтернатива Redis — лишняя инфраструктурная зависимость при том, что контракт `IPluginHost` уже есть. Предлагаю: механика испускания — вызов `IPluginHost.notify(event: IPluginEvent)` через контракт, транспорт — выбор реализации, не контракт.

[Верстальщик]: Для меня важно, что форма события не меняется в зависимости от транспорта. Если плагин видит `IPluginEvent` независимо от того, пришло оно через HTTP или in-process — витрина M5 может показывать событие единообразно. Если транспорт просачивается в контракт — появятся два разных shape события. Поддерживаю: контракт `IPluginEvent` в `plugin-contracts`, транспорт — деталь реализации дома.

[Teamlead]: Механика зафиксирована: испускание — вызов `IPluginHost.notify(event: IPluginEvent)` по контракту из `plugin-contracts`. Встроенный EventEmitter Nest — исключён, потому что не работает через процессную границу. Redis — исключён, потому что лишняя инфра при наличии готового контракта. Переходим к пропущенному событию — самому неприятному куску.

[Музыкант]: Пропущенное событие — это потеря ноты. В аудио это клик или выпадение. Здесь вопрос тот же: если плагин выключен в момент `journal.entry_created`, запись уже есть в доме результатов, плагин просто её не видел. У нас есть M3: дом результатов с `StateRecord`, `resumeMode` и окном. `resumeMode` — это именно механизм догонялок. Значит пропущенное событие не копится в очереди: оно теряется как живое событие, но плагин при включении может запросить дом результатов и восстановить пропущенное. Это согласованно с M3.

[Архитектор]: Формулирую конструкцию явно. Два режима по M3: если `resumeMode = true`, плагин при включении запрашивает дом результатов за окно — это и есть «постфактум-запрос». Живое событие, пропущенное при выключенном плагине, не буферизуется нигде: оно теряется как живой сигнал. Буферизация на стороне `IPluginHost` — отклоняется: это стейт, который нужно хранить вечно (неизвестно, когда плагин включится), что нарушает границу ответственности `IPluginHost`. Правильная форма: живое событие — fire-and-forget; догонялка — через дом результатов по `resumeMode`.

[Математик]: Важное следствие для журнала. Журнал сегодня событий не испускает (Т3.7 — названная цена). При `resumeMode` плагин журнала запрашивает записи за окно напрямую у дома результатов, не через события. Это значит, что «постфактум-запрос» для журнала работает без изменения Т3.7: журнал не обязан испускать события, чтобы поддержать `resumeMode` — плагин сам читает дом результатов. Журнал испускает `journal.entry_created` только для живого режима (подписки), и это — добавляемая функциональность, реализуемая позже.

[Структурщик]: Уточняю термин «пропущенное событие» для контракта. В `IPluginEvent` нет поля «пропущено» — это не свойство события, это состояние плагина. Контракт `StateRecord` из M3 несёт `resumeMode` и `windowStart` — это всё, что нужно плагину, чтобы понять, нужно ли ему догонять. Не нужен отдельный тип «отложенное событие» или «очередь пропущенных». Форма проста: live-событие пришло — плагин обработал; плагин был выключен — при включении смотрит `resumeMode` и читает дом результатов. Две ветки, без буфера.

[Верстальщик]: С точки зрения будущей витрины: статус «плагин пропустил N событий» — это вычислимое из `StateRecord.windowStart` и текущего времени. Витрина M5 сможет это показать без дополнительного поля в контракте события. Хорошо, что мы не заводим буфер пропущенных — это лишний стейт, который надо рисовать и объяснять пользователю.

[Teamlead]: Принимаю по доставке и пропуску: live — fire-and-forget, пропущенное — теряется как живой сигнал, плагин догоняет через `resumeMode` и дом результатов. Буфер пропущенных — не заводим. Последний кусок: запрос как повод — кто вправе дёргать постфактум-плагин и как называется канал.

[Музыкант]: Запрос как повод — это не подписка, это вызов. Я слышу его как ручной старт трека: не автоматика, а команда. Кто командует — витрина (M5), CLI, расписание. Все три — внешние агенты. Им нужен один канал: `IPluginHost.request(pluginId, trigger, ctx)`. Имя канала — `request`. Это симметрично `notify` для живых событий: `notify` — дом уведомляет, `request` — внешний агент запрашивает.

[Архитектор]: Согласен по форме. `IPluginHost` получает два метода: `notify(event: IPluginEvent)` — для живых событий от домов; `request(pluginId: string, trigger: PluginTrigger, ctx: PluginContext)` — для внешнего вызова. Важно: `request` не создаёт новый тип повода — он использует тот же `PluginTrigger` из словаря. Различие режимов Т2 (запрос vs подписка) реализуется не разными именами в словаре, а разным входом в `IPluginHost`. Единый словарь триггеров, два метода контракта.

[Математик]: Формализую предикат: `notify` — отношение «дом испускает, все подписанные активные плагины с этим `trigger` получают»; `request` — отношение «внешний агент называет конкретный плагин и конкретный триггер, плагин выполняется». Это два разных предиката над одним словарём. Не нужно вводить `trigger: 'manual'` или специальный тип — это было бы лишней сущностью. Триггер при `request` — тот же `journal.entry_created` или иной из словаря; плагин не знает, пришёл ли он через `notify` или `request`.

[Структурщик]: Важное следствие: плагин не знает канала, по которому пришёл повод. Это правильно — слабая связанность. `PluginExecutor.execute(ctx)` получает один и тот же `ctx` независимо от канала. Это значит, что `ctx` должен нести `trigger: PluginTrigger` и `payload`, но не нести `deliveryMode: 'live' | 'request'`. Если вдруг потребуется — это решение M6, не M4. Сейчас — контракт без `deliveryMode`.

[Верстальщик]: Для витрины M5 важно знать, что `request` — это именованный метод контракта, а не отдельный REST-эндпоинт или CLI-команда. M5 сам решит, как выставить его наружу. Сейчас достаточно зафиксировать: канал называется `request`, живёт в `IPluginHost`, принимает `pluginId`, `trigger`, `ctx`. Детали витрины — не сегодня.

[Teamlead]: Всё. У нас есть ответы по всем пяти граням. Свожу итог.

[Музыкант]: Перед итогом — одно уточнение по словарю. Мы назвали три события: `journal.entry_created`, `collections.collection_created`, `collections.sample_added`. Нужно явно зафиксировать, что это закрытый список первой волны — расширение только через новое заседание или ADR. Иначе кто-то добавит `journal.entry_read` в порыве и словарь станет открытым простором.

[Архитектор]: Поддерживаю. Словарь закрытый, расширяется только через контракт в `plugin-contracts` с явным ADR или вердиктом комнаты. Сам словарь — `const` объект в `plugin-contracts/src/triggers.ts`, экспорт типа `PluginTrigger = keyof typeof PLUGIN_TRIGGERS`. Никаких добавлений в обход этого файла.

[Математик]: По `IPluginEvent<T>`: payload типизируется отдельно для каждого триггера. `JournalEntryCreatedPayload` — минимум: `{ entryId: string; occurredAt: Date }`. `CollectionCreatedPayload` — `{ collectionId: string; occurredAt: Date }`. `SampleAddedPayload` — `{ collectionId: string; sampleId: string; occurredAt: Date }`. Это контракт, не реализация — детали полей дом решает при испускании, но минимум зафиксирован.

[Структурщик]: Фиксирую итоговую структуру в `plugin-contracts`: `triggers.ts` — словарь `PLUGIN_TRIGGERS` и тип `PluginTrigger`; `plugin-event.ts` — `IPluginEvent<T>` с `trigger`, `occurredAt`, `payload`; обновление `IPluginHost` — методы `notify` и `request`; payload-типы для трёх событий первой волны. Всё в одном пакете `plugin-contracts` — ни `background-office`, ни `background-media` не объявляют типы событий сами.

[Верстальщик]: Принимаю. Форма данных позволяет витрине M5 работать без хаков. Словарь типизирован, payload предсказуем, два метода контракта различают каналы. Готово.

[Teamlead]: Принимаю. Комбинация сыграна чисто. Все пять граней закрыты, буфера нет, лишней инфры нет, витрина M5 получила форму без лишнего. LGTM по вердикту.

## Итоговое решение консилиума

| Грань | Решение |
|-------|---------|
| **Типизация `triggers`** | Тип `PluginTrigger` — закрытый юнион из `const`-объекта `PLUGIN_TRIGGERS` в `plugin-contracts/src/triggers.ts`; `triggers: PluginTrigger[]` в манифесте. Форма имени: `<дом>.<событие>` (например `journal.entry_created`). Произвольные строки — исключены. |
| **Два режима Т2** | Единый словарь `PluginTrigger`; режимы различаются каналом в `IPluginHost`: `notify` — живой (подписка), `request` — постфактум (запрос). Плагин не знает, каким каналом пришёл повод; `deliveryMode` в `ctx` — не вводится. |
| **Словарь событий первой волны** | Закрытый список: `journal.entry_created`, `collections.collection_created`, `collections.sample_added`. Расширение — только через `plugin-contracts` с вердиктом комнаты или ADR. |
| **Payload контракт** | `IPluginEvent<T>` с полями `trigger: PluginTrigger`, `occurredAt: Date`, `payload: T`. Минимальные payload-типы: `JournalEntryCreatedPayload { entryId, occurredAt }`, `CollectionCreatedPayload { collectionId, occurredAt }`, `SampleAddedPayload { collectionId, sampleId, occurredAt }`. Объявляются в `plugin-contracts`. |
| **Механика испускания** | Дом вызывает `IPluginHost.notify(event: IPluginEvent)` по контракту из `plugin-contracts`. Встроенный EventEmitter Nest — исключён (не работает через процессную границу).
