# Консилиум: В3 — Граница контейнера `network` с `infra-policy`

**Повестка:** Где проходит граница контейнера `network` с `infra-policy` и чем она проверяется? Вердикт: разрез + механизм проверки шва + ссылочность, с посылками.

**Участники:** Архитектор (Vesnin), Teamlead (Tarasov), Структурщик (Ozhegov), Математик (Dynin), Верстальщик (Rodchenko), Музыкант (Kuryokhin).

**Порядок реплик:** Архитектор → Teamlead → Структурщик → Математик → Верстальщик → Музыкант

---

[Архитектор]: Начну с конструкции. «Мощности там, маршруты здесь» — формула рабочая, но неточная без операционализации. Мощность — это характеристика узла или канала: пропускная способность, класс устройства, адрес. Маршрут — это наблюдение о путях между узлами в конкретный момент. Разрез по существу: `infra-policy.json` (#1393) владеет декларациями об узлах и их допустимых конфигурациях — это нормативный пласт. Зонд-снимок в `docs/audit/network` фиксирует наблюдённое состояние маршрутизации — это эмпирический пласт. Два дома, два рода записи, одна предметная область. Граница проходит по оси «норма vs. наблюдение».

[Teamlead]: Хорошо, конструкция ясна. Но мне нужна проверяемость, а не описание. Если оба дома говорят об одном узле — один нормативно, другой эмпирически — это ещё не дубль, это законная ссылка на один предмет. Дубль возникает, когда network-снимок начинает хранить нормативные атрибуты узла, которые уже есть в `infra-policy`. Вопрос механизма: чем ловить этот переход? Глагол `audit` в network — он читает и фиксирует, но не предписывает. Если глагол держит форму, дубль не вырастет. Это дисциплина словом, а не зубом?

[Структурщик]: Уточню лемму «дубль». Дубль — это когда два дома несут поле об одном предмете с одним семантическим статусом. «Узел X имеет пропускную способность 1 Гбит» в `infra-policy` и то же поле в зонд-снимке — дубль. «Узел X наблюдался с трафиком 0.3 Гбит в момент T» в снимке — не дубль, это другой тип записи. Разрез по семантике поля: `infra-policy` владеет полями класса «что должно быть», снимок владеет полями класса «что было в момент T». Если форма снимка закрыта и не содержит полей-деклараций — дубль структурно невозможен. Механизм: ограничение схемы снимка.

[Математик]: Формализую предикат шва строго. Пусть `F_p` — множество полей записи `infra-policy`, `F_s` — множество полей зонд-снимка. Дубль существует тогда и только тогда, когда `∃ f: f ∈ F_p ∩ F_s AND sem(f, policy) = sem(f, snapshot)`, где `sem` — семантический статус поля (норма vs. наблюдение). Если схема снимка зафиксирована с явной аннотацией `type: observation` на каждом поле, пересечение по `sem` пусто по конструкции. Проверка шва — это проверка схемы, не проверка содержимого. Этот предикат вычислим статически, до создания любого конкретного снимка.

[Верстальщик]: Мне важно понять форму ссылки для будущей витрины: если снимок ссылается на `infra-policy`-запись — чем? Путём — хрупко: `infra-policy.json` может переехать. Id — стабильнее, если id канонический. Ничем — тогда связь теряется при анализе. С точки зрения читаемости и честности структуры: снимок должен нести ровно один атрибут-ссылку на нормативный источник своего предмета — канонический id узла из `infra-policy`. Не путь, не название файла. Так витрина сможет сопоставить наблюдение с нормой без хрупкой строчной привязки.

[Музыкант]: Слышу риск в обратной связи: а может ли `infra-policy` ссылаться на снимок? Это было бы инверсией тракта — норма, зависящая от наблюдения. Архитектурно: нет. `infra-policy` — upstream, снимок — downstream. Обратная ссылка создаёт цикл. Если policy-запись хочет сослаться на «последний наблюдённый снимок» — это уже аналитика, и она живёт в производных мастерской, не в самом `infra-policy`.

[Архитектор]: Возвращаюсь к вопросу о достаточности формулы «мощности там, маршруты здесь». Она недостаточна в одном месте: маршрут как атрибутивный блок внутри снимка (решение M1) может содержать упоминание узла. Узел — предмет `infra-policy`. Без явного указания, что упоминание узла в снимке есть ссылка, а не декларация, формула оставляет зазор. Дополнение: снимок может упоминать узел только через ссылочный атрибут (id), но не описывать его характеристики. Это закрывает зазор.

[Teamlead]: Ожегов поставил ключевое: дубль невозможен, если схема снимка закрыта. Это проверяемо. Но закрытость схемы — это норма нашей комнаты, а не факт сегодня. Нужен механизм, который держит закрытость. Глагол `audit` создаёт снимок — он должен работать по зафиксированной схеме. Если схема записана и глагол не может создать поле вне неё — это и есть механизм. Зуб здесь не нужен: зуб ловит после создания, схема ловит до. Предпочитаю схему.

[Структурщик]: Схема снимка как механизм — согласен, но уточню: «схема» здесь не JSON Schema как файл, а закрытый список полей в документе решения комнаты. Глагол `audit` производит снимок строго по этому списку. Глагол `decompose` разбирает снимок по тому же списку. Если список закрыт и не содержит полей-деклараций — шов держится дисциплиной формы. Дополнительный зуб (автоматическая проверка) — вопрос В6/В7, не этой комнаты.

[Математик]: Фиксирую: ссылочный атрибут в снимке имеет форму `infra_node_id: <canonical_id>`. Это скалярное поле, не путь, не имя файла. Каноничность id — ответственность `infra-policy`, не снимка. Снимок только несёт этот id как непрозрачный ключ. Проверяемость: наличие поля `infra_node_id` в схеме снимка — факт, который читается из документа решения без прод-замера.

[Верстальщик]: Обратная ссылка из `infra-policy` в снимок — Курёхин прав, это инверсия. Но я добавлю: если `infra-policy` не ссылается на снимки, то связь «норма → наблюдение» устанавливается только через общий `infra_node_id`. Обе стороны знают id, и этого достаточно для сопоставления. Витрина делает join по id на этапе отображения — не в самих записях.

[Музыкант]: Хочу зафиксировать асимметрию ссылочности явно: снимок → `infra-policy` через `infra_node_id` — разрешено; `infra-policy` → снимок — запрещено. Это не вкусовое решение, а следствие из направленности тракта. Норма не знает о конкретном наблюдении — иначе она перестаёт быть нормой.

[Архитектор]: Теперь о механизме проверки шва суммарно. Три слоя: первый — закрытая схема снимка (структурный; дубль невозможен по форме); второй — ссылка через `infra_node_id` (ссылочный; связь без копирования нормативного содержания); третий — дисциплина глагола `audit` (процедурный; глагол создаёт только то, что в схеме). Зуб (автоматический) — за пределами этой комнаты. Три слоя вместе образуют механизм проверки шва.

[Teamlead]: Принимаю конструкцию. Резюмирую для вердикта: разрез — по оси «норма vs. наблюдение»; снимок наблюдает, `infra-policy` предписывает; ни один снимок не несёт нормативного поля. Механизм — закрытая схема снимка плюс дисциплина глагола `audit`. Ссылочность — односторонняя: снимок несёт `infra_node_id` как непрозрачный ключ; обратная ссылка запрещена. Это полный и достаточный ответ на В3. Вопросы В2, В4, В5, В6, В7 — не в этом протоколе.

[Структурщик]: Один уточняющий пункт по форме ссылки: `infra_node_id` — атрибут внутри атрибутивного блока маршрута (решение M1: маршрут — атрибутивный блок внутри снимка). Это значит, что ссылка живёт внутри снимка, а не на уровне заголовка записи. Снимок в целом наблюдает сетевой путь; внутри этого наблюдения атрибутивный блок маршрута несёт id узлов-участников. Структурно чисто.

[Математик]: Проверяю предикат полноты вердикта. Требование повестки: назвать (1) разрез, (2) механизм проверки шва, (3) форму ссылочности. Все три названы. Дополнительное требование: список посылок. Посылки — в отдельной секции. Лишних посылок быть не должно: только те, на которых стоит рассуждение. Готов перечислить.

[Верстальщик]: Со стороны формы документа: протокол несёт секцию «Список посылок» с разметкой «факт / норма» на каждой строке. Это требование машинного гейта, не опция. Убеждаюсь, что секция будет в итоговом решении, а не в теле диалога.

[Музыкант]: Добавлю наблюдение о BRIEF-ограничении «не строить второй реестр мощностей» (#1425 контекстно). Это ограничение напрямую поддерживает разрез: network-снимки, не содержащие нормативных полей мощности, не образуют второго реестра. Механизм шва — это и есть исполнение этого ограничения.

[Архитектор]: Уточняю по посылке «материал такта 1 + дополнение 12.08 (карта маршрутов из кода)»: карта маршрутов из кода входит в предметное поле снимка, а не в `infra-policy`. Маршрут из кода — наблюдение о том, как система маршрутизирует, а не декларация о том, как она должна. Это подтверждает разрез: карта принадлежит снимкам.

[Teamlead]: Финальная проверка: нет ли в вердикте захвата чужих комнат. В2 (словарь состояний) — не упомянут. В4 (такт, субъект проверки) — не упомянут. В5 (хранение) — не упомянут. В6, В7 (зубы) — упомянуты только как «за пределами этой комнаты». Чисто. Вердикт готов.

[Структурщик]: Финально по ссылочности: форма «ничего» (то есть снимок вообще не ссылается на `infra-policy`) отклонена, потому что тогда теряется возможность сопоставления наблюдения с нормой при анализе. Форма «путь» отклонена как хрупкая. Форма «id» принята. Это решение, не предположение.

[Математик]: Формально фиксирую: `infra_node_id` является непрозрачным ключом с точки зрения схемы снимка. Снимок не интерпретирует его содержимое, не валидирует его существование в `infra-policy`. Он только несёт его. Интерпретация — в мастерской при агрегации.

[Верстальщик]: Принимаю вердикт. Форма ссылки через `infra_node_id` даёт витрине достаточную основу для join без встраивания нормативных данных в снимок.

[Музыкант]: Принимаю. Асимметрия ссылочности зафиксирована явно — это важнее симметричной формы, которая создала бы цикл.
