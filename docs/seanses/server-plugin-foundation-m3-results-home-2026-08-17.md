[Математик]: Начну с посылок, которые определяют форму. PluginId из M1 уже несёт пространство имён — вида `module:plugin`. mountTarget из M2 уже длинной формы — `background-office/journal`. Цепочка Т3.3: «модуль → плагин → версия → коллекция → прогон». Если PluginId = `module:plugin`, то в адресе записи модуль уже закодирован внутри PluginId — повторять его отдельным сегментом значит кодировать дважды одно и то же. Предлагаю адрес записи результата: `{pluginId}/{version}/{collectionId}/{runId}` — без отдельного `module`-сегмента.

[Teamlead]: Хорошо. Ставлю вопрос жёстко: шесть граней, одно заседание, вердикт нужен по всем. Нет «зависит от реализации» — форма сейчас. По носителю сразу скажу позицию: архивариус уже живёт в Mongo офиса, 106К спанов. Класть результаты плагинов туда же — значит не плодить инфраструктуру. Отдельная коллекция в той же Mongo — да, именно отдельная, не в спаны архивариуса. Переходим к обсуждению.

[Архитектор]: Конструкция адреса. PluginId из M1 имеет вид `{namespace}:{name}` — namespace и есть модуль. Если ввести в адрес отдельный `module`-сегмент, получим двойное кодирование: `journal-analyzer/journal-analyzer:word-count/1.0.0/...`. Это нарушение. Форма ключа в Mongo-документе: `{ pluginId, version, collectionId, runId }` — четыре поля, каждое несёт ровно один смысл. Составной индекс по этим четырём полям даёт адресацию без дубля. Именовать интерфейс: `RunAddress`.

[Верстальщик]: Смотрю на структуру как на карточку, которую будет читать витрина (M5 её нарисует, сейчас не проектирую). Важно: `runId` должен быть человекочитаемым или хотя бы сортируемым по времени — UUID v7 или `{timestamp}-{random}`. Это не декор, это требование к форме: без монотонного runId витрина не может показать «последний прогон» без сортировки по полю `completedAt`. Прошу зафиксировать форму runId в вердикте.

[Структурщик]: Уточняю термины. `collectionId` — это идентификатор коллекции звуков из home `background-media/collections` (вердикт M2). Он внешний ключ, не вложенная структура. Запись результата живёт в доме результатов (Mongo офиса, отдельная коллекция), ссылается на коллекцию по id — не дублирует её содержимое. Один термин — один смысл: `collectionId` всюду одинаков. Интерфейс записи: `RunRecord` с полями `address: RunAddress`, `fingerprints: RunFingerprints`, `result: RunResult`, `completedAt`.

[Музыкант]: Два отпечатка — это два разных сигнала, которые нельзя смешивать в одном поле. Отпечаток входа: хеш состава коллекции — что именно в ней на момент прогона (список сэмплов с их id и contentHash). Отпечаток конфигурации: хеш множества `{pluginId, version}` всех включённых плагинов. Оба — детерминированные функции от своих входов, SHA-256 достаточно. Если состав коллекции изменился — отпечаток входа расходится, результат протухает. Кто объявляет протухшим — это вопрос формы, не реализации: чтение сравнивает отпечаток в записи с текущим отпечатком коллекции.

[Математик]: Формализую предикат протухания. Пусть `fp_input_stored` — отпечаток входа в записи, `fp_input_current` — хеш текущего состава коллекции. Результат протухший если и только если `fp_input_stored ≠ fp_input_current`. Хешируется: отсортированный по `sampleId` список пар `(sampleId, contentHash)`. Сортировка обязательна — хеш от неупорядоченного множества не детерминирован. Для конфигурации: отсортированный по `pluginId` список пар `(pluginId, version)`. Оба отпечатка — чистые функции от своих входов, без скрытого состояния.

[Teamlead]: Фиксирую. Протухание объявляет чтение — не сторож. Это важно: сторож, который фоново помечает записи протухшими, — лишняя движущаяся часть до M4. Чтение сравнивает отпечатки на месте и возвращает `{ stale: true }` если расхождение. Это форма ответа `RunRecord`, не событие. Дальше — заморозка. Накопительный плагин имеет состояние. Где оно живёт?

[Архитектор]: Состояние накопительного плагина — жилец того же дома результатов, под тем же адресом, но с `kind: 'state'` вместо `kind: 'result'` (kind из RunResult, M1). Форма заморозки: при выключении плагина — запись с `frozenAt` и `payload` (сериализованное состояние). При включении: читаем последнюю запись `kind: 'state'` по тому же `RunAddress` (без `runId` — последняя по `completedAt`). Если есть — объявляем `resumeMode: 'from-freeze'`, если нет — `resumeMode: 'fresh'`. Это честное объявление, не вывод из ниоткуда.

[Верстальщик]: Важная деталь для формы: `resumeMode` должен быть полем в записи результата следующего прогона, не только в логе. Иначе витрина не может показать «этот прогон возобновлён с заморозки» без парсинга истории. Прошу зафиксировать `resumeMode` как поле `RunRecord`.

[Структурщик]: Соглашусь, но уточню: `resumeMode` — поле `RunRecord`, а не поле `RunAddress`. Адрес — это координата, не семантика прогона. Семантика — в теле записи. Граница чёткая: `RunAddress` несёт только то, что нужно для поиска; `RunRecord` несёт то, что нужно для интерпретации. Без этой границы адрес начнёт пухнуть смыслами.

[Музыкант]: Окно накопления — где оно объявляется? Манифест плагина несёт `windowSize` как параметр конфигурации. Запись состояния накопительного плагина несёт `windowStart` и `windowEnd` — это наблюдаемые границы текущего окна. На границе окна: плагин завершает накопление, пишет итоговый `kind: 'result'`, затем пишет новую запись `kind: 'state'` с `windowStart = windowEnd`, `payload = initial`. Это чистая последовательность, без side-effect в сторонние системы.

[Математик]: Уточняю: `windowSize` в манифесте — это норма (наше решение), а не факт. Запись состояния с `windowStart`/`windowEnd` — это факт наблюдения. Граница окна — детерминированная функция: `windowEnd = windowStart + windowSize`. Никаких скрытых переменных. Важно: `windowSize` входит в отпечаток конфигурации? Нет — он параметр плагина, не версия плагина. Если `windowSize` меняется — меняется конфигурация → меняется `fp_config`. Это покрыто вторым отпечатком.

[Teamlead]: Стоп. Если `windowSize` входит в хеш конфигурации, то изменение окна делает все предыдущие результаты протухшими по конфигурации, а не по входу. Это правильно: результаты с другим окном — другая модель, не другие данные. Фиксирую: `fp_config` хешируется от `{pluginId, version, params}`, где `params` включает `windowSize` и прочие параметры манифеста. Это честно.

[Архитектор]: Теперь сходимость (Т3.9). Живой прогон и пересчёт должны давать один результат при одинаковых входах. Зуб сверяемости — это форма, не реализация. Форма: запись `kind: 'convergence-check'` в том же доме с полями `{ liveRunId, recomputeRunId, inputFingerprintMatch: boolean, outputDiff: unknown }`. Это не событие (M4 не тронут), не витрина (M5 не тронута) — это просто запись в доме результатов с именованным интерфейсом `ConvergenceRecord`. Живёт по тому же `RunAddress` без `runId` — или с отдельным `convergenceId`.

[Верстальщик]: Предлагаю не вводить отдельный `convergenceId` — это плодит четвёртую ось координаты. Лучше: `kind: 'convergence-check'` с `runId = {liveRunId}+{recomputeRunId}` — составной, человекочитаемый. Витрина M5 сможет его показать без угадывания структуры.

[Структурщик]: Возражаю по форме. Составной `runId` с `+` — это кодирование двух значений в одном поле. Нарушение того же принципа, что мы применили к адресу: одно поле — один смысл. Правильно: `ConvergenceRecord` — отдельный интерфейс с `liveRunId` и `recomputeRunId` как отдельными полями, и собственным `convergenceId` (UUID v7). Он живёт в той же коллекции дома результатов, адресуется по `{ pluginId, version, collectionId }` + `kind: 'convergence-check'`.

[Музыкант]: Поддерживаю Структурщика. Смешивать два runId в одно поле — это как записать два канала в один моно-трек и потом спорить, что там было. Интерфейс `ConvergenceRecord` — отдельный, с собственным id.

[Математик]: Соглашусь. `ConvergenceRecord` как отдельный интерфейс — чисто. Зуб сверяемости: `inputFingerprintMatch = (fp_input(liveRun) === fp_input(recomputeRun))` — булева проверка. `outputDiff` — это поле типа `unknown` на данном этапе (форма M3, не содержимое M5). Предикат сходимости: `inputFingerprintMatch AND outputDiff === null`.

[Teamlead]: Носитель. Mongo офиса — да. Обосновываю против альтернатив. Файлы: нет транзакций, нет индексов, параллельные прогоны дадут конфликты при записи — отклонено. Prisma / Mongo медиа: медиа несёт коллекции звуков (вердикт M2), результаты плагинов — не медиа-данные, смешивать = нарушение границы дома — отклонено. Mongo офиса, коллекция `plugin-results` — архивариус там уже живёт, инфраструктура готова, добавляем коллекцию, не сервис. Принято.

[Архитектор]: Уточняю: коллекция называется `plugin-results` в пространстве Mongo-базы `background-office`. Не в коллекцию спанов архивариуса — отдельная коллекция с отдельными индексами. Индекс: `{ pluginId: 1, version: 1, collectionId: 1, runId: 1 }` — уникальный для `RunRecord`; `{ pluginId: 1, version: 1, collectionId: 1, kind: 1, completedAt: -1 }` — для поиска последнего состояния. Имена — в HOME_REGISTRY пакета `plugin-contracts` (вердикт M2 уже предписывает HOME_REGISTRY там).

[Верстальщик]: HOME_REGISTRY из M2 живёт в `plugin-contracts`. Туда же добавляем константу `PLUGIN_RESULTS_COLLECTION = 'plugin-results'` и `PLUGIN_RESULTS_DB = 'background-office'`. Это не новый пакет — расширение уже ратифицированного HOME_REGISTRY. Витрина M5 импортирует эту константу, не hardcode-ит строку.

[Структурщик]: Финальная проверка лемм. `RunAddress` — четыре поля: `pluginId`, `version`, `collectionId`, `runId`. `RunFingerprints` — два поля: `inputHash` (хеш отсортированного списка `(sampleId, contentHash)`), `configHash` (хеш отсортированного списка `(pluginId, version, params)`). `RunRecord` — объединяет `RunAddress`, `RunFingerprints`, `RunResult` (из M1), `completedAt`, `resumeMode?`, `stale?: boolean`. `StateRecord` — `RunAddress` без `runId`, `kind: 'state'`, `frozenAt`, `windowStart`, `windowEnd`, `payload`. `ConvergenceRecord` — `convergenceId`, `pluginId`, `version`, `collectionId`, `liveRunId`, `recomputeRunId`, `inputFingerprintMatch`, `outputDiff`. Все пять интерфейсов — в пакете `plugin-contracts`.

[Музыкант]: Слышу целостную картину. Один момент про границу окна: что происходит на границе — это последовательность записей, не одиночное событие. Порядок: 1) `RunRecord` с итогом окна, 2) `StateRecord` с `windowStart = prev.windowEnd`, `payload = initial`. Между ними не должно быть состояния «окно закрыто, новое не открыто» — это гонка. Значит обе записи пишутся в одной транзакции Mongo. Это требование к форме, не к реализации движка.

[Математик]: Транзакционность — свойство носителя. Mongo 4+ поддерживает транзакции. Это один из аргументов за Mongo против файлов: файловая запись двух документов атомарно невозможна без внешнего локка. Фиксирую как обоснование носителя.

[Teamlead]: Хорошо. Собираю решение. По всем шести граням позиции согласованы. Возражений без вещдока не осталось. Объявляю вердикт.

[Архитектор]: Одна последняя точность: `stale` — не поле записи, а результат вычисления при чтении. Хранить `stale: true` в Mongo означает, что при изменении коллекции нужно обновлять записи — это лишняя операция. Чтение вычисляет `stale` на лету: `fp_input_stored ≠ currentCollectionHash`. Поле `stale` не хранится, оно возвращается в ответе чтения. Исправляю формулировку Структурщика: `RunRecord` в БД не несёт `stale`, но `RunRecord` в ответе API несёт `stale?: boolean`.

[Структурщик]: Принимаю поправку. Граница чёткая: `RunRecord` как документ БД (без `stale`) и `RunRecordView` как ответ чтения (с `stale`). Два разных интерфейса, оба в `plugin-contracts`.

[Верстальщик]: `RunRecordView` — принимаю. Витрина M5 потребляет именно его. Форма зафиксирована.

[Музыкант]: Принимаю решение по всем граням.

## Итоговое решение консилиума

| Грань | Решение |
|-------|---------|
| **Адресация** | `RunAddress = { pluginId, version, collectionId, runId }`. `pluginId` несёт namespace модуля (вердикт M1) — отдельный `module`-сегмент не вводится, двойного кодирования нет. `runId` — UUID v7 (монотонный, сортируемый по времени). |
| **Два отпечатка** | `RunFingerprints = { inputHash, configHash }`. `inputHash` = SHA-256 от отсортированного по `sampleId` списка `(sampleId, contentHash)`. `configHash` = SHA-256 от отсортированного по `pluginId` списка `(pluginId, version, params)` — `params` включает `windowSize` и прочие параметры манифеста. Протухание объявляет **чтение** на лету: `inputHash_stored ≠ hash(currentCollection)` → `stale: true` в `RunRecordView`. Сторож не вводится. |
| **Заморозка состояния** | `StateRecord = { pluginId, version, collectionId, kind:'state', frozenAt, windowStart, windowEnd, payload }`. При выключении плагина пишется `StateRecord`. При включении: читается последний `StateRecord` по `(pluginId, version, collectionId, kind:'state')`, сортировка по `frozenAt` desc. Наличие → `resumeMode: 'from-freeze'`; отсутствие → `resumeMode: 'fresh'`. `resumeMode` — поле документа `RunRecord` следующего прогона. |
| **Окно накопления** | `windowSize` объявляется в манифесте плагина. `StateRecord` несёт `windowStart` и `windowEnd` — наблюдаемые границы текущего окна. На границе: `RunRecord` (итог окна) и новый `StateRecord` (сброс) пишутся в одной Mongo-транзакции — нет состояния «окно закрыто, новое не открыто». |
| **Сходимость** | Интерфейс `ConvergenceRecord = { convergenceId, pluginId, version, collectionId, liveRunId, recomputeRunId, inputFingerprintMatch: boolean, outputDiff: unknown }`. Живёт в той же коллекции `plugin-results`. Зуб: `inputFingerprintMatch AND outputDiff === null`. Форма M3; содержимое `outputDiff` — за пределами M3. |
| **Носитель** | Mongo офиса (`background-office`), отдельная коллекция `plugin-results`. Индексы: уникальный `{ pluginId, version, collectionId, runId }` для `RunRecord`; `{ pluginId, version, collectionId, kind, completedAt: -1 }` для поиска последнего состояния. Файлы — отклонены (нет транзакций, конфликты при параллельных прогонах). Mongo медиа — отклонена (нарушение границы дома M2: медиа несёт коллекции звуков, не результаты плагинов). |
| **Интерфейсы** | Все пять: `RunAddress`, `RunFingerprints`, `RunRecord` (документ БД), `RunRecordView` (ответ чтения, добавляет `stale?: boolean`), `StateRecord`, `ConvergenceRecord` — в пакете `plugin-contracts`. Константы `PLUGIN_RESULTS_COLLECTION`, `PLUGIN_RESULTS_DB` — в HOME_REGISTRY того же пакета. |
