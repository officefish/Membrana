# Консилиум: состав `/health/deep` кабинета (H1 / K2)

**Повестка:** H1 — какие числа издаёт `/health/deep` кабинета вместо «ок»: состав предметных величин, форма ответа, пороги с физическим смыслом, различение трёх родов отказа — так, чтобы авария 23.08 была видна этим прибором за часы до пятисоток.

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Структурщик (Ozhegov), Математик (Dynin), Музыкант (Kuryokhin), Верстальщик (Rodchenko).

[Структурщик]: Начну с границ словаря. `/health` и `/health/deep` — две разные статьи, не синонимы. `/health` — liveness процесса кабинета: жив, версия, uptime. `/health/deep` — read-model предметного состояния кабинета: зависимости и очереди, без которых продукт врёт «ок». Публичный контракт — один endpoint-издатель; сборщики (Prometheus и род) в эту комнату не входят — Т1.

[Teamlead]: Планка ясна: прибор обязан поймать класс аварии 23.08 за часы до пятисоток. Иначе это тренировка, не матч. Не размазываем scope: состав величин, форма, пороги, три genus. Сборщики, сторож, #2113/#2110 — вне комнаты. Жду от Математика числа с физическим смыслом, от Архитектора — форму отказа в контракте M1.

[Математик]: Фиксирую предикат видимости 23.08 численно. Факт: лента ~2400 записей → ~115 тыс. строк на пробу, квадратичный рост стоимости чтения. Пусть `tape_len = N` — число записей (или строк-участников агрегата — уточним носитель) в ленте, подлежащей тяжёлому чтению. Авария растёт как Θ(N²) по стоимости пробы. Порог не «магические 2000», а N, при котором ожидаемая стоимость пробы превышает бюджет latency базы. Задержка базы 3,9–8,2 с — второй канал; меряем легально, не боковым логином.

[Музыкант]: С тракта записи: media-буфер на узле уже отдаёт пульс M1b — `media_used_mb / media_cap_mb`. Кабинет не должен петь ту же партию другим голосом. В `/health/deep` — кабинетные величины: что давит *сервер* (лента, база, доля доехавших в дом кабинета). «Буфер media» как дубль пульса — фальшь; optional read-model пульса — да, но без переопределения словаря.

[Архитектор]: Конструкция: `/health/deep` — издатель кабинета, лежит в том же отказном контракте M1. При деградации/отказе тело несёт `genus ∈ {broken, busy, unreachable}`; при `broken` — `incidentId` + заголовок `X-Incident-Id`, рядом `requestId`. Не изобретаем четвёртый статус «degraded» как отдельный enum отказа: деградация — это ещё 200 с числами выше порога *или* явный `busy`, если кабинет сознательно отказывает в работе. Граница модуля: health-controller читает дешёвые gauge/счётчики, не гоняет тяжёлые JOIN ленты.

[Верстальщик]: С витрины дежурного: глазочитаемость — числа `tabular-nums`, не проза «всё плохо». Три рода отказа — три слова на бейдже, без легенды. Но экраны и Grafana эта комната не проектирует; мне важно, чтобы JSON ответа сам читался человеком в `curl`: плоская структура, короткие ключи, порог рядом с величиной или в отдельном блоке `verdict`, без вложенных романов.

[Структурщик]: Леммы величин, чтобы не поплыли имена. (1) `tape_length` — длина ленты кабинета (записи/строки, один канон единицы в контракте). (2) `db_latency_ms` — задержка законного probe к базе. (3) `ingest_arrived_ratio` — доля доехавших записей (принятых домом кабинета к ожидаемым/заявленным за окно). (4) media с узла — **не** словарная статья этого endpoint; при optional read-model — вложенный объект `duty_pulse?` as-is из M1b, без rename. Машинные `heap`, `event_loop_lag` — сознательно вне минимального состава: Т2, предметные важнее.

[Teamlead]: Принимаю четыре оси: лента, база, доля доехавших, и явно «не дублировать пульс». Цена вызова — жёсткий DoD: deep-health сам не должен стать второй аварией 23.08. Источники — только заранее накопленные счётчики/последний sample, не SELECT на 115k строк внутри запроса health.

[Математик]: Дешёвые источники. `tape_length`: counter/gauge, обновляемый на write-path или периодическим `COUNT` с TTL ≥ step пульса, не на каждый HTTP. `db_latency_ms`: один лёгкий round-trip (`SELECT 1` или `SELECT current_timestamp`) с таймаутом; p99/last — хранить last + EWMA, в ответ отдать `db_latency_ms` (last) и опционально `db_latency_ewma_ms`. `ingest_arrived_ratio`: `arrived / expected` за фиксированное окно T (предлагаю T = 15 мин как горизонт «часы до пятисоток» требуют более длинного тренда ленты, а ratio — короче); при `expected = 0` — `null`, не 1.0.

[Музыкант]: Доля доехавших на слух продукта: это не SNR и не DSP, но это «дошла ли лента звука до дома». Если узлы пишут, а кабинет не принимает — оператор должен увидеть ratio < 1 задолго до того, как UI начнёт врать пустотой. Согласен: media cap остаётся у узла. Кабинет может показать «последний увиденный пульс», но не считать его своим порогом.

[Архитектор]: Форма ответа (здоровый случай, HTTP 200):

```json
{
  "status": "ok" | "degraded",
  "version": "...",
  "protocolVersion": "...",
  "uptime_s": 0,
  "measured_at": "ISO-8601",
  "tape_length": 0,
  "tape_length_warn": 0,
  "tape_length_fail": 0,
  "db_latency_ms": 0,
  "db_latency_warn_ms": 0,
  "db_latency_fail_ms": 0,
  "ingest_arrived_ratio": 0.0,
  "ingest_window_s": 900,
  "ingest_ratio_warn": 0.0,
  "genus": null,
  "requestId": "..."
}
```

При отказе — не этот «ok-shaped» вранём: HTTP 5xx/503 по роду, тело M1: `genus`, `incidentId` при broken, `requestId`, плюс те же числа, что успели снять (best-effort gauges). `status: degraded` — ещё обслуживаем, но есть warn-порог; это не четвертый genus.

[Верстальщик]: Глазочитаемо: в одном взгляде три числа и три порога. Предлагаю в ответе держать пороги явно (как у Архитектора) — тогда `curl` без документации отвечает «почему красный». Цвета UI потом возьмут `status` + `genus`; сейчас достаточно контракта чисел. Не прятать `degraded` в `ok`.

[Структурщик]: Различители трёх родов — строго M1, прикладная семантика для deep:

- `unreachable` — зависимость (БД/диск метрик) не отвечает в budget таймаута; probe не завершился.
- `busy` — зависимость жива, но latencies/очередь выше fail; кабинет перегружен, «подожди».
- `broken` — инвариант нарушен: схема, падение критичного пути, невозможность доверять read-model; нужен `incidentId`.

Лента выше fail при живой БД — это `busy` (деградация нагрузки), не `broken`. `broken` — когда сам прибор не может честно измерить или внутреннее состояние противоречиво.

[Teamlead]: Жёстко: путаница busy/broken — BLOCK на приёмке. Правило Тарасова: перегруз — busy; ложь контракта/порча — broken; нет связи с зависимостью — unreachable. Пятисотки 23.08 на пике — симптом; deep обязан поднять busy по ленте и db_latency за часы до этого.

[Математик]: Пороги с физическим смыслом, не подгонка.

1. **Лента.** Факт 23.08: N≈2400 → ~1,15·10⁵ строк/пробу. Пусть стоимость пробы C ≈ α N² (или α N · rows_per_record). Budget чтения B — доля допустимого db time (например B = 500 ms wall на фоновую агрегацию, не на health). Тогда `tape_length_fail = max N: C(N) ≤ B`, `tape_length_warn = fail / 2` (или fail · 0,5). Константа α калибруется один раз замером на staging тем же запросом, что душит прод — не из «красивого круглого». Для DoD ретроспективы: при N=2400 warn и fail уже пробиты, если α взята из того дня.

2. **db_latency.** Физика: p95 интерактивного запроса кабинета. Warn = 1000 ms (уже заметно человеку), fail = 3000 ms (ниже факта 3,9–8,2 с пика, чтобы поймать *до* потолка). Альтернатива: fail = 0,5 · timeout_HTTP_клиента. Беру fail = 3000 ms, warn = 1000 ms как стартовые нормы с явным пересчётом после калибровки α.

3. **ingest_arrived_ratio.** Warn = 0,95 (5% потерь/лага за окно), fail = 0,80. Physical: «каждый пятый не доехал» — уже инцидент потока, не шум.

[Музыкант]: 3 с latency базы — уже «запись есть, дом не слышит вовремя». Поддерживаю fail 3000 ms. По ленте: важнее не абсолют 2400, а связка «длина → стоимость пробы → бюджет». Иначе снова подгоним число под вчерашнюю аварию и промахнёмся на завтрашней схеме.

[Архитектор]: Чем deep отличается по потребителю:

| Endpoint | Кто | Когда |
|----------|-----|--------|
| `/health` | оркестратор/proxy liveness | часто, без зависимостей |
| `/health/deep` | дежурный человек, будущий scraper, pre-deploy gate | редко (≤ 1/min), с числами |

Liveness-проба оркестратора **не** должна бить в deep — иначе сам оркестратор станет нагрузкой. Это норма границы, не деталь деплоя.

[Верстальщик]: Для человека в curl важен порядок ключей: сначала `status`, потом три величины, потом пороги, потом `genus`. Optional `duty_pulse` — в хвосте, приглушённо по смыслу (не спорит с лентой). Пустые: `ingest_arrived_ratio: null` + причина в `ingest_ratio_note` короткой строкой, не stacktrace.

[Структурщик]: Что сознательно **не** входит в минимальный состав: heap/RSS, event loop lag, CPU%, полные дампы очередей, дубль `media_used/cap`, вердикты сторожа, номера #2113/#2110, бизнес-метрики DSP/детекции, «ok» без чисел. Расширения — за отдельным ADR, не smuggling в H1.

[Teamlead]: Цена вызова — вписываю в DoD: p99 самого `/health/deep` ≤ 50 ms wall, ноль тяжёлых запросов на request-path, только чтение memory/gauge. Нарушение — BLOCK, даже если числа красивые. Связка на реализацию: Структурщик (контракт/controller) + Математик (калибровка α и probe) ; Верстальщик не нужен до UI.

[Математик]: Калибровка α — одноразовая методика в DoD, не «на глаз в проде»: на копии схемы выполнить тот же класс агрегата, снять C(N) для N ∈ {100,500,1000,2000,2400}, fit C≈αN², вычислить fail. Ретро-предикат 23.08: подставить N=2400 → status∈{degraded} при warn *или* genus=busy при fail; и/или db_latency_ms ≥ warn на боковом замере дня (3,9 с > 3 с fail). Прибор «видит за часы», если tape_length пересекает warn при росте N задолго до N_peak — это тренд, не точка; для точки DoD достаточно: при входных фактах дня ответ ≠ ok-liveness.

[Музыкант]: Не смешивать «доехали записи» с «пробы дежурства». probes_total — словарь узла (M1b). Кабинетный ratio — про ingest в дом кабинета (journal/media accept path), другое ухо. Имена не пересекать: только `ingest_arrived_ratio`, никогда `probes_*` в корне deep.

[Архитектор]: HTTP-семантика согласовать с genus (норма):

- 200 + `status: ok|degraded` — процесс обслуживает; degraded = есть warn, genus=null.
- 503 + `genus: busy` — перегруз (лента/latency fail).
- 503 + `genus: unreachable` — зависимость не ответила.
- 500/503 + `genus: broken` + `incidentId` + `X-Incident-Id` — поломка инварианта.

Числа в теле при 503 — best-effort. Контракт M1 не нарушаем.

[Верстальщик]: `status: degraded` глазом — жёлтый, не зелёный и не красный. Три genus — красные состояния с разными словами. Этого достаточно, чтобы потом бейдж не врал. В контракте зафиксировать enum строк case-sensitive: `broken|busy|unreachable`.

[Структурщик]: Носитель `tape_length`: одно число в контракте — **записи ленты** (records), не «строки разворота». Строки — внутренность стоимости C(N); наружу records, как предмет. В комментарии калибровки α — rows_per_record как константа дня схемы. Иначе UI и ops начнут спорить единицами.

[Teamlead]: Единица — records. Принято. Дальше не расползаться. Нужен явный DoD-предикат одной фразой и список посылок без выводов комнаты. Архитектор — собери форму в итог; Математик — пороги; Структурщик — что не входит.

[Математик]: Сводка порогов-норм (стартовые, α — из калибровки):

| Величина | warn | fail | смысл |
|----------|------|------|--------|
| tape_length (records) | ⌊N_fail/2⌋ | N: C(N)=B | стоимость пробы vs budget B |
| db_latency_ms | 1000 | 3000 | интерактив / до пика 3,9 с |
| ingest_arrived_ratio | 0,95 | 0,80 | потери/лаг окна 900 с |

Окно ingest: 900 s. При невозможности expected — null, не порог.

[Музыкант]: Принимаю таблицу. С поля: если ratio null при живой записи с узлов — это тоже сигнал витрине «счётчик ожиданий не сконфигурирован», не тихий ok. Пусть `status` не станет ok при null всех предметных — минимум лента и db обязаны быть числами; иначе broken.

[Архитектор]: Уточнение инварианта честности: если `tape_length` или `db_latency_ms` снять нельзя — `genus: unreachable` или `broken` (если gauge обязан существовать always-on). Нет пути «200 ok без предметных чисел» — иначе повторим health.controller.ts:33. `/health` остаётся тонким; deep — толстым и честным.

[Верстальщик]: Принимаю. Для curl-человека: отсутствие числа хуже, чем плохое число. Пустых «ok» не будет — конструкция честная.

[Структурщик]: Optional `duty_pulse`: тип as-is M1b (`probes_total`, `step_s`, `media_used_mb`, `media_cap_mb`), nullable, не участвует в вычислении genus кабинета. Смешать пороги media узла с genus кабинета — нарушенная связанность доменов.

[Teamlead]: Сводка на приёмку: состав из трёх обязательных величин + optional pulse; форма M1; пороги с методикой α; потребители разведены; цена ≤50 ms p99 без тяжёлого SQL. Вердикт комнаты — **да, фиксируем**. Реализация — отдельной задачей, прод не трогаем из этой комнаты.

[Математик]: DoD-предикат (проверяемый): *Если подать в издатель входные факты замера 23.08 (`tape_length ≥ 2400` и/или `db_latency_ms ≥ 3900`), ответ `/health/deep` не является liveness-ok: либо `status=degraded`, либо HTTP 503 с `genus=busy|broken|unreachable`, и в теле видны предметные числа.* Дополнительно: warn по ленте достигается при N ≤ N_fail/2 < 2400, т.е. на траектории роста N прибор краснеет раньше пика.

[Музыкант]: Принимаю предикат. Это тот прибор, который услышал бы давку в доме до пятисоток.
