## Пункт 8 — исполнимость в границах B: развилка владельца

Границы B по M0: новый модуль клиента офиса в `packages/background-cabinet/src/modules/`, собственный файл-схема пары «адрес + ключ офиса», `deploy/generate-cabinet-env.sh`. Вердикт требует правки трёх файлов сверх этого, и они различаются по тому, что о них сказала комната:

**(1) `packages/background-cabinet/src/config/config.module.ts` — комната назвала расширение словами, в таблице.** Строка 147 вердикта: «`config.module.ts` в M0 не закреплён; по решению комнаты его правит сессия B. `env.schema.ts` — не трогается (файл C)». Основание в репликах — *[Архитектор], стр. 58: «Тогда `config.module.ts` надо править — он в M0 не закреплён. Он читает `parseEnv` из `env.schema.ts` на строке 4 и зовёт его в фабрике на строке 11. Второй источник сам себя не подключит: `parseEnv(process.env)` в одиночку новый файл не увидит, потому что тот никем не импортируется.»*; *[Teamlead], стр. 60: «Он в M0 ничей; логика — тот, кто расширяет конфиг, тот и правит модуль. Значит `config.module.ts` — сессии B, с обязательным условием: правка не касается `env.schema.ts`.»* Аудит по этому файлу — PASS.

**(2) `packages/background-cabinet/src/modules/health-deep/` — комната проговорила границу трижды, в таблицу не перенесла.** *[Верстальщик], стр. 76: «Правильное место — `health-deep`: существующий модуль `health-deep` в списке кабинета расширяется одним чекером „офис регистрации“. Это тоже граница B, если `health-deep` не закреплён за другой сессией.»*; *[Математик], стр. 78: «Проверю по факту: в списке модулей кабинета `health-deep` есть, отдельного владельца в M0 на него нет. Считаю расширение `health-deep` границей B.»*; *[Верстальщик], стр. 128: «договорённость про `health-deep` — говорить как „модуль `health-deep` расширяется чекером“ и не молчать о границе. Если B и D пересекутся по `health-deep`, Teamlead разрешит при исполнении, но по M0 у D нет притязаний — фиксирую.»* В таблице (стр. 155) и готовности (стр. 185) — только «из расширенного `health-deep`», без слова о границе. Ствол: `health-deep.module.ts` импортирует только `PrismaModule`; чекер живости потребует импорта нового модуля клиента и правки сервиса и модуля глубокой проверки.

**(3) `packages/background-cabinet/src/app.module.ts` — комната не называла вовсе.** Вердикт (стр. 107, готовность) велит создать «новый модуль Nest: `office-registration.module.ts`, …». В стволе все модули кабинета подключаются в одном месте — `app.module.ts:47–62`, `imports: [AppConfigModule, PrismaModule, …, HealthDeepModule]`; модуль Nest, не подключённый в `imports`, не существует для приложения. Значит правка `app.module.ts` — необходимое следствие вердикта, одна строка, и ни один сеанс не был на неё уполномочен.

Председатель границы не двигает — это правило M0, ратифицированное владельцем. Два выхода, решение при ратификации:

1. **Расширить границы B** (рекомендация председателя): к трём позициям M0 добавить `packages/background-cabinet/src/config/config.module.ts` (комната назвала), `packages/background-cabinet/src/modules/health-deep/` — файлы модуля и сервиса глубокой проверки и её тесты (комната проговорила), `packages/background-cabinet/src/app.module.ts` — **только строка подключения нового модуля в `imports`** (следствие вердикта). Правило «каждый путь — ровно одной сессии» не нарушается: ни один из этих путей не принадлежит A, C или D; `env.schema.ts` остаётся у C. ## Замечания аудита, которые уходят в задание B как факты ствола (решение не трогают)

- **Составной тип конфига.** Тип `AppConfig` объявлен в `env.schema.ts:51` как `z.infer<typeof envSchemaWithDefaults>` — файл C. «`APP_CONFIG` несёт поле `office`» без правки этого файла означает новый составной тип (в `config.module.ts` или в `office-env.schema.ts`), который расширяет `AppConfig` полем `office: OfficeEnv | null`; сессии, читающие `APP_CONFIG`, получают его через тот же токен. Вердикт способ не называет — задание B называет: составной тип рядом со схемой пары, `env.schema.ts` не трогать.
- **Кто рождает ключ.** Значение ключа офиса рождается в `deploy/generate-office-env.sh:21,29` при первом развёртывании офиса; вердикт описывает только перенос. Задание B фиксирует источник: файл окружения офиса на его VDS; корневой `.env` — промежуточный носитель.
- **Условия включения регистрации.** Вердикт (стр. 145) выводит «флаг регистрации» из наличия пары; существующий `ALLOW_REGISTRATION` (`env.schema.ts:37,47`, файл C, в проде `false`) в вердикте не назван. Два условия включения — предмет M3 и сессии C; B отдаёт только `APP_CONFIG.office === null` как факт, регистрацию не включает и не выключает.
- **Имена тестов.** Прецедент кабинета — `media-bridge.service.test.ts`, не `.spec.ts`.
- **Сдвиг строк в фактуре.** `mediaFetch` — строка 145, `assertOk` — 155 (в повестке и вердикте на строку раньше); существо ссылок верно.
