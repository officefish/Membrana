[Teamlead]: Положение — орган, судящий содержание документа вечера, в дереве не найден. Это не умолчание, это результат поиска, зафиксированный в повестке. Вопрос узкий: нам нужен предикат, который отличает «покрыл» от «сгенерировался». Планка матча — дать форму ворот с явными посылками, не достраивать чужие карточки. Каждый говорит по своей зоне.

[Музыкант]: На слух сейчас три документа вечера — три mono-take без ленты подтверждения: скрипт отработал, exit-код сказал «прогон состоялся», а содержание никто не слышал. Exit занят под «прогон жив» — это счётчик такта, не ревью. Чтобы понять, что сыграно по партитуре, а не шум, нужна отдельная шина: структура с полями, которые проверяет гейт до сборки в диалог. Именно так устроен `angelina-validate` — он прототип, а не исключение.

[Верстальщик]: С витрины капитана сейчас три документа выглядят одинаково: «шаг завершён». Нет различия между «покрыл пустой день» и «покрыл шесть карточек» и «не покрыл ни одной». Это фальшивое присутствие — хуже пустоты. Ворота обязаны показывать два честных состояния: `coverage: full | partial | empty-day`, и это должно читаться без легенды. Пустой день — не красный, но явный: `inputCards: 0, verdict: no-cards-day`.

[Архитектор]: Граница вопроса — не «как устроен скрипт», а «что является входом предиката покрытия». Из M1: единица суждения — карточка реестра, активная за день; вход тройка `(карточка, коммиты, контракт)`. Значит предикат покрытия — это отношение между множеством карточек дня `C_day` и множеством суждений документа `J_doc`. Форма отношения: для каждой карточки в `C_day` должно существовать хотя бы одно суждение в `J_doc` с полями `boundary/checks/safety`. Это не умозаключение — это прямое следствие из M1.

[Математик]: Формализую без UI. Пусть `C_day` — множество карточек, активных за день (из реестра). Пусть `J_doc` — множество суждений документа с типизированными полями `boundary`, `checks`, `safety`. Предикат покрытия: `covered(doc) ⇔ ∀c ∈ C_day: ∃j ∈ J_doc: j.cardId = c.id ∧ j.boundary ≠ ε ∧ j.checks ≠ ε ∧ j.safety ≠ ε`. Частный случай: `C_day = ∅ ⇒ covered(doc) = true` — вакуумная истина, но требует явного маркера `inputCards: 0`, иначе неотличима от необработанного. Непокрытый остаток: `uncovered(doc) = C_day \ {c : ∃j ∈ J_doc, j.cardId = c.id}` — типизированный сигнал, не молчание.

[Структурщик]: Лемма про разделение ответственности. Три документа вечера имеют разную природу входа: `day-memo` суммирует день целиком (вход: `C_day`), `audit-evening` отражает ход цепочки (вход: артефакты прогона), `code-review` судит код (вход: коммиты и контракты). Один предикат покрытия на три документа — синоним, который стирает эту разницу. Нужны три схемы входа с разными полями обязательности. Это не вкус — это разные области определения одного глагола «покрыл».

[Teamlead]: Ожегов прав в разделении, но рано уходить в три схемы. Сначала — общая форма ворот. Из повестки: `exit` занят под «прогон состоялся», `findingExitCodes` — под находку. Значит вердикт покрытия не может жить ни там ни там. Остаётся одно место: отдельный орган-валидатор, гоняется до сборки — по образцу `isValid`. Это не новое изобретение, это тот же паттерн, что уже работает в цепочке.

[Музыкант]: Согласен с паттерном. Добавлю семантику: у `audit-evening` и `code-review` сейчас нет `findingExitCodes` — это значит, что у них нет даже канала для находки, не то что для покрытия. Если мы добавляем орган-валидатор, его выход — не exit и не finding, а поле в машинном фронтматтере документа: `coverageVerdict: full | partial | empty-day | incomplete`. Это читается и человеком, и гейтом.

[Верстальщик]: Поддерживаю поле во фронтматтере. По образцу M4 F1: машинный фронтматтер первичен, markdown — детерминированная проекция. Поле `coverageVerdict` живёт в машинном носителе, в markdown рендерится как строка. Пустой день: `inputCards: 0, coverageVerdict: empty-day` — честный зелёный, не ложный. Непокрытый остаток: `uncoveredCards: [id1, id2]` — явный список, не молчание.

[Архитектор]: Форма носителя правильная, но есть граница, которую нельзя перейти: орган-валидатор не может одновременно быть частью документа, который он валидирует. Этот скрипт гоняется до сборки документа в диалог — по точному образцу `isValid` из нормы #1573. Результат пишется в фронтматтер документа валидатором, не самим документом.

[Математик]: Уточняю сигнатуру. Вход: `(docPath: string, registryPath: string, date: string) → CoverageResult`. Предикат непустоты суждения по полю: поле присутствует и не равно пустой строке и не равно типизированному сигналу пробела (`no_contract | orphan_commits | input_incomplete` — это M1, не покрытие). [Структурщик]: Уточню леммы для трёх документов. `day-memo`: вход `C_day`, предикат полный — каждая карточка покрыта суждением с тремя полями. `audit-evening`: вход — артефакты прогона цепочки (не карточки напрямую); его предикат покрытия — не тот же, что у мемо. `code-review`: вход — коммиты и контракты; предикат — наличие суждения по каждому коммиту в пределах дня. | Вопрос | Решение |

| (б) Форма ворот | Отдельный скрипт-валидатор `doc-coverage-validate.mjs`, гоняется до сборки документа. Возвращает `CoverageResult` — структуру с проверяемыми полями. | (г) Область действия | Один скрипт `doc-coverage-validate.mjs` с параметром `kind: 'day-memo' \| 'audit-evening' \| 'code-review'` — три схемы входа в одном органе. Схема для `day-memo`: карточки реестра + поля `boundary/checks/safety`. Схема для `code-review`: коммиты и контракты за день. Схема для `audit-evening`: **не определена этой комнатой** — входные данные для этого `kind` в повестке не описаны; комната говорит «не знаю». |
