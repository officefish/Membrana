[Структурщик]: Начну с лемм, иначе разъедемся в словах. «Дом» — адрес плоскости артефактов контейнера, не runtime-сервис и не пакет в monorepo. «Единица звена» — одна append-запись контейнера, из которой строятся отчёты; не маршрут как объект политики и не правило firewall. Образец жанра в посылках — `docs/audit/llm-calls`: дом + мастерская + закрытый список запрещённых полей. Предлагаю зеркало: `docs/audit/network`.

[Teamlead]: Планка комнаты узкая: только дом и определение записи. В3 (граница с infra), В2 (словарь состояний), В4–В7 — чужие комнаты; кто потянет их сюда — BLOCK по колонизации. BRIEF держим: не чиним сеть (#1425), не второй реестр мощностей (#1393). Форма живёт без прод-замера — значит дом обязан быть audit-плоскостью, а не capacity-registry. К Ожегову: зеркало llm-calls принимаю как рабочую гипотезу — спорьте по существу единицы.

[Музыкант]: Слышу это как вопрос о дорожке, а не о микшере. Органы такта 1 — `net:diag`, `llm:probe`, `infra:probe`, `net:http`, `outbound-self-check`, `scripts/network/*` — это микрофоны на шине, не сама партитура маршрутов. Одна запись должна звучать как снимок прослушивания: кто слушал, что услышал, когда. Маршрут «кто→куда→выход» — тембр внутри снимка, не отдельный жанр ленты. Иначе получим два параллельных bus.

[Архитектор]: Конструкция. Плоскость `docs/audit/*` уже несёт жанр «наблюдаемое без права чинить». Класть `network` рядом с `llm-calls` оправдано функцией: отчётность о пробах, не управление сетью и не inventory мощностей. Цена альтернативы «отдельная плоскость `docs/network/`» — второй жанр дома без образца и риск смешения с infra-доками. Рекомендую дом: `docs/audit/network`. Единица — не правило и не «живая» сессия.

[Математик]: Формализую кандидат единицы. Пусть запись `r` = результат одного акта зонда: `(organ, target_ref, observed_at, outcome_class, metrics_subset)`. Это функция наблюдения, не объект конфигурации. Маршрут и правило — либо поля/проекции, либо сущности других комнат; если сделать единицей «маршрут», контейнер начнёт дублировать топологию и поползёт в #1393. Численно: органы такта 1 все являются probe/check, не route-store — эмпирика материала совпадает с предикатом «зонд-снимок».

[Верстальщик]: С витрины читателя отчёта: в `llm-calls` человек открывает дом и видит ленту однородных карточек вызова, не кашу из политик и сырых дампов. Для network нужна та же конструкция: одна карточка = один зонд-снимок, заголовки честные (`organ`, `outcome`, время), без сырого тела ответа и без секретов в явном виде. Глаголы мастерской потом лягут на эту карточку; если единица будет «правило», UI отчёта превратится в редактор firewall — это не audit-витрина.

[Структурщик]: Фиксирую термин: **зонд-снимок состояния** — каноническая лемма единицы. Маршрут (кто→куда→каким выходом) — допустимый *атрибутивный блок внутри* снимка, когда зонд его наблюдает; не отдельный род записи в ленте. Правило — вне этой комнаты (политика/infra). Производные: агрегаты по organ, timeline, сводки audit — читаются мастерской, не пишутся как второй род единицы. Иначе нарушим «один термин — один смысл».

[Teamlead]: Единица «зонд-снимок» — принимаю как рабочий стержень. Проверяю BRIEF: чинить сеть этой записью нельзя по определению жанра — хорошо. Второй реестр мощностей не строится: снимок не capacity-record. Дальше закройте запрещённые поля жёстким списком классов — без «и т.д.» в вердикте. Мастерская — ровно три глагола по норме HOME_WORKSHOP, каждый с предметом чтения.

[Музыкант]: Запреты по слуху с шины: сырое тело HTTP/пакетный payload — это как писать WAV целиком в лог репетиции, шум убивает партитуру. Секреты и токены в заголовках/URL — недопустимы. Приватные абсолютные пути хоста и env с credential — тоже. Что можно оставить в снимке: класс исхода, код/статус нормализованный, latency, имя органа, санитизированный target (host/service id без userinfo).

[Архитектор]: Запрещённые классы полей — закрытый список, зеркало llm-calls по роли, не копипастой имён домена LLM:
1) секреты и credentials (токены, пароли, ключи, `Authorization`, userinfo в URI);
2) приватные локальные пути и домашние директории оператора;
3) сырые тела запросов/ответов и пакетные payload’ы;
4) полные дампы заголовков/env без редактирования (как носители секретов и PII).
Всё, что нужно для диагноза, — нормализованные коды, классы, метрики, ссылки на organ. Границу «что такое infra vs network identity» не трогаем — это В3.

[Математик]: Проверяю список запретов на полноту относительно утечки. Сырое тело ⊆ запрет; credential ⊆ запрет; абсолютный path с user home ⊆ запрет. Отдельно: не запрещаем *факт* измерения (rtt_ms, exit_code, outcome_class) — иначе контейнер теряет предикативную ценность. Идемпотентность ленты и формат хранения — В5; здесь только классы полей записи. Лишнюю посылку «прод уже меряет X» вводить нельзя: BRIEF говорит форма без прод-замера.

[Верстальщик]: Мастерская дома по норме трёх глаголов, читаемо с витрины:
- `audit` — читает ленту снимков (множество записей) → сводный отчёт/целостность корпуса;
- `decompose` — читает срез или набор снимков → разложение по organ/outcome/времени без сырых тел;
- `inspect` — читает **одну** запись → карточка полей снимка, санитизированный target, метрики.
Никакого четвёртого глагола «repair/fix» — это нарушило бы #1425 уже на уровне словаря мастерской.

Путать `scripts/network` с домом контейнера — `нарушена слабая связанность` жанров: скрипт исполняет, audit-дом хранит наблюдаемое. Зависимость односторонняя: отчёт ссылается на organ id, скрипт не импортирует markdown-ленту как API.
