## Пункт 3 — «Список посылок»: три посылки поставлены на реплики

Девять посылок (П1–П4, П6, П8, П10–П12) аудитор признал дословными и у заявленной роли — они остаются как в протоколе. Ниже три починенные; форма — та же, что в протоколе: тип, содержание, реплика с ролью и номером строки.

5. **факт** — Выдача/отзыв под `@OwnerAdmin`; аудит `mint-code` / `revoke-code`; state — `PanelUsersState`, не Prisma (ADR-0005). (*[Архитектор], стр. 58: «Почему не отдельный вид: выдача/отзыв уже под `@OwnerAdmin`, модель, аудит `mint-code`/`revoke-code`, нормализация `normalizeGrants` — переиспользуем.»*; *[Музыкант], стр. 95: «Аудит-лента: сегодня `mint-code` / `revoke-code`.»*; *[Архитектор], стр. 93: «Хранилище — `PanelUsersState` parse/write.»*)

7. **норма** — ADR-0005 / Q3: ошибки регистрации не различают причину **наружу**; на внутреннюю service-дверь не переносится. (*[Архитектор], стр. 70: «наружу пользователя кабинета норма Q3 (ADR-0005) сохраняется и на внутреннюю дверь не переносится: Q3 — про публичный контур регистрации, не про service-to-service.»*; *[Teamlead], стр. 124: «Q3: „наружу причину не различать“ — норма публичной регистрации (панель и будущий UX кабинета). Внутренняя дверь различает reason. Кабинет-сервис не протаскивает reason в браузер.»*)

9. **план** — Контракт двери `POST /v1/internal/cabinet/registration-codes/consume` + internal auth + mode check/redeem + enum reason. (*[Структурщик], стр. 62: «Охрана: внутренний guard сервиса (shared secret / service token между `background-cabinet` и `background-office`). Имя в фактуре позже; в контракте: внутренняя охрана офиса. Путь предлагаю: `POST /v1/internal/cabinet/registration-codes/consume`. Не под `/v1/panel/…`, чтобы не смешать с PanelAuthGuard-семантикой партнёров.»*; *[Математик], стр. 66: «Контракт операции: одна дверь, тело `{ "code": string, "mode": "check" | "redeem" }`. `check` — read-only, без инкремента; `redeem` — атомарный check+inc.»*; *[Архитектор], стр. 70: «Успех redeem: HTTP 200, тело `{ "ok": true, "code": "<normalized>", "grant": "cabinet-register", "uses": { "used": n, "max": m } }`. Успех check: 200, `{ "ok": true, "redeemable": true, "grant": "cabinet-register", "uses": { "used": n, "max": m } }` без инкремента.»*; *[Структурщик], стр. 85: «Тело отказа: `{ "ok": false, "reason": "<enum>" }`. Без PII.»*)

Жирное начертание внутри реплик при цитировании снято; слова, знаки и порядок — как в протоколе (проверка: `grep -cF` по нормализованному тексту, как у аудитора).

## Пункт 8 — исполнимость в границах сессии A: развилка владельца

Комната это произнесла, но в вердикт не внесла: *[Структурщик], стр. 62: «Не под `/v1/panel/…`, чтобы не смешать с PanelAuthGuard-семантикой партнёров.»*; *[Структурщик], стр. 130: «Пакет: `background-office` modules/panel-users (+ internal controller или subpath).»* Ствол (`origin/main` = `72bc026a`): в NestJS путь метода относителен префиксу класса, а классовый страж накрывает все методы; значит дверь вне `/v1/panel` и вне `PanelAuthGuard` — это **новый файл контроллера** в том же модуле и **одна строка** в `panel-users.module.ts` (`controllers: [PanelUsersController]`). Ни тот ни другой путь границами A по M0 не покрыт (A: `panel-users-core.ts`, `panel-users.controller.ts`, `scripts/_ssh-panel-smoke.mjs`); тесты для A в M0 тоже не оговорены (для C — оговорены).

Председатель границы не двигает — это правило M0, ратифицированное владельцем. Два выхода, решение при ратификации:

1. **Расширить границы A** (рекомендация председателя): к трём файлам M0 добавить новый файл контроллера внутренней двери в `packages/background-office/src/modules/panel-users/` (имя — за сессией, например `panel-users-internal.controller.ts`), файл `panel-users.module.ts` и новые тесты в том же каталоге по образцу `panel-users-core.test.ts`. Правило «каждый путь — ровно одной сессии» не нарушается: ни один из этих путей не принадлежит B, C или D. Решение комнаты при этом не меняется — меняется только карта файлов задания A.
2. **Повторный прогон M1** с повесткой, где границы A названы явно и комната обязана уложить дверь в них или расширить их вердиктом.

## Замечания аудита, которые уходят в задание A как факты ствола (решение не трогают)

- **Имя стража.** Комната оставила «имя в фактуре позже» (стр. 62). В стволе канон внутренней охраны офиса один: `packages/background-office/src/common/guards/api-token.guard.ts` — класс `ApiTokenGuard`, заголовок `X-Membrana-Token`, сравнение с `API_INTERNAL_TOKEN`; 14 файлов офиса его уже используют. Задание A называет его по имени; это уточнение внутри решения «внутренняя охрана офиса», не новое решение.
- **Сериализация.** «Классическая гонка read → check → write» ([Математик], стр. 54) описывает возможную реализацию, не ствол: сегодня контроллер работает «snapshot-first» без ожидания между снимком и записью (`panel-users.controller.ts:91–92`), а запись хранилища синхронна — временный файл и переименование (`panel-users.store.ts:77–95`). Замок из вердикта — дополнительный страж; обязательный предмет приёмки — инвариант «успешных redeem ≤ maxUses при гонке» и красный зуб на него (DoD 3), как комната и записала.
- **Словарь.** Латиница в вердикте (`redeem`, `reason`, `mode`, `check` — имена полей и значений контракта) остаётся; англицизмы «inc», «lock», «writer-контур», «unavailable office» в задание A переводятся: приращение, замок, единственный пишущий контур, недоступность офиса.
