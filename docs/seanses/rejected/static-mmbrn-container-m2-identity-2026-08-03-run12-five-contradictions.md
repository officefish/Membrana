[Teamlead]: Вопрос I1 стоит прямо: что именно регистрируется, как именно идентифицируется, и чему именно верить как источнику истины. M1 дала классы, но оставила единицу регистрации для составных форматов и семантику версионирования пустыми. Сегодня закрываем всё это. Порядок держим, каждый говорит по делу. Начнём с единицы регистрации.

[Музыкант]: По составным форматам — архив и PDF-с-вложением — ситуация понятна: регистрируем целиком, побайтно. Член архива или встроенный объект PDF получает отдельную запись только если поступает независимо или M6 его предоставляет явно. До этого момента составной файл есть атомарная единица регистрации. Это не потеря информации — это честная граница между тем, что мы знаем сейчас, и тем, что решит M6.

[Верстальщик]: С точки зрения представления: единица — это то, у чего есть `sha256` и `bytes`. Всё остальное в записи строится поверх этой пары. Если нет байтового слепка — нет записи вещдока, это прямо из README-предиката. Для PDF как целого это выполняется автоматически; для его страниц или вложений — нет, пока M6 не предоставит их как самостоятельный поток байтов.

[Архитектор]: Форма решения здесь такая: одна запись `EvidenceRecord` = один байтовый объект с установленным `sha256`. Это инвариант, а не соглашение. Из него следует всё остальное: простой файл — один объект, архив — один объект (содержимое членов непрозрачно до M6), PDF — один объект. Граница чёткая, стоимость изменения — высокая, поэтому фиксируем её сейчас.

[Математик]: Формально: единица регистрации `U` — это пара `(content: Bytes, sha256: Hash)` где `sha256 = SHA256(content)` при принятом предположении о коллизионной устойчивости. `bytes = |content|` — положительное целое, верифицируется при доступе сравнением фактического размера с заявленным. Математическая уникальность хешем не доказывается, но коллизионная устойчивость SHA-256 принята как рабочее допущение контракта.

[Структурщик]: Терминологически: `EvidenceRecord` — это не «файл», это запись о байтовом объекте. Поля `id`, `sha256`, `bytes`, `addedAt`, `source`, `location` обязательны; `about`, `measured` — опциональны. Ключевое: `id` — имя записи, `sha256` — тождество байтов, `location` — адресуемость, `source` — провенанс. Это четыре разных смысла, четыре разных поля, и смешивать их нельзя даже в речи.

[Teamlead]: Хорошо, единица согласована. Теперь к ролям полей и к тому, как `sha256`, `id` и root линии соотносятся как три разных тождества. Веснин — конструкция.

[Музыкант]: Прежде чем к конструкции — уточню про `source`. Это провенанс байтов: откуда они пришли физически — мессенджер, почта, полевой носитель. При адресной поправке (новый `location`, тот же контент) `source` повторяется, потому что байты не изменились. При новой редакции `source` фиксируется заново и честно — он может совпасть с прежним или различаться. Это не поле авторства операции.

[Верстальщик]: По `addedAt` — это дата регистрации записи, формат `YYYY-MM-DD…`, валидатор проверяет. Важно: `addedAt` не является датой создания контента и не является датой события. Это метка момента, когда конкретная строка была добавлена в `registry.jsonl`. У поправки адреса будет свой `addedAt`, отличный от исходной записи.

[Архитектор]: Три тождества — разные предметы с разными инвариантами. `sha256` идентифицирует конкретный байтовый объект — он неизменен, пока байты те же. `id` идентифицирует конкретную запись в реестре — он создаётся один раз и не мутирует; любое изменение любого поля порождает новую запись с новым `id`. Root линии идентифицирует логическую сущность через всю историю её записей — он равен `id` первой записи линии и не меняется при любых последующих поправках. Это три уровня, три разных вопроса.

[Математик]: Формализую функцию effective predecessor: `ep: R → Id(R) ∪ {⊥}`. Для записи с явным полем `supersedes` — `ep(r) = supersedes(r)`. Для четырёх named legacy-записей без `supersedes` — `ep(r)` равен `id` записи с максимальным номером ревизии, меньшим текущего, в той же логической линии, либо `id` base root если такой записи нет. Для всех прочих записей без `supersedes` — `ep(r) = ⊥`. Точный `r(N-1)` как механическое вычитание запрещён; вывод числа линий из количества записей без `supersedes` запрещён.

[Структурщик]: Root и tip — разные роли с разными критериями, это важно зафиксировать как термин. Root — запись, для которой `ep(r) = ⊥`. Tip — `id`, который не входит в множество `{ep(r) | r ∈ R, ep(r) ≠ ⊥}`. В линии длины 1 одна запись исполняет обе роли одновременно, но определения различны: root — по отсутствию predecessor, tip — по отсутствию в множестве predecessors. Нельзя говорить, что они «совпадают» — они выполняются одной записью при разных критериях.

[Teamlead]: По legacy — три линии, четыре записи. Нужно разобрать их точно, без условностей.

[Музыкант]: По `ozon-receipt-3765-field-kit-r2`: одна legacy-запись в этой линии из измеренных. Root линии — `ozon-receipt-3765-field-kit` (base, без суффикса). `ep(r2)` равен `id` записи `ozon-receipt-3765-field-kit` — это base root. Tip линии — `ozon-receipt-3765-field-kit-r2`, так как его `id` отсутствует среди всех значений `ep`.

[Верстальщик]: По `day-memo-2026-07-28-r2`: аналогично. Root — `day-memo-2026-07-28`. `ep(r2)` = `id` записи `day-memo-2026-07-28`. Tip — `day-memo-2026-07-28-r2`. Линия из двух записей: base и r2.

[Архитектор]: По bpla-линии: две legacy-записи в одной линии — `bpla-guidance-methodology-partner-r2` и `bpla-guidance-methodology-partner-r3`. Root — `bpla-guidance-methodology-partner` (base). `ep(r2)` = `id` записи `bpla-guidance-methodology-partner`. `ep(r3)` = `id` записи `bpla-guidance-methodology-partner-r2` — это максимальная меньшая ревизия. Tip — `bpla-guidance-methodology-partner-r3`, так как его `id` не является ничьим effective predecessor.

[Математик]: `canonicalRef` формулируется точно: `canonicalRef = "urn:mmbrn:static:" + rootId`. Инъективность формулы обеспечена уникальностью `rootId` в реестре и фиксированным префиксом. Для bpla-линии: `canonicalRef = "urn:mmbrn:static:bpla-guidance-methodology-partner"` — не меняется при переходе от r2 к r3, при смене склада, при любой адресной поправке. Альтернативные формулы и абстрактный `det(root)` запрещены.

[Структурщик]: `canonicalRef` не является публичным URL — это идентификатор в пространстве имён реестра. Доступность и авторизация — M3. В записи реестра `canonicalRef` выводится из lineage, не хранится как отдельное поле записи. Это вычислимый атрибут линии, не поле `EvidenceRecord`.

[Teamlead]: Переходим к области истины реестра и к отношению между реестром, байтами и складом.

[Музыкант]: Реестр — единственный источник истины о регистрации, о `record id` и lineage, о заявленных полях и истории. Байты — независимый предмет: они верифицируют заявленный `sha256` и `bytes` при доступе, но не восстанавливаются из JSONL автоматически. Склад — сменная деталь; `location` — заявление реестра о том, где байты находятся, а не гарантия их наличия. Достижимость — внешнее состояние склада, не инвариант реестра.

[Верстальщик]: Для представления это означает: реестр — индекс, байты — содержание. Потеря байтов не делает реестровую запись недействительной; она становится исторически зафиксированной записью с недостижимым `location`. Потеря записи реестра при живых байтах означает, что байты существуют как неиндексированный факт — семантически нетеряемость обеспечивается именно append-only реестром.

[Архитектор]: `registry.jsonl` append-only — это конструктивное ограничение, а не просто соглашение. Правка старых строк запрещена физически и семантически. Любая корректировка — новая строка с `supersedes`. Это означает, что история полностью сохранна: старая запись всегда читаема, новая добавляет контекст, а не стирает прежний. Это фундамент для любых аудитов.

[Математик]: Строго: `registry.jsonl` является источником истины для предикатов регистрации, идентификации и истории. Для предиката `sha256(r) = hash(bytes_at_location(r))` реестр является только заявлением — верификация требует обращения к байтам. Это разделение заявления и верификации — важный инвариант: реестр не лжёт о том, что зафиксировал, но может не знать о текущем состоянии склада.

[Структурщик]: `location.kind` — строго перечислимый тип: `local`, `affine`, `url`, `archivarius`. `sensitive` — не kind: чувствительность описывается отдельным `sensitive.reason`. Валидатор требует непустой `location.ref` при любом kind. Это означает, что sensitive-материал имеет допустимый kind и непустой ref в записи реестра — вопрос видимости этого ref решает M3, физический склад — M4.

[Teamlead]: Sensitive-поведение — последний блок перед таблицами. Зафиксируем точно.

[Музыкант]: Для sensitive-материала: байты могут находиться вне репозитория. Запись реестра при этом содержит обязательный `sha256`, обязательный `bytes`, допустимый `location.kind`, непустой `location.ref` и `sensitive.reason`. Реестр не скрывает факт существования записи — он только хранит причину чувствительности. Видимость ref — M3, склад байтов — M4. M2 устанавливает только то, что ref обязан быть в записи.

[Верстальщик]: С точки зрения формы: sensitive-запись ничем структурно не отличается от обычной — те же обязательные поля, тот же `location` с kind и ref. Добавляется `sensitive.reason`. Это позволяет реестру оставаться единообразным источником истины вне зависимости от чувствительности материала.

[Архитектор]: Принципиальный момент: sensitive не является исключением из контракта — это дополнение к нему. Контракт идентичности (sha256, id, lineage, canonicalRef) полностью применим к sensitive-материалу. Не выстраивается параллельная система — добавляется поле причины и делегируются решения видимости и хранения соответствующим заседаниям.

[Математик]: Для дубля: одинаковый `sha256` у двух записей с разными `id` означает, что байты одни, но записи разные. M2 не сливает их автоматически — это находка для человека. Две записи, два `id`, два canonicalRef, две независимые линии. Слияние не проектируется: M2 выбирает минимальную линейную цепь.

## Итоговое решение консилиума

### Единая пропозиция (вердикт I1)

Каждый материал `static.mmbrn.tech` при поступлении получает начальную запись `EvidenceRecord` в append-only `registry.jsonl`; последующие состояния той же линии получают новые записи. Единица регистрации — байтовый объект в целом (`sha256` = контрактное тождество байтов, `bytes` = размер, верифицируемый при доступе). Неизменяемый `record id` именует запись; `root` линии именует логическую сущность. Любое изменение поля порождает новую запись с `supersedes`; старая строка не мутирует. `registry.jsonl` — единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории; байты — независимый верифицирующий предмет. `canonicalRef = "urn:mmbrn:static:" + rootId` — стабильный идентификатор линии. Sensitive-материал сохраняет полный контракт записи плюс `sensitive.reason`.

### Таблица полей и инвариантов `EvidenceRecord`

| Поле | Обяз. | Тип/формат | Инвариант | Уровень |
|---|---|---|---|---|
| `id` | да | строка-идентификатор | создаётся один раз, не мутирует; любое изменение поля = новый `id` | Запись |
| `sha256` | да | hex-строка SHA-256 | тождество байтов; неизменен пока байты те же; контрактное допущение коллизионной устойчивости | Байты |
| `bytes` | да | положительное целое | размер конкретного байтового объекта; верифицируется при доступе сравнением фактического размера с заявленным; изменение требует новой записи | Байты |
| `addedAt` | да | `YYYY-MM-DD…` | дата добавления строки в реестр; валидатор проверяет формат | Запись |
| `source` | да | строка провенанса | происхождение байтов, не автор операции; повторяется при адресной поправке; фиксируется заново при новой редакции | Байты |
| `location.kind` | да | `local` / `affine` / `url` / `archivarius` | только перечисленные значения; `sensitive` не является kind | Запись |
| `location.ref` | да | непустая строка | непустой при любом kind; хранится в записи реестра независимо от чувствительности; видимость — M3 | Запись |
| `about` | нет | строка описания | смысловое описание; не влияет на тождество | Запись |
| `measured` | нет | объект измерений | дополнительные метрики; не влияют на тождество | Запись |
| `supersedes` | нет | `id` предшествующей записи | обязателен при любой поправке; отсутствие = начальная запись или legacy без явной ссылки | Линия |
| `sensitive.reason` | нет | строка | причина чувствительности; при наличии — байты могут быть вне репозитория | Запись |

**Lineage-атрибуты (вычисляемые, не поля `EvidenceRecord`):**

| Атрибут | Определение | Инвариант |
|---|---|---|
| `root` | `id(r0)` — запись без effective predecessor | неизменен для всей линии; равен `id` первой записи |
| `tip` | `id`, отсутствующий среди всех значений `ep` | определяется по полному множеству effective predecessors, включая вычисленные legacy |
| `canonicalRef` | `"urn:mmbrn:static:" + rootId` | стабилен; не меняется при поправках, смене склада, редакциях |
| `ep(r)` | `ep: R → Id(R) ∪ {⊥}` | см. семантику ниже |

**Семантика `ep`:**
- Явный `supersedes` → `ep(r) = supersedes(r)`
- Legacy named без `supersedes` → `ep(r)` = `id` записи с максимальным меньшим номером ревизии в линии, либо `id` base root
- Прочие без `supersedes` → `ep(r) = ⊥`

### Линейная семантика для legacy-записей

|---|---|---|---|---|
| ozon-receipt | `ozon-receipt-3765-field-kit` | base, r2 | ep(r2) = id(base) | `ozon-receipt-3765-field-kit-r2` |

### Таблица шести случаев

#### Случай 1: Простой PDF (первичная регистрация)

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | объект зарегистрирован целиком; `sha256` и `bytes` фиксируют конкретный файл | — (начальное состояние) |
| Запись | создана одна начальная запись; `id` уникален; `supersedes` отсутствует | — (начальное состояние) |
| Линия | линия из одной записи; запись одновременно root и tip по разным критериям | — (начальное состояние) |

**Доказательство:** `ep(r) = ⊥` → r есть root; `id(r)` не входит ни в одно значение ep → r есть tip. Численно root = `id(r)`, но байты, запись и линия — три разных предмета. В record-ячейке: запись имеет уникальный `id`, обязательные поля заполнены. Равенство root и `id` объясняется только в lineage-колонке.

---

#### Случай 2: Дубль (второй файл с тем же содержимым, другой `id`)

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | `sha256` совпадает у обеих записей — байтовое тождество одно | то же (`sha256` идентичен) |
| Запись | два разных `id`, два разных `addedAt`; записи независимы | иное (разные `id`, разные записи) |
| Линия | две независимые линии с разными root; два разных `canonicalRef` | иное (разные root, разные canonicalRef) |

**Доказательство:** совпадение `sha256` не означает тождества записей. M2 не сливает дубли автоматически — это находка для человека. Реестр фиксирует обе записи честно.

---

#### Случай 3: Новая редакция (изменился контент)

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | новый `sha256`, новый `bytes` — байтовый объект иной | изменилось (`sha256` и `bytes` новые) |
| Запись | новый `id`, новый `addedAt`, новый `supersedes` на прежний `id`; `source` фиксируется заново | изменилось (новая запись, новый `id`) |
| Линия | root и `canonicalRef` сохраняются; tip переходит к новой записи | то же (root, canonicalRef); изменилось (tip) |

**Доказательство:** `ep(новая) = id(прежней)` → прежняя уже не tip; новая не входит ни в какое ep → новая становится tip. Root неизменен, `canonicalRef` стабилен.

---

#### Случай 4: Архив или PDF со встроенным объектом

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | регистрируется весь архив или весь PDF целиком; `sha256` и `bytes` — всего объекта | — (единица регистрации — объект целиком) |
| Запись | одна запись для всего архива или PDF; компонент не получает отдельной записи до M6 | — (одна запись, нет компонентных записей) |
| Линия | линия из одной записи; семантика та же, что для простого PDF | — (начальное состояние) |

**Доказательство:** M2 не требует извлечения, производной или хранения компонента. Компонент регистрируется отдельно только при независимом поступлении или предоставлении M6. До этого — единица регистрации неделима.

---

#### Случай 5: Перенос склада (изменился `location`, контент тот же)

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | `sha256` и `bytes` не меняются — байты те же | то же (`sha256`, `bytes` идентичны) |
| Запись | новый `id`, новый `location`, новый `supersedes` на прежний `id`; `source` повторяется | изменилось (новая запись, новый `id`, новый `location`) |
| Линия | root и `canonicalRef` сохраняются; tip переходит к новой записи | то же (root, canonicalRef); изменилось (tip) |

**Доказательство:** адресная поправка — изменение поля `location`. Любое изменение поля → новая запись. `sha256` и root неизменны, `canonicalRef` стабилен. `ep(новая) = id(прежней)`.

---

#### Случай 6: Sensitive-материал

| Уровень | Что происходит | То же / иное / изменилось |
|---|---|---|
| Байты | `sha256` и `bytes` фиксируются; байты могут находиться вне репозитория | то же (контракт байтового тождества полностью применим) |
| Запись | полный контракт `EvidenceRecord` соблюдён; добавлен `sensitive.reason`; `location.kind` допустимый, `location.ref` непустой | то же (структура записи идентична); добавлено (`sensitive.reason`) |
| Линия | lineage-семантика неизменна; `canonicalRef` стабилен | то же |

**Доказательство:** `sensitive` не является `location.kind`. Запись реестра полная. Видимость `location.ref` — M3; физический склад байтов — M4. M2 устанавливает только обязательность `location.ref` в записи реестра независимо от чувствительности.
