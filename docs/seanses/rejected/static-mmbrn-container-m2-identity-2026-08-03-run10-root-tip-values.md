[Математик]: Начну с формального фундамента. Нам нужны три непересекающихся уровня тождества: байтовый (SHA-256 при принятом предположении коллизионной устойчивости), записный (неизменяемый `id` конкретной строки реестра) и линейный (root — `id` записи без predecessor в данной линии). Эти три значения могут совпадать численно у одноэлементной линии, но остаются разными предметами: путать их — ошибка типа, не просто неточность именования.

[Teamlead]: Позиция ясна. Три уровня — три разных предмета, граница регистрации — по поступлению, не по внутренней структуре составного формата. Веснин, нужен чёткий контракт полей: что неизменяемо, что обновляется поправочной записью, что несёт провенанс байтов, а не операции.

[Архитектор]: Контракт полей прямой. `id` — неизменяемый идентификатор конкретной строки реестра; создаётся при её добавлении и не пересматривается никогда. `sha256` — контрактное байтовое тождество: при адресной поправке он повторяется в новой записи без изменения, поскольку байты не менялись. `source` — происхождение самих байтов или материала, не автор регистрации или переноса; при адресной поправке повторяется, при новой редакции фиксируется заново и может совпасть либо различаться. ## Итоговое решение консилиума

### Вердикт M2 — пропозиция-контракт

Каждый материал контейнера `static.mmbrn.tech` при поступлении получает начальную запись в `docs/evidence/registry.jsonl`; последующие состояния той же логической линии получают новые append-only записи. Существуют три различных уровня тождества, которые никогда не смешиваются:

**Байтовый уровень.** SHA-256 идентифицирует конкретную байтовую последовательность контрактно, при принятом предположении коллизионной устойчивости SHA-256; математическая уникальность и доказательство равенства байтов одним хешем не утверждаются.

**Уровень записи.** Неизменяемый `id` идентифицирует конкретную строку реестра. Строка создаётся однократно и не мутирует никогда. Любое изменение любого поля — `about`, `measured`, `location` или иного — создаёт новую строку с новым `id` и полем `supersedes`, указывающим на прежнюю строку.

**Уровень логической линии.** Root — точный `id` записи, достигнутой следованием effective predecessor до записи без predecessor. `canonicalRef = "urn:mmbrn:static:" + rootId`. Root и `canonicalRef` фиксируются при создании первой записи линии и не изменяются никогда. `canonicalRef` — стабильный канонический адрес логической линии, детерминированный, инъективный, независимый от физического `location`, склада и движка; он не является публичным URL и не предрешает доступность или права — это M3.

**Каноническая единица регистрации.** Простой файл — одна запись. Архив и PDF со встроенными объектами — одна запись на составной объект целиком. Член архива или встроенный объект PDF получает отдельную запись только если он независимо поступил как материал либо M6 позднее предоставил его как материал. M2 не требует извлечения, производной или отдельного хранения компонентов.

**Effective predecessor.** Для записи с явным полем `supersedes` — effective predecessor равен значению этого поля. Для четырёх legacy-записей без `supersedes` — `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3` — predecessor вычисляется как существующая запись с максимальным суффиксом `M < N` в той же именной серии, либо base-запись без суффикса. Для всех прочих записей без `supersedes` predecessor отсутствует. Порядок определяется отношением effective predecessor, не `addedAt`. Циклы, fork, merge запрещены. Все новые поправки обязаны иметь явный `supersedes`.

**Live tip.** `id` записи, которая не является effective predecessor ни для одной другой записи реестра, включая вычисленные legacy-связи. Определение только через отсутствие в физических полях `supersedes` других записей запрещено.

**Источник истины.** `docs/evidence/registry.jsonl` — единственный источник истины о регистрации, record-тождестве, lineage-тождестве, заявленных полях и истории. Байты — независимый предмет и доказательство; они верифицируют заявленные `sha256` и `bytes` при доступе, но не восстанавливаются из JSONL автоматически и не заменяют реестр. `location` — заявление реестра; достижимость — внешнее состояние склада.

**Sensitive-поведение.** Запись чувствительного материала содержит допустимый `location.kind` (один из `local`, `affine`, `url`, `archivarius`) и непустой `location.ref` — честный адрес, даже если он честно непереносим. `sensitive` не является `location.kind`. Чувствительность фиксируется полем `sensitive.reason`. `sha256` и `source` сохраняются в записи полностью. Видимость `location.ref` — M3; выбор физического склада байтов — M4.

### Разбор шести случаев

| Случай | Байты | Запись | Линия |
|---|---|---|---|
| Простой PDF | SHA-256 и `bytes` фиксированы; `source` = происхождение файла | Создаётся одна строка: новый `id`, `sha256`, `bytes`, `addedAt`, `source`, `location`, опционально `about` и `measured`; `supersedes` отсутствует | Однозаписная линия; `canonicalRef` = `"urn:mmbrn:static:" + id` этой записи; tip = `id` этой же записи; байты, запись и линия — три различных предмета |
| Байтовый дубль под другим именем | SHA-256 идентичен первой записи — байтовое тождество то же | Создаётся новая строка с новым `id`; `supersedes` отсутствует; это самостоятельная запись, не поправка первой | Новая однозаписная линия с собственным root и `canonicalRef`; реестр не сливает дубли автоматически; дубль — находка для человека |
| Новая редакция содержания | SHA-256 иной — байтовое тождество новое; `source` фиксируется заново, может совпасть с прежним или отличаться | Создаётся новая строка с новым `id`, новым `sha256`, `supersedes` на предыдущую строку; прежняя строка не мутирует | Линия та же — root и `canonicalRef` сохраняются; tip переходит к новой записи; предыдущая запись перестаёт быть tip |
| Архив и его член | SHA-256 архива — байтовое тождество архива целиком; байты члена образуют своё байтовое тождество только при его независимой регистрации | Архив получает одну запись; член не получает отдельной записи, пока не поступил самостоятельно или M6 не предоставил его как материал; если поступил — создаётся своя запись с собственным `id` и `source` | Архив образует свою линию; член при самостоятельном поступлении образует свою независимую линию; M2 не требует извлечения |
| Перемещение байтов между складами | SHA-256 и `bytes` те же — байтовое тождество сохраняется; `source` повторяется без изменений | Создаётся новая строка с новым `id`, тем же `sha256`, новым `location`, `supersedes` на предыдущую строку, повторённым `source`; прежняя строка не мутирует | Линия та же — root и `canonicalRef` сохраняются; tip переходит к новой записи; склад — сменная деталь |
| Чувствительный материал без публичного локатора | SHA-256 и `bytes` фиксированы и хранятся в записи реестра; байты могут лежать вне репозитория | Запись содержит `id`, `sha256`, `bytes`, `addedAt`, `source`, `location {kind, ref}` с допустимым kind и непустым ref (честным, пусть непереносимым), `sensitive.reason`; `sensitive` не является `location.kind` | Линия образуется по тем же правилам; `canonicalRef` стабилен; видимость `location.ref` — M3; выбор физического склада — M4 |

### Доказательства тождества по уровням

**Что остаётся тем же и чем доказано:**

- Байтовое тождество сохраняется тогда и только тогда, когда SHA-256 в новой записи совпадает с SHA-256 предыдущей. Доказательство: верификация хеша при доступе к байтам.
- Record-тождество сохраняется тогда и только тогда, когда `id` строки тот же. Доказательство: строка реестра не мутирует; `id` создан однократно.
- Линейное тождество сохраняется тогда и только тогда, когда root и `canonicalRef` те же. Доказательство: следование цепи effective predecessor приводит к одной и той же записи без predecessor — root.

**Что становится иной сущностью:**

- Новая строка реестра — всегда новое record-тождество (новый `id`).
- Новая редакция содержания — новое байтовое тождество (новый SHA-256).
- Байтовый дубль под другим именем — новое record-тождество и новая линия с новым root.

**Что меняется без смены тождества:**

- `location` меняется при перемещении байтов — байтовое и линейное тождество сохраняются; меняется только record-тождество (новая строка).
- `about` или `measured` меняются при уточнении описания — байтовое и линейное тождество сохраняются; меняется только record-тождество.
- Физический склад меняется — `canonicalRef` и SHA-256 не меняются.

## Список посылок

- M1 определила классы материалов, но не назначила единицы простым и составным форматам — **норма** (закрытая пропозиция M1)
- Принятое содержание не мутирует на месте; отношение последующего поступления к прежнему M1 оставила полностью неклассифицированным — **норма** (закрытая пропозиция M1)
- `docs/evidence` — контейнерная запись управления, семантически нетеряемая и независимая от движка; автоматическая восстановимость не предполагается — **норма** (закрытая пропозиция M1)
- Производные только классифицированы; их хранение остаётся M6 — **норма** (закрытая пропозиция M1)
- `registry.jsonl` append-only: одна JSON-запись на строку, правка старых строк запрещена — **факт** (измеренная схема)
- Полная живая форма `EvidenceRecord`: обязательные `id`, `sha256`, `bytes`, `addedAt`, `source`, `location {kind, ref}`; опциональные `about` и `measured` — **факт** (измеренная схема)
- Валидатор требует положительный целый `bytes` и дату `addedAt` формата `YYYY-MM-DD…` — **факт** (поведение валидатора)
- Валидатор допускает для `location.kind` только `local`, `affine`, `url`, `archivarius` и при любом kind требует непустой `location.ref` — **факт** (поведение валидатора)
- `sensitive` не является `location.kind`; чувствительность определяется отдельным `sensitive.reason` — **факт** (поведение валидатора)
- Без хеша и адреса запись не является вещдоком; хеш даёт тождество, адрес — достижимость, описание — смысл — **норма** (несущий предикат README)
- Склад объявлен сменной деталью, индекс — сутью — **норма** (несущий предикат README)
- Существующие поправки используют `<id>-rN`; старая строка остаётся историей, последняя в цепочке считается живой; один и тот же SHA-256 уже встречается у исходной записи и поправки адреса — **факт** (измеренная схема)
- В живом реестре четыре legacy-записи с суффиксом `-rN` и без поля `supersedes`: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`; это четыре записи в трёх логических линиях; пара bpla `r2`, `r3` принадлежит одной линии — **факт** (измеренная схема)
- Дубль одинакового содержимого под разными `id` является находкой для человека, а не автоматически слитым объектом — **факт** (измеренная схема)
- Для чувствительного материала байты могут оставаться вне репозитория; SHA-256, провенанс и причина чувствительности сохраняются в записи — **факт** (измеренная схема)
- `sha256`, неизменяемый record `id` и root линии — три разных тождества; любое изменение поля создаёт новую запись с новым `id` и `supersedes`; старая строка не мутирует — **норма** (консолидированное ограничение M2)
- Effective predecessor: явный `supersedes`, а для четырёх named legacy без него — вычисленный predecessor по серии; для прочих без `supersedes` predecessor отсутствует — **норма** (консолидированное ограничение M2)
- `canonicalRef = "urn:mmbrn:static:" + rootId`; альтернативы и абстрактный `det(root)` запрещены — **норма** (консолидированное ограничение M2)
- `source` — провенанс байтов, не автор операции; при адресной поправке повторяется — **норма** (консолидированное ограничение M2)
- Реестр — единственный источник истины; байты верифицируют заявленный SHA-256, не восстанавливаются из JSONL — **норма** (консолидированное ограничение M2)
- Sensitive сохраняет допустимый kind, непустой ref в записи и отдельный reason; M3 решает видимость ref, M4 — склад байтов — **норма** (консолидированное ограничение M2)
- Live tip определяется отсутствием `id` среди всех effective predecessor, включая вычисленные legacy-связи — **норма** (консолидированное ограничение M2)
- Legacy-root трёх измеренных линий определён точно существующими base-записями без условности — **норма** (консолидированное ограничение M2)
- `sha256` служит контрактным байтовым тождеством при принятом предположении коллизионной устойчивости; математическая уникальность не утверждается — **норма** (консолидированное ограничение M2)
