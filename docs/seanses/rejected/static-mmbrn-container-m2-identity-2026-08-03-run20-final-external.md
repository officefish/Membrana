[Архитектор]: Начну с конструкции. У нас три уровня тождества, и путать их — значит сломать систему с первого же дня. Первый — байтовое тождество: `sha256` при принятом предположении о коллизионной устойчивости SHA-256 говорит, что байты те же. Второй — record identity: неизменяемый `id` строки в `registry.jsonl`, никогда не мутирует. Третий — lineage identity: `canonicalRef`, вычисляемый из root линии. Три разных значения, три разные роли.

[Верстальщик]: Для меня важно понять единицу регистрации с точки зрения того, что именно попадает в реестр. PDF — это один объект целиком, один `sha256` на весь файл, одна запись. Архив тоже регистрируется целиком — один `sha256` на весь архив. Компонент архива — отдельный разговор: он может получить свою запись при независимом поступлении или при фактическом предоставлении M6. M2 не навязывает извлечение. Это правильно понято?

[Структурщик]: Правильно. Добавлю точность по терминам. Единица регистрации — конкретные байты, принятые как единое целое. У PDF — весь PDF. У архива — весь архив. Поле `bytes` фиксирует размер именно этих байтов: положительное целое, верифицируемое при доступе. Изменение любого поля записи, включая `bytes`, требует новой записи с новым `id` и полем `supersedes`. Поле `bytes` не просто метаданные — оно часть record identity.

[Teamlead]: Стоп. Прежде чем идти дальше, зафиксируем: `bytes` входит в обязательные поля `EvidenceRecord` — это факт схемы. Изменение `bytes` влечёт новый record `id` — это норма M2, принятая с сегодня. Не путаем. Ожегов, ты сказал «изменение любого поля» — уточни насчёт `about` и `measured`, они опциональные.

[Музыкант]: Подхвачу: `about` и `measured` — опциональные поля, но изменение любого из них тоже создаёт новый `id`. Они не меняют байтовое тождество — `sha256` остаётся тем же — и не меняют lineage-тождество — root и `canonicalRef` сохраняются. Но record identity всегда меняется при любой правке. Ни одно поле не является «бесплатным» для record.

[Математик]: Формализую `ep`. Определяем функцию `ep: R → Id(R) ∪ {⊥}`. Она возвращает `id` predecessor либо `⊥` — не объект записи, только идентификатор. Root линии — запись `r`, для которой `ep(r) = ⊥`. Tip линии — `id`, отсутствующий среди всех значений `ep(r)` по всем `r ∈ R`, включая вычисленные legacy-связи. В линии длины 1 эти роли исполняет одна запись. В линии длины больше 1 — разные записи.

[Архитектор]: Теперь canonicalRef. Формула однозначна: `canonicalRef = "urn:mmbrn:static:" + rootId`, где `rootId = id(r0)`, `r0` — запись с `ep = ⊥`. Фиксированный префикс и уникальный rootId делают отображение инъективным: разные линии дают разные canonicalRef. Формула не меняется при поправках адреса, смене склада или редакциях — всё это продолжает ту же линию, rootId не меняется.

[Верстальщик]: Хочу уточнить адресную поправку, потому что это частый кейс. Документ лежит по одному адресу, потом его переложили. Байты не изменились — `sha256` тот же. Но `location.ref` изменился. Создаём новую запись с новым `id`, новым `location`, полем `supersedes` на старый `id`. `source` повторяется — провенанс байтов не изменился. Root, canonicalRef, `sha256` — все сохранились. Это верно?

[Структурщик]: Верно. И здесь важен факт из измеренного дома: один и тот же `sha256` уже встречается у исходной записи и поправки адреса — это подтверждает, что адресная поправка не меняет байтовое тождество. По полям: `location.kind` принимает только четыре значения — `local`, `affine`, `url`, `archivarius`. При любом kind `location.ref` обязан быть непустым. Это факт валидатора.

[Teamlead]: Перейдём к legacy. Факт: в реестре четыре записи с суффиксом `-rN` без поля `supersedes`. Их имена: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`. Три логические линии. Bpla-пара — одна линия. Норма M2: для этих четырёх применяем fallback — effective predecessor равен существующей base-записи или максимальной меньшей ревизии. Это норма, не измеренный факт.

[Музыкант]: По bpla-линии: она трёхзвенная — `base + r2 + r3`. `ep(bpla-guidance-methodology-partner-r2)` по fallback равен `id` base-записи. `ep(bpla-guidance-methodology-partner-r3)` по fallback равен `id` `bpla-guidance-methodology-partner-r2`. Root линии — base-запись. Tip — `bpla-guidance-methodology-partner-r3`, потому что его `id` не встречается ни в одном значении effective predecessor. Это строго по определению.

[Математик]: По ozon и day-memo: каждая — двухзвенная линия `base + r2`. Root — base-запись. Tip — `r2`, поскольку `id(r2)` не появляется ни в одном значении `ep` по всему реестру, включая вычисленные legacy-связи. Важно: мы не выводим число линий из количества физических записей без `supersedes`. Три линии установлены фактом измерения, не арифметикой.

[Архитектор]: Теперь sensitive. Запись для чувствительного материала полностью валидна: `location.kind` — один из допустимых четырёх, `location.ref` — непустой, в записи сохраняется. `sensitive` — не kind, а отдельное поле с подполем `reason`. `sha256` и провенанс (`source`) сохраняются в записи. Байты могут находиться вне репозитория — это факт существующей практики. Видимость `ref` — M3. Физический склад байтов — M4.

[Верстальщик]: Мне важно понять дубль с точки зрения record. Два файла с одинаковым содержимым, разные `id`. `sha256` у них одинаков — это байтовое тождество совпадает. Но это две разные записи, две разные строки в реестре, две разные линии. Они не сливаются автоматически. Дубль сейчас — находка для человека. Record-ячейка дубля содержит новый уникальный `id` и отдельную строку реестра.

[Структурщик]: По реестру как источнику истины: `registry.jsonl` — единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории. Байты — независимый предмет и доказательство. При доступе они верифицируют заявленные `sha256` и `bytes`. Они не восстанавливаются из JSONL автоматически. `location` — заявление реестра; достижимость — внешнее состояние склада, не инвариант реестра.

[Teamlead]: Зафиксируем форму линии. Линия — конечная связная последовательность `r0..rk`. У `r0` predecessor отсутствует: `ep(r0) = ⊥`. Для каждого следующего: `ep(r_{i+1}) = id(r_i)`. Циклы, fork, merge запрещены. Порядок определяется цепочкой `ep`, не полем `addedAt`. Root = `id(r0)`. Tip = `id(rk)`. Множества roots и tips равночисленны, но определения разные.

[Музыкант]: Про новую редакцию: у неё обязан отличаться `sha256` — байты изменились. Поле `bytes` измеряется и фиксируется заново, но численно может совпасть с прежним размером, если объём не изменился. Говорить «bytes изменился» без факта изменения размера — нельзя. Новая редакция всегда продолжает ту же линию: root и canonicalRef сохраняются, новая запись становится tip. Новая линия не возникает.

[Математик]: Уточню про `sha256` и коллизии. `sha256` служит контрактным байтовым тождеством при принятом предположении о коллизионной устойчивости SHA-256. Математическая уникальность и доказательство равенства байтов одним хешем не утверждаются — это предположение, принятое контрактно. Система работает в рамках этого предположения; если предположение нарушено — это выходит за пределы контракта M2.

[Архитектор]: Перейдём к полной таблице полей. Вопрос по `source`: при адресной поправке `source` повторяется из прежней записи — провенанс байтов не менялся. При новой редакции `source` фиксируется заново — может совпасть или различаться. `source` — не автор операции добавления, а происхождение байтов. Это важно для случая переноса: новый `location`, тот же `source`, тот же `sha256`.

[Верстальщик]: По случаю переноса отдельно: материал тот же, байты не изменились, `sha256` тот же. Новый `location` — склад сменился. Запись-поправка: новый `id`, `supersedes` на прежний `id`, `location` обновлён, `source` повторён. Root, canonicalRef, `sha256` не меняются. Это структурно идентично адресной поправке PDF — разница только в мотивации операции, не в механике.

[Структурщик]: Уточнение по случаю «архив/член». M2 регистрирует архив целиком. Компонент архива может получить собственную запись при двух условиях: независимое поступление или фактическое предоставление M6. Обе двери открыты. M6 не «решает» тождество компонента — M2 задаёт контракт: если компонент получает запись, у него свой `id`, свой `sha256`, своя линия, независимая от линии архива.

[Teamlead]: Хочу проверить живой tip для четырёх legacy. Для `ozon-receipt-3765-field-kit-r2`: tip — этот `id`, если он не встречается ни в одном effective predecessor. Для `day-memo-2026-07-28-r2` — аналогично. Для bpla-линии: tip — `bpla-guidance-methodology-partner-r3`, потому что `bpla-guidance-methodology-partner-r2` встречается как effective predecessor этого `r3`. Правильно?

[Музыкант]: Правильно. И дополню: root трёх линий определён точно, без условности. Ozon — root это base-запись `ozon-receipt-3765-field-kit`. Day-memo — root это `day-memo-2026-07-28`. Bpla — root это `bpla-guidance-methodology-partner`. Эти base-записи существуют в реестре; говорить «предположительно» или «если существует» запрещено — это измеренный факт структуры реестра.

[Математик]: Проверю инъективность canonicalRef. Пусть две разные линии имеют `rootId1 ≠ rootId2`. Тогда `"urn:mmbrn:static:" + rootId1 ≠ "urn:mmbrn:static:" + rootId2` — строгая инъекция за счёт уникальности rootId. Уникальность record `id` — принятый инвариант M2. Из него следует уникальность rootId, из него — уникальность canonicalRef. Не измеренный факт схемы, а инвариант.

[Архитектор]: Соберём пропозицию целиком для вердикта. Три тождества: байтовое (`sha256`), record (`id`), lineage (`canonicalRef = "urn:mmbrn:static:" + rootId`). Реестр — единственный источник истины о регистрации и истории. Байты — независимое доказательство, верифицирующее заявленные поля при доступе. Root — запись с `ep = ⊥`, tip — `id`, не являющийся значением ни одного effective predecessor. В линии длины 1 одна запись совмещает обе роли; в линии длины больше 1 — разные записи.

[Верстальщик]: По таблице случаев — хочу проговорить case «простой PDF» детально, потому что он базовый. Байты: `sha256` вычислен по всему файлу; он отличен от record `id` и от rootId — все три значения не совпадают. Запись: новый уникальный `id`, обязательные поля заполнены, `supersedes` отсутствует — это начальная запись линии. Lineage: root равен record id этой записи, canonicalRef = `"urn:mmbrn:static:" + id`. В record-ячейке слово «root» не употребляем.

[Структурщик]: По case «дубль»: байты идентичны первому — `sha256` совпадает с уже зарегистрированным. Запись: новый уникальный `id`, отдельная строка реестра — не ссылка на первый. Lineage: отдельная линия, отдельный root, отдельный canonicalRef. Дубль не сливается автоматически — человек видит совпадение `sha256` и принимает решение. M2 не проектирует слияние.

[Teamlead]: Case «редакция»: байты новые, `sha256` обязан отличаться от предыдущей записи линии. `bytes` измеряется заново — численно может совпасть. Запись: новый `id`, `supersedes` указывает на tip предыдущей линии. Lineage: та же линия продолжается, root не меняется, canonicalRef не меняется, новая запись становится tip. Никакой новой линии. Именно этот инвариант отличает редакцию от нового поступления.

[Музыкант]: Case «архив/член»: байты компонента — отдельный объект с отдельным `sha256`, если компонент получает запись. Запись: новый `id`, `location` компонента, независимые поля. Lineage: отдельная линия компонента, не связанная с линией архива. Обе двери открыты: независимое поступление или фактическое предоставление M6. M6 не решает тождество — он лишь открывает вторую дверь.

[Математик]: Case «перенос»: байты не изменились, `sha256` тот же. Запись: новый `id`, новый `location` (kind и ref обновлены), `supersedes` на прежний `id`, `source` повторён. Lineage: та же линия продолжается, root и canonicalRef не меняются. Доказательство: предикат README — хеш даёт тождество, адрес — достижимость; смена адреса не меняет тождество, поэтому новая запись сохраняет rootId.

[Архитектор]: Case «sensitive»: байты могут находиться вне репозитория — факт практики. `sha256` и `source` сохраняются в записи. `location.kind` — один из допустимых четырёх, `location.ref` — непустой и хранится в записи. `sensitive.reason` — отдельное поле. Lineage: нормальная линия, root и canonicalRef вычисляются стандартно. Видимость `ref` — M3; физический склад байтов — M4; обе нормы выходят за пределы M2.

[Верстальщик]: Хочу зафиксировать итог по `location`. Для sensitive: запись в реестре содержит непустой `ref` — это факт (валидатор требует непустой ref при любом kind). Скрытие ref от конкретных пользователей или ролей — это M3, не M2. Хранение байтов вне репо — факт. Выбор физического хранилища — M4. M2 только требует, что ref существует и непустой в записи.

[Структурщик]: Подытожу по области истины реестра. `registry.jsonl` append-only: новые строки добавляются, старые не мутируют. Живая запись линии — последняя в цепочке `supersedes`. Исторические записи сохраняются как история. Живой tip определяется отсутствием `id` среди всех effective predecessor — включая вычисленные legacy-связи. Это важно: не только среди физических полей `supersedes`.

[Teamlead]: Мне нужна проверка по таблице полей. `id` — обязательный, уникальный, неизменяемый. `sha256` — обязательный, байтовое тождество. `bytes` — обязательный, положительное целое, размер конкретных байтов, верифицируется при доступе; изменение требует новой записи. `addedAt` — обязательный, формат `YYYY-MM-DD…`. `source` — обязательный, провенанс байтов. `location` — обязательный объект с `kind` и `ref`. `about`, `measured` — опциональные; изменение любого создаёт новый `id`.

[Музыкант]: Добавлю derived-строки, которые не поля `EvidenceRecord`, но входят в контракт. `root`: record без effective predecessor (`ep = ⊥`); rootId = `id` этой записи. `canonicalRef`: вычисляемое значение `"urn:mmbrn:static:" + rootId`; фиксируется при создании линии, сохраняется при всех поправках. Эти derived-значения не хранятся в строке JSONL как поля — они вычисляются из структуры линии.

[Математик]: Финальная проверка формулы tip. Пусть `EP = { ep(r) | r ∈ R, ep(r) ≠ ⊥ }` — множество всех значений effective predecessor по всем записям реестра. Tip линии — запись `r`, чей `id` не входит в `EP`. Root линии — запись `r`, для которой `ep(r) = ⊥`. В линии длины 1: `id(r0) ∉ EP` и `ep(r0) = ⊥` — одна запись удовлетворяет обоим. В линии длины больше 1: `id(r0) ∈ EP` (на него ссылается `r1`), `ep(r0) = ⊥` — разные записи.

## Итоговое решение консилиума

### Пропозиция I1

Каждый зарегистрированный материал `static.mmbrn.tech` несёт три различных тождества:

1. **Байтовое тождество** — `sha256`, вычисленный по конкретным байтам при принятом предположении о коллизионной устойчивости SHA-256. Математическая уникальность не утверждается; это контрактное тождество.

2. **Record identity** — неизменяемый `id` строки `EvidenceRecord` в `registry.jsonl`. Любое изменение любого поля создаёт новую строку с новым `id` и `supersedes`; старая строка не мутирует.

3. **Lineage identity** — `canonicalRef = "urn:mmbrn:static:" + rootId`, где `rootId = id(r0)`, `r0` — запись с `ep(r0) = ⊥`. Формула инъективна: фиксированный префикс и уникальный rootId дают уникальный canonicalRef для каждой линии. Пропозиция различает три **тождества**, не объявляет три значения попарно различными: в одноэлементной линии rootId и record `id` совпадают; `sha256` остаётся отдельным значением при любой конфигурации линии.

**Функция effective predecessor:** `ep: R → Id(R) ∪ {⊥}`. Возвращает `id` predecessor либо `⊥`, не объект записи. Для новых записей: `ep(r) = supersedes` если поле присутствует; `ep(r) = ⊥` если поле отсутствует и запись не входит в четыре named legacy. Для четырёх named legacy без `supersedes`: `ep` вычисляется по fallback-норме M2 — существующая максимальная меньшая ревизия либо base root.

**Линия:** конечная связная последовательность `r0..rk`, где `ep(r0) = ⊥` и `ep(r_{i+1}) = id(r_i)`. Циклы, fork и merge запрещены. Порядок определяется цепочкой `ep`, не `addedAt`.

**Root и tip:** Root — запись `r`, для которой `ep(r) = ⊥`. Tip — `id`, отсутствующий в множестве `EP = { ep(r) | r ∈ R, ep(r) ≠ ⊥ }`, включая вычисленные legacy-связи. Это разные роли и разные критерии: в линии длины 1 их исполняет одна запись; в линии длины больше 1 — разные записи. Множества roots и tips равночисленны, но их определения нельзя отождествлять.

**Реестр как источник истины:** `registry.jsonl` — единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории. Байты — независимый предмет и доказательство; при доступе верифицируют заявленные `sha256` и `bytes`, не восстанавливаются из JSONL автоматически и не заменяют реестр. `location` — заявление реестра; достижимость — внешнее состояние склада.
