[Структурщик]: Начнём с единицы регистрации. M1 определила классы, но оставила открытым вопрос об единице для простых и составных форматов — это наша прямая юрисдикция. Предлагаю зафиксировать: регистрируемая единица — это конкретные байты, поступившие как единое целое при данном поступлении. Простой файл, PDF-документ и архив регистрируются целиком своим `sha256`. Компонент архива или встроенный объект PDF получает запись только при независимом поступлении либо предоставлении M6 — обе двери остаются открытыми, ни одну не закрываем.

[Верстальщик]: С точки зрения структуры отображения важно понимать: record `id` — это неизменяемый идентификатор конкретной записи в реестре, а не идентификатор материала как такового. Если у нас адресная поправка — старый `id` остаётся историей, новый `id` появляется как новая строка. Это должно быть отражено в любом UI: живая запись — последняя в цепочке, но история не стирается. Для отображения нам нужен стабильный `canonicalRef`, не зависящий от смены `id` при поправках.

[Архитектор]: Форма решения здесь такова: три уровня тождества — байтовое (`sha256`), record (`id`) и lineage (`root`) — образуют ортогональные предметы. Численно у первичной записи одноэлементной линии `root` равен `id` этой записи, но это совпадение значений, а не совпадение понятий: байты, запись и линия остаются разными уровнями. Функция `ep: R → Id(R) ∪ {⊥}` возвращает `id` предшественника либо `⊥`, не объект записи. Root — запись, где `ep = ⊥`; tip — `id`, отсутствующий среди всех значений `ep` по всем записям, включая вычисленные legacy-связи.

[Teamlead]: Фиксирую позицию команды по приоритетам. Реестр — единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории. Байты — независимый предмет: при доступе они верифицируют заявленные `sha256` и `bytes`, но не восстанавливаются из JSONL автоматически и не заменяют реестр. `location` — заявление реестра; достижимость — внешнее состояние склада. Это граница M2: что дальше с доступом — M3, что со складом — M4. Продолжаем.

[Музыкант]: Меня интересует случай архива с несколькими членами. Если я получаю ZIP с тремя треками — регистрируется архив целиком, один `sha256` на весь ZIP. Если потом один трек поступает отдельно — это независимое поступление, и он получает свою запись. Это логично: каждое поступление — это событие, у события есть своя запись. Вопрос об извлечении членов — не наш, это M6. Обе двери: независимое поступление или предоставление M6.

[Математик]: Уточню формальную сторону. `sha256` служит контрактным байтовым тождеством при принятом предположении о коллизионной устойчивости SHA-256 — математическая уникальность этим не утверждается, равенство байтов одним хешем не доказывается. `bytes` — обязательное положительное целое, измеренный размер конкретных байтов; при новой редакции `bytes` измеряется и фиксируется заново, но численно может совпасть с прежним размером. Фразы «bytes изменился» или «новый bytes» без факта изменения размера запрещены.

[Структурщик]: Теперь о legacy-записях. В живом реестре четыре записи с суффиксом `-rN` и без поля `supersedes`: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`. Это три логические линии. Линия ozon: root — `ozon-receipt-3765-field-kit`, tip — `ozon-receipt-3765-field-kit-r2`. Линия day-memo: root — `day-memo-2026-07-28`, tip — `day-memo-2026-07-28-r2`. Линия bpla: root — `bpla-guidance-methodology-partner`, tip — `bpla-guidance-methodology-partner-r3`; `r2` — промежуточная запись. Никакой условности: base-записи существуют, root определён точно.

[Верстальщик]: Важно для отображения: effective predecessor для legacy-записей без `supersedes` — существующая максимальная меньшая ревизия либо base root. Для `bpla-r3` predecessor — `bpla-r2`; для `bpla-r2` predecessor — `bpla-guidance-methodology-partner`. Для прочих записей без `supersedes` predecessor отсутствует — они не legacy-rN. Точный `r(N-1)` применим только к четырём named legacy; вывод числа линий из количества физических записей без `supersedes` запрещён.

[Архитектор]: `canonicalRef = "urn:mmbrn:static:" + rootId`. Фиксированный префикс и уникальный rootId делают формулу инъективной. При адресной поправке root не меняется, значит `canonicalRef` не меняется — это стабильная внешняя ссылка на линию. При новой редакции root также сохраняется, `canonicalRef` сохраняется. Альтернативные формулы и абстрактный `det(root)` запрещены. Это не публичный URL — доступность и авторизация принадлежат M3.

[Teamlead]: Проверяю по брифу: M2 задаёт тождество и канонический адрес, не workflow получения байтов. `source` — провенанс байтов, не автор операции. При адресной поправке `source` повторяется из прежней записи. У новой редакции `source` фиксируется заново и может совпасть либо различаться — зависит от фактического происхождения новых байтов. Чистота посылок: нормы M1 и предикат README маркируются как норма; измеренная схема и поведение валидатора — как факт. Нельзя выдавать нормы за факты.

[Музыкант]: Sensitive-поведение: материал чувствителен, байты могут оставаться вне репозитория. Но запись в реестре обязана сохранять `sha256`, `source`, `sensitive.reason` и `location` с допустимым kind и непустым `ref`. `sensitive` — не `location.kind`: валидатор допускает только `local`, `affine`, `url`, `archivarius`. Чувствительность определяется отдельным `sensitive.reason`. Видимость `location.ref` — M3; физический склад байтов — M4. Это не наше.

[Математик]: Уточню определения root и tip через `ep`. Пусть `R` — множество всех записей реестра, `ep: R → Id(R) ∪ {⊥}`. Root линии — запись `r ∈ R`, для которой `ep(r) = ⊥`. Tip — `id(r)`, такой что `id(r) ∉ {ep(s) | s ∈ R, ep(s) ≠ ⊥}`, то есть `id(r)` не встречается среди всех значений effective predecessor. Для legacy включаем вычисленные связи в это множество. В линии длины 1 root и tip совпадают как одна запись — но это разные критерии, выполненные одной записью, не отождествление понятий.

[Структурщик]: Поле `about` и `measured` — опциональные. Изменение любого поля записи создаёт новый `id` — это инвариант: record identity всегда меняется при любом изменении поля. `about` и `measured` не меняют байтовое тождество (`sha256` остаётся) и lineage-тождество (root/canonicalRef остаются), но record identity меняется. Таблица полей не может называть их «не влияющими на тождество вообще» — они влияют на record identity.

[Верстальщик]: По таблице случаев: нам нужно три уровня для каждого случая — Байты, Запись, Линия — с ответами «то же / иное / изменилось» и доказательством. Ячейки не должны содержать сырой `|`. В record-ячейке простого PDF запрещено слово `root` и любое равенство root с `id`. Равенство root и record `id` появляется ровно один раз во всём carrier — в lineage-ячейке случая simple-PDF. Больше нигде: ни в репликах, ни в доказательстве, ни в вердиктной прозе, ни в DoD.

[Архитектор]: Случай переноса склада — важный для архитектуры. Байты физически перемещаются на новый склад. `sha256` тех же байтов не меняется. Создаётся новая запись с новым `id`, новым `location.ref` (указывающим на новое место), `supersedes` на прежнюю запись. Root и `canonicalRef` сохраняются — линия продолжается. `location` — это заявление реестра; достижимость — внешнее состояние склада. После переноса старая запись остаётся историей, новая — живой записью.

[Teamlead]: Дублирующий случай. Два разных `id` с одинаковым `sha256` — это находка для человека, не автоматически слитый объект. M2 не проектирует слияние дублей. Каждая запись живёт в своей линии. Байты физически одни и те же (при принятом предположении о коллизионной устойчивости), но записи и линии — разные. Слияние — не наше решение.

[Музыкант]: PDF со встроенными объектами. Регистрируется PDF целиком — один `sha256` на весь документ, одна запись. Встроенный объект (например, прикреплённый файл) получает запись только при независимом поступлении либо предоставлении M6. Обе двери открыты. M2 не требует извлечения — это M6. Важно: мы не утверждаем «нет записи до M6» и не говорим «только M6».

[Математик]: Теперь запишем инвариант для новой редакции. Новая редакция — это иной материал: `sha256` отличается (обязательно). `bytes` измеряется заново. Создаётся новая запись с новым `id` и `supersedes` на прежнюю. Root сохраняется, `canonicalRef` сохраняется, новая запись становится tip. Утверждать новую линию, новый root или новый canonicalRef в любой части carrier запрещено. Это — продолжение той же линии, не начало новой.

[Структурщик]: Подведу итог по структуре полей для таблицы. `id` — неизменяемый идентификатор конкретной записи; создаётся один раз, не мутирует. `sha256` — контрактное байтовое тождество; отличается при новой редакции. `bytes` — обязательное положительное целое, размер конкретных байтов; измеряется заново при новой редакции, численно может совпасть. `addedAt` — дата формата `YYYY-MM-DD…`; фиксируется при создании записи. `source` — провенанс байтов; повторяется при адресной поправке, фиксируется заново при новой редакции.

[Верстальщик]: Продолжу по полям. `location.kind` — один из допустимых: `local`, `affine`, `url`, `archivarius`; меняется при адресной поправке с новым `id`. `location.ref` — непустая строка; обязательна при любом kind; хранится в реестре даже для sensitive. `root` — `id` первой записи линии; не изменяется никогда в жизни линии. `canonicalRef` — `"urn:mmbrn:static:" + rootId`; стабилен на протяжении всей линии. `supersedes` — `id` предыдущей записи; обязателен для всех записей кроме первой в линии (и legacy-rN без него — обрабатываются правилом вычисленного predecessor).

[Архитектор]: Завершаю картину полей. `about` — опциональное описание; изменение создаёт новый `id`. `measured` — опциональные данные измерений; изменение создаёт новый `id`. `sensitive.reason` — опциональный; обязателен при sensitive-материале; хранится в реестре. Инвариант: любое изменение любого поля — новый `id`, новая запись, старая строка не мутирует. Реестр append-only: правка старых строк запрещена.

[Teamlead]: Сводная позиция по области истины реестра. `registry.jsonl` — единственный источник истины о: (1) факте регистрации материала, (2) record и lineage identity, (3) заявленных полях и их значениях, (4) истории записей. Реестр не является источником истины о байтах как таковых — байты независимы. Реестр не является источником достижимости — это внешнее состояние склада. Это граница: index — суть, склад — сменная деталь.

[Музыкант]: Проверю себя по sensitive: запись в реестре существует всегда, даже если байты вне репозитория. `location.kind` — допустимый (`local` или другой), `location.ref` — непустой (указывает на физическое место, пусть и вне репо). `sha256` и `source` присутствуют. `sensitive.reason` присутствует. Видимость `ref` в публичных выдачах — M3. Физическое хранение байтов — M4. M2 только фиксирует: ref обязательно хранится в записи реестра.

[Математик]: Формализую ep-функцию окончательно для вердикта. `ep: R → Id(R) ∪ {⊥}`, где для записи `r`: если у `r` есть явный `supersedes` → `ep(r) = supersedes(r)`; если `r` — одна из четырёх named legacy без `supersedes` → `ep(r)` = id существующей максимальной меньшей ревизии либо id base-root; иначе → `ep(r) = ⊥`. Root линии: `{id(r) | ep(r) = ⊥}`. Live tip: `{id(r) | id(r) ∉ {ep(s) | s ∈ R, ep(s) ≠ ⊥}}`. Множества roots и tips равночисленны, критерии различны.

[Структурщик]: Финальная проверка инварианта по lineage для новой редакции. Поступает материал с новым `sha256`. Создаётся запись `rk` с новым `id`, `supersedes = id(r_{k-1})`, тем же `root = id(r0)`, тем же `canonicalRef`. `ep(rk) = id(r_{k-1})`. `id(rk)` не входит ни в какое `ep(s)` — значит `rk` — новый tip. `r0` по-прежнему root: `ep(r0) = ⊥`. Линия продолжена, не разорвана, не раздвоена.

[Верстальщик]: Убеждаюсь, что DoD будет чистым. В таблице случаев record-ячейка simple-PDF: только record-факты — новый `id`, `sha256`, `bytes`, `addedAt`, `source`, `location`. Слово «root» и равенство root с `id` в этой ячейке отсутствуют. В lineage-ячейке simple-PDF: здесь и только здесь — `root = id(r0)` (это первая запись линии, где `ep = ⊥`), `canonicalRef = "urn:mmbrn:static:" + id(r0)`. Это единственное место во всём carrier, где это равенство зафиксировано.

[Архитектор]: Случай дубля в таблице: два `id` с одинаковым `sha256`. Байтовый уровень: то же (при предположении о коллизионной устойчивости — те же байты). Record-уровень: иное — два разных `id`, две разных записи. Lineage-уровень: иное — две независимые линии с разными root и canonicalRef. Доказательство: слияние не происходит автоматически; каждый `id` — начало своей линии; M2 не проектирует merge. Это находка для человека.

[Teamlead]: Итоговая проверка. Все шесть случаев покрыты: PDF, дубль, новая редакция, архив/член, перенос склада, sensitive. Три уровня для каждого. Таблица полей с отдельной строкой `bytes`. Линейная семантика для четырёх legacy-записей — без условности, roots определены точно. `canonicalRef` стабилен. sensitive хранит ref в реестре. Область истины реестра зафиксирована. Запреты M3-M7 не нарушены. Принимаю к оформлению вердикта.

[Музыкант]: Одно дополнение по архиву/члену для таблицы. Случай «архив/член»: при регистрации архива целиком — байты архива те же, запись архива новая (новый `id`), линия архива новая. Член до независимого поступления или M6 не имеет записи — это не запрет, это просто отсутствие события поступления. При независимом поступлении члена — создаётся отдельная запись с новым `id`, новой линией, своим `sha256`. Байты члена и байты архива — разные предметы.

[Математик]: Последнее уточнение по `bytes` для таблицы полей. `bytes` — обязательное положительное целое (**факт**: валидатор требует). Это размер конкретных байтов данного поступления. При адресной поправке `bytes` не меняется (те же байты). При новой редакции `bytes` измеряется заново и фиксируется — численно может совпасть с прежним. ## Итоговое решение консилиума

### Вердикт I1 (пропозиция)

Каждый материал `static.mmbrn.tech` получает единый контракт тождества: регистрируемая единица — конкретные байты единого поступления; тождество существует на трёх ортогональных уровнях — байтовом (`sha256`), record (`id`) и lineage (`root`/`canonicalRef`); единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории — `registry.jsonl`; байты — независимый предмет верификации, не производная реестра; линия — конечная линейная цепочка записей, управляемая функцией `ep: R → Id(R) ∪ {⊥}`, где root — запись с `ep = ⊥`, tip — `id`, отсутствующий среди всех значений `ep`.

### Линейная семантика четырёх legacy-записей

Функция `ep: R → Id(R) ∪ {⊥}`:
- Если у записи `r` есть явный `supersedes` → `ep(r) = supersedes(r)`
- Если `r` — одна из четырёх named legacy без `supersedes` → `ep(r)` = id существующей максимальной меньшей ревизии или id base-root
- Иначе → `ep(r) = ⊥`

Root линии — `id(r)`, где `ep(r) = ⊥`. Tip — `id(r)`, где `id(r) ∉ {ep(s) | s ∈ R, ep(s) ≠ ⊥}`. Множества roots и tips равночисленны; критерии различны; в линии длины 1 оба критерия выполняет одна запись.
