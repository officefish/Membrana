## Итоговое решение консилиума

### Вердикт I1 — пропозиция-контракт

Каждый материал контейнера `static.mmbrn.tech` при поступлении получает **начальную запись** в `docs/evidence/registry.jsonl`. Каждое последующее изменение любого поля этой линии порождает **новую append-only запись** с новым уникальным `id` и явным `supersedes` на предшествующую запись; старая строка не мутирует никогда. Байтовое тождество задаётся `sha256` конкретных байтов при принятом предположении коллизионной устойчивости SHA-256 — математическая уникальность не утверждается. Логическая линия определяется через effective predecessor и идентифицируется стабильным `canonicalRef = "urn:mmbrn:static:" + rootId`, который не является публичным URL и не предрешает доступность. Реестр `registry.jsonl` — единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории; байты — независимый предмет, верифицирующий заявленный `sha256` и `bytes` при доступе, но не восстанавливаемый из JSONL автоматически. Архив и PDF регистрируются целиком; компонент получает отдельную запись только при независимом поступлении либо предоставлении M6. Чувствительный материал сохраняет полную запись с допустимым `location.kind`, непустым `location.ref` и отдельным `sensitive.reason`; видимость `ref` решает M3, физический склад байтов выбирает M4.

### Таблица полей и инвариантов EvidenceRecord

| Поле | Обязательность | Тип тождества | Инвариант |
|---|---|---|---|
| `id` | обязательное | record identity | уникален, неизменяем после добавления строки; новая запись всегда получает новый `id` |
| `sha256` | обязательное | byte identity | контрактное байтовое тождество при предположении коллизионной устойчивости; одинаков у оригинала и адресной поправки; различается у новой редакции |
| `bytes` | обязательное | byte fact | положительный целый; совпадает с реальным размером байтов; не меняется при адресной поправке |
| `addedAt` | обязательное | record timestamp | дата формата `YYYY-MM-DD…`; не используется для построения effective predecessor |
| `source` | обязательное | byte provenance | происхождение байтов, не автор операции; повторяется при адресной поправке; фиксируется заново при новой редакции |
| `location.kind` | обязательное | address type | одно из: `local`, `affine`, `url`, `archivarius`; `sensitive` не является kind |
| `location.ref` | обязательное | address fact | непустой при любом kind; хранится в записи безусловно; видимость — M3 |
| `about` | опциональное | description | изменение создаёт новую запись с `supersedes` |
| `measured` | опциональное | measurement | изменение создаёт новую запись с `supersedes` |
| `sensitive.reason` | опциональное | sensitivity flag | отдельный признак; не заменяет `location.kind`; хранится при честно недостижимых байтах |
| `supersedes` | обязательное для поправок | lineage link | явный effective predecessor для всех новых поправок; отсутствует у первичных записей и четырёх legacy-записей |

### Производные поля линии (не в record-колонке)

| Поле | Источник | Инвариант |
|---|---|---|
| root | `id` записи без predecessor | неизменяем для линии; равен `id` первой записи |
| canonicalRef | `"urn:mmbrn:static:" + rootId` | стабилен при смене склада и движка; не публичный URL |
| live tip | `id` записи, на которую не ссылается ни один `supersedes` | единственный в линии; меняется при каждой поправке |

### Разбор шести случаев

| Случай | Байты | Запись | Логическая линия | Что меняется без смены тождества | Доказательство |
|---|---|---|---|---|---|
| Простой PDF при поступлении | новый предмет; sha256 фиксирует байтовое тождество | новая начальная запись; `id` уникален; root = этот `id` | новая одноэлементная линия; canonicalRef = `urn:mmbrn:static:` + `id` | ничего: первая запись линии | sha256 верифицирует байты при доступе |
| Байтовый дубль под другим `id` | те же байты (sha256 совпадает); два независимых предмета регистрации | две отдельные записи с разными `id`; не сливаются автоматически | две независимые линии с разными root и canonicalRef | ничего: дубль — находка для человека, не автоматическое слияние | sha256 совпадает, но `id` различны; M2 не проектирует слияние |
| Новая редакция содержания | иные байты; новый sha256; байтовое тождество разрывается | новая запись с новым `id`, новым `sha256`, `supersedes` на прежнюю запись; source фиксируется заново | та же линия; root и canonicalRef не изменились; tip сменился на новую запись | байтовое тождество: sha256 иной; record identity: новый `id`; lineage identity: та же | root достигается следованием effective predecessor от нового tip |
| Архив и его член | архив — один байтовый предмет; член — отдельный предмет только при независимом поступлении или предоставлении M6 | архив получает одну запись; член получает отдельную запись только в двух условиях | архив и член (если зарегистрирован) — независимые линии | ничего: регистрация целиком не влечёт регистрации компонента | M2 не требует извлечения; M6 предоставляет член как материал |
| Перемещение байтов между складами | те же байты; sha256 не изменился | новая запись с новым `id`, новым `location`, `supersedes` на прежнюю запись; source повторяется | та же линия; root и canonicalRef не изменились; tip сменился | физический адрес байтов и заявление реестра об адресе — без смены байтового и lineage тождества | sha256 идентичен до и после; root не изменился |
| Чувствительный материал без публичного локатора | байты могут быть физически недостижимы; sha256 и bytes сохраняются в записи | полная запись: `id`, `sha256`, `bytes`, `addedAt`, `source`, `location` с допустимым kind и непустым ref, `sensitive.reason` | линия та же; canonicalRef стабилен | физическая достижимость байтов — внешнее состояние склада, не состояние реестра | реестр не скрывает факт существования; видимость ref — M3; склад — M4 |

### Semantic effective predecessor

| Случай | Правило |
|---|---|
| Запись с явным `supersedes` | effective predecessor = значение поля `supersedes` |
| `ozon-receipt-3765-field-kit-r2` (legacy, без `supersedes`) | effective predecessor = `ozon-receipt-3765-field-kit` (base root) |
| `day-memo-2026-07-28-r2` (legacy, без `supersedes`) | effective predecessor = `day-memo-2026-07-28` (base root) |
| `bpla-guidance-methodology-partner-r2` (legacy, без `supersedes`) | effective predecessor = `bpla-guidance-methodology-partner` (base root) |
| `bpla-guidance-methodology-partner-r3` (legacy, без `supersedes`) | effective predecessor = `bpla-guidance-methodology-partner-r2` (максимальная меньшая ревизия) |
| Прочие записи без `supersedes` | predecessor отсутствует; это root своей линии |

Все новые поправки обязаны иметь явный `supersedes`. Точный `r(N-1)` как универсальная формула запрещён. Вывод числа линий из количества записей без `supersedes` запрещён. Порядок по `addedAt` для построения линии запрещён. Fork, merge и циклы запрещены.
