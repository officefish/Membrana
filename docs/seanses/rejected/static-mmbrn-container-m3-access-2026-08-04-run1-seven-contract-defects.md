Грант на lineage не может превысить политику коллекции; грант на коллекцию не может превысить политику контейнера. Исключение ровно одно и зафиксировано в фактуре: индивидуальный грант на `sectionId` открывает доступ к нему, даже если `role < minRole`, но не открывает owner-only. Это не нарушение принципа — это явно заявленный allow-grant с потолком `operator`.

[Верстальщик]: Со стороны видимости хочу уточнить sensitive-срез. В фактуре M2: sensitive-запись имеет `location.ref` и `sensitive.reason`. M3 решает видимость `location.ref`. Для UI это означает: карточка материала может быть видна (факт записи, metadata, reason), но поле `location.ref` должно быть скрыто серверно — не через CSS, не через conditional render, а через отсутствие поля в ответе API для неавторизованного субъекта. Скрытие ref не защищает байты — это отдельный предикат. Оба должны быть явными в алгоритме.

[Музыкант]: Раз мы говорим о серверной границе — нужно назвать точку. Из фактуры: `office /v1/panel/gate/:sectionId` это проверочный endpoint, но не `forward_auth`. [Математик]: Формализую алгоритм effective access полностью. Вход: `(subjectId, objectRef, action)`. Шаги: 1) разрешить identity — если сессия невалидна, `role = public`; 2) найти объект в реестре — если не найден, `deny` (404 не открывает данные); 3) вычислить effective role: `max(baselineRole, grantedRole(subjectId, objectRef))`; 4) проверить потолок: если объект owner-only и effective role < owner — `deny`; 5) проверить `effectiveRole >= minRole(action, objectRef)`; 6) если авторизатор недоступен на шаге 3 или 5 — `deny`. Каждый из восьми случаев выводится из этих шести шагов без исключений.

[Teamlead]: Хорошо. Теперь полномочия — нужно развести семь, не смешивая с API. `discover` — видеть факт существования объекта в реестре. `read-metadata` — видеть поля записи, кроме `location.ref`. `read-bytes` — получить содержимое по `location.ref`. `download` — получить байты для локального сохранения. `write-metadata` — изменить поля записи в реестре. `upload-revision` — добавить новую ревизию байтов. `manage-access` — менять политику доступа и гранты. Это политика, не API. Таблицу назначим в carrier.

[Структурщик]: Про гранты — нужно закрыть «грант без объекта». Грант всегда имеет три составляющих: `(subjectId, objectRef, grantedPermissions[])`. `objectRef` — это либо `urn:mmbrn:static:<rootId>` для lineage-гранта, либо `sectionId` для коллекции-гранта. Грант не может существовать без явного объекта. Конфликт правил: если baseline role даёт `discover`, а грант даёт `read-metadata` на конкретный объект — применяем объединение, но с потолком owner-only. Если два гранта конфликтуют — более ограничивающий выигрывает (fail-closed).

[Архитектор]: Про Affine — минимальный контракт. Panel принимает решение. Affine получает короткоживущий токен делегации: `{subjectId, affineDocId, permittedRole, expiresAt}`. Affine-роль `reader/editor/manager` назначается как механизм исполнения на основе этого токена. Токен истекает — Affine-роль отзывается. Это единственный контракт: Panel → токен → Affine. Нативная роль Affine не переопределяет Panel-решение; она только исполняет его в рамках движка. Если токен истёк, а сессия жива — доступ к Affine-документу deny, даже если Affine-роль технически ещё в workspace.

[Верстальщик]: По sensitive-видимости детально. Уровни видимости для sensitive-записи: факт записи (`discover`) — виден от `ally` и выше, плюс explicit grant; metadata без `location.ref` (`read-metadata`) — виден от `ally` и выше; `sensitive.reason` — часть metadata, виден тем же субъектам; `location.kind` — часть metadata, виден тем же субъектам; `location.ref` — только от `operator` и выше или explicit grant `read-bytes`; байты — отдельный предикат `read-bytes`, не следует автоматически из видимости ref. Это значит: API не возвращает поле `location.ref` в ответе, если effective role < operator и нет явного гранта.

[Музыкант]: Случай 7 из обязательных — прямой URL Affine в обход Panel. Сейчас это работает, потому что `forward_auth` для Affine не настроен. Если Panel говорит deny — Affine-документ недоступен, даже если пользователь знает прямой URL workspace. Это не UX-вопрос и не M5 — это серверная граница, которую мы устанавливаем сейчас.

[Математик]: Случай 4 — отзыв гранта при живой сессии или делегации. Алгоритм: изменение гранта увеличивает `permVersion` в Panel (факт из фактуры). Максимальная семантика кеша решения: кеш действителен до конца текущего запроса (no-store) или максимум 60 секунд при явном TTL. После отзыва гранта — следующий запрос к gate вернёт 403. Старая короткоживущая делегация Affine истекает по `expiresAt`; максимальный TTL делегации — 5 минут. Это не «мягкий» отзыв: по истечении TTL доступ закрыт без перевыпуска.

[Teamlead]: Audit contract. Обязательные поля события `allow/deny`: `{eventId, ts, subjectId, objectRef, action, decision, effectiveRole, grantSnapshot, policyVersion, requestOrigin}`. Обязательные поля события изменения политики: `{eventId, ts, actor, targetSubject, targetObject, prevPolicy, nextPolicy, permVersionBefore, permVersionAfter}`. Хранилище — реализация; структура — норма M3. Fail-closed при недоступности авторизатора: deny + audit-запись с `decision: deny, reason: authorizer_unavailable`. Это не опциональное поведение — это условие принятия контракта.

[Структурщик]: Уточню наследование для контейнерного уровня. Контейнер `static.mmbrn.tech` как целое не имеет отдельной минимальной роли — он наследует строжайшую политику из своих коллекций. Это означает: нет «открыть весь контейнер одним грантом». Грант на контейнер технически допустим только как грант на все коллекции одновременно с потолком `operator`. owner-only разделы остаются закрытыми даже при контейнерном гранте. Достаточность: все практические случаи покрываются коллекцией и lineage без контейнерного уровня как отдельного объекта политики.

[Архитектор]: Закрываю вопрос о двух истинах окончательно. Panel — единственная истина: он хранит роли, гранты, permVersion, аудит. Affine — исполнитель, получающий токен. `registry.jsonl` — источник истины о lineage и canonicalRef, но не об авторизации. Смешивать нельзя: решение «кто имеет доступ» принимает только Panel. Решение «как отобразить документ» принимает Affine на основании токена. Если Panel и Affine дают противоречивые сигналы — Panel выигрывает: токен не выпускается или отзывается.

[Верстальщик]: По случаю 8 — sensitive metadata без права на ref. Алгоритм: шаг 5 Математика применяется дважды. Это два отдельных предиката на одном запросе, не один. API не должен возвращать `location.ref` в базовом ответе metadata — только при явном разрешении `read-bytes`. Байты — отдельный запрос с отдельной проверкой.

[Музыкант]: Случай 3 — пользователь ниже baseline с грантом на коллекцию. Шаг 3 алгоритма: `effectiveRole = max(baselineRole=public, grantedRole=ally)` → effective role = `ally`. [Математик]: Случай 5 — operator читает metadata без автоматического manage-access. Шаг 5: `operator >= minRole(read-metadata)` → allow. Таблица полномочий в carrier явно фиксирует: `manage-access` требует `owner` или explicit grant с потолком `owner`.

[Teamlead]: Случай 6 — owner меняет политику. Шаг 5: `owner >= minRole(manage-access)` → allow. Действие: обновление `minRole` объекта или гранта. Результат: `permVersion++`, audit-запись события изменения политики с полным снапшотом. Это единственная роль, которая может менять политику без explicit grant. Explicit grant на `manage-access` не поддерживается — слишком высокий риск эскалации привилегий.

## Итоговое решение консилиума

### Пропозиция A1

**Panel является единственным каноническим источником авторизационных решений для `static.mmbrn.tech`; любой запрос к metadata, `location.ref` или байтам проверяется через `forward_auth → Panel gate` до выдачи ресурса; при неизвестной identity принимается роль `public`, при недоступности авторизатора — `deny`; Affine-роли суть механизм исполнения, получающий короткоживущий токен от Panel, и не являются второй истиной.**

---

### Таблица объектов политики и наследования

| Уровень | Идентификатор | Поддерживается | Наследование |
|---|---|---|---|
| Контейнер | `static.mmbrn.tech` | Нет отдельной политики | Наследует строжайший `minRole` из коллекций; контейнерный грант = грант на все коллекции с потолком `operator` |
| Коллекция | `sectionId` | Да | `minRole` задаётся явно; грант на коллекцию покрывает все lineage в ней |
| Lineage | `urn:mmbrn:static:<rootId>` | Да | Наследует от коллекции; грант на lineage не может превысить политику коллекции |

Правило конфликта: более ограничивающий уровень выигрывает. Allow-grant ограничен потолком `operator`; owner-only не открывается грантом.

### Таблица полномочий по ролям

| Полномочие | public | ally | operator | owner | explicit grant (max) |
|---|---|---|---|---|---|
| `discover` | ✓ (если minRole=public) | ✓ | ✓ | ✓ | до `operator` |
| `read-metadata` (без ref) | — | ✓ | ✓ | ✓ | до `operator` |
| `read-bytes` / `location.ref` | — | — | ✓ | ✓ | до `operator` |
| `download` | — | — | ✓ | ✓ | до `operator` |
| `write-metadata` | — | — | ✓ | ✓ | до `operator` |
| `upload-revision` | — | — | ✓ | ✓ | до `operator` |
| `manage-access` | — | — | — | ✓ | не поддерживается грантом |

Sensitive-запись: `discover` и `read-metadata` (без `location.ref`) — от `ally`; `location.ref` и байты — от `operator`. Поле `location.ref` отсутствует в ответе API, если effective role < `operator` и нет explicit grant `read-bytes`.

### Последовательность проверки запроса

```
Запрос → forward_auth
  │
  ├─ Шаг 1: Разрешить identity
  │   невалидная/отсутствующая сессия → role = public
  │
  ├─ Шаг 2: Найти объект в реестре
  │   не найден → 404 (не раскрывать факт существования если discover закрыт)
  │
  ├─ Шаг 3: Вычислить effective role
  │   effectiveRole = max(baselineRole, grantedRole(subjectId, objectRef))
  │   авторизатор недоступен → deny (403) + audit(reason: authorizer_unavailable)
  │
  ├─ Шаг 4: Проверить потолок owner-only
  │   objectRef.ownerOnly = true AND effectiveRole < owner → deny (403)
  │
  ├─ Шаг 5a: Проверить полномочие для запрошенного действия
  │   effectiveRole >= minRole(action, objectRef) → pass
  │   иначе → deny (403)
  │
  ├─ Шаг 5b (только для metadata-ответа): sensitive ref pass
  │   если action включает read-bytes: effectiveRole >= operator OR explicit grant
  │   иначе: поле location.ref исключается из ответа
  │
  └─ Шаг 6: Allow → audit(decision: allow) → выдача ресурса
              Deny  → audit(decision: deny)  → 403/404
```

### Таблица соответствия Panel → Affine

| Panel-решение | Механизм Affine | Время жизни | Отзыв |
|---|---|---|---|
| `allow, effectiveRole=ally` | токен → Affine role `reader` | TTL ≤ 5 мин | истечение TTL или явный отзыв при permVersion change |
| `allow, effectiveRole=operator` | токен → Affine role `editor` | TTL ≤ 5 мин | то же |
| `allow, effectiveRole=owner` | токен → Affine role `manager` | TTL ≤ 5 мин | то же |
| `deny` | токен не выпускается | — | — |
| токен истёк, permVersion изменён | Affine-роль отзывается | — | следующий запрос к gate |

Нативная роль Affine (`owner/manager/editor/commenter/reader`) — механизм исполнения, не источник авторизационного решения. Противоречие Panel vs Affine: Panel выигрывает — токен не выпускается или отзывается.

### Минимальный audit contract и правила отзыва

**Событие allow/deny:**
```
{
  eventId: uuid,
  ts: ISO8601,
  subjectId: string,
  objectRef: string,           // canonicalRef или sectionId
  action: permission,
  decision: "allow" | "deny",
  effectiveRole: role,
  grantSnapshot: grant[],
  policyVersion: number,       // permVersion на момент решения
  requestOrigin: string,       // IP или service id
  reason?: string              // при deny: причина
}
```

**Событие изменения политики:**
```
{
  eventId: uuid,
  ts: ISO8601,
  actor: subjectId,
  targetSubject: subjectId | null,
  targetObject: objectRef,
  prevPolicy: policySnapshot,
  nextPolicy: policySnapshot,
  permVersionBefore: number,
  permVersionAfter: number
}
```

**Правила отзыва и fail-closed:**

| Ситуация | Поведение |
|---|---|
| Неизвестная/невалидная identity | role = public; применяется общий алгоритм |
| Авторизатор недоступен | deny; audit с reason: authorizer_unavailable |
| Токен Affine истёк | доступ к Affine-документу закрыт; перевыпуск только через новый Panel gate |
| permVersion изменён с момента последнего кеша | кеш инвалидируется; новый запрос к gate |
| Кеш решения (не sensitive) | TTL ≤ 60 секунд |
| Кеш решения (sensitive, location.ref, байты) | no-store |

**A1 — назначьте единый исполнимый контракт доступа к `static.mmbrn.tech`: источник решения, субъект и объект авторизации, гранулярность, роли и индивидуальные гранты, серверную границу, отношение к нативным ролям Affine, видимость sensitive-адресов, отзыв и аудит решения. ## Закрытые посылки M1–M2

- `static.mmbrn.tech` — полноценный контейнер Membrana; Affine — сменный человеческий движок, а не граница контейнера и не источник стратегических документов.

## Измеренная фактура доступа

- Panel определяет полный порядок ролей `public < ally < operator < owner`.
- Доступ к разделу сейчас вычисляется как `role >= minRole` **или** индивидуальный грант на `sectionId`; грант не открывает owner-only раздел.
- Изменение грантов пользователя увеличивает `permVersion` и добавляет запись в аудит Panel с actor, target, временем и прежним/новым набором грантов.
- Серверный endpoint `office /v1/panel/gate/:sectionId` возвращает 204 или 403 по тому же предикату Panel; неизвестный раздел даёт 404, отсутствующая/невалидная сессия — identity `public`.
- Реальный `forward_auth` и реестр серверно защищённых мостов сейчас существуют только для `graphify` и `research-tree`, оба с `minRole: operator`.
- Раздел Panel `strategic-docs` имеет `minRole: ally`, но сейчас это UX-доступ к карточке и ссылке; он не защищает прямой URL `strategy.mmbrn.tech`.
- Affine имеет независимые workspace privacy, document roles и гранты `owner/manager/editor/commenter/reader`. Передачи идентичности, решений Panel и отзывов грантов в Affine сейчас нет.

## Обязательные решения

1. **Источник авторизации.** Назвать ровно один канонический источник решений доступа Membrana и отдельно определить статус нативных ролей Affine. Две конкурирующие истины запрещены.
2. **Субъект и объект.** Определить стабильную identity субъекта и объекты политики: контейнер, коллекция и конкретная lineage по `canonicalRef`. Если какой-либо уровень не поддерживается, это должно быть сказано явно с доказательством достаточности.
3. **Гранулярность и наследование.** Дать точный алгоритм effective access, включая baseline роли, индивидуальный allow-grant, более узкое ограничение, наследование, конфликт правил и fail-closed default. Нельзя оставить слово «грант» без объекта и правила приоритета.
4. **Полномочия.** Развести минимум `discover`, `read-metadata`, `read-bytes`, `download`, `write-metadata`, `upload-revision`, `manage-access`. Это политика доступа, не дизайн API или workflow M6.
5. **Серверная граница.** Назвать точку, которая проверяет каждый запрос до выдачи metadata, `location.ref` или байтов. Скрытая карточка, iframe и UI Affine не считаются защитой. Прямой URL к Affine или складу не должен обходить решение.
6. **Affine.** Определить минимальный способ применения решения выбранного канонического авторизатора к Affine: mapping, короткоживущая делегация, proxy или иной один контракт. Нативная роль Affine может быть механизмом исполнения, но не второй истиной. UX и продуктовая роль Affine — M5.
7. **Sensitive.** Установить, кто может видеть сам факт записи, metadata, reason, `location.kind`, `location.ref` и байты. Нельзя отождествлять скрытие ref с защитой байтов или делать sensitive отдельным `location.kind`.
8. **Отзыв и аудит.** Установить fail-closed поведение при неизвестной identity, недоступности авторизатора и устаревшей делегации; максимальную семантику кеша решения; обязательные поля audit-события allow/deny и изменения политики. Конкретное хранилище журнала остаётся реализации.

## Обязательные случаи для доказательства

Таблица случаев содержит колонки `Субъект`, `Объект`, `Действие`, `Решение`, `Где проверяется`, `Почему` и включает не меньше восьми строк:

1. анонимный пользователь открывает разрешённый public-материал;
2. анонимный пользователь запрашивает ally-материал;
3. пользователь ниже baseline получает явный грант на коллекцию;
4. тот же грант отозван, но старая сессия или делегация ещё существует;
5. operator читает metadata, но не получает автоматически право `manage-access`;
6. owner меняет политику доступа;
7. пользователь открывает прямой URL Affine в обход Panel UI;
8. пользователь видит sensitive metadata, но не имеет права видеть `location.ref` или получать байты.

Для каждого случая решение должно следовать из единого алгоритма, а не из отдельного исключения. Если public-материалы отвергнуты как класс, первая строка всё равно должна показать честный deny и объяснить выбранный default.
