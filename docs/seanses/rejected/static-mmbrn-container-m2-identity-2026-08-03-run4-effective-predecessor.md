# Консилиум: M2 — тождество и источник истины (I1, Run4)

**Повестка:** Единый контракт тождества и источника истины для каждого материала контейнера `static.mmbrn.tech`: канонические единицы, роли полей, линейный supersedes с fallback, canonicalRef, sensitive-поведение.

**Порядок реплик:** Структурщик → Математик → Teamlead → Верстальщик → Музыкант → Архитектор (циклически, ≥36 реплик советчиков)

[Структурщик]: Начну с терминологического разграничения — без него любой контракт смешает три несмешиваемых понятия. Байт-тождество — это `sha256`: одинаковые байты дают одинаковый хеш, разные — разный. Запись-тождество — это `id`: неизменяемое имя одной строки реестра, которую нельзя мутировать. Линейное тождество — это корень логической линии: стабильный ключ, именующий всю цепочку поправок как одну сущность. Три концепта, три имени, никакого пересечения.

[Математик]: Добавлю формальное определение живой записи — оно единственное, не допускающее двусмысленности. Пусть R — множество всех `id` реестра, S — множество всех значений поля `supersedes` (там, где оно есть). Живая запись линии — единственный элемент R, не входящий в S и принадлежащий данной линии. `addedAt` в это определение не входит вообще: оно может использоваться для аудита, но не для выбора живой записи. Это инвариант, а не эвристика.

[Teamlead]: Хорошо, база терминологии заложена. Теперь про источник истины: `docs/evidence/registry.jsonl` — единственное место, где фиксируется факт принятия материала. Фактические байты лежат на складе, который сменяем; реестр — несменяем в смысле семантики. Это значит: склад — физика, реестр — логика. Контракт должен явно утверждать, что при утере байтов реестр не теряет смысл — он сохраняет свидетельство о факте поступления.

[Верстальщик]: С точки зрения читаемости и навигации: `canonicalRef` должен быть стабильным человекочитаемым адресом логической линии. Он не должен быть `id` конкретной поправочной записи, потому что тот меняется при каждой поправке. Он не должен быть `location.ref`, потому что тот привязан к физическому складу. `canonicalRef` — это адрес линии, инвариантный к числу поправок и смене склада. Публичность этого адреса — M3, здесь только его стабильность как идентификатора.

[Музыкант]: Меня интересует граница для архива и PDF. Если я приношу архив `tar.gz` — регистрируется он целиком, один `sha256` на весь архив. Если внутри есть файл, который я приносил отдельно раньше — у него уже есть своя запись с собственным `id` и `sha256`. Эти две записи сосуществуют; их связь — семантическая, а не структурная в реестре. M2 не требует, чтобы я что-то извлекал или дублировал хранение: зафиксировать факт принятия архива как единицы — достаточно.

[Архитектор]: Обозначу форму решения для sensitive-материала. Чувствительность — это не `location.kind`. Валидатор принимает только `local`, `affine`, `url`, `archivarius`. Значит чувствительная запись обязана иметь один из этих kind и непустой `ref` — это не опционально, это инвариант. Рядом с этим полем существует отдельный объект `sensitive` с полем `reason`. Адрес в `ref` может быть непереносимым и недоступным публично — это честное состояние, не ошибка реестра. M3-M4 решат, кому ref раскрывается; M2 только фиксирует, что он обязан присутствовать.

[Структурщик]: Теперь про append-only инвариант для полей. Любое поле записи — `about`, `measured`, `location`, `source`, любое другое — неизменяемо внутри строки. Если нужно исправить адрес, обновить описание, уточнить размер — создаётся новая строка с новым `id` и полем `supersedes`, указывающим на исправляемую запись. Старая строка остаётся в файле и никогда не удаляется. Это не «версионирование» в смысле git-diff — это физическая неизменяемость каждой строки JSONL.

[Математик]: Разберу fallback для четырёх legacy-записей формально. Имеем: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`. Алгоритм fallback: (1) корень линии = id с отброшенным конечным `-rN`; (2) запись `<root>-rN` считается продолжателем `<root>-r(N-1)` если N > 1, либо самого `<root>` если N = 1; (3) живая запись — та, у которой нет продолжателя с бо́льшим номером ревизии в том же корне. Итого три корня: `ozon-receipt-3765-field-kit`, `day-memo-2026-07-28`, `bpla-guidance-methodology-partner`. Живые: `-r2`, `-r2`, `-r3`. Важно: `-r1` при его наличии был бы predecessor `-r2`, но не корнем линии; корень — всегда base-имя без суффикса.

[Teamlead]: Про источник `source` — это не автор операции. Если я беру файл с партнёрского сервера и регистрирую его — `source` указывает на партнёрский сервер, а не на меня. Если поправка только меняет `location` тех же байтов — `source` новой записи совпадает с `source` исходной, потому что байты не изменились и их происхождение то же. Если поступает новая редакция содержания — `source` фиксирует откуда пришла именно эта редакция. Автор регистрации может быть описан в других полях, но не подменяет провенанс.

[Верстальщик]: Хочу прояснить отношение `canonicalRef` к `id` поправочной записи на конкретном случае PDF. Поступает `report.pdf` — создаётся запись `report-pdf-2026-07-01` с корнем `report-pdf` и `canonicalRef: evidence/report-pdf`. Меняется адрес хранения — создаётся новая запись `report-pdf-2026-07-01-r1` (или новый уникальный `id`) с `supersedes: report-pdf-2026-07-01`. `sha256` у новой записи тот же — байты не изменились. `canonicalRef` тот же — `evidence/report-pdf`. Корень линии тот же. Новый только `id` поправочной записи и `location`. Это ровно то, что нельзя было помещать в старую строку.

[Музыкант]: Уточню про PDF со встроенными объектами. PDF регистрируется одной записью по своим байтам. Если внутри PDF есть изображение — оно не получает отдельную запись автоматически. Оно получает отдельную запись только если: (а) это изображение уже поступало как самостоятельный материал до PDF — тогда его запись существует независимо; (б) M6 позднее предоставил его как отдельный материал в рамках своего workflow. M2 не инициирует извлечение и не требует производной. Два `sha256` — один для PDF целиком, один для изображения — могут сосуществовать в реестре, но это два независимых факта поступления, а не структурная связь parent-child.

[Архитектор]: Разграничу три уровня тождества через призму каждого случая, чтобы контракт был конкретным. Уровень байтов: `sha256` — единственный судья; совпадает ли `sha256` у двух записей — не важно для их `id`, важно для вопроса «те же ли это байты». Уровень записи: `id` — неизменяемое имя конкретной строки реестра; он не несёт смысл «тот же материал», только «та же строка». Уровень линии: корень (`canonicalRef` или явное поле `lineage`) — стабильный ключ, означающий «одна и та же логическая сущность через все поправки». Смешивать эти три уровня — архитектурная ошибка.

[Структурщик]: Про дубль под другим именем. Два файла с разными именами, но одинаковым содержимым — это два разных поступления: разные `id`, одинаковый `sha256`, разные корни линий (если имена разные). Реестр не сливает их автоматически — это находка для человека, не структурный факт. M2 не предписывает слияние дублей; слияние двух линий в одну через `supersedes` запрещено, потому что `supersedes` линейна и ациклична, а две независимые линии не могут иметь одного продолжателя без нарушения этого инварианта.

[Математик]: Формализую инвариант supersedes как граф. Отношение `supersedes` задаёт ориентированный граф на множестве `id`. Инварианты: (1) граф ациклический — нет пути от узла к самому себе; (2) каждый узел имеет не более одного исходящего ребра `supersedes` (он ссылается не более чем на одну предыдущую запись); (3) каждый узел имеет не более одного входящего ребра (не более одного продолжателя); (4) нет рёбер между разными корнями линий. Это даёт строгую линейную цепь без ветвлений и слияний.

[Teamlead]: Зафиксирую решение по чувствительному материалу. Байты могут быть физически вне репозитория и недоступны публично — это честное состояние. `sha256` обязан присутствовать в записи и верно отражать байты. `location.kind` — один из допустимых четырёх значений. `location.ref` — непустой, даже если адрес непереносим. `sensitive.reason` — отдельный объект, описывающий причину чувствительности. Кто и как получает доступ к `location.ref` — M3. Где физически хранятся байты — M4. M2 только утверждает: запись валидна, `location` обязателен, `sensitive` — дополнительный признак, а не замена `location`.

[Верстальщик]: Добавлю к sensitive-случаю: индекс в производной описи скрывает `location.ref` от широкого доступа — это операционное решение, не изменение структуры записи. Запись в `registry.jsonl` остаётся полной и неизменной. Производная опись — артефакт M6. M2 не проектирует ни производную опись, ни кому она доступна; M2 только утверждает, что сама строка реестра содержит валидный `location` с реальным `ref`.

[Музыкант]: Хочу подтвердить: для перемещения байтов между складами — тот же сценарий, что и для адресной поправки PDF. Байты не изменились — `sha256` тот же. Корень линии тот же. `canonicalRef` тот же. Создаётся новая запись с новым `id` и `supersedes` на предыдущую, с новым `location` под новый склад. `source` — тот же, что у исходной записи: байты пришли из того же источника, перемещение байтов не меняет их происхождение. Старая запись с устаревшим `location` остаётся в реестре как история.

[Архитектор]: Сформулирую контракт для новой редакции содержания, чтобы отличить её от адресной поправки. Новая редакция — это другие байты: другой `sha256`, другой `id`, новая запись с `supersedes` на предыдущую запись линии. Корень линии тот же, `canonicalRef` тот же — это продолжение той же логической сущности, но уже другой версией байтов. `source` может не совпадать с предыдущей записью: если новая редакция пришла от другого поставщика, это честно фиксируется в новой записи. Это единственный случай, когда `sha256` меняется внутри одной линии.

[Структурщик]: Суммирую правило о member архива. Архив: одна запись, `sha256` архива целиком. Член архива до этого не поступал самостоятельно — нет отдельной записи, нет требования создавать её. Член архива поступал самостоятельно до архива — его запись существует независимо, корни разные, связь семантическая. M6 позднее предоставляет член как материал — создаётся новая запись с новым `id` и `source` из этого факта поступления; M2 не предрешает это решение. Три ситуации, три разных ответа, ни одна не требует изменения записи архива.

[Математик]: Проверю, что legacy fallback не создаёт коллизий с новыми записями. Fallback применяется только к четырём перечисленным записям: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`. Для всех новых записей — явный `supersedes` обязателен; паттерн `-rN` не является структурным механизмом для новых записей. Если новая запись случайно оканчивается на `-r2` в имени — это не делает её продолжателем кого-либо; только явный `supersedes` создаёт связь в цепочке.

[Teamlead]: Про запрет fork и merge — это не только теоретическое ограничение, это операционный запрет. Если два человека независимо зарегистрировали один и тот же материал под разными `id` — получили две линии. Нельзя написать третью запись с `supersedes: [id1, id2]` — это merge, запрещён. Нельзя от одной записи сделать два продолжателя — это fork, запрещён. Обнаружение дублей — находка для человека и потенциальный вопрос для будущих заседаний; M2 только утверждает линейность и ацикличность.

[Верстальщик]: Хочу зафиксировать визуальный инвариант таблицы полей: никаких pipe-символов внутри ячеек без экранирования. В повестке это требование явно: перечисления kind пишутся через запятые. Это технический запрет, который я буду контролировать при финальной вёрстке протокола. Все четыре допустимых значения: `local`, `affine`, `url`, `archivarius` — перечислены через запятую, не через `|`.

[Музыкант]: Подтверждаю граничный случай: что если sensitive-материал хранится на внешнем сервере и адрес этого сервера — непереносимый? Это честное состояние. `location.kind: url` с `location.ref: https://secure.internal/...` — валидная комбинация. Или `location.kind: local` с `location.ref: /mnt/encrypted/...` — тоже валидно. Главное: `ref` непустой и соответствует реальному адресу на момент регистрации. Переносимость не обязательна; актуальность не гарантируется реестром.

[Архитектор]: Закреплю: `canonicalRef` — это не `id` последней записи в цепочке. Это стабильный адрес логической линии, который не меняется при поправках. Форма `canonicalRef` — `evidence/<корень-линии>`. Пример: для линии с корнем `bpla-guidance-methodology-partner` — `canonicalRef: evidence/bpla-guidance-methodology-partner`. Этот адрес одинаков у `r2` и у `r3` и у всех будущих поправок этой линии. Он не является публичным URL — это M3.

[Структурщик]: Сформулирую точный инвариант для адресной поправки простого PDF, потому что этот случай трижды упоминается в повестке как источник ошибки. Исходная запись: `id: report-pdf-a1b2`, `sha256: abc...`, `location: {kind: local, ref: /old/path}`, `source: partner-x`, корень линии `report-pdf`, `canonicalRef: evidence/report-pdf`. Поправка адреса: новая строка, `id: report-pdf-a1b2-addr1` (новый уникальный id), `sha256: abc...` (тот же), `location: {kind: affine, ref: space-id/block-id}` (новый), `source: partner-x` (тот же провенанс), `supersedes: report-pdf-a1b2`, корень линии `report-pdf`, `canonicalRef: evidence/report-pdf`. Старая строка неизменна.

[Математик]: Добавлю численный инвариант для проверки реестра на корректность: при обходе всех записей количество записей без `supersedes` должно равняться количеству логических линий. Если у нас N линий — ровно N «корневых» записей (либо legacy fallback-корней) без `supersedes`. Это проверяемое утверждение, которое валидатор может вычислить автоматически. Для legacy-записей корень линии логически существует, даже если физической строки без `-rN` нет — fallback это учитывает.

[Teamlead]: Видимо, пора закрыть дискуссию и перейти к вердикту. Все шесть случаев повестки разобраны: простой PDF с адресной поправкой, байтовый дубль, новая редакция, архив с членом, перемещение байтов, sensitive без публичного локатора. Три уровня тождества (байты/запись/линия) разграничены формально. Fallback для четырёх legacy-записей определён точно. ### Пропозиция-контракт M2

**Каждый материал контейнера `static.mmbrn.tech` существует на трёх независимых уровнях тождества:**

1. **Байтовое тождество** (`sha256`): криптографический хеш конкретных байтов. Одинаковые байты дают одинаковый `sha256` независимо от имени, местоположения и числа записей в реестре. Это единственный судья вопроса «те же ли байты».

2. **Запись-тождество** (`id`): неизменяемое имя одной строки `registry.jsonl`. Строка не мутирует никогда. Любое изменение любого поля — `about`, `measured`, `location`, `source`, любого другого — создаёт новую строку с новым `id` и полем `supersedes`, указывающим на исправляемую запись. `id` не несёт смысл «тот же материал» — только «та же неизменяемая строка реестра».

3. **Линейное тождество** (`canonicalRef` / корень линии): стабильный адрес логической линии, инвариантный к числу поправок и смене склада. Форма: `evidence/<корень>`, где корень — base-имя без суффикса поправки. Не является публичным URL; доступность и авторизация — M3.

**Источник истины:** `docs/evidence/registry.jsonl` — единственный источник истины о факте принятия материала. Фактические байты хранятся на сменном складе; при утере байтов реестр сохраняет свидетельство о факте поступления. Склад — физика, реестр — логика.

**Живая запись линии:** единственный `id` в линии, не являющийся значением поля `supersedes` ни в одной записи этой линии. `addedAt` в выборе живой записи не участвует.

**Supersedes:** линейный ациклический граф. Каждая запись ссылается не более чем на одну предыдущую (не более одного `supersedes`). У каждой записи не более одного продолжателя. Fork (одна запись — два продолжателя) и merge (два `id` в одном `supersedes`) запрещены. Две независимые линии не могут быть слиты.

**Каноническая единица регистрации:** простой файл — одна запись. Архив — одна запись по байтам архива целиком. PDF — одна запись по байтам PDF целиком. Член архива или встроенный объект PDF получает отдельную запись только если: (а) он независимо поступал как материал до архива/PDF, либо (б) M6 позднее предоставил его как самостоятельный материал. M2 не требует извлечения, отдельного хранения или производной.

**`source`:** провенанс байтов или материала конкретной записи — откуда они пришли, а не кто регистрировал или перемещал. При адресной поправке тех же байтов `source` повторяется из исходной записи. При новой редакции содержания `source` фиксирует фактическое происхождение новой редакции. Автор операции регистрации, переноса, поправки в `source` не записывается.

**Чувствительный материал:** запись обязана содержать валидный `location.kind` (один из: `local`, `affine`, `url`, `archivarius`) и непустой `location.ref`. `sensitive` — отдельный объект с полем `reason`; он не заменяет `location` и не является допустимым `kind`. Байты могут физически находиться вне репозитория и быть недоступны публично — это честное состояние, не ошибка реестра. Кому раскрывается `location.ref` — M3; где хранятся байты — M4.

### Таблица полей и инвариантов

| Поле | Тип | Изменяемость | Инвариант |
|------|-----|--------------|-----------|
| `id` | строка | неизменяем | именует ровно одну строку реестра; уникален глобально |
| `sha256` | строка | неизменяем | тождество байтов; одинаков у всех записей с одинаковым содержимым |
| `bytes` | целое > 0 | неизменяем | размер байтов на момент регистрации |
| `addedAt` | дата `YYYY-MM-DD…` | неизменяем | дата регистрации строки; не задаёт порядок цепочки |
| `source` | строка | неизменяем | провенанс байтов/материала; не автор операции |
| `location.kind` | enum | неизменяем | только `local`, `affine`, `url`, `archivarius` |
| `location.ref` | строка | неизменяем | всегда непустой; адрес на момент регистрации |
| `about` | строка | только через новую запись | описание смысла материала |
| `measured` | объект | только через новую запись | измеренные характеристики |
| `supersedes` | строка | только через новую запись | ссылка на `id` предыдущей записи линии; у одной записи — не более одного значения |
| `sensitive.reason` | строка | только через новую запись | причина чувствительности; не заменяет `location` |
| `canonicalRef` | строка | неизменяем для линии | `evidence/<корень>`; стабилен через все поправки линии |

### Разбор шести случаев

#### Случай 1: Простой PDF, адресная поправка

Поступает `report.pdf`. Создаётся запись:
```
id: "report-pdf-a1b2"
sha256: "abc..."
location: {kind: "local", ref: "/old/path/report.pdf"}
source: "partner-x"
canonicalRef: "evidence/report-pdf"
```

Файл перемещён. Создаётся новая запись:
```
id: "report-pdf-a1b2-addr1"   ← новый id
sha256: "abc..."               ← тот же: байты не изменились
location: {kind: "affine", ref: "space/block-id"}  ← новый
source: "partner-x"           ← тот же провенанс
supersedes: "report-pdf-a1b2" ← явная ссылка
canonicalRef: "evidence/report-pdf"  ← тот же
```

| Уровень | Состояние |
|---------|-----------|
| Байты (`sha256`) | **то же** — `abc...` не изменился |
| Запись (`id`) | **новая** — `report-pdf-a1b2-addr1` |
| Линия (`canonicalRef`) | **та же** — `evidence/report-pdf` |

Старая строка `report-pdf-a1b2` неизменна. Нельзя помещать новый `location` в старую строку.

---

#### Случай 2: Байтовый дубль под другим именем

Два файла `file-a.pdf` и `file-b.pdf` с идентичным содержимым:
```
id: "file-a-001", sha256: "xyz...", source: "source-a", canonicalRef: "evidence/file-a"
id: "file-b-001", sha256: "xyz...", source: "source-b", canonicalRef: "evidence/file-b"
```

| Уровень | Состояние |
|---------|-----------|
| Байты (`sha256`) | **те же** — `xyz...` совпадает |
| Запись (`id`) | **разные** — два разных `id` |
| Линия (`canonicalRef`) | **разные** — две независимых линии |

Реестр не сливает их автоматически. Слияние через `supersedes` запрещено: это создало бы merge двух линий. Обнаружение дублей — находка для человека.

---

#### Случай 3: Новая редакция содержания

Существует запись `doc-001` с `sha256: "old..."`. Поступает новая версия документа с изменённым содержимым:
```
id: "doc-002"          ← новый id
sha256: "new..."       ← новый: байты изменились
source: "partner-y"    ← может не совпадать с source исходной записи
supersedes: "doc-001"  ← явная ссылка
canonicalRef: "evidence/doc"  ← та же
```

| Уровень | Состояние |
|---------|-----------|
| Байты (`sha256`) | **иные** — `new...` ≠ `old...` |
| Запись (`id`) | **новая** — `doc-002` |
| Линия (`canonicalRef`) | **та же** — `evidence/doc` |

`source` может отличаться: новая редакция могла прийти от другого поставщика.

---

#### Случай 4: Архив и его член

Поступает архив `kit.tar.gz`. Создаётся одна запись:
```
id: "kit-archive-001"
sha256: "arch-hash..."
location: {kind: "local", ref: "/storage/kit.tar.gz"}
source: "field-team"
canonicalRef: "evidence/kit-archive"
```

Внутри архива есть `manual.pdf`, который не поступал самостоятельно. Отдельная запись для `manual.pdf` **не создаётся** — M2 не требует извлечения.

Если `manual.pdf` ранее поступал самостоятельно, его независимая запись существует. Если M6 позднее предоставит `manual.pdf` как отдельный материал — будет создана новая запись с новым `id`, `source` из того факта поступления и своим `canonicalRef`.

| Уровень | Архив | Член (если независим) |
|---------|-------|-----------------------|
| Байты (`sha256`) | хеш архива целиком | хеш члена отдельно |
| Запись (`id`) | `kit-archive-001` | отдельный `id` |
| Линия (`canonicalRef`) | `evidence/kit-archive` | своя линия |

---

#### Случай 5: Перемещение байтов между складами

Байты `report.pdf` перемещены с локального хранилища на Affine. `sha256` не изменился. Создаётся новая запись:
```
id: "report-pdf-a1b2-move1"
sha256: "abc..."               ← тот же
location: {kind: "affine", ref: "new-space/block"}  ← новый склад
source: "partner-x"           ← тот же: байты не изменились, провенанс тот же
supersedes: "report-pdf-a1b2"
canonicalRef: "evidence/report-pdf"  ← та же
```

| Уровень | Состояние |
|---------|-----------|
| Байты (`sha256`) | **то же** |
| Запись (`id`) | **новая** |
| Линия (`canonicalRef`) | **та же** |

Изменилось: `location.ref`. Не изменилось: `sha256`, корень линии, `canonicalRef`, `source`.

---

#### Случай 6: Чувствительный материал без публичного локатора

Поступает документ, байты которого не могут быть в репозитории. Запись:
```
id: "sensitive-doc-001"
sha256: "sec-hash..."
bytes: 204800
addedAt: "2026-08-03"
source: "internal-ops"
location: {kind: "local", ref: "/mnt/encrypted/sensitive-doc.pdf"}
sensitive: {reason: "содержит персональные данные"}
canonicalRef: "evidence/sensitive-doc"
```

| Уровень | Состояние |
|---------|-----------|
| Байты (`sha256`) | присутствует в записи; сами байты — вне репозитория |
| Запись (`id`) | полная валидная запись |
| Линия (`canonicalRef`) | `evidence/sensitive-doc` |

`location.kind` — один из допустимых четырёх значений. `location.ref` — непустой, реальный адрес. `sensitive.reason` — отдельный признак, не заменяющий `location`. Кому доступен `ref` — M3. Где хранятся байты — M4.

### Legacy fallback: четыре записи, три линии

| Legacy `id` | Корень линии | Predecessor по fallback | Живая? |
|-------------|--------------|------------------------|--------|
| `ozon-receipt-3765-field-kit-r2` | `ozon-receipt-3765-field-kit` | `ozon-receipt-3765-field-kit-r1` или корень | да |
| `day-memo-2026-07-28-r2` | `day-memo-2026-07-28` | `day-memo-2026-07-28-r1` или корень | да |
| `bpla-guidance-methodology-partner-r2` | `bpla-guidance-methodology-partner` | `bpla-guidance-methodology-partner-r1` или корень | нет (есть r3) |
| `bpla-guidance-methodology-partner-r3` | `bpla-guidance-methodology-partner` | `bpla-guidance-methodology-partner-r2` | да |

Три корня линий: `ozon-receipt-3765-field-kit`, `day-memo-2026-07-28`, `bpla-guidance-methodology-partner`.

Правила fallback:
- Корень = base-имя после снятия конечного `-rN`.
- Запись `-rN` считается продолжателем `-r(N-1)` при N > 1, либо корня при N = 1.
- Запись `-r1` может быть predecessor следующей ревизии, но никогда не является корнем линии.
- Живая запись линии — та, у которой нет продолжателя с бо́льшим номером ревизии в том же корне.
- Fallback действует только на эти четыре перечисленные legacy-записи.
- Все новые поправки обязаны иметь явный `supersedes`; паттерн `-rN` не является структурным механизмом для новых записей.

## Измеренная фактура существующего дома

- `registry.jsonl` append-only: одна JSON-запись на строку, правка старых строк запрещена.
- Полная живая форма `EvidenceRecord`: обязательные `id`, `sha256`, `bytes`, `addedAt`, `source`, `location {kind, ref}`; опциональные `about` и `measured`. Валидатор требует положительный целый `bytes` и дату `addedAt` формата `YYYY-MM-DD…` наряду с остальными обязательными полями. Четыре поля `id + sha256 + location + source` — не вся запись, а только существующее ядро имени, тождества, адреса и провенанса.
- Валидатор допускает для `location.kind` только `local`, `affine`, `url`, `archivarius` и при любом kind требует непустой `location.ref`. `sensitive` не является kind: чувствительность определяется отдельным `sensitive.reason`.
- Несущий предикат README: без хеша и адреса запись не является вещдоком; хеш даёт тождество, адрес — достижимость, описание — смысл.
- Склад объявлен сменной деталью, индекс — сутью. `location` сейчас бывает repo-relative, абсолютным локальным или чувствительным честно непереносимым адресом.
- Существующие поправки используют `<id>-rN`; старая строка остаётся историей, последняя в цепочке считается живой. Один и тот же `sha256` уже встречается у исходной записи и поправки адреса.
- В живом реестре четыре legacy-записи с суффиксом `-rN` и без поля `supersedes`: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2` и `bpla-guidance-methodology-partner-r3`. Это четыре записи в трёх логических линиях; пара bpla `r2`, `r3` принадлежит одной линии.
- Дубль одинакового содержимого под разными `id` сейчас является находкой для человека, а не автоматически слитым объектом.
- Для чувствительного материала байты могут оставаться вне репозитория; индекс скрывает адрес в производной описи, а `sha256`, провенанс и причина чувствительности сохраняются.

## Обязательные поправки после отклонённого run1

- `sha256` свидетельствует о тождестве байтов; `id` именует одну неизменяемую запись; корень цепочки или эквивалентный ему механизм именует логическую линию. Эти три вещи нельзя называть одним тождеством.
- Поправка и новая редакция создают новую запись с новым record `id`; контракт обязан отдельно назвать, что сохраняет корень логической линии и `canonicalRef`.
- `source` обязателен и честен в каждой записи. Он неизменяем внутри записи, но не обязан совпадать у новой редакции или иного поступления той же логической линии.
- Чувствительная запись сохраняет допустимые и непустые `location.kind` и `location.ref` вместе с отдельным `sensitive`; M2 не придумывает новый kind, не опускает ref и не решает, где или кому раскрывается адрес.
- Собственный числовой счёт модели и футер о числе реплик запрещены. Единственный счёт — механический отчёт председателя, который отдельно ратифицирует read-only аудитор.

## Обязательные поправки после отклонённого run2

- `addedAt` не задаёт порядок цепочки и не выбирает живую запись. Живая запись линии — единственный record `id`, который не назван значением `supersedes` ни в одной записи, продолжающей эту линию.
- У каждой записи не более одного непосредственного продолжателя, `supersedes` ссылается только на более раннюю запись, циклы, fork и merge запрещены. Две дубль-линии нельзя слить одиночным `supersedes`; они остаются отдельными линиями.
- Для четырёх перечисленных legacy-записей без `supersedes` нужен ограниченный fallback: корень определяется снятием конечного `-rN`, а `rN` продолжает запись с наибольшим меньшим номером ревизии того же корня либо сам корень, если меньшей ревизии нет; fallback не действует на новые записи и не превращает паттерн имени в основной структурный механизм.
- `source` — провенанс материала или байтов конкретной записи. Автор регистрации, перемещения либо иной операции не заменяет `source`; его можно описать в иных метаданных. При адресной поправке тех же байтов исходный провенанс повторяется, при новой редакции записывается фактический провенанс новой редакции.

## Обязательные поправки после отклонённого run3

- PDF или архив получает запись целиком. Встроенный объект или член получает отдельную запись только если уже независимо поступил как материал либо M6 позднее предоставил его как материал; M2 не требует извлечения, отдельного физического хранения или производной.
- Любая правка `about`, `measured`, `location` либо другого поля требует новой append-only записи с новым record `id` и `supersedes`; старая строка и её поля не меняются.
- В случае простого PDF адресная поправка сохраняет `sha256`, корень и `canonicalRef`, но создаёт новую запись с новым `id`; нельзя помещать новый location в старую record-строку.
- Legacy-корень всегда равен `<root>` после снятия конечного `-rN`; существующий `-r1` может быть predecessor следующей ревизии, но никогда не становится корнем линии.
- Фактура называется точно: четыре legacy-записи образуют три линии.
- В Markdown-таблицах перечисления kind пишутся через запятые либо с экранированными разделителями; неэкранированный `|` внутри ячейки запрещён.

## Требования к посылкам и исполнению

Секция **«Список посылок»** содержит только реально использованные входы: закрытые пропозиции M1, измеренные факты существующего дома, нормы общего брифа и ограничения M2. Выводы самой M2 не маскируются под факты или посылки M1.

Фактически требуется не менее 30 ролевых реплик. Модель не считает себя и не включает числовой DoD или числовой футер; механический счёт делает председатель, вердикт по нему даёт read-only аудитор. Каждый ненумерический `[x]` DoD должен быть истинным; любой `[ ]` или ложный `[x]` означает BLOCK.

## Запреты этой комнаты

- Не выбирать источник решений доступа, роли, гранулярность и серверный гейт: M3.
- Не выбирать VDS, объектное хранилище, host, quota, backup, restore, retention: M4.
- Не проектировать роль, API или UX Affine: M5.
- Не проектировать загрузку/ingest, выдачу, просмотр, скачивание и хранение производных: M6. M2 задаёт идентичность и канонический адрес, не workflow получения байтов.
- Не решать судьбу 82 страниц, DNS/Caddy, редиректы, Panel и Issues: M7.
- Не считать канонический адрес публичным URL: доступность и авторизация принадлежат M3.
- Не определять место хранения или круг читателей чувствительного `location.ref`: M3-M4.
- Не проектировать слияние дублей, ветвление или многородительские версии: M2 выбирает минимальную линейную цепь.
- Не создавать второй носитель или менять общий бриф.
