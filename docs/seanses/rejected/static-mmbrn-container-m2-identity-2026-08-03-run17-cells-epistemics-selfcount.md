[Архитектор]: Начну с конструкции. У нас три независимых тождества: байтовое — `sha256` при принятом предположении о коллизионной устойчивости; record-тождество — неизменяемый `id`; lineage-тождество — `root` линии. Ни одно из трёх не выводится из другого. Форма решения: контракт фиксирует их разделение как инвариант, а не как деталь реализации.

[Верстальщик]: Меня интересует единица файла с точки зрения регистрации. PDF — один файл, одна начальная запись. Если у PDF меняется адрес, байты те же — новая запись с новым `id`, `supersedes` на прежнюю, `sha256` сохраняется. Это должно быть явно в таблице случаев, иначе «перенос» и «редакция» смешаются в восприятии.

[Структурщик]: Термины должны быть однозначны. «Запись» — строка в `registry.jsonl` с неизменяемым `id`. «Линия» — конечная связная последовательность записей, связанных функцией `ep`. «Материал» — физический объект, чьи байты зафиксированы `sha256`. Эти три термина не взаимозаменяемы, и в таблицу полей они должны войти с точными определениями.

[Teamlead]: Вопрос по legacy. Четыре записи без `supersedes`: `ozon-receipt-3765-field-kit-r2`, `day-memo-2026-07-28-r2`, `bpla-guidance-methodology-partner-r2`, `bpla-guidance-methodology-partner-r3`. Три линии, не четыре. Правило вычисления effective predecessor для них нужно зафиксировать точно и без условностей — это измеренный факт существующего дома, не предположение.

[Музыкант]: Архив как единица — это интересный момент. Регистрируем целиком: ZIP или TAR имеет свой `sha256`, свой `bytes`, одну запись в реестре. Его члены — отдельная история, которую M2 не разворачивает. Важно, что контракт двух дверей компонента фиксируется ровно один раз — в ячейке случая «архив/член» таблицы.

[Математик]: Формализую функцию effective predecessor. `ep: R → Id(R) ∪ {⊥}`. Для записи с явным полем `supersedes`: `ep(r) = r.supersedes`. Для четырёх named legacy без `supersedes`: `ep(r) = id` максимальной меньшей ревизии той же логической линии либо base-root. Для всех прочих без `supersedes`: `ep(r) = ⊥`. Тип возвращаемого значения — `id`, не объект записи.

[Архитектор]: Root и tip — разные роли с разными критериями. Root: запись `r` такая, что `ep(r) = ⊥`. Tip: `id` такой, что он не встречается ни в одном значении `ep` по всем записям реестра, включая вычисленные legacy-связи. В линии длины 1 одна запись исполняет обе роли; в линии длины больше 1 — это строго разные записи. Множества равночисленны, но определения нельзя смешивать.

[Верстальщик]: Поле `bytes` — отдельная строка таблицы полей, обязательное положительное целое. Это размер конкретных байтов, верифицируемый при доступе. При адресной поправке байты не меняются, значит `bytes` не меняется — новая запись несёт то же числовое значение. При редакции `bytes` измеряется заново; числовое значение может совпасть, а может нет — это факт замера, не утверждение об изменении.

[Структурщик]: `canonicalRef = "urn:mmbrn:static:" + rootId`. Формула инъективна: фиксированный префикс плюс уникальный `rootId` дают однозначное соответствие. При адресной поправке `rootId` не меняется, `canonicalRef` сохраняется. При редакции тоже — линия продолжается, root не меняется. `canonicalRef` — derived-атрибут линии, не поле записи `EvidenceRecord`.

[Teamlead]: Sensitive. Чувствительный материал сохраняет `location.kind` из допустимых (`local`, `affine`, `url`, `archivarius`) и непустой `location.ref` в записи реестра. Отдельное поле `sensitive.reason` фиксирует причину. Видимость `ref` — M3. Склад байтов — M4. M2 только закрепляет, что ref обязан присутствовать в записи реестра.

[Музыкант]: По дублям: два разных `id` с одинаковым `sha256` — это находка для человека, не автоматически слитый объект. M2 не проектирует слияние. Факт дубля фиксируется в реестре как есть; человек принимает решение. `sha256` совпадает — байты, по принятому предположению, те же. Записи разные, линии разные.

[Математик]: Разберу три legacy-линии точно. Линия ozon: `ozon-receipt-3765-field-kit` (base) → `ozon-receipt-3765-field-kit-r2`. Двухзвенная. Root = `ozon-receipt-3765-field-kit`, tip = `ozon-receipt-3765-field-kit-r2`. Линия day-memo: `day-memo-2026-07-28` (base) → `day-memo-2026-07-28-r2`. Двухзвенная. Root = `day-memo-2026-07-28`, tip = `day-memo-2026-07-28-r2`. Линия bpla: `bpla-guidance-methodology-partner` (base) → `bpla-guidance-methodology-partner-r2` → `bpla-guidance-methodology-partner-r3`. Трёхзвенная. Root = `bpla-guidance-methodology-partner`, tip = `bpla-guidance-methodology-partner-r3`.

[Архитектор]: Источник истины — только `registry.jsonl`. Он сообщает о регистрации, record/lineage identity, заявленных полях и истории. Байты — независимый предмет: при доступе они верифицируют `sha256` и `bytes`, но не восстанавливаются из JSONL автоматически. `location` — заявление реестра; достижимость байтов — внешнее состояние склада, независимое от записи.

[Верстальщик]: Поле `source` — провенанс байтов, не автор операции. При адресной поправке `source` повторяется из предшествующей записи без изменений. При редакции `source` фиксируется заново честно — может совпасть, может отличаться. Это принципиальное разделение: кто предоставил байты, а не кто добавил строку в реестр.

[Структурщик]: Таблица случаев требует три колонки: `Байты`, `Запись`, `Линия`. В record-колонке не появляются `root` и `canonicalRef` — это derived, не поля записи. В каждой ячейке — ответ и доказательство. Напомню: сырой символ `|` в ячейке таблицы недопустим, для разделения в ячейке используем другие средства.

[Teamlead]: Уникальность `id` записи — принимаемый инвариант M2. Это не измеренный факт схемы, не вывод из структуры JSONL. Append-only реестр физически не запрещает дубли `id`, но контракт M2 объявляет: каждый `id` уникален. Таблица полей должна это отразить с пометкой «инвариант M2», не «факт схемы».

[Музыкант]: Поле `about` и поле `measured` — опциональные. Но изменение любого из них создаёт новый `id`. Они не меняют байтовое тождество и lineage-тождество — `sha256` и `root` остаются. Но record identity меняется всегда при любом изменении любого поля. Таблица полей не может называть `about` и `measured` нейтральными для тождества вообще.

[Математик]: `addedAt` — дата формата `YYYY-MM-DD…`, обязательное поле, валидатор проверяет формат. Это факт: измеренное поведение валидатора. Изменение `addedAt` тоже создаёт новый `id` — по общему правилу record identity. Порядок записей по `addedAt` не используется для определения tip или predecessor; порядок определяется только через `ep`.

[Архитектор]: Проверю конструкцию инъективности `canonicalRef`. Допустим, два root с разными `id` — два разных `canonicalRef`. Обратно: один `canonicalRef` однозначно указывает на один root, следовательно, на одну линию. Формула `"urn:mmbrn:static:" + rootId` реализует биекцию между множеством root-id и множеством canonicalRef. Альтернативных формул M2 не принимает.

[Верстальщик]: Случай «перенос» в таблице: тот же материал, новый адрес. `sha256` сохраняется, `bytes` сохраняется. Новый `id` записи, `supersedes` на старую, `location` новый. `root` линии не меняется, `canonicalRef` сохраняется. Это не редакция: байты не изменились. `source` повторяется.

[Структурщик]: Случай «редакция»: новое содержимое, новый `sha256`. `bytes` измеряется заново, числовое значение может совпасть с прежним. Новый `id`, `supersedes` на прежнюю. `root` и `canonicalRef` сохраняются — линия продолжается, новая запись становится tip. Объявлять новую линию, новый root или новый `canonicalRef` при редакции запрещено.

[Teamlead]: Случай «PDF»: поступает простой файл. Начальная запись — `id` уникален, `ep(r) = ⊥`. `sha256` отличен от `id` записи. Байты верифицируют хеш при доступе. В таблице: байты фиксируют `sha256` как контрактное тождество; запись получает новый уникальный `id`; в колонке «Линия» — фиксируем, что `ep = ⊥` и что для линии длины 1 одна запись исполняет роли root и tip одновременно.

[Музыкант]: Добавлю по случаю «sensitive»: запись в реестре полная — `id`, `sha256`, `bytes`, `addedAt`, `source`, `location` с допустимым kind и непустым `ref`, плюс `sensitive.reason`. Байты могут лежать вне репозитория. `sha256` и провенанс сохраняются в записи реестра независимо от местонахождения байтов. Реестр остаётся источником истины о факте регистрации.

[Математик]: Проверю live tip формально. Множество all_ep = { ep(r) | r ∈ R, ep(r) ≠ ⊥ }, включая вычисленные legacy-значения. Tip(r) = true тогда и только тогда, когда `id(r) ∉ all_ep`. Это точное определение; оно не опирается только на физическое поле `supersedes`, потому что legacy-связи вычисляются, а не хранятся явно.

[Архитектор]: Поле `location.kind` принимает ровно четыре значения: `local`, `affine`, `url`, `archivarius`. Это факт: измеренное поведение валидатора. `sensitive` — не kind. Чувствительность ортогональна адресу: sensitive-материал имеет обычный kind и ref, плюс отдельное `sensitive.reason`. Видимость ref — вне M2.

[Верстальщик]: Derived-строки в таблице полей: `root` и `canonicalRef`. Они не являются полями `EvidenceRecord`. `root` — роль записи с `ep = ⊥` в линии. `canonicalRef` — вычисляемый атрибут линии по формуле. Обе строки необходимы для полного контракта; их отсутствие означало бы неполную таблицу.

[Структурщик]: Строка `bytes` в таблице полей: обязательное положительное целое, размер конкретных байтов, верифицируемый при доступе к байтам. Изменение требует новой записи. Числовое значение `bytes` измеряется независимо от предыдущих записей — это факт замера, не вычисление из реестра.

[Teamlead]: По вопросу «каждый материал получает ровно одну запись» — эта формулировка запрещена. При поступлении материал получает начальную запись. Последующие состояния той же линии получают новые append-only записи. Линия растёт; реестр не мутирует.

## Итоговое решение консилиума (I1)

### Единая пропозиция

Материал `static.mmbrn.tech` управляется тремя независимыми тождествами: **байтовым** (`sha256` при принятом предположении о коллизионной устойчивости SHA-256), **record** (неизменяемый `id` строки реестра) и **lineage** (`root` — `id` записи с `ep = ⊥`). Единственный источник истины о регистрации, record/lineage identity, заявленных полях и истории — `registry.jsonl` (append-only). Байты — независимый верифицирующий предмет. Линия — конечная связная последовательность записей, связанных функцией `ep: R → Id(R) ∪ {⊥}`; root — запись с `ep(r) = ⊥`; tip — `id`, отсутствующий во множестве всех значений `ep` (включая вычисленные legacy-связи); в линии длины 1 одна запись исполняет обе роли, в линии длины больше 1 — строго разные записи. `canonicalRef = "urn:mmbrn:static:" + rootId` — инъективный вычисляемый атрибут линии.

### Таблица полей и инвариантов `EvidenceRecord`

| Поле / атрибут | Тип / статус | Роль и инвариант |
|---|---|---|
| `id` | обязательное; принимаемый инвариант M2: уникально | Неизменяемый идентификатор записи; любое изменение любого поля создаёт новый `id`; старая строка не мутирует |
| `sha256` | обязательное | Контрактное байтовое тождество (при принятом предположении о коллизионной устойчивости); при доступе к байтам — верифицируется; математическая уникальность не утверждается |
| `bytes` | обязательное; положительное целое | Размер конкретных байтов; измеряется при регистрации и заново при каждом новом состоянии; верифицируется при доступе; изменение требует новой записи |
| `addedAt` | обязательное; формат `YYYY-MM-DD…` | Дата добавления строки; валидатор проверяет формат (факт); не используется для определения порядка в линии |
| `source` | обязательное | Провенанс байтов, не автор операции; при адресной поправке — повторяется; при редакции — фиксируется заново |
| `location.kind` | обязательное; одно из: `local`, `affine`, `url`, `archivarius` | Тип адреса; `sensitive` не является kind (факт: поведение валидатора) |
| `location.ref` | обязательное; непустая строка | Адрес байтов; заявление реестра; достижимость — внешнее состояние склада |
| `about` | опциональное | Описание; изменение создаёт новый `id`; не меняет байтовое и lineage-тождество, но меняет record identity |
| `measured` | опциональное | Измеренные атрибуты; изменение создаёт новый `id`; не меняет байтовое и lineage-тождество, но меняет record identity |
| `supersedes` | опциональное | Явный effective predecessor: `ep(r) = r.supersedes`; у legacy-записей `-rN` без этого поля — вычисляется по правилу M2 |
| `sensitive.reason` | опциональное | Причина чувствительности; ортогональна `location.kind`; ref обязан присутствовать в записи реестра |
| *(derived)* `root` | не поле `EvidenceRecord` | `id` записи с `ep = ⊥` в данной линии; фиксирует lineage-тождество |
| *(derived)* `canonicalRef` | не поле `EvidenceRecord` | `"urn:mmbrn:static:" + rootId`; инъективен; сохраняется при любом продолжении линии |
