[Структурщик]: Начнём с определения. Контейнер — это граница принятия, а не механизм тождества. Положительная граница: оригиналы, внешние по отношению к системе Membrana — чеки, PDF, доклады, материалы исследований, иные первичные документы, переданные владельцем. Отрицательная граница: всё, что порождено системой из уже принятого — OCR, превью, индексные записи движка. Движок (Affine или иной) — сменная деталь; контейнер существует независимо от него. Это структурный каркас, на который ляжет контракт.

[Музыкант]: Меня интересует граница по производным. Превью и OCR — это сигналы, порождённые из оригинала: они не существуют без него, но оригинал существует без них. По аналогии с аудио: мастер-запись и её MP3-дериватив — разные объекты с разными судьбами. Контракт должен явно сказать: производное не замещает оригинал в контейнере и не является самостоятельным каноническим материалом. Важно зафиксировать это на уровне класса, не на уровне конкретного файла.

[Архитектор]: Форма контракта: три части. Первая — положительная граница (что принимается). Вторая — отрицательная граница (что отвергается). Третья — инварианты смены движка. Неизменяемость означает только одно: принятое содержание не мутирует на месте. Это не утверждение о тождестве последующих поступлений — M1 не вправе этого решать. Любое последующее поступление остаётся неклассифицированным по отношению к прежнему: ни «новый объект», ни «версия», ни «не новый объект». Это должно войти в контракт как явный пункт нейтралитета.

[Верстальщик]: С точки зрения читаемости контракта: таблица шести примеров должна быть однозначной — каждый пример ложится в ровно один класс. Предлагаю зафиксировать классы прямо сейчас: «канонический материал контейнера», «производное представление», «запись управления», «состояние движка», «предмет вне границы». Для архива исходных данных исследования: класс «канонический материал» присваивается без назначения единицы фиксации, приёма или тождества — ни архиву как целому, ни его членам. Это граница между классификацией и механизмом тождества, которую M1 не пересекает.

[Teamlead]: Два риска слышу в обсуждении. Первый: соблазн классифицировать архив как «одну запись поступления» — это запрещено до M2. Второй: соблазн объявить `docs/evidence` восстановимой через движок — это тоже запрещено. Запись управления и состояние движка — разные классы, и контракт обязан зафиксировать это явно. Нецели тоже должны войти в тело контракта: Panel — отдельный продукт, код и DNS в этой комнате не трогаем. Пока каркас держится — продолжаем.

Нейтральная форма: «отношение любого последующего поступления к прежнему содержанию не определено настоящим контрактом». Это единственная формулировка, которая не нарушает запрет. Все остальные варианты — либо положительное, либо отрицательное утверждение о тождестве. Контракт должен содержать именно эту фразу, не её синонимы.

[Структурщик]: Уточняю положительную границу. ## Итоговое решение консилиума

### Пропозиция-контракт границы `static.mmbrn.tech`

**Положительная граница (принимается):**
`static.mmbrn.tech` принимает оригиналы внешнего происхождения — первичные документы, существовавшие до и независимо от контейнера и переданные владельцем: PDF докладов, сканы чеков, архивы исходных данных исследований и иные первичные материалы.

**Отрицательная граница (отвергается как канонический материал):**
Производные представления, порождённые системой из принятого содержания (OCR, превью, кеши), страницы и служебные изображения движка, автоматически генерируемые артефакты — не являются каноническими материалами контейнера.

**Инвариант неизменяемости:**
Принятое содержание не мутирует на месте. Отношение любого последующего поступления к прежнему содержанию настоящим контрактом не определено — ни как новый объект, ни как версия, ни как не-новый объект.

**Инварианты смены движка:**
1. Каноническое содержание контейнера не зависит от установленного движка.
2. `docs/evidence` как запись управления является частью контейнера и не теряется при смене движка. Её судьба при реконструкции определяется M2, не M1.
3. Движок (включая Affine) сменяем без нарушения контракта содержания.

**Таблица шести примеров:**

| Пример | Класс |
|---|---|
| Исходный PDF доклада | Канонический материал контейнера |
| Скан чека | Канонический материал контейнера |
| Архив исходных данных исследования | Канонический материал контейнера (единица фиксации, приёма, тождества или версии не назначена ни архиву, ни его членам) |
| Превью или OCR | Производное представление |
| Запись индекса `docs/evidence` | Запись управления |
| Страница Affine | Состояние движка |

**Нецели (явный список):**
- Стратегический редактор — отдельный продукт Panel; не часть контейнера.
- Код, DNS, конфигурация прода — не изменяются в рамках M1.
- Единица тождества, приёма, фиксации, версионирование, хеши, адреса — M2.
- Модель доступа, роли, гранулярность — M3.
- Физическое хранилище, backup, retention, quota — M4.
- Детальный API и возможности Affine — M5.
- Загрузка, выдача, просмотр, мастерская вещдоков — M6.
- Судьба 82 страниц, домены, Panel, Issues — M7.
