# Консилиум: Единица владения треком и поведение двери при пустом membraneId

**Повестка:** O1 — Что считать единицей владения треком, и как дверь отвечает, когда звено цепочки отсутствует (membraneId пуст)?

**Участники:** Структурщик (Ozhegov), Teamlead (Tarasov), Музыкант (Kuryokhin), Математик (Dynin), Верстальщик (Rodchenko), Архитектор (Vesnin).

**Порядок реплик:** Структурщик → Teamlead → Музыкант → Математик → Верстальщик → Архитектор

---

[Структурщик]: Начну со словарного различения, которое здесь решающее. «Единица владения» — не «единица хранения» и не «единица адресации». Адресация в media идёт прибором (`deviceId`), это факт кода. Но адресация ≠ владение. Владение — это «кому принадлежит трек» в смысле, кто вправе открыть доступ. Цепочка `User → Membrane → Device → Collection → Sample` задаёт граф владения. Трек — это `Sample`, он принадлежит `Collection`, та принадлежит `Device`, устройство через `membraneId` — `Membrane`, мембрана — `User`. Единица владения треком, следовательно, — **пара (Device, Membrane)**: device даёт адресацию, membrane даёт принадлежность. Без membrane пара неполна.

[Teamlead]: Стоп. «Пара (Device, Membrane)» — это уже кандидат на форму контракта, а форма контракта — предмет M2, не M1. M1 спрашивает, что считать единицей владения, а не как её кодировать в запрос. Различаем: носитель факта «чей трек» и форму его передачи — это разные вопросы. Не смешивать. Ожегов, переформулируй без упоминания формы контракта.

[Музыкант]: С края тракта слышу вот что: прибор записывает трек физически — он носитель источника сигнала. Но «чей трек» — это не про источник, а про право. Можно сравнить: микрофон записывает звук, но правообладатель — студия, купившая сессию. Прибор без мембраны — как микрофон без студии: звук есть, право не определено. Так что тракт без мембраны не просто «неполный» — он не имеет субъекта права. Это важно для поведения двери: анонимный трек не значит публичный, он значит «право не установлено».

[Математик]: Формализую. Пусть функция `owner: Sample → Membrane` строится как транзитивное замыкание по цепочке. `owner(s) = membrane(device(collection(s)))`. Если `device.membraneId = null`, то `owner(s) = ⊥` — значение неопределено. Это не ошибка вычисления, это область определения функции: функция `owner` частична, она не определена для приборов без мембраны. Система должна это знать явно. Два вопроса разделяю: (1) что есть единица владения — это `membraneId` как значение в вершине цепочки; (2) что делать при `⊥` — это политика, а не математика. Политику должен назвать вердикт.

[Верстальщик]: Мне как верстальщику UI здесь не нужен — но мне нужно понимать, что оператор увидит, когда запросит «мои треки». Если единица владения не определена (membraneId пуст), оператор должен получить не пустой список с молчанием, а явный сигнал: «треки этого прибора не привязаны к мембране». Это требование к поведению двери, не к вёрстке. Дверь не может молчать — молчание на витрине оператора читается как «треков нет», а не как «права не установлены». Это два разных состояния, и они не взаимозаменяемы.

[Архитектор]: Конструкция. Цепочка `User → Membrane → Device → Collection → Sample` — это граф владения с одним корнем (`User`) и одним узлом пересечения кабинет/media (`Membrane ↔ Device`). Пересечение проходит через `Device.membraneId`. Это единственная точка, где media знает о кабинете. Убирать её нельзя — ось пользователя в media не заводить (закрыто штормом), значит `membraneId` — единственный допустимый носитель ответа «чей» в media. Единица владения треком — это `membraneId` на устройстве. Не `deviceId`, не `collectionId`, именно `membraneId`: он и только он несёт принадлежность к субъекту права.

[Структурщик]: Принимаю уточнение Тарасова. Переформулирую без формы контракта: единицей владения треком является `membraneId` — ссылка на мембрану кабинета, прочитанная из `Device`. Именно здесь живёт ответ «чей трек» в media-сервисе. `Device` — носитель этой ссылки, `membraneId` — сама ссылка. Адресация (`deviceId`) и владение (`membraneId`) — разные атрибуты одной модели, не взаимозаменяемые.

[Teamlead]: Хорошо. Теперь второй вопрос: что делает дверь при `membraneId = null`? Три кандидата звучали в комнате — отказ, владение по прибору, иное. «Владение по прибору» — значит заменить субъект права с мембраны на прибор. Но прибор в media — не субъект права, он носитель данных. Это подмена, а не альтернатива. «Иное» без определения — молчание, что запрещено вердиктом. Остаётся отказ. Но отказ с каким кодом и с каким смыслом — это надо договорить.

[Музыкант]: Отказ — правильный выбор. Но уточню жанр: это не «403 Forbidden» (нет прав у запрашивающего), это «409 Conflict» или «422 Unprocessable» (запрос структурно верен, но объект в состоянии, при котором операция невозможна). «Чьи треки» при отсутствующей мембране — не запрос без прав, а запрос к объекту без субъекта права. Это важно для диагностики: клиент должен понять, что дело не в его токене.

[Математик]: Согласен с различением. Добавлю строгость: если `owner(s) = ⊥`, то предикат `owner(s) = membrane_X` ложен для любого `membrane_X`. Значит, любой запрос вида «дай треки мембраны X» при пустом `membraneId` вернёт пустое множество — это не ошибка, а корректный пустой результат. Ошибка нужна только если запрашивается операция, требующая установленного владельца: «открыть доступ», «выдать ключ». Там `⊥` блокирует явно.

[Верстальщик]: Математик верно разделил два случая: чтение списка (пустой результат) и операция над треком (ошибка). Добавлю: пустой результат без объяснения — это та же ложь формы. Если список пуст потому что «треков нет», и пуст потому что «мембрана не установлена» — это разные пустоты. В ответе должен быть маркер или метаданные. Но это уже форма контракта — предмет M2. Для M1 достаточно: пустой membraneId → дверь не видит владельца → операции над «чьими-то треками» не выполняются.

[Архитектор]: Здесь важна граница: что кабинет говорит, и что делает media, если кабинет недоступен. Кабинет отвечает за «чьё» — это значит, кабинет хранит факт «мембрана X существует и принадлежит пользователю Y». Media хранит только `membraneId` как строку — она не проверяет его валидность в кабинете при каждом запросе. Это принципиально: media не зависит от доступности кабинета в рантайме. Она смотрит на своё поле `Device.membraneId`. Если поле пусто — владелец не установлен в media. Точка. Кабинет недоступен или доступен — для этого решения безразлично.

[Структурщик]: Это ключевая лемма. Media не ходит в кабинет при чтении треков. `Device.membraneId` — это уже материализованная ссылка, не live-запрос. Кабинет отвечает за то, чтобы при привязке прибора к мембране правильно проставить это поле. После этого media работает автономно. Поэтому «спросить кабинет» не является политикой поведения двери при пустом membraneId: кабинет уже дал ответ (или не дал) в момент записи поля. Дверь читает то, что есть.

[Teamlead]: Отлично. Фиксирую: кабинет отвечает на вопрос «чья мембрана» — один раз, при привязке, записью в `Device.membraneId`. Media читает это поле как данность. При пустом поле — данность такова: владелец не установлен. Дверь не ходит за ответом в кабинет в рантайме. Это закрывает вопрос «что делает media при недоступном кабинете»: ничего не делает иначе, чем обычно — поле либо есть, либо пусто, кабинет здесь ни при чём.

[Музыкант]: Поддерживаю. Добавлю аналогию для протокола: это как серийный номер инструмента, впаянный на заводе. Дверь читает номер с корпуса, а не звонит на завод при каждом входе. Если номер не впаян — инструмент не числится ни за кем. Завод недоступен — номер с корпуса никуда не делся.

[Математик]: Формализую итог по двум случаям. Случай 1: `Device.membraneId ≠ null`. Функция `owner` определена, запрос «треки мембраны X» выполнятся, если `membraneId = X`. Случай 2: `Device.membraneId = null`. Функция `owner = ⊥`. Запрос «треки мембраны X» → пустое множество (владелец не совпадает ни с чем). Запрос операции, требующей владельца → ошибка с явным кодом. В обоих случаях кабинет в рантайме не вызывается.

[Верстальщик]: С точки зрения контракта ответа: пустое множество при `membraneId = null` — допустимо только если запрос был «дай треки моей мембраны», и мембрана есть у запрашивающего, но устройство к ней не привязано. Тогда «ноль треков» честный. Но если запрос «дай все треки этого устройства» — пустой membraneId не влияет на результат: треки есть, они просто без владельца. Это M2 — форма запроса. Для M1 зафиксируем: единица владения — membraneId, при пустом — владелец отсутствует, не «неизвестен», а именно отсутствует.

[Архитектор]: Уточню разграничение, важное для M2: два типа запросов к двери различаются именно этим. «Дай треки по владельцу» — запрос через ось владения, ключевой для открытого API. «Дай треки по прибору» — внутренний запрос, не требующий установленного владельца. Открытое API партнёров работает через первый тип. Поэтому для открытого API устройство без membraneId — вне видимости: его треки не войдут ни в один ответ по оси владения. Это не баг — это архитектурное следствие необязательности поля.

[Структурщик]: Обозначу ещё одну лемму: необязательность `membraneId` — не временное состояние ожидания привязки, а легитимный постоянный статус. Прибор может никогда не принадлежать мембране. Это не «ошибка данных» и не «незаполненное поле». Поэтому политика дверь не должна пытаться восстановить или угадать владельца. Если поле пусто — владелец отсутствует по дизайну.

[Teamlead]: Согласен. Закрепляю: восстановление владельца по косвенным признакам — недопустимо. Дверь не угадывает. «Не привязан к мембране» — полный и окончательный ответ для целей открытого API. Движемся к вердикту.

[Музыкант]: Один вопрос перед финалом: исполнитель — кто? Архитектор назвал носителя (`Device.membraneId` в media-сервисе). Но кто реализует логику «если пусто — не выдавать»? `MediaDeviceAccessGuard`? Или это уровень сервиса выборки треков?

[Математик]: По фактуре: `MediaDeviceAccessGuard` — охрана на уровне маршрутизации, она проверяет доступ к устройству. Логика «чьи треки» — это уже внутри сервиса выборки, после прохода охраны. Исполнитель — слой выборки в media-сервисе, который читает `Device.membraneId` и фильтрует по нему. Guard — не исполнитель этой логики, он исполнитель другой: «есть ли доступ к устройству вообще».

[Верстальщик]: Поддерживаю. Guard и слой выборки — разные контракты. Guard: «пускать ли в маршрут». Выборка: «что выдавать из пущенного». Единица владения живёт в выборке, не в guard.

[Архитектор]: Итого по исполнителю: **слой выборки треков в media-сервисе** — тот, кто читает `Device.membraneId` и применяет правило «пусто → владелец отсутствует → трек вне оси владения». Guard остаётся охраной маршрута, не носителем логики владения.

[Структурщик]: Принимаю. Вердикт собран.

[Teamlead]: LGTM по существу. Выношу на фиксацию.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Что есть единица владения треком? | `membraneId` — поле модели `Device` в media-сервисе. Это единственная точка, где media хранит принадлежность к субъекту права (мембране кабинета). Не `deviceId` (адресация), не `collectionId` (группировка) — именно `membraneId`. |
| Где живёт ответ «чей трек» (носитель)? | В поле `Device.membraneId` внутри media-сервиса. Media не ходит в кабинет в рантайме: кабинет отвечает за корректную запись этого поля при привязке прибора — однократно, не при каждом запросе. |
| Кто исполняет логику владения (исполнитель)? | Слой выборки треков в media-сервисе: он читает `Device.membraneId` и применяет правило оси владения. `MediaDeviceAccessGuard` — охрана маршрута, не носитель логики «чей трек». |
| Что делает дверь при пустом `membraneId`? | Владелец отсутствует — не «неизвестен», не «ожидает привязки», а отсутствует по дизайну. Для запросов по оси владения («треки мембраны X») устройство без `membraneId` не попадает в результат: возвращается пустое множество. Для операций, требующих установленного владельца (выдача ключа, открытие доступа) — явная ошибка. Дверь не пытается восстановить или угадать владельца. |
| Что делает media при недоступном кабинете? | Ничего иначе: media читает `Device.membraneId` как материализованную ссылку. Кабинет мог быть недоступен — поле либо было записано ранее, либо нет. Логика двери от доступности кабинета в рантайме не зависит. |
| Легитимен ли статус «без мембраны»? | Да. `membraneId` объявлен необязательным по дизайну. Устройство без мембраны — полноправное состояние, не ошибка данных. Его треки просто не входят в ось владения открытого API. |

| Адресация в media идёт прибором (`/v1/devices/:deviceId/…`); охрана — `API_INTERNAL_TOKEN` + `MediaDeviceAccessGuard` | факт |

| Прибор без `membraneId` — легитимное постоянное состояние, не ошибка данных и не ожидание привязки | норма |

**Definition of Done (M1):**
- В media-сервисе зафиксировано правило: `Device.membraneId` — носитель принадлежности трека к оси владения.
- Слой выборки треков по оси владения фильтрует только устройства с непустым `membraneId`.
- При `membraneId = null` запрос «треки мембраны X» возвращает пустое множество (не ошибку); операция, требующая установленного владельца, возвращает явную ошибку с читаемым кодом.
- Логика выборки не вызывает кабинет в рантайме — работает только с полем `Device.membraneId`.
- `MediaDeviceAccessGuard` не изменяется в рамках M1: он охраняет маршрут, не несёт логику владения.
- DoD M2, M3, M4 в эту секцию не входят.
