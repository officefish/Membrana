# Консилиум: M3 — порядок гашения кода и режим отказа регистрации

**Повестка:** Q3 — в каком порядке сервер кабинета гасит код в офисе и создаёт пользователя, и что отвечает дверь регистрации при каждом исходе клиента, чтобы код не сгорал без пользователя, пользователь не появлялся без кода, а наружу уходила одна фраза?

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Музыкант (Kuryokhin), Верстальщик (Rodchenko), Математик (Dynin), Структурщик (Ozhegov).

**Порядок реплик:** Teamlead → Архитектор → Музыкант → Верстальщик → Математик → Структурщик

[Teamlead]: Комната M3. Данности M1–M2 не переоткрываем. Нужен исполняемый контракт для сессии C: порядок шагов, ответы двери, компенсация полуудач, ограничитель, DTO, зубы. Планка — контракт числами и именами, не «примерно». Границы C по M0 узкие: если трогаем `auth.dto.ts` и `auth.module.ts` — говорим это словами.

[Архитектор]: Конструкция из двух хранилищ: гашение в офисе, пользователь в базе кабинета. Атомарности «как в панели» (`panel-users.controller.ts:92–97`, один `store.mutate`) нет. Единственный порядок, который минимизирует полуудачи без отката гашения: (1) проверки без побочных эффектов, (2) удалённое гашение `redeem`, (3) локальное `user.create`. `check` до `redeem` запрещён M1 — TOCTOU.

[Музыкант]: Слышу ритм «сначала сухой прогон, потом удар по офису, потом запись». Любой параллельный «создать и гасить» даст рассинхрон двух партий — пользователь без кода или код без пользователя. Таймаут 5000 мс из M2 — это пауза в такте: после паузы без ответа офиса не пишем в базу.

[Верстальщик]: Наружу одна фраза — это конструкция экрана M4, но контракт двери M3 уже задаёт, что браузер не ветвится по `reason`. Не различать `not_found` и `exhausted` во входе формы. Тексты кнопок не трогаем — только HTTP-код и одна серверная строка-заглушка.

[Математик]: Инварианты: ¬(пользователь ∧ ¬код_погашен_успешно_с_нашей_стороны); стремимся к ¬(код_погашен ∧ ¬пользователь), но второе не гарантируется при гонке/падении `create` — кабинет гашение не откатывает (M1/M2). Значит компенсация полуудачи «гашение ok, create fail» — журнал инцидента, не сага и не ретрай `redeem`.

[Структурщик]: `AuthService` сегодня не видит клиента офиса: `auth.module.ts` без импортов модулей. Нужно явное расширение границы C: импорт модуля M2 (`office-registration`) в `auth.module.ts` и поле кода в `RegisterDto` (`auth.dto.ts`). Имя метода для C уже зафиксировано M2: `redeemRegistrationCode(code)`.

[Teamlead]: Фиксирую расширение границ: `auth.dto.ts` и `auth.module.ts` — в зоне C этого вердикта, потому что без DTO кода и без DI моста сессия C не исполнит контракт. Аудитор M0 их не назвал — комната называет. Дальше — порядок списком до буквы.

[Архитектор]: Порядок шагов в `AuthService.register(login, password, code)` строго:
1. Включение: если `ALLOW_REGISTRATION === false` **или** `APP_CONFIG.office === null` → отказ «регистрация выключена», без вызова офиса и без `create`.
2. Ограничитель частоты → при превышении 429.
3. Нормализация и длины логина/пароля (как сейчас, строки 19–21).
4. Нормализация кода (trim; пустой после trim → тот же отказ, что `refused`).
5. `findUnique` по логину → занят → отказ без гашения.
6. `hashPassword` (локально, без записи).
7. `await redeemRegistrationCode(normalizedCode)`.
8. Ветвление по `kind` исхода; при `ok` — `prisma.user.create` + `createSessionForUser`.
Иного порядка нет: гашение до локальных проверок сжигает код на опечатке логина; `create` до гашения рождает пользователя без кода.

[Музыкант]: Шаг 6 (хеш до гашения) — правильный: CPU на нашей стороне дешевле, чем повторные удары в офис. Если гашение refused — хеш просто отбрасываем, побочного следа в БД нет.

[Верстальщик]: Дверь `POST /v1/auth/register` для браузера: успех — как сегодня (сессия). Все `refused` — один код, одна фраза. Не плодим семейство сообщений «код истёк / не найден» — это M4 иначе начнёт рисовать три цвета ошибки.

[Математик]: Полуудача A: `kind === 'ok'`, затем `user.create` бросает (unique на логин в гонке, диск БД). Код в офисе уже погашен; повтора с тем же кодом нет (`exhausted`). Компенсация: (i) код считается сгоревшим; (ii) наружу — та же одна фраза, что у `refused` (не «login taken» после гашения — иначе утечка порядка); (iii) в лог — уровень error/incident: `registration_redeem_orphaned`, login, code (или hash кода), prisma message; (iv) владельцу кода — только через ops/ручной разбор панели, автоматического un-redeem нет.

[Структурщик]: Полуудача B «create прошёл, гашение неизвестно» при нашем порядке **не возникает**: `create` стоит после успешного исхода клиента. Таймаут/сеть дают `office-unavailable` — пользователя нет. Остаточный риск M2: офис мог погасить, а клиент получил таймаут и вернул `office-unavailable` — код «сирота» в офисе без пользователя. По M2 ретраев нет; компенсируем только логом warning `registration_redeem_outcome_unknown` с code и detail, наружу — «попробуйте позже». Повтор той же формы с тем же кодом: если офис не гасил — ok; если гасил — `exhausted` → одна фраза refused. Это допустимо данностями.

[Teamlead]: Складывание флагов: регистрация включена ⇔ `ALLOW_REGISTRATION === true` **и** `APP_CONFIG.office !== null`. Дизъюнкция отказа: любое из двух ложно → дверь ведёт себя как «регистрация выключена», офис не зовём. В проде `generate-cabinet-env.sh` пишет `false` — поведение сохраняем. M2-условие `office === null` — второй предохранитель, не замена флага.

[Архитектор]: Ответы двери `POST /v1/auth/register` по исходам:
- включение ложно → **401**, тело/сообщение: `Registration is disabled` (как сейчас строка 16; едино для обоих условий);
- ограничитель → **429**, `Too many requests`;
- `kind: 'ok'` и create успешен → **201/200** как сегодня + сессия (`createSessionForUser`);
- `kind: 'refused'` (любой из five `reason`) → **403**, одна фраза `Registration was not accepted`; `reason` только в серверный лог (warn);
- локальный отказ до гашения (длины, пустой код, логин занят на `findUnique`) → **403**, та же фраза `Registration was not accepted` (норма ADR-0005: наружу причины не различаем); исключение не вводим;
- полуудача A (create после ok) → **403**, та же фраза; лог incident;
- `kind: 'office-unavailable'` → **503**, `Please try again later`; пользователь не создан;
- `kind: 'config-invalid'` → **503**, `Please try again later`; лог error как инцидент конфигурации (`registration_office_config_invalid`).

Почему 403 на refused, не 401: 401 сейчас занят «выключено»; панель-прецедент — Forbidden на отказ кода. Одна фраза на refused и на локальные отказы до гашения — чтобы браузер не зондировал занятость логина отдельно от кода… Спорная точка: раньше был `ConflictException('Login already taken')`.

[Музыкант]: Зондирование логина без кода — отдельный канал. Если всегда одна фраза, перебор логинов и перебор кодов звучат одинаково — это плюс против утечки. Принимаю 403 + одна фраза и на «логин занят» до гашения.

[Верстальщик]: Согласен: один отказной рисунок. M4 не получит ветку «займите другой логин» vs «код плохой» из API — если понадобится подсказка, это уже продуктовое исключение владельца, не M3. Сессия на успехе — без смены контракта ответа.

[Математик]: Уточнение по зондированию: ограничитель обязателен, иначе одна фраза не спасает от brute-force кодов. Прецедент панели: sliding window. Предлагаю для кабинета: ключ = IP адрес клиента; окно **600_000 мс (10 мин)**; порог **10** запросов на `POST /v1/auth/register` за окно; ответ **429** `Too many requests`. Логин в ключ не включать — иначе атакующий меняет логин и обходит. Счётчик hit — до тяжёлых шагов (до bcrypt и до офиса).

[Структурщик]: Ограничитель — в `auth.controller` или в начале `auth.service.register`, по образцу `panel-users.controller.ts:56,86`. Нет общего throttle в `modules/auth` — C вносит локальный `createSlidingWindowLimiter` (тот же util, что панель, если он доступен пакетом; иначе копировать нельзя через границы — проверить импорт; при отсутствии общего — минимальный sliding window рядом с auth в границах C). Предпочтение: controller берёт IP из request, service принимает optional key или hit делается в controller до service. Чище: hit в `auth.controller.ts` на register, чтобы service оставался без HTTP.

[Teamlead]: Решение по ограничителю: нужен; ключ — IP; окно 600000 мс; порог 10; 429. Реализация hit в `auth.controller.ts` (граница C). Утилиту sliding window — только если уже есть в cabinet packages; иначе тонкий private helper в модуле auth, без новых пакетов. Не тащить panel-код кросс-приложением.

[Архитектор]: DTO: в `auth.dto.ts` поле **`code: string`**, обязательное. Нормализация в service: `trim`; пустой после trim → refused-путь без офиса. Регистр: не lower-case принудительно, если панель хранит код как есть; trim обязателен. Имя поля `code`, не `promoCode` — не смешивать с тарифным `PromoCode` кабинета (`schema.prisma:314`). Сигнатура service: `register(login, password, code)`.

[Музыкант]: Тарифный `redeemPromo` не трогаем — другая партитура. Регистрационный код только через мост M2.

[Верстальщик]: Поле `code` в API — для M4 input; подпись и placeholder не задаём здесь.

[Математик]: Гонка двух регистраций одним кодом `maxUses=1`: оба прошли findUnique, оба вызвали redeem; офис сериализует — один `ok`, второй `exhausted`→refused. Один пользователь. Гонка одним логином: оба findUnique пусто; оба redeem (два кода или один); create — один успех, второй unique fail. Если один код на двоих — риск orphan на втором redeem ok + create fail: полуудача A, лог incident. Это цена двух хранилищ; зубы C обязаны воспроизвести.

[Структурщик]: Подключение клиента: `auth.module.ts` импортирует `OfficeRegistrationModule` (M2); `AuthService` получает `OfficeRegistrationBridgeService` (или как назван провайдер M2) через constructor DI. Это расширение границы C — явно. `env.schema.ts` в M3 для ALLOW_REGISTRATION не меняем семантику строк 37/47 — только читаем; пару OFFICE_* не трогаем (M2).

[Teamlead]: Зубы C (новый файл теста auth.service или auth.register — красный вход):  
1) mock клиента `ok` → пользователь создан, сессия;  
2) mock `refused` ×5 reason — всегда 403 одна фраза, create не вызван;  
3) mock `office-unavailable` — 503, create нет;  
4) mock `config-invalid` — 503 + лог-инцидент;  
5) `ALLOW_REGISTRATION=false` — 401, mock не вызван;  
6) `office === null` — 401, mock не вызван;  
7) гонка двух redeem одним кодом maxUses=1 — ровно один create ok (mock/офис-поведение);  
8) гонка логина — один create, второй 403/фраза, при orphan-пути лог;  
9) ограничитель — 11-й запрос с одного IP → 429;  
10) полуудача A: mock ok + prisma create throw → 403 фраза + лог orphaned.  
Подмена клиента, не сеть.

[Архитектор]: Что НЕ строить: ретраи redeem; очередь/outbox; компенсирующий un-redeem; mode `check` перед redeem; кэш кодов; вторая модель кодов в кабинете; смешение с `PromoCode` тарифа; sagа/distributed transaction; изменение контракта M1/M2; тексты лендинга/формы (M4); мембрану на register (лениво при входе, `membrane.service.ts:157`).

[Музыкант]: Инцидент orphan — не «тихий провал», а слышимый лог: без метрики ops не узнает, что код сгорел зря. Имя события единое: `registration_redeem_orphaned`.

[Верстальщик]: Фраза `Registration was not accepted` — английская серверная, как текущие `Registration is disabled` / panel `code was not accepted`. Локализация UI — M4.

[Математик]: Нормализация кода: только `trim`. Не lower-case, пока M1/панель не зафиксировали case-fold; иначе ложно exhausted. Длины кода минимально: после trim length ≥ 1; верхнюю границу — 128 символов, защита от мусора до офиса.

[Структурщик]: `RegisterDto` валидация class-validator: `@IsString()`, `@IsNotEmpty()` на `code` (после trim в pipe или service). Граница файла — `auth.dto.ts`, расширена вердиктом.

[Teamlead]: Контроллер: `auth.controller.ts` register передаёт `body.code`; hit limiter по IP; не пробрасывает `reason` в response. Service не возвращает reason наружу — только throw HttpException с фиксированными строками.

[Архитектор]: Итоговая формула компенсации: кабинет **никогда** не откатывает гашение; полуудача A = сгоревший код + лог + одна фраза; полуудача B (unknown redeem) при нашем порядке = нет пользователя + 503 + лог unknown; владелец кода при orphan — ручной канал, не API кабинета.

[Музыкант]: Ритм отказа 503 vs 403: 503 — «повторите», 403 — «этот набор не примут». Браузер M4 сможет мигнуть retry только на 503 — этого достаточно без различения reason.

[Верстальщик]: 429 — отдельный рисунок «слишком часто», не смешивать с 403. Три видимых класса: выключено 401, отказ 403, позже/лимит 503/429.

[Математик]: Проверка: при `ok` payload офиса не обязан писаться в user row — грант `cabinet-register` уже израсходован; роль `user` как сейчас. Мембрана free-v1 лениво — инвариант приёмки владельца вне register.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Порядок шагов | 1) отказ если `ALLOW_REGISTRATION === false` **или** `office === null`; 2) ограничитель по IP; 3) нормализация/длины login/password; 4) `code = trim(code)`, пустой или length>128 → отказ без офиса; 5) `findUnique(login)` занят → отказ без офиса; 6) `hashPassword`; 7) `redeemRegistrationCode(code)`; 8) только при `kind==='ok'` → `user.create` + `createSessionForUser`. Иначе — не создавать. |
| Почему так | Нет общей транзакции двух хранилищ; `create` до гашения даёт пользователя без кода; гашение до проверок сжигает код на валидации; `check` запрещён M1. |
| Компенсация A: redeem ok, create fail | Код сгорел; повтор того же кода невозможен (`exhausted`); наружу 403 `Registration was not accepted`; лог error `registration_redeem_orphaned` (login, code, ошибка БД); un-redeem нет; разбор — ops/панель вручную. |
| Компенсация B: исход redeem неизвестен (таймаут) | При принятом порядке `create` не вызывается; ответ 503 `Please try again later`; лог warn `registration_redeem_outcome_unknown`; ретрай клиента M2 нет; возможен сирота в офисе без пользователя — допустимо данностями. Сценарий «create прошёл при неизвестном гашении» **запрещён порядком**. |
| Исход `ok` | Как сегодня: пользователь + сессия; HTTP успех двери register без смены контракта сессии. |
| Исход `refused` (5 reason) | HTTP **403**, фраза **`Registration was not accepted`**; `reason` только в лог. |
| Локальный отказ до redeem (длины, код пустой, логин занят) | HTTP **403**, та же фраза; офис не звать. |
| `office-unavailable` | HTTP **503**, **`Please try again later`**; пользователь не создан. |
| `config-invalid` | HTTP **503**, **`Please try again later`**; лог error `registration_office_config_invalid`. |
| Регистрация выключена | `!(ALLOW_REGISTRATION && office≠null)` → HTTP **401**, **`Registration is disabled`**; mock/офис не вызывать. |
| Ограничитель | Нужен; ключ = IP; окно **600000** мс; порог **10**; HTTP **429**, **`Too many requests`**; hit в `auth.controller.ts` до service. |
| DTO | `auth.dto.ts`: обязательное поле **`code: string`**; нормализация trim в service; не смешивать с тарифным promo. |
| Подключение клиента | `auth.module.ts` импортирует модуль M2 `office-registration`; DI в `AuthService`; расширение границы C — явное. |
| Зубы C | Mock всех kind; оба флага выключения; 429; гонка кода maxUses=1; гонка логина; orphan create after ok; reason не в HTTP-теле. |
| Что НЕ строить | un-redeem, ретраи, outbox, check-before-redeem, кэш кодов, вторая система кодов, трогать тарифный PromoCode, мембрану на register, контракты M1/M2, UI-тексты M4. |
