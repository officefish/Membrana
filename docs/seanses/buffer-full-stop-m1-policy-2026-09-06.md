Форма: носитель = запись прибора на сервере записей.

[Teamlead]: Планка ясна. M1 закрывает только «где живёт и как доходит». Не лезем в код отказа, остановку на приборе, окно оператора. Связка после вердикта: Структурщик — контракт поля и разноски, Верстальщик — место в кабинете, Музыкант — чтение на клиенте подчинением серверу.

Поле в кабинете как единственный source of truth без копии на records — нарушает T1 и плодит связанность client→cabinet для полевого тракта.

[Верстальщик]: Фактура UI: страницы настроек прибора нет; у мембраны — блок «Сменить тариф»; узлы — список и ключи. Отдельную «страницу прибора» под одну галку не плодим без нужды. Подтверждение включения «на всех» — явный диалог, не тихий checkbox.

[Математик]: Формализую fail-closed. Пусть домен политики `P ∈ {stop, smart-cleanup}`. Функция чтения: `effective(P_stored) = stop`, если `P_stored ∈ {⊥, null, undefined, unknown, corrupt}`; иначе `P_stored`. Миграция старых приборов: отсутствие поля → `stop`, не `auto-cleanup`. Клиентский дефолт `auto-cleanup` сегодня — анти-инвариант; его надо инвертировать. Численно: один бит режима + обязательные параметры второго режима либо ⊥.

[Музыкант]: Подчинение на тракте: плагин записи больше не владеет истиной. Он **читает** `bufferPolicy` с сервера записей (при старте сессии/синхроне контекста прибора) и исполняет. Локальный кэш — только зеркало с TTL/версией, при сомнении — `stop`. Иначе снова «ночь с авто-очисткой из локальных настроек».

[Архитектор]: Вариант «поле только в кабинете, прибор читает cabinet» дороже: cabinet становится runtime-зависимостью захвата, records остаётся без политики при 413, раскол квоты и политики. [Teamlead]: Принимаю records + разноска. BLOCK любой схеме, где клиентский `auto-cleanup` остаётся дефолтом после привязки. M2/M3 не трогаем, но M1 обязан гарантировать: первая привязка и апдейт старого → `stop`.

[Структурщик]: Механизм разноски — тот же пайплайн, что квоты/лимиты: cabinet при привязке и при смене политики мембраны/тарифного контекста пушит в records по всем приборам мембраны со счётом «обновлено/не удалось». Галочка «применить ко всем» = привязка: пока true, source of truth для каждого device.policy — membrane.policy (в т.ч. будущие приборы); false — у device остаётся/возвращается собственное значение. [Верстальщик]: UX привязки: снятие галочки возвращает приборам их настройки — на витрине сразу видны per-device значения, не «пусто». ## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| (а) Носитель | **Сервер записей**, поле (контракт) политики переполнения **в записи прибора**, с **разноской из кабинета** по тому же классу, что квоты/лимиты. Не «только кабинет, прибор читает cabinet». Origin команды — кабинет; runtime carrier — records.device. Клиентский `bufferPolicy` — mirror, не master. |
| (б) Место в кабинете | **Страница мембраны**: режим + параметры + галочка «применить ко всем» (**привязка**, не снимок) + при снятой привязке — per-device режим в списке узлов на той же витрине. Отдельную страницу настроек прибора в M1 **не** строим. Включение привязки — с явным confirm. |
| (в) Умолчание и fail-closed | При **первой привязке** и при **обновлении/миграции старого** прибора режим = **`stop`**. Гарантии: backfill → stop; DEFAULT/NOT NULL после backfill; reject unknown enum; `effective(⊥/corrupt/sync-fail) = stop` на records и на client; запрет fallback на legacy `auto-cleanup`. |
| (г) Умная очистка | Выбираема **только** при `paramsComplete(S)`. Каркас S (без алгоритма T12): порог срабатывания, критерий отбора, защита вещдоков (запрет-лист/флаги). **Проверяет сервер** (cabinet при записи + records при разноске); UI disable — UX. Пустой/частичный S → режим не записывается. |
| Что строить | Поле policy+S на records.device; разноска cabinet→records; UI на MembranePage; миграция/backfill stop; гейт S; client read/mirror + stop fallback. |
| Что НЕ строить | Master-политика в плагине; дефолт `auto-cleanup`; чтение policy прибором через cabinet; snapshot-галочка; автозаполнение S «для удобства»; алгоритм очистки (T12); форма кода отказа (M2); остановка на приборе (M3); каналы M4; окно M5; тарифы #2297. |

### Definition of Done (только M1)

1. На records.device существует носитель режима + S; в стволе/миграции все существующие ряды = `stop`.
2. Разноска из кабинета при привязке и смене политики/привязки; счёт updated/failed.
3. MembranePage: управление режимом, S, apply-to-all (binding + confirm), per-device при off.
4. API отвергает `smart-cleanup` без `paramsComplete(S)`.
5. Client не использует local auto-cleanup как source of truth; при дыре синка — effective stop.
6. Тесты на backfill, effective(⊥)=stop, reject incomplete S, binding-семантику (новые приборы слушают мембрану пока flag on).

# Заседание «Полный буфер: контракт остановки» — M1 (P) Политика на сервере и её место

**Объединяющее задание (одно на всё заседание):** превратить тезисы шторма 06.09 в исполнимый
контракт остановки при полном буфере — сервер, прибор, оператор, — чтобы ночь 05→06.09 не
повторилась и вещдоки в буфере не пострадали.

**Порядок M0 (ратифицирован владельцем 06.09):** M1 (P) политика на сервере → M2 (C) код
отказа → M3 (S) остановка на приборе → M4 (L) жизнь после остановки → M5 (W) окно оператора.
Это M1 — первый узел, предшественников нет; посылки — только данности шторма, фактура и
вердикт M0.

## Данности (закрыто штормом, НЕ переоткрывать)

- Умолчание политики — «стоп»; умная очистка — только осознанный выбор при заданных параметрах (вердикт владельца 06.09).
- Политика — у каждого прибора; галочка «применить ко всем» — ПРИВЯЗКА к мембране (не снимок): пока стоит, источник истины — политика мембраны для всех приборов, включая будущие; снятие возвращает приборам их настройки; включение — с явным подтверждением (T13, T17).
- Режим задаётся на сервере; клиент читает его и подчиняется (T1). Место настройки владельцем НЕ названо.
- Буфер — архив вещдоков; чистит только оператор вручную или алгоритмы второго режима (T7); алгоритм второго режима — вне заседания (T12).

## Фактура (сверено в стволе da051639 и на проде 06.09)

- Сегодня политика живёт ТОЛЬКО на клиенте: плагин записи хранит `bufferPolicy` в своих настройках, умолчание `auto-cleanup`; сервер о политике не знает и отказывает одинаково (413 «квота прибора исчерпана»).
- Контекст мембраны (квоты, каталог, лимиты) разносится с кабинета на сервер записей при привязке прибора и при смене тарифа (разноска по всем приборам мембраны, с счётом «обновлено/не удалось»). Носитель на сервере записей — запись прибора; поле политики в ней отсутствует.
- В кабинете страница мембраны несёт блок «Сменить тариф»; страницы приборов (узлы) — список узлов и ключи; настройки прибора как отдельной страницы нет.
- Серверная очистка буфера — две ручные ручки «план/исполнить» без расписания и без параметров политики; вызовов за ночь ноль.
