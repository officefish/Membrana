# Консилиум: M4 — две памяти в тарифной сетке (горячая / холодная)

**Повестка:** Как тарифная сетка выражает две памяти — горячую (область, доступную детекторам для пользовательских задач) и холодную (хранилище треков): двумя отдельными ячейками рода `quota`, одной ячейкой с разделением или иначе? Единственный вердикт M4 — выбранная форма выражения с основаниями, правило учёта занятого (кто считает и в какой момент) и поведение при исчерпании каждой из памятей. Список посылок обязателен.

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Структурщик (Ozhegov), Математик (Dynin), Музыкант (Kuryokhin), Верстальщик (Rodchenko).

**Порядок реплик:** Верстальщик → Структурщик → Архитектор → Математик → Музыкант → Teamlead

[Верстальщик]: С витрины кабинета и борда две памяти обязаны читаться без легенды: «горячая» и «холодная» — разные роли, не «старое / новое». Если спрятать обе в одну полоску «хранилище N ГБ», оператор не поймёт, почему детектор отказал при «свободном месте». Требую в контракте данных две честные метки занятости и две зоны исчерпания — пустота тоже честна: `0 / limit`, не «—».

[Структурщик]: Начинаю со словаря, иначе снова синонимы. **Горячая память** — квота области, из которой детекторы и пользовательские задачи читают/пишет рабочий объём. **Холодная память** — квота хранилища треков (media/library). **Ячейка quota** (M1) — `EntitlementValue` kind `quota{limit, unit}`. На дереве сегодня: `userStorageQuotaBytes` и `bufferQuotaBytes` — холодной квоты как id **нет**. M1 записала «hot/cold — два quota id» вне очереди; эта комната пересматривает форму заново.

[Архитектор]: Конструкция: сетка — author прав (M1–M2), не движок учёта байтов. Форма выражения — сколько `entitlementId` рода quota и какие unit/семантика. Варианты с ценой: (A) два id quota; (B) один id + внутренний split ratio; (C) один storage + hot как instrument/gated. Цена B — скрытая семантика вне kind-union; цена C — hot перестаёт быть числовым потолком. Рекомендую не смешивать роли в одной ячейке: роль ≠ возраст, это слово владельца.

[Математик]: Формализую без UI. Пусть \(H\) — occupied hot (байты), \(C\) — occupied cold, \(L_h, L_c\) — limits из сетки. Инварианты: \(0 \le H \le L_h\), \(0 \le C \le L_c\), **независимо**: исчерпание \(H\) не вычитает из \(L_c\) и наоборот. Предикат допуска записи в контур \(x \in \{hot, cold\}\): `admit(x, Δ) ⇔ occupied(x) + Δ ≤ L_x`. Одна ячейка с ratio r даёт \(L_h = r·L\), \(L_c = (1-r)·L\) — лишняя переменная без входа владельца (у «Блокпоста» явно 2+2, не «4 с долей»).

[Музыкант]: На слух это две шины, не один fader с меткой «архив». Холодная — tape library треков; горячая — working set, который детекторы трогают в задаче. Возраст take роли не меняет — владелец опроверг «архив = финал цикла». `bufferQuotaBytes` слышу как live-буфер concurrent devices, не как hot-память детекторов: другое назначение, другой клиппинг. Не склеивать buffer и hot ради экономии id.

[Teamlead]: Планка матча: форма выражения + кто считает occupied + что при hard stop. Не лезем в M5 (produce), M6 (смена SKU), M7 (зубы), M8 (план интеграции целиком). M1 «два quota id» — не якорь; если придём к тому же — только своими основаниями. Связка: Архитектор/Структурщик — id и homes учёта; Математик — предикаты admit/exhaust; Музыкант — не смешать buffer; Верстальщик — честные два индикатора. Поехали по существу.

[Верстальщик]: Вариант B (одна ячейка, split) на витрине потребует либо лжи «осталось X», либо второго ряда, вычисленного клиентом из ratio — декор-логика в JSX. Вариант A даёт два progress с `tabular-nums` и двумя aria. Исчерпание: soft на витрине (M3), hard на борде/сервере — два разных бейджа «квота горячей исчерпана» / «хранилища треков», не общий «storage full».

[Структурщик]: Леммы id. Предлагаю словарно: `hotMemoryQuotaBytes` (или `detectorWorkingSetQuotaBytes`) и `coldStorageQuotaBytes` (треки). Существующий `userStorageQuotaBytes` — кандидат в **синоним/переименование** в cold, не третья сущность: один термин — один смысл. `bufferQuotaBytes` остаётся отдельной леммой live-buffer; в M4 не сливаем. Учёт occupied — не в `resolveEntitlement`: pure резолв только limit; occupied — runtime meter с home на сервере.

[Архитектор]: Граница модулей: `TariffGridDocument` хранит **limits**; **occupied** — состояние ресурса пользователя/мембраны, не поле матрицы SKU. Кто владеет счётчиком: сервер (media для cold tracks; контур рабочей области детекторов/office для hot). Клиент получает wire: `{ limit, occupied, unit }` как DTO проекции, не как author. Deny-by-default: нет entitlement id → нет права писать в контур.

[Математик]: Момент учёта. Для cold: `occupied_c` пересчитывается при commit/delete объекта трека (size on disk / content-length), атомарно с метаданными library. Для hot: `occupied_h` — сумма байт объектов в working-set namespace (загрузки задач, промежуточные окна, явно удерживаемые буферы детектора), не «возраст файла». Reserve-on-intent: `reserve(x,Δ)` до записи, `commit`/`release` после; иначе гонка двух устройств съест лимит без hard fail.

[Музыкант]: Reserve слышу правильно: без pre-flight два concurrent capture упрутся в клиппинг «после факта» — хуже, чем отказ на count-in. Hot не должна молча выталкивать cold-треки и наоборот: разные шины, mute одной не освобождает другую. При исчерпании hot — задача/детектор не стартует или не дописывает working set; playback треков из cold жив. При исчерпании cold — нельзя сохранить/загрузить новый трек; live-детект на hot может продолжаться, если H свободен.

[Teamlead]: Фиксирую развилку для вердикта: клонюсь к **двум quota id** своими основаниями — разные роли, независимые инварианты, разные homes учёта, разные UX-исчерпания. Buffer — третья квота, вне пары hot/cold. Сид `free-v1` 1 ГБ vs слово владельца 512 МБ на «Датчике» — **не предмет цифр этой комнаты**, но носитель cold id должен позволить сиду совпасть с решением владельца позже (T5). Дальше — исчерпание и fail-closed.

[Верстальщик]: Поведение UI при exhaust: не общий toast «память кончилась». Cold full — alert на library/upload, CTA понятен («освободите треки» / «тариф»). Hot full — состояние на зоне задач/детекторов, `aria-live="polite"`, без притворства что upload трека виноват. Пустой occupied при нуле объектов — `0`, не скрытие progress. Соответствие DESIGN: danger только на hard block действия, не на всю карточку тарифа.

[Структурщик]: Контракт kind не расширяем: обе памяти — `quota{limit, unit:"bytes"}`. Не invent kind `splitStorage`. Преcondition (M3) — для gated-инструментов; исчерпание квоты — **не** unmet precondition, а runtime denial `quota_exceeded` с `entitlementId`. Иначе троичность M3 размоется: «право есть, условие не выполнено» ≠ «лимит съеден». Словарь ошибок — закрытый enum на сервере, клиент мапит в бейдж.

[Архитектор]: Согласен: exhaust ≠ precondition. Форма: матрица SKU даёт limit; enforcement point пишет deny с id квоты. Альтернатива «одна квота + policy module» отвергаю: policy вне сетки = второй author прав, ломка M2. Затронутые модули (форма, не код сегодня): entitlement registry ids; media-library учёт cold; сервис/контур working-set hot; pure `resolveEntitlement` без occupied; DTO статуса квот для кабинета. ADR не обязателен, если вердикт M4 ляжет в канон заседания.

[Математик]: Предикаты исчерпания: `exhausted(x) ⇔ occupied(x) ≥ L_x`. `hardDenyWrite(x, Δ) ⇔ ¬admit(x,Δ)`. Чтение (list, playback, get metrics) **не** зависит от exhausted того же x — только write/reserve. Идемпотентный delete уменьшает occupied; overflow запрещён: сервер не принимает commit > reserve. Метрика для M8/зубов позже: `quota_deny_count{id}` — здесь только контракт, порогов не ставим (как C5 памяти персон: счётчик без threshold в контракте).

[Музыкант]: Edge: «детектор пишет результат в library как трек» — это cold commit, режет cold, не hot. «Детектор держит окно/кэш feature для задачи пользователя» — hot. Если продукт смешает пути без метки контура — снова один fader и клиппинг доверия. Прошу в DoD явное правило классификации байта: каждый write path объявляет `memoryClass: hot | cold | buffer`, иначе structural fail на ревью.

[Teamlead]: Правило классификации байта — в вердикт. Связка на исполнение после заседания: Структурщик — id в registry и запрет синонимов; кто будет в M8 — провод enforcement. Здесь не колонизируем M8 планом интеграции всего кабинета. Нужен ещё отпор варианту «cold = userStorage, hot = buffer»: buffer про concurrent devices / live ring, hot про working set задач — разные нагрузки, разные единицы смысла.

[Верстальщик]: Если hot подменят buffer на витрине, подпись «буфер записи» vs «память детекторов» разъедется с фактом — фальшивая этикетка. Рисую требование к copy: три строки квот максимум (hot / cold / buffer), каждая с role-subtitle из канона, не из маркетинга SKU. Числа — только из wire DTO, не хардкод «2 ГБ» в JSX.

[Структурщик]: Итого лемм учёта. **Meter home cold:** background-media / media-library index (сумма size треков пользователя). **Meter home hot:** серверный контур working-set (office или выделенный storage-accounting — имя пакета в M8, не здесь); клиент не sum-ит localStorage как truth. **buffer:** как сейчас задумано engine/device path — вне M4 pair. Публичный read API: `getQuotaUsage(userId) → Record<entitlementId, {occupied, limit}>` — фасад, не протечка внутренних таблиц.

[Архитектор]: Форма выражения — **окончательно A**: два отдельных `entitlementId` рода quota в registry + матрица SKU→limit. Основания: (1) роль≠возраст; (2) независимые инварианты admit; (3) разные enforcement homes; (4) M2 — числовые потолки = quota cells, не catalog rail; (5) kind-union не расширяем. Переименование `userStorageQuotaBytes` → cold-id — миграция словаря сида, не новая концепция. M1 совпала по выводу; основания — наши, перечисленные.

[Математик]: Поведение при исчерпании — таблица истинности: cold exhausted ⇒ deny create/upload/copy-in track; allow delete/read. Hot exhausted ⇒ deny reserve/write working-set и старт задачи, требующей Δ>remaining; allow read-only detect? — уточню: **новый** захват working-set deny; уже reserved — commit в рамках reserve. Нет auto-evict между классами (нет silent GC cold→free hot). Нет negative occupied: floor 0.

[Музыкант]: Auto-evict «почистим старые треки за пользователя» — как ножницы по master-tape без индикатора; только manual или отдельный product-жест вне M4. При hot full честный stop задачи лучше, чем quality degrade «втихаря» (урезание окон детектора без сигнала) — это клиппинг смысла, Музыкант против. Signal пользователю обязателен на hard path.

[Teamlead]: Вердикт собираю. Форма: два quota id. Учёт: серверные meters по class, reserve/commit для write, limit из сетки. Исчерпание: hard fail-closed на write path своего class; read/delete по правилам Математика; без cross-evict; exhaust ≠ precondition. Buffer не в паре. Цифры SKU — вход, не спор. Возражения последним кругом — или «принимаю».

[Верстальщик]: Принимаю. Витрина: два (или три с buffer) честных meter; soft-притемнение CTA upload при cold near-full — опционально UX, hard — ответ сервера. Не рисую admin-дашборд набора — вне контура.

[Структурщик]: Принимаю. Леммы id и запрет второго author occupied в клиенте. `resolveEntitlement` остаётся pure limit/catalog/gate; usage — отдельный порт.

[Архитектор]: Принимаю. Конструкция A, границы limit vs occupied соблюдены. Совпадение с M1 по «два id» — зафиксировать как независимое подтверждение, не как зависимость от out-of-order.

[Математик]: Принимаю. Инварианты \(H,C\) независимы; `admit`/`exhausted`; reserve-протокол как обязательная семантика write path.

[Музыкант]: Принимаю. Две шины, buffer отдельно, no silent cross-mute, no auto-evict tape.

[Teamlead]: LGTM комнаты. Матч M4 сыгран: форма, учёт, исчерпание. Не тащим M5–M8. Запись в протокол — таблица + посылки + DoD только M4.

[Верстальщик]: Уточнение в DoD: контракт DTO usage для витрины — поле `memoryClass` / id квоты + occupied/limit; без этого UI снова склеит подписи. Это не layout, а data-contract потребителя.

[Структурщик]: Внесу в словарный след: enum `MemoryClass = hot | cold` (+ `buffer` вне пары, но в том же metering vocabulary). Write path without class = `нарушена слабая связанность` / fail review.

[Архитектор]: Последнее: сиды SKU обязаны заполнять **оба** id; пустой limit ≠ infinite — deny-by-default (нет строки матрицы → нет права). Явный `limit: 0` допустим как «контур закрыт тарифом».

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Форма выражения hot/cold в сетке | **Две отдельные ячейки** рода `quota` с разными `entitlementId` (рабочие имена-леммы: cold ← хранилище треков, напр. эволюция `userStorageQuotaBytes` → `coldStorageQuotaBytes`; hot ← working-set детекторов/задач, напр. `hotMemoryQuotaBytes`). Unit: `bytes`. Kind-union **не** расширять. |
| Альтернативы | **Отвергнуты:** (B) одна quota + split/ratio; (C) hot как non-quota (instrument/gated без limit); (D) hot ≡ `bufferQuotaBytes`. |
| Основания выбора A | Роль≠возраст (P4); независимые инварианты occupied/limit; разные homes enforcement; M2 — потолки = quota cells; один author прав; витрина без клиентской семантики split; совпадение с записью M1 — **независимое**, не subordinate. |
| `bufferQuotaBytes` | **Третья** квота вне пары hot/cold; в M4 не сливать и не переименовывать в hot. |
| Что в сетке vs runtime | Сетка/матрица SKU задаёт только **limit**. **Occupied** — серверное состояние ресурса, не поле author-матрицы. |
| Кто считает occupied | **Сервер.** Cold: контур media/library (сумма размеров треков). Hot: контур working-set учёта (конкретный пакет/home — в интеграции, не пересмотр M1). Клиент не source of truth. |
| Момент учёта | Write path: **reserve → commit | release** с `memoryClass` / entitlementId. Cold: пересчёт при успешном commit/delete объекта трека. Hot: учёт объектов working-set и резервов задач. Чтение/list/playback не увеличивает occupied. |
| Классификация байта | Каждый write path **обязан** объявить class `hot \| cold` (buffer — свой path). Запись без class — дефект контракта на ревью. |
| Поведение при исчерпании cold | Hard deny на create/upload/copy-in; allow read/playback/delete. Нет auto-evict. |
| Поведение при исчерпании hot | Hard deny на reserve/write и старт задачи с Δ>remaining; commit в рамках успешного reserve допустим; read-only не маскирует deny на write. Нет silent degrade окон. Нет cross-free из cold. |
| Исчерпание vs M3 | `quota_exceeded` — **runtime denial** с id квоты, **не** `unmetPreconditions`. |
| Absent limit vs 0 | Нет строки матрицы / нет entitlement → deny-by-default (не ∞). Явный `limit: 0` → контур закрыт. |
| Витрина | Два независимых meter (occupied/limit); раздельные сообщения hard-deny; soft warning near-full не подменяет server deny (M3). |
| Цифры SKU («2+2», 512 МБ «Датчик») | Вход владельца; сиды приводятся к нему отдельно (T5) — **не** вердикт M4 о величинах. |

1. В каноне/вердикте заседания зафиксированы **два** `entitlementId` рода `quota` (hot и cold) с определением роли одной фразой каждое; `bufferQuotaBytes` явно вне пары.

3. Зафиксированы предикаты `admit` / `exhausted` и семантика **reserve/commit/release** для write path.
4. Зафиксирована таблица hard-deny при исчерпании **по каждому** class без cross-evict и без отождествления с precondition.
5. Зафиксирован обязательный `memoryClass` (или эквивалент entitlementId квоты) на write path.
6. Словарь ошибок: runtime `quota_exceeded` + id; витринные подписи разведены (hot vs cold).
7. Нет обязательств M5–M8, нет цифр лимитов SKU, нет миграций пользователей, нет admin-UI набора в DoD.
