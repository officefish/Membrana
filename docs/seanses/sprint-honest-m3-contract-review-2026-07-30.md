# Консилиум: ревью контракта исполнителем (sprint-honest M3)

**Повестка:** когда наступает ревью контракта исполнителем; что судит (соответствие сделанного контракту, НЕ качество кода); форма вердикта как вещдок-записи; что при расхождении «сделано ≠ контракту». Предмет — формат спринта. Вход (не спорим): M1 — исполнитель есть проекция; M2 — контракт из трёх полей, принятие вещдоком. Чужие вопросы 4–9 не решать.

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Структурщик (Ozhegov), Математик (Dynin), Музыкант (Kuryokhin), Верстальщик (Rodchenko).

**Порядок реплик:** Верстальщик → Математик → Архитектор → Структурщик → Teamlead → Музыкант

[Верстальщик]: С витрины капитана и агента: «ревью» без момента и без честного исхода — декор. Нужны два читаемых состояния рядом с карточкой спринта: `contract-review: pending | pass | fail`, и отдельно — code-review/LGTM/ship. Не смешивать бейджи. Пустота: если окно закрыто, а вердикта нет — `missing`, не прочерк.

[Математик]: Формализую без UI. Пусть C — контракт спринта (M2, три поля), D — след исполнения (evidence bundle), p — исполнитель как проекция (M1). Предикат ревью: `match(C, D) → {pass, fail(diff[])}`. Независимо: `codeQuality(PR) ∈ {LGTM, BLOCK}` и `shipOk(HEAD)` — другие предикаты, другие homes. R_contract ⇔ match, не quality.

[Архитектор]: Граница ясна: ревью контракта — слой *формата спринта*, не слой кода. Home вердикта — вещдок рядом с принятием контракта (M2), не комментарий в PR и не check ship-gate. Когда: после того, как исполнитель заявил «сделано» и приложил D; до или ортогонально code-review — но никогда *вместо* него и никогда *как* LGTM.

[Структурщик]: Леммы, иначе синонимы. **ContractReview** — именованный акт: subject = performer projection (M1), object = Contract (M2), input = EvidenceDone, output = VerdictRecord. **VerdictRecord** — вещдок-запись, не chat-реплика. **diff[]** — список полей/пунктов контракта, где D ⊭ C. Не путать с `code-review:pr` и не класть в тот же файл, что LGTM тимлида.

[Teamlead]: Планка матча: честное закрытие спринта, не «красивый PR». Ревью контракта — обязательный кадр *после* заявления done исполнителем и *до* пометки спринта accepted/closed по смыслу контракта. LGTM по коду и ship по HEAD — другие ворота. Связка: Математик — предикат match; Структурщик — леммы и home записи; Архитектор — граница слоёв. Чужие 4–9 не трогаем.

[Музыкант]: На слух это прослушивание партитуры *тем, кто играл*, не мастеринг и не gate на шине CI. Партитура = C (M2). Take = D. Исполнитель говорит: «я сыграл то, что в партитуре» — и оставляет метку на ленте. Клиппинг доверия: зелёный ship при fail match — mono-take с фейковым аплодисментом.

[Верстальщик]: Когда рисовать бейдж: не в начале спринта (там contract accepted — уже M2), а в момент `done-claimed`. Три честных исхода на витрине: pass / fail+причина / missing (заявили done, вердикта нет). Fail не красится как «code BLOCK» — другая пиктограмма/строка, иначе оператор читает «плохой код» вместо «не то сделали».

[Математик]: Момент t_review: `doneClaimed(S)=true ∧ ∃ D=Evidence(S)`. До doneClaimed предикат match не определён (нет области). После: тотальность — ровно один VerdictRecord на пару (S, C.version). Инвариант: `closed_by_contract(S) ⇒ verdict=pass`. Иначе закрытие по контракту запрещено. quality и ship в импликацию не входят.

[Архитектор]: Форма решения: один артефакт `ContractReviewVerdict` с полями минимум: sprintId, contractRef (id+version), performerRef (projection M1), claimedDoneAt, verdict ∈ {pass,fail}, diff[] (пусто ⇔ pass), evidenceRefs[], createdAt, authorSlot=performer. Не расширять quality-полями. Цена альтернативы «вердикт = комментарий в PR»: потеря адресуемости и смешение слоёв — отклоняю.

[Структурщик]: Home записи: рядом с home контракта и принятия (M2) — тот же контур sprint-format (реестр/карточка/вещдок-цепочка), **не** `docs/seanses` как замена, **не** status check ship. Имя леммы: `contract-review-verdict`, не `review` голый. Связь: Contract --reviewed-by→ VerdictRecord; VerdictRecord --cites→ EvidenceDone; VerdictRecord --about→ PerformerProjection.

[Teamlead]: Расхождение «сделано ≠ контракту» = fail. Не «допилите код», а **возврат в исполнение по контракту**: либо D дополняется до C, либо контракт явно переоткрывается/меняется отдельным актом (это уже не silent edit). Тихий pass при непустом diff — BLOCK по духу бестиария (молчаливый зелёный). Кто чинит код-стиль — не эта комната и не этот вердикт.

[Музыкант]: Fail на слух — «take не попал в партитуру»: переиграть пассаж, не EQ на мастеринге. Pass — «ноты те, что написаны», даже если тембр спорный: тембр = code-review. Если исполнитель пишет fail и тут же закрывает спринт — обрыв ленты; нужен запрет машинный или процедурный: fail ⇒ sprint остаётся open по контрактной оси.

[Верстальщик]: На карточке при fail витрина обязана показать `diff[]` коротко: пункты контракта, не эссе. Одна строка на пункт + ссылка на evidence. При pass — `contract-review: pass` и id вердикта, без фейерверка. Missing после done — жёлтый, как stale: «заявлено сделано, сверки нет».

[Математик]: diff формально: для каждого атомарного обязательства o ∈ obligations(C) (из трёх полей M2 — развёртка в проверяемые clauses): `sat(o,D) ∈ {0,1}`; `diff = { o | sat=0 }`; `pass ⇔ diff=∅`. Не вводим score 0…1 — бинарь по контракту, иначе снова «почти» как у Тарасова не проходит. Три поля C не переопределяем — только operationalize в clauses на уровне процедуры позже.

[Архитектор]: «Кто судит» по M1: author вердикта = performer projection, не аудитор и не тимлид-LGTM. Тимлид может *не принять закрытие* без pass, но не подменяет текст match. Иначе снова «исполнитель = строка», а судит сосед — M1 ломается. Граница: self-review контракта ≠ self-merge кода.

[Структурщик]: Словарь исходов расхождения, закрытый: (1) **amend-evidence** — D неполон, C тот же; (2) **rework** — D опровергнут, C тот же, новое исполнение; (3) **contract-change** — нужен новый C (новый version + принятие вещдоком M2), старый verdict остаётся на старом contractRef. Silent overwrite C запрещён. Четвёртого «ну почти pass» нет.

[Teamlead]: Когда наступает — фиксирую приказом комнаты: **триггер = done-claimed исполнителем при наличии C accepted (M2)**. Не календарный конец спринта сам по себе, не merge PR, не green CI. Если done не заявлен — ревью контракта не стартует (нет матча). Если заявлено и молчание — missing, планка не сыграна.

[Музыкант]: Ортогональность шин: шина A — contract match (этот вердикт); шина B — code-review:pr; шина C — LGTM тимлида; шина D — ship HEAD SHA. Можно услышать pass на A и BLOCK на B — это не парадокс, это два разных прослушивания. Путать ручки — клиппинг смысла спринта.

[Верстальщик]: Не рисую UI продукта. Для агентской/капитанской витрины sprint-format: блок «Контракт» (M2) → блок «Исполнитель» (M1 assigned/participated) → блок «Сверка контракта» (verdict+diff) → отдельно «Код/ship». Порядок глаз = порядок честности.

[Математик]: Идемпотентность: повторный done-claim без смены C.version и без нового D не плодит второй pass; новый VerdictRecord только если изменился D или C.ref. Иначе `supersedes` связь на предыдущий id. Инвариант один актуальный verdict per (S, contractVersion).

[Архитектор]: Цена «ревью после merge only»: контрактная ось опаздывает, спринт уже «закрыт» кодом. Отклоняю как единственный триггер. Допускаю *параллель* с PR, но канонический триггер — done-claimed, а не merge. Ship-gate остаётся на HEAD; contract-gate — на VerdictRecord.pass.

[Структурщик]: Поля VerdictRecord ещё раз словарём (норма): `id`, `sprintId`, `contractId`, `contractVersion`, `performerProjection` (ссылка M1), `evidenceRefs[]`, `verdict`, `diff[]`, `claimedDoneAt`, `recordedAt`, `supersedes?`. Без `qualityScore`, без `lgtm`, без `headSha` — эти ключи чужим леммам.

[Teamlead]: При fail связка простая: исполнитель не снят автоматически; статус контрактной оси = `open_rework` или `awaiting_evidence`; закрытие спринта по смыслу контракта — нет. Назначение (assigned) живёт; participation дополнится новым следом. Не путать с заменой персоны — это не вопрос 1, M1 уже закрыт.

[Музыкант]: Вещдок как take marker: короткий, адресуемый, на ленте спринта. Не дневник чувств «мне кажется совпало». Если diff пустой — один удар в колокол pass; если нет — список тактов, где ноты другие. Дальше либо overdub (amend D), либо новая сессия (rework), либо правка партитуры (contract-change) — три дорожки Структурщика.

[Верстальщик]: Фальшь, которую режем: один бейдж «ревью ✓», склеивший LGTM и match. Два бейджа минимум. При fail — не красный «build», а `contract-mismatch` с числом пунктов diff. Missing — отдельно от fail.

[Математик]: Связь с M2: принятие контракта — предикат `accepted(C)` уже вещдок; ревью — `matched(C,D)`. Цепочка закрытия: `accepted(C) ∧ doneClaimed ∧ matched ∧ …` — дальнейшие конъюнкты (4–9) вне комнаты. Мы фиксируем только введение matched и запрет closed_by_contract без matched.

[Архитектор]: Рекомендация формы: **да, вводим ContractReview как обязательный вещдок-акт формата спринта** с триггером done-claimed, предикатом match(C,D), вердиктом pass|fail+diff, home в sprint-format, author=performer projection. Не ADR на код; при необходимости — короткая запись в канон sprint-honest, не в ARCHITECTURE пакетов.

[Структурщик]: Зависимости лемм: M1 performer → author слот; M2 contract → object; EvidenceDone → input (след участия M1 qualify может пересекаться с D, но review судит не «был ли participate», а «покрыт ли C»). Участие без match ≠ закрытый контракт. Нарушение нормы: вердикт без contractRef.version — возврат, нет области.

[Teamlead]: Вердикт комнаты готов к фиксации. Не LGTM кода — **LGTM формы M3**. Расхождение: fail → amend-evidence | rework | contract-change; silent pass запрещён; закрытие по контракту только при pass. Код-качество — другие ворота. Вопросы 4–9 не открывали.

[Музыкант]: Принимаю: сверка партитуры исполнителем — отдельный take marker на ленте спринта. Без него финальный bounce контракта не честный, даже если ship поёт зелёным.

[Верстальщик]: Принимаю. Витрина: три блока честности + раздельные бейджи match vs code/ship; fail читается как mismatch, не как «плохой код».

[Математик]: Принимаю. `match(C,D)`, тотальность вердикта, `closed_by_contract ⇒ pass`, diff как множество clauses, без score.

[Архитектор]: Принимаю. Граница слоя sprint-format; VerdictRecord; author=performer; не PR-comment как SoT.

[Структурщик]: Принимаю. Леммы ContractReview, VerdictRecord, закрытый словарь исходов fail; home и поля без чужих ключей.

[Teamlead]: Принимаю. Матч M3 сыгран: форма ревью контракта исполнителем зафиксирована. Дальше — не 4–9 в этой комнате.

## Итоговое решение консилиума

| Вопрос | Решение |

| Когда наступает | **Триггер = `done-claimed` исполнителем** при уже принятом контракте C (M2). Не конец календаря, не merge, не green CI сами по себе. До done-claimed предикат не определён; после done без вердикта — статус **`missing`**. |

| Форма вердикта | Вещдок-запись **`ContractReviewVerdict`**: `id`, `sprintId`, `contractId`, `contractVersion`, `performerProjection`, `evidenceRefs[]`, `verdict ∈ {pass,fail}`, `diff[]` (пусто ⇔ pass), `claimedDoneAt`, `recordedAt`, `supersedes?`. Home — контур **sprint-format** рядом с C/accept (M2), не SoT в PR-comment и не ship check. |
| Предикат | `pass ⇔ diff=∅`; clauses из обязательств C (три поля M2 operationalize); **бинарь**, без score «почти». Один актуальный вердикт на `(sprintId, contractVersion)`; смена D/C → новый record + `supersedes`. |

**Definition of Done (для канона sprint-honest / процедуры, не для product-кода):**

1. В каноне формата спринта описан акт `contract-review` с триггером `done-claimed` и ссылкой на M1/M2.
2. Зафиксирована схема `ContractReviewVerdict` (поля выше) и home в sprint-format.
3. Явно разведены бейджи/оси: contract-match vs `code-review:pr` vs LGTM vs ship HEAD.
4. Запреты: закрытие по контракту без pass; silent pass при непустом diff; ключи quality/lgtm/headSha в VerdictRecord.
5. Словарь post-fail: amend-evidence | rework | contract-change — без четвёртого «почти».
6. Вопросы 4–9 не смешаны в этот документ.
