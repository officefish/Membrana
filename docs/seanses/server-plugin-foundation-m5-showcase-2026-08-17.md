# Консилиум: Форма самоописания плагина для витрины (M5)

**Повестка:** Q5 — Что объявляет плагин о себе, чтобы клиентская страница показала и включила его, не зная заранее? Состав `ShowcaseManifest`, словарь форм показа, каналы чтения и включения, самоописание не-витринных родов.

[Математик]: Начну с постановки предиката. Форма показа — это не произвольная строка и не открытое поле; это элемент конечного множества. Если множество открыто, клиентская страница не может декларативно сопоставить значение с рендерером без ветвящейся логики — это нарушение Т3.6. Предлагаю закрытый дискриминированный union первой волны: `row` (одна строка ключ→значение), `table` (матрица), `zone-map` (разметка зон по диапазонам), `histogram` (частотный профиль). Гейт расширения — отдельный символ-маркер `__experimental`, не значение основного словаря.

[Верстальщик]: Поддерживаю закрытый словарь — с оговоркой. Четыре формы покрывают Т2 полностью: сортировка по громкости читается как `row`, пиковые зоны — `zone-map`, аномалии — `row` или `table`, тренды — `histogram`. Но мне важно, чтобы `displayForm` был обязательным полем `ShowcaseManifest`, а не опциональным: страница без него не может нарисовать ничего предсказуемого. Опциональность здесь — дыра, в которую падает T3.6.

[Архитектор]: Конструкция проясняется. M1 отдал нам пять базовых полей `PluginManifest` и `ShowcaseManifest extends PluginManifest` с незаполненными полями — это наша работа. Структура должна быть минимальной: только то, что нужно странице для показа и включения без знания о внутренностях плагина. Предлагаю три дополнительных поля сверх базы: `displayForm` (дискриминант из словаря), `label` (человекочитаемое имя), `description` (опциональная подпись). Схема данных результата — вне манифеста: страница читает `RunRecordView` (M3), форму его отображения задаёт `displayForm`. Лишних полей не вношу — декора без смысла не существует.

[Музыкант]: С аудио-стороны добавлю: витринный плагин — это «инструмент на сцене», и зрителю важно видеть его имя и тип звучания до того, как он заиграет. `label` + `displayForm` — это именно программка концерта: что будет исполняться и в какой форме. Не нужно выносить в манифест технические параметры DSP или формат буфера — это внутренности. Аналогия: на афише пишут «фортепианный концерт», не «Steinway Model D с молоточковым механизмом».

[Teamlead]: Хорошая связка. Теперь каналы — главная развилка. IPluginHost уже несёт `getRegisteredPlugins(): ReadonlyArray<PluginManifest>` (M2). Вопрос: достаточно ли этого для чтения витринных самоописаний, или нужен отдельный метод? Я против второго метода без нужды: лишний контракт — лишняя связь. Если витринный плагин отдаёт `ShowcaseManifest` через тот же массив (полиморфно), клиентская страница фильтрует по признаку вида. Канал чтения: `IPluginHost.getRegisteredPlugins()` — единственный канал, никакого дополнительного HTTP-эндпоинта на уровне контракта. Канал включения — отдельный метод `IPluginHost.setPluginEnabled(id, enabled)`: право — серверная сторона, детали UI вне предмета.

[Структурщик]: Уточняю лемму «полиморфно». `getRegisteredPlugins()` возвращает `ReadonlyArray<PluginManifest>`. Чтобы страница отличила `ShowcaseManifest` от базового, нужен дискриминант в типе — поле `kind`. Предлагаю: базовый `PluginManifest` несёт `kind: PluginKind`, где `PluginKind` — закрытый enum: `showcase | handler | report`. `ShowcaseManifest` сужает до `kind: 'showcase'`. Страница делает `instanceof`-free narrowing по `kind`, без кастов и без знания о конкретном классе. Слабая связанность сохранена: страница зависит от контракта, не от реализации.

[Математик]: Дискриминант `kind` — правильный ход. Добавлю требование полноты: `kind` должен присутствовать во всех трёх родах, иначе узкое место в типах: при появлении нового рода страница потребует изменений в нескольких местах. Формально: тип `PluginManifest` — это `BaseManifest & { kind: PluginKind }`, где `PluginKind = 'showcase' | 'handler' | 'report'`. Расширение через `| 'experimental-X'` — через гейт, как и в словаре форм. Это изоморфно тому, что я предложил для `displayForm`: закрытый union, явный гейт.

[Верстальщик]: Хочу зафиксировать форму беднее для не-витринных родов — это важно для предсказуемости страницы. `handler` и `report` возвращаются в том же массиве, но у них нет `displayForm`, нет `description` (опциональна), только базовые поля плюс `kind`. Страница их видит — для включения по Т1 — но не пытается рисовать: нет `displayForm`, нет рендерера. Это защита от случайного показа обработчика в витрине.

[Архитектор]: Точно. Сформулирую различие конструктивно: `ShowcaseManifest` несёт всё, что нужно для показа — `label`, `displayForm`, опциональный `description`; `handler`- и `report`-манифесты несут только `label` (для списка включения) и `kind`. Разница не в «богатстве» — в назначении полей. `displayForm` у не-витринного рода физически отсутствует, не просто пустой: страница не может его ошибочно прочитать.

[Музыкант]: Мне нравится аналогия с программкой: витринный плагин — полная афиша (имя, жанр, форма показа), обработчик — технический rider (только имя для переключателя, внутри всё скрыто). Зрителю не нужно видеть схему микрофонной расстановки в программке концерта.

[Teamlead]: Зафиксируем развилку по каналу включения — здесь было молчаливое допущение, которое надо проговорить. Т1 даёт переключаемость «на уровне модуля». Я сказал: отдельный метод `setPluginEnabled(id, enabled)` на `IPluginHost`. Альтернатива — канал M4 (`request`). Против альтернативы: канал `request` (M4) предназначен для постфактум-запуска, это пусковой канал, не управляющий. Смешивать «запустить» и «включить/выключить» — нарушение единственности назначения. Остаётся отдельный метод на IPluginHost.

[Структурщик]: Согласен. Лемма точнее: `request` — глагол «исполни», `setPluginEnabled` — глагол «разреши/запрети». Это разные смысловые слои. В словаре Ожегова — разные статьи, не синонимы. Добавлю границу прав: `setPluginEnabled` — серверная операция; клиентская страница вызывает её через тот же `IPluginHost`, но вправе это делать только в роли «владелец дома» — что это значит в рантайме, решает M6; здесь фиксируем только контракт и именование.

[Математик]: Проверю полноту словаря форм против Т2. Т2 называет: сортировка по громкости — упорядоченный список значений → `row`. Пиковые зоны — пространственное распределение → `zone-map`. Аномалии — выбросы в наборе → `row` с маркером (или `table`). Тренды в реальном режиме — временной ряд → `histogram`. Покрытие полное. Гейт расширения: значение начинается с `x-` (по аналогии с HTTP-заголовками), не `__experimental` — более явный сигнал расширения.

[Музыкант]: Поддерживаю `x-`-гейт — это языковой конструктивизм: форма сигнализирует статус. Плагин, заявляющий `displayForm: 'x-waveform'`, сам объявляет, что его рендерер экспериментальный. Страница может безопасно его проигнорировать или показать fallback.
