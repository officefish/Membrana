# Консилиум: предмет вечернего ревью (M1 — фундамент)

**Повестка:** Что вечер обязан сказать о дне, чего структурно не может сказать ни одно потактовое ревью, и через какую единицу суждения, какой вход и какую форму вердикта он это говорит?

**Участники:** Математик (Dynin), Структурщик (Ozhegov), Teamlead (Tarasov), Музыкант (Kuryokhin), Верстальщик (Rodchenko), Архитектор (Vesnin).

**Порядок реплик:** Математик → Структурщик → Teamlead → Музыкант → Верстальщик → Архитектор

---

[Математик]: Начну с предиката различия. Потактовое ревью судит diff(t, t+1) — коммит или uncommitted на шине задачи. Вечер обязан судить нечто иное по структуре, а не по размеру. Утверждение «тот же прибор на большем диффе» — формально верное описание текущего кода, но не основание оставить его таким. Вечер видит то, что не видно ни в каком одном диффе: отношение между разработками. Потактовое ревью — предикат над одной задачей; вечернее — предикат над множеством задач за день. Это смена области определения, а не масштаба.

[Структурщик]: Уточняю лемму единицы. «Разработка, прожитая тремя-четырьмя сессиями» — слово владельца, но для машинного опознания нужна однозначная статья. Предлагаю: единица суждения вечера — **активная карточка реестра** (`docs/tasks/registry.json`), затронутая в течение дня. Карточка — это и есть «разработка»: у неё есть id, leadPersona, status, home. Набор коммитов по предмету вычисляется через git log с фильтром по id карточки из сообщений коммитов или через branch-соответствие. Это вычислимо. «Направление хендофа» — производное от карточки, не самостоятельная единица. Карточка реестра — единственная структура, у которой есть и предмет, и граница, и владелец.

[Teamlead]: Позиция принята в части карточки как единицы. Добавляю планку: если карточка не опознаётся по коммитам — она не вошла в игру, и вечер её не судит. Это не дефект вечера, это дефект оформления работы. Здесь важно зафиксировать: вечер судит карточки, по которым есть коммиты за расчётный день, — а не все карточки реестра. Факт 31.07 прямо из фактуры: `consumes: []`, диапазон самовычисляется, шесть коммитов ушли строкой `oversized`. Карточка не была опознана. Вывод: вход обязан объявлять карточки явно, иначе прибор слеп по конструкции.

[Музыкант]: На слух: вечер — это не «тот же take, только длиннее». Это **прослушивание микса**, где каждый трек — отдельная карточка, и задача — услышать, не режут ли они друг друга. Потактовое ревью слышит один инструмент в изоляции. Вечер слышит интерференцию: две разработки касаются одного модуля, одна блокирует другую, граница одной карточки вошла в тело другой. Это не слышно в одном диффе никогда. Структурно — предмет вечера есть отношение между карточками, а не содержание каждой.

[Верстальщик]: С витрины: если вердикт вечера — свободный текст, это украшение без несущей. Бестиарий прямо говорит — «Проза» #1204. Значит, форма вердикта обязана быть структурированной. Но закрытый перечень требует владельца. Предлагаю не изобретать новый перечень с нуля: взять три поля из слова владельца — **границы разработки**, **требуемые проверки**, **меры безопасности** — и объявить их полем с закрытым типом значений. Каждое поле — не свободный текст, а перечислимые теги или ссылки. Владелец перечня — тот, кто ведёт карточку реестра; порядок расширения — через заседание, как сейчас.

[Архитектор]: Фиксирую конструкцию. Единица суждения — карточка реестра: вычислима, имеет id, граница определена предметом задачи. Это правильная форма. Теперь о входе: `consumes: []` — это не нейтральное состояние, это структурная слепота. Вход вечернего шага обязан объявлять: (1) список карточек-кандидатов за день — берётся из реестра по дате активности; (2) git-диапазон per карточка — по id в сообщениях коммитов или по ветке; (3) контракты карточек (предмет + границы из поля карточки). Если часть входа отсутствует — карточка помечается `input_incomplete` и в суждение не входит; вечер не молчит, он сообщает о пробеле.

[Математик]: Формализую предикат входа. Пусть D — множество карточек, активных за день (∃ коммит с ref на id карточки, или ∃ коммит в ветке карточки). Вход вечера: `E = {(c, commits(c), contract(c)) | c ∈ D}`. Для каждого `c ∈ D`: если `commits(c) = ∅` — карточка в D по другому признаку (ветка без коммитов) — пропускаем; если `contract(c) = ⊥` — карточка помечается `no_contract`, суждение невозможно. Это не проза — это конкретный предикат допуска к суждению.

[Структурщик]: Уточняю лемму формы вердикта. «Свободный текст в поле оценки» — зверь #1204, запрещён на уровне структуры. Три поля из слова владельца — **boundary**, **checks**, **safety** — обязаны быть типизированы. Предлагаю: `boundary` — ссылки на модули/пакеты из карточки (вычислимо через home карточки и затронутые пути); `checks` — теги из закрытого реестра проверок; `safety` — теги из закрытого реестра мер. Владелец обоих реестров — тот же субъект, что ведёт `docs/tasks/registry.json`; порядок расширения тегов — через заседание аналогичного формата.

[Teamlead]: Хорошо. Но не хочу ещё одного реестра без хозяина. Реестр тегов проверок и мер безопасности — это живой документ, который требует ритуала поддержки. Если его не объявить явно с владельцем сейчас, он протухнет. Предлагаю: реестр тегов `checks` и `safety` хранится в `docs/meeting/evening-review-predicate/` — том же доме, что и этот протокол. Владелец — тот, кто принимает вердикт этого заседания. Расширение — только через заседание с вердиктом, не через commit без ревью.

[Музыкант]: Возвращаюсь к структурному отличию вечера. Потактовое ревью не может увидеть интерференцию между карточками по построению: оно не знает о других карточках дня. Вечер видит весь микс. Значит, поле `boundary` вердикта вечера — это не просто «границы этой карточки», это «граница этой карточки относительно других карточек дня». Если две карточки задели один пакет — это пересечение границ, и вечер обязан его назвать. Это то, что потактовое ревью структурно не видит никогда.

[Верстальщик]: Тогда `boundary` нужно читать как отношение, а не как список. С витрины: «граница карточки A пересекает карточку B в пакете X» — это честная запись. Не «карточка A трогает пакет X» в изоляции. Форма записи: `{card_a, card_b, shared_module}` — машинно читаема, не проза.

[Архитектор]: Принимаю форму. Теперь зафиксируем, что происходит при отсутствии части входа. Три случая: (1) карточка есть в реестре, коммитов нет — не входит в суждение, не ошибка вечера; (2) коммиты есть, карточки нет — `orphan_commits`, вечер сообщает, суждения нет; (3) карточка и коммиты есть, контракт отсутствует — `no_contract`, суждение невозможно, вечер фиксирует пробел. Во всех трёх случаях вечер не молчит: он выдаёт структурированный сигнал о пробеле, а не строку `oversized`.

[Математик]: Про `oversized` — это симптом того, что движок сейчас не различает «большой дифф одной разработки» и «много маленьких диффов разных разработок». Если единица суждения — карточка, то `oversized` per карточка — это уже осмысленная метрика: карточка выросла за день за разумный порог. А `oversized` по дню целиком — бессмысленная агрегация. Новый прибор per карточка убирает этот артефакт структурно.

[Структурщик]: Важно зафиксировать: движок `scripts/code-review.mjs` сейчас один для четырёх режимов. Вечернее ревью по карточкам — это иной предмет суждения, не просто иной диапазон. Значит, либо движок получает новый режим `--evening` с другим входом и другим выходом, либо это отдельный движок. Но это решение — не этой комнаты: это M2 или отдельная карточка. Здесь фиксируем только: **контракт входа и выхода вечернего режима отличается от `--uncommitted` и `--pr` по структуре**, а не по размеру диффа.

[Teamlead]: Точно. Не лезем в реализацию. Наш вердикт — что судить, чем кормить и что выдавать. Как это ложится в `code-review.mjs` — следующий шаг, другая карточка. Сейчас фиксирую: три части определены. Единица — карточка реестра. Вход — карточки дня + коммиты per карточка + контракты карточек; при отсутствии части — структурированный сигнал пробела. Форма вердикта — три типизированных поля (`boundary`, `checks`, `safety`) с тегами из реестра, не свободный текст.

[Музыкант]: Последнее про структурное отличие: вечер говорит о дне как целом, потому что только он видит **отношения между разработками**. Не содержание каждой — это уже сказало потактовое ревью. А именно: пересечения границ, накопленные риски от нескольких карточек вместе, меры безопасности, которые не видны в одной карточке, но видны в паре. Это и есть то, что вечер структурно обязан говорить.

[Верстальщик]: Честность витрины: если вечер выдал три поля с тегами и пустыми `checks: []` при реальных пересечениях — это фальшь не хуже `oversized`. Значит, в Definition of Done этого вердикта обязан быть признак: хотя бы одна проверка `boundary` per карточка выполнена машинно. Пустой вечерний вердикт при непустом множестве карточек дня — украшение по прецеденту `insight-sunrise-flash`.

[Архитектор]: Итог конструкции. Вечер структурно отличается от потактового ревью не объёмом диффа, а областью определения предиката: он работает над множеством карточек, а не над одной. Единица — карточка реестра (машинно: `registry.json` по дате активности). Вход — тройка `(карточка, коммиты карточки, контракт карточки)` per карточка в множестве дня. ## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| **(а) Единица суждения** | Карточка реестра (`docs/tasks/registry.json`), активная за день. Машинное опознание: карточка входит в множество дня, если существует хотя бы один коммит с ref на её `id` в сообщении, или существует ветка карточки с коммитами за день. |
| **Что вечер говорит, чего не может сказать потактовое ревью** | Отношения между карточками: пересечения границ (два разных коммита задели один модуль в рамках двух разных карточек), накопленные риски от пары/группы карточек вместе, меры безопасности, невидимые в одной карточке. Область определения предиката вечера — множество карточек дня, а не одна карточка. |
| **(б) Вход** | Тройка `(c, commits(c), contract(c))` per карточка `c` из множества дня. При `commits(c) = ∅` по ref-признаку, но наличии ветки — проверяется ветка. При `contract(c) = ⊥` — карточка помечается `no_contract`, суждение по ней невозможно, вечер фиксирует пробел структурированным сигналом. Коммиты без карточки — `orphan_commits`, вечер сообщает, суждения нет. `consumes: []` должно быть заменено явным объявлением этих трёх компонентов. |
| **Что при отсутствии части входа** | Вечер не молчит и не выдаёт `oversized`. Он выдаёт структурированный сигнал о пробеле с типом: `no_contract` / `orphan_commits` / `input_incomplete`. |
| **(в) Форма вердикта** | Три типизированных поля: `boundary` (ссылки на пересечения модулей между карточками дня, форма `{card_a, card_b, shared_module}`), `checks` (теги из реестра требуемых проверок), `safety` (теги из реестра мер безопасности). Свободный текст в полях оценки запрещён (#1204). Реестр тегов `checks` и `safety` хранится в `docs/meeting/evening-review-predicate/`; владелец — принимающий вердикт этого заседания; расширение — только через заседание с вердиктом. |
| **Отличие от LGTM/BLOCK** | Вечер не выносит бинарного вердикта per карточка — это уже сделало потактовое ревью. Вечер выносит реляционное суждение: пересечения, совокупные риски, меры. |

**Definition of Done (только M1):**

- [ ] В `docs/tasks/registry.json` зафиксирован механизм ref-связи коммита с id карточки (или подтверждено существующее соглашение по сообщениям коммитов / веткам).
- [ ] Создан файл реестра тегов `checks` и `safety` в `docs/meeting/evening-review-predicate/` с объявленным владельцем и порядком расширения.
- [ ] Шаг `code-review` в цепочке получает объявленный `consumes` с тремя компонентами (карточки дня, коммиты per карточка, контракты); `consumes: []` удалён для вечернего режима.
- [ ] Вечерний вердикт содержит три поля `boundary` / `checks` / `safety`; поля типизированы, не принимают свободный текст.
- [ ] Пустой вечерний вердикт при непустом множестве карточек дня блокируется как украшение (по прецеденту `insight-sunrise-flash` / вердикт M3 T1 заседания `meeting-evening-auditor`).
