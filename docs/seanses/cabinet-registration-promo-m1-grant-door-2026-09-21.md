# Консилиум: грант и дверь офиса для регистрации в кабинете по панельному коду

**Повестка:** M1 (К1) — как панельный код становится кодом регистрации в кабинете и какой дверью офис даёт кабинету проверить и погасить его атомарно, не заводя пользователя панели.

[Teamlead]: Комната M1. Одна цель: вид кода и дверь офиса. Не лезем в клиент кабинета, не пишем порядок «погасить → юзер», не трогаем форму. Данности 21.09: правда о коде в панели, новая система промокодов в кабинете — запрет. Вердикт без контракта двери — BLOCK.

[Архитектор]: Конструкция ясна по фактуре: `PromoCode.grants[]` уже несёт право; гашение сегодня только в `POST /v1/panel/register` и плодит пользователя панели. Кабинету нужен **тот же** код с **другим смыслом гранта** и **отдельной внутренней дверью**, которая не вызывает register панели. Отдельный вид кода — вторая система; это нарушение данности.

[Музыкант]: Мне здесь не DSP, а стык потоков: панель выдаёт, кабинет гасит. Если два контура на одном коде без общего гранта — будет рассинхрон «партнёрский» vs «кабинетный». Один код, один грант-маркер — чище, чем два префикса генерации.

[Структурщик]: Словарь: **код** — сущность панели; **грант** — строка в `grants[]`; **дверь** — маршрут офиса; **гашение** — инкремент `usedCount` (и побочные эффекты); **отзыв** — `revoke-code`. Кабинет не хранит правду о коде. Граница пакета: логика гашения остаётся в `panel-users-core`, контроллер только открывает дверь. Клиент офиса в кабинете — M2, здесь не размещаем.

[Верстальщик]: Форму и тексты ошибок M4. Но контракт ответов мне нужен заранее: одно тело отказа наружу кабинета vs детальный отказ на внутренней двери. Иначе M4 начнёт угадывать причины. Фиксируйте, различает ли дверь офиса причины **для кабинета-сервиса**.

[Математик]: Атомарность при `PanelUsersState` (не Prisma): read → check → write `usedCount` — классическая гонка. Без взаимного исключения два параллельных погашения обоих пройдут проверку `usedCount < maxUses`. Нужен один критический участок на процесс/инстанс и тест гонки с красным входом до фикса. Численно: при `maxUses=1` ровно один success из N параллельных.

[Teamlead]: Принимаю рамку: грант в существующем коде, не новый тип. Архитектор — точное имя строки гранта и путь двери. Структурщик — охрана. Математик — атомарность и зубы. Дальше без утечек в M3.

[Архитектор]: **Вид кода:** тот же `PromoCode`; новый грант в `grants[]`. Имя словами: «регистрация в кабинете». Точная строка: `cabinet-register`. Почему не отдельный вид: выдача/отзыв уже под `@OwnerAdmin`, модель, аудит `mint-code`/`revoke-code`, нормализация `normalizeGrants` — переиспользуем. Почему не секционный грант панели: `grantsAllowSection` про разделы панели; регистрация кабинета — не sectionId. Отдельный литерал не пересекается с section grants.

[Музыкант]: `cabinet-register` звучит как билет на один контур. Партнёрский register панели по-прежнему смотрит свои гранты разделов; кабинетная дверь принимает **только** код, у которого после normalize есть `cabinet-register`. Код с обоими наборами грантов — возможен (владелец так смintит), но двери разные: панель register не гасит «только кабинет», кабинетная дверь не заводит panel user.

[Структурщик]: Дверь — не `@PanelPublic`, не `@OwnerAdmin`. Охрана: внутренний guard сервиса (shared secret / service token между `background-cabinet` и `background-office`). Имя в фактуре позже; в контракте: **внутренняя охрана офиса**. Путь предлагаю: `POST /v1/internal/cabinet/registration-codes/consume`. Не под `/v1/panel/…`, чтобы не смешать с PanelAuthGuard-семантикой партнёров.

[Верстальщик]: Поле «проверить или погасить»: для UI регистрации достаточно одного атомарного «погасить» в счастливом пути. Отдельный check без гашения — риск TOCTOU и лишний круг в M3. Если оставляете check — только для админ-отладки, не для формы. M1 пусть зафиксирует: форма кабинета зовёт **consume**, не preview.

[Математик]: Согласен с TOCTOU. Контракт операции: одна дверь, тело `{ "code": string, "mode": "check" | "redeem" }`. `check` — read-only, без инкремента; `redeem` — атомарный check+inc. Кабинет в проде для регистрации шлёт только `redeem`. `check` — зуб на контракт и будущие ops, не обязательный путь M3.

[Teamlead]: Оставляем оба mode в контракте двери, продуктовый путь — только redeem. Отказ «не тот грант» — если нет `cabinet-register`. Дальше тела ответов — жёстко, без «примерно».

[Архитектор]: **Успех redeem:** HTTP 200, тело `{ "ok": true, "code": "<normalized>", "grant": "cabinet-register", "uses": { "used": n, "max": m } }`. **Успех check:** 200, `{ "ok": true, "redeemable": true, "grant": "cabinet-register", "uses": { "used": n, "max": m } }` без инкремента. Истёк / исчерпан / отозван / нет гранта / неизвестный код — **на внутренней двери различаем кодом причины** в теле для сервиса кабинета; наружу пользователя кабинета норма Q3 (ADR-0005) **сохраняется** и **на внутреннюю дверь не переносится**: Q3 — про публичный контур регистрации, не про service-to-service.

[Музыкант]: Если внутренность врёт одной кашей «invalid», кабинет в логах оглохнет, а M3 не отличит «офис сказал нет» от «офис лёг». Различать внутри — правильно. Снаружи формы — один отказ, это M4/M3.

[Структурщик]: Отказы внутренней двери (единый HTTP 409 или 400 + машинный `reason`):

| reason | когда |
|--------|--------|
| `not_found` | кода нет в state |
| `expired` | `expiresAt` в прошлом |
| `exhausted` | `usedCount >= maxUses` |
| `revoked` | код отозван |
| `grant_mismatch` | нет `cabinet-register` в grants |
| `invalid_code` | пусто/нормализация в пусто |

Тело отказа: `{ "ok": false, "reason": "<enum>" }`. Без PII. Успех не тащит список всех grants — только факт кабинетного гранта (минимизация утечки модели панели в кабинет).

[Верстальщик]: Для M4 мне достаточно: кабинет-сервис мапит любой `ok: false` в один пользовательский отказ; `reason` — в серверный лог. Не светим `exhausted` vs `expired` в JSX. Принял.

[Математик]: Нормализация кода до lookup — та же, что в panel-users-core (регистр/префикс), иначе «чужой код» из-за пробела. Зуб: normalize → lookup. Гонка: два `redeem` с `maxUses=1` → ровно один 200, второй `exhausted`; state.usedCount итого 1; в аудите одна запись гашения на успех.

[Teamlead]: Атомарность — в core, не в контроллере. Кто пишет mutex — Математик со Структурщиком на реализации; здесь контракт: «гашение сериализовано относительно PanelUsersState».

[Архитектор]: Хранилище — `PanelUsersState` parse/write. Операция redeem под **exclusive lock** на обновление state (in-process mutex + запись state как сейчас в ADR-0005). Если позже несколько инстансов офиса — отдельный ADR; в M1 фиксируем: **один writer-контур state**, как нынешняя панель. Двойное гашение исключается сериализацией read-check-inc-write. При `mode=check` lock shared/read допустим, но проще один lock на оба mode — цена мала.

[Музыкант]: Аудит-лента: сегодня `mint-code` / `revoke-code`. Добавить действие `redeem-cabinet-code` (или `consume-cabinet-register`) с полями: код (или id кода), mode, результат ok/reason, usedCount после. Неуспехи тоже в ленту — иначе гонку и брут не разобрать. Панель UI ленты — не эта комната, только запись в state audit.

[Структурщик]: Отзыв: `revoke-code` помечает код отозванным. Уже погашенные использования **не откатываются**: `usedCount` не уменьшается, кабинетных пользователей M1 не создаёт и не удаляет. Повторный redeem отозванного с остатком uses → `revoked`. Полностью исчерпанный и потом revoked → по-прежнему `exhausted` или `revoked` (порядок проверок: exists → revoked → expired → grant → exhausted), чтобы отозванный всегда был явен для ops.

[Верстальщик]: Порядок reason для уже мёртвого кода владельцу панели не виден в кабинетной форме. Ок. Не строим в M1 экраны админки под новый грант — минт уже умеет grants[]; владелец передаёт `cabinet-register` в массиве. Документация минта — зубы/smoke, не UI.

[Математик]: Порядок предикатов фиксирую численно-однозначно: (1) not_found (2) revoked (3) expired (4) grant_mismatch (5) exhausted (6) else ok. На redeem после прохождения — inc usedCount, persist, audit success. Зубы — по одному красному тесту на каждый reason + параллельный suite на гонку. Красный вход: тест падает, пока lock/inc не сделаны.

[Teamlead]: Что НЕ строить — списком в вердикт. M2: где клиент и ключ. M3: порядок погашение/создание пользователя и unavailable office. M4: форма. Также не строить: пользователя панели на этой двери; Prisma; публичную @PanelPublic дверь; отдельную таблицу промокодов кабинета.

[Архитектор]: Итоговая форма двери:

- **Метод/путь:** `POST /v1/internal/cabinet/registration-codes/consume`
- **Охрана:** internal service auth (не PanelPublic, не OwnerAdmin, не пользовательская сессия панели)
- **Запрос JSON:** `{ "code": string, "mode": "check" | "redeem" }` — `code` обязателен, `mode` обязателен
- **200:** как выше ok/uses/grant
- **400:** невалидное тело / `invalid_code`
- **401/403:** нет/плохой internal token (без detail)
- **409:** бизнес-отказ с `reason` из enum
- **Запрет:** создание PanelUser; изменение grants пользователя панели

[Музыкант]: Smoke-зубы: минт с `grants: ["cabinet-register"]` через уже существующий admin mint (как `_ssh-panel-smoke.mjs`), затем consume redeem, повтор — exhausted. Минт без гранта — grant_mismatch. Revoke затем redeem — revoked. Это приёмка двери до M2.

[Структурщик]: `normalizeGrants` должен пропускать `cabinet-register` как opaque string (если сейчас фильтрует только section — проверить ствол при реализации; контракт: литерал **не** отбрасывается). `grantsAllowSection` не обязан знать этот грант: кабинетная дверь проверяет `grants.includes("cabinet-register")` после normalize, не через section helper.

[Верстальщик]: Словарь в ответах API — английские reason для машины; в протоколе заседаний — русские «истёк/исчерпан/отозван/не тот грант/чужой код». M4 не цитирует reason. Пусто.

[Математик]: Инвариант: ∀ код с maxUses=K, число успешных redeem ≤ K на всём жизненном цикле, включая параллелизм. Revoke не уменьшает счётчик успехов. Check не меняет usedCount. Это DoD математики двери.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Вид кода | Тот же панельный `PromoCode`; **не** отдельный вид и **не** новая система в кабинете |
| Грант | Словами: «регистрация в кабинете»; строка: **`cabinet-register`** в `grants[]` после `normalizeGrants` |
| Почему грант, не новый тип | Выдача/отзыв/аудит/state уже в панели; данность «правда в панели»; `cabinet-register` не sectionId и не идёт через `grantsAllowSection` |
| Дверь | `POST /v1/internal/cabinet/registration-codes/consume` |
| Охрана | Внутренняя service-auth офиса; **не** `@PanelPublic`, **не** `@OwnerAdmin`, **не** сессия пользователя панели |
| Запрос | `{ "code": string, "mode": "check" \| "redeem" }` оба поля обязательны; иной/пустой mode → 400 |
| Успех check | 200 `{ "ok": true, "redeemable": true, "grant": "cabinet-register", "uses": { "used", "max" } }` без inc |
| Успех redeem | 200 `{ "ok": true, "code", "grant": "cabinet-register", "uses": { "used", "max" } }` после inc |
| Отказы | 409 `{ "ok": false, "reason" }` где reason ∈ `not_found` \| `revoked` \| `expired` \| `grant_mismatch` \| `exhausted`; `invalid_code`/тело → 400; auth → 401/403 |
| Порядок предикатов | not_found → revoked → expired → grant_mismatch → exhausted → ok |
| Q3 (не различать причину) | На **публичный** контур (и UX кабинета) — да; на **внутреннюю** дверь — **нет**, reason для сервиса кабинета; в браузер reason не отдавать |
| Атомарность | В `panel-users-core`: сериализованный read-check-inc-write `PanelUsersState` (mutex/exclusive lock writer-контура); успех redeem ≤ maxUses при гонке |
| Аудит | Запись `redeem-cabinet-code` (успех и отказ) в аудит-ленту state |
| Отзыв | `revoke-code` не откатывает `usedCount` и не трогает кабинетных пользователей; дальнейший consume → `revoked` |
| Эффект двери | **Не** создаёт пользователя панели и **не** копирует section-grants panel user |
| Что НЕ строить в M1 | Клиент офиса и ключ в кабинете (M2); порядок «погасить → создать пользователя» и unavailable office (M3); форма/тексты (M4); Prisma; публичная дверь; вторая система промокодов; UI админки под грант |

**Definition of Done (только M1):**

1. В core офиса: проверка литерала `cabinet-register`; `consume` с mode check/redeem; lock на state; audit `redeem-cabinet-code`.
2. Маршрут `POST /v1/internal/cabinet/registration-codes/consume` под internal guard; ответы и reason как в таблице.
3. Зубы (красные до правки, затем зелёные): каждый reason; invalid/missing mode; check не меняет `usedCount`; redeem inc; **гонка** maxUses=1 → один success; revoke после/до; код без гранта; код только с section grants → `grant_mismatch`.
4. Дверь не вызывает register панели и не создаёт PanelUser.
