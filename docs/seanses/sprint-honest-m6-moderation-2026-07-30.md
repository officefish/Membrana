# Консилиум: модерация ведущей — гейты, несовместимость, отсутствие

**Повестка:** формат спринта (не код). Перечень актов ведения, где ведущая обязана остановиться и спросить владельца; предикат несовместимости ведущего с исполнителем и почему; что при отсутствии ведущей; кандидатура Ангелины — предложение владельца, не решение. [Верстальщик]: С витрины капитана и агента: если «ведущая» рисуется тем же бейджем, что «исполнитель», — фальшивое присутствие, уже битое в M1. Нужны **два разных индикатора**: `lead` (держит гейты) и `performer` (след на ленте). Пустота ведущей тоже честна: `lead: absent`, не прочерк «—». Не рисую layout — требую в контракте формата спринта раздельную маркировку ролей на карточке окна.

[Музыкант]: На слух ведущая — это **count-in и meters**, не соло на шине исполнения. Кто дал отсчёт, не должен одновременно жать take: иначе mono-take, где «принял» = «сыграл». Инцидент 29.07 слышу как клиппинг канала: председатель сам вынес procedural judgment — рот дирижёра вместо рта аудитора/владельца. Граница: ведущая держит темп и стоп-кран; партитуру по существу не дописывает.

[Архитектор]: Конструкция. Ведущая — **орган потока**, не орган предметного суждения (канон 27.07, контур исполнения). Граница модуля «ведение»: (a) маршрут дня/окна, (b) останов на гейтах, требующих слова владельца, (c) фиксация *что* спросили и *какой* ответ пришёл. За границей: вердикт по коду, LGTM, процедурное суждение «достаточно ли доказательств», замена аудитора. Форма решения комнаты — перечень гейтов + предикат несовместимости + fallback отсутствия; не персона в вакууме.

[Teamlead]: Положение: матч про формат спринта, не про то, «нравится ли Ангелина». Планка — проверяемые правила ведения. Связка: Математик — предикаты гейта и несовместимости; Структурщик — леммы ролей; Архитектор — граница ведение/надзор; Верстальщик — честные метки на витрине. Кандидатура Ангелины — **предложение** владельца: комната согласует носителя или даёт иного с основанием. Не решаем 7–9.

[Математик]: Формализую без UI. Роли на окне S: `lead(S)`, `performer(S)`, `auditor(S)` — не обязательно persona из одного алфавита, но **попарно различимы по функции**. Предикат несовместимости: `incompatible(lead, performer) ⇔ ∃S: lead(S)=performer(S) ∧ role(lead)≠role(performer)` в смысле одного субъекта на обоих слотах. Инвариант: `lead(S) = performer(S) ⇒ invalid(S)`. Гейт G — пара `(trigger, needsOwnerWord)`; при `needsOwnerWord=true` ведение **не** решает payload — только `halt → ask → record(answer)`.

[Структурщик]: Леммы, иначе синонимы. **Ведение (facilitation)** — оркестрация окна: очередь, гейты, журнал «спросили/ответили». **Надзор (supervision)** — предметно-процедурное суждение: достаточно ли следа, LGTM/BLOCK, «рот тот». **Исполнитель** — M1: assignment + participation evidence. **Ведущая** — слот потока, не `leadPersona` карточки кода. Home истины формата — документ спринт-контракта (не UI, не PR-описание от руки). Два слота на одного субъекта = нарушена слабая связанность ролей окна.

[Верстальщик]: Гейты, которые обязаны **читаться** капитану до продолжения: (1) смена цели дня / PRIMARY; (2) принятие риска irreversible (force-push, drop data, secret rotate в prod); (3) закрытие спринта без evidence M1; (4) назначение/снятие аудитора; (5) «исключение из кодекса» (ведущая чинит код, исполнитель сам себе LGTM). На витрине каждый такой стоп — явная плашка `awaiting_owner`, не тихий continue.

[Музыкант]: Ещё на слух: стоп, когда **шина аудитора молчит**, а комната уже хочет final bounce. Ведущая не подменяет take аудитора своим «звучит нормально». И стоп, когда просят **сменить пресет процесса** (другой DoD, другая дверь приёмки) mid-sprint — это слово владельца, не fade на пульте ведущей. Иначе снова 29.07: дирижёр дописал партитуру.

[Архитектор]: Где кончается ведение и начинается надзор — по **типу речевого акта**, не по громкости. Ведение: «сейчас гейт G3; без слова владельца окно стоит». Надзор: «доказательств достаточно / процедура соблюдена / вердикт X». Второе — рот Teamlead (исполнение) или аудитора (независимая проверка) или владельца (канон), **не** рот ведущей. Председатель 29.07, вынеся procedural judgment сам, перешёл из модуля facilitation в supervision без контракта — отсюда «рот не тот».

[Teamlead]: Принимаю границу речевых актов. Для матча фиксирую: ведущая **не** выдаёт LGTM/BLOCK по работе и **не** закрывает procedural dispute по существу. Она поднимает флаг и передаёт нужному рту. Если спор «достаточно ли M1-следа» — сначала аудитор или я как приёмка исполнения; если спор «менять ли канон» — владелец. Ведущая только не даёт окну поехать дальше без адресата.

[Математик]: Перечень гейтов как тотальная функция на актах ведения. Пусть акт A ∈ Acts. `mustAskOwner(A) ⇔ A ∈ {setPrimary, grantExceptionToCode, irreversibleOpsRisk, changeAcceptanceDoor, appointOrRemoveAuditor, closeSprintWithoutPerformerEvidence, overrideAuditorFinding, bindLeadEqualsPerformer}`. Остальные акты: `mayProceedUnderLead` при условии, что не расширяют этот список молча. Инвариант закрытия: `close(S) ⇒ ¬∃g∈openGates(S) ∨ ownerWaiver(g)`.

[Структурщик]: Словарь актов (закрытый, без жирных ID кода):  
1) установка/смена primary focus окна;  
2) исключение из кодекса 27.07;  
3) необратимый ops-риск;  
4) смена двери приёмки / DoD окна;  
5) назначение или снятие аудитора;  
6) попытка закрыть окно без performer-evidence (M1);  
7) override нахождения аудитора;  
8) совмещение lead+performer на одном субъекте.  
Любой новый акт с `needsOwnerWord` — только через явное расширение словаря (иначе снова «сочинили посылку о входе»).

[Верстальщик]: При `lead: absent` витрина не должна рисовать зелёный «ведётся». Честные состояния: `lead_active` | `lead_absent_owner_proxy` | `lead_absent_halted`. Если пошли без ведущей и без proxy — бейдж `unguarded`, чтобы капитан видел голый провод. Пустота лучше декоративной Ангелины-по-умолчанию без решения комнаты.

[Музыкант]: Отсутствие ведущей на слух = **нет count-in**. Два режима, не «как получится»: (α) владелец явно берёт proxy на гейты (`owner_proxy`) — окно играет; (β) гейты с `needsOwnerWord` встают в halt, остальной шум (черновики, разборы без закрытия) может идти как rehearsal, но **final bounce / close sprint** — только после count-in. Rehearsal без meters не выдаём за матч.

[Архитектор]: Fallback — часть конструкции, не afterthought. Варианты с ценой:  
- **Halt-on-gate:** дёшево, безопасно, режет throughput.  
- **Owner-proxy:** быстро, но владелец снова в операционке.  
- **Deputy-lead из канона** (именованный запасной слот): средняя цена, нужен явный roster.  
Рекомендую: default = halt-on-gate для списка mustAskOwner; owner-proxy — только явным словом; deputy — если комната утвердит носителя и заместителя вместе. Не плодим «тихую Ангелину» из воздуха.

[Teamlead]: Решение по отсутствию: **default halt на owner-гейтах**; без ведущей нельзя закрыть спринт и нельзя снять/поставить аудитора. Остальная подготовка — rehearsal, не матч. Заместителя не выдумываем в этой комнате, если не утвердим носителя. Связка на носителя — отдельной строкой вердикта, не вперемешку с предикатами.

[Математик]: Предикат несовместимости усиливаю. Не только `lead(S)=performer(S)`, но и: `incompatible(lead, auditor)` на том же S — иначе самопроверка потока. Почему численно: если один субъект пишет evidence и же держит gate close, вероятность ложного `close(S)` не отделена от конфликта интереса — нет независимого наблюдения. M1 уже развёл assigned/participated; здесь разводим **control plane** и **data plane** окна.

[Структурщик]: Почему несовместимость — словарно: ведущая **определяет**, что окно ещё открыто; исполнитель **порождает** след. Совмещение = один рот и на «достаточно?» и на «вот лента». Это не мораль, а сбой леммы single-author на два home. Auditor — третий home; lead≠auditor, performer≠auditor (это уже эхо M1/аудитор≠исполнитель из порядка M0 — не решаем 7–9 по существу, только не ломаем ребро).

[Верстальщик]: Кандидатура Ангелины на витрине — статус `proposed_lead`, не `appointed_lead`. Комната либо `accept` с основанием «уже секретарь контура исполнения 27.07, код не пишет», либо `counter-propose` с именем и основанием. Фальшь: сразу писать в шапку спринта «Ведущая: Ангелина» без строки решения комнаты.

[Музыкант]: За Ангелину как proposal — слышу канон: она **не** советующая, нет голоса в консилиуме, не leadPersona кода. Это как раз нужный тембр count-in. Риск: привычка зала тянуть её в «рот по существу» — тогда снова 29.07. Основание «за»: разведение шин уже в промпте. Основание сменить носителя — только если кто-то иной **жёстче** держит «не сужу предмет» и не пишет код.

[Архитектор]: Носитель слота ≠ личность в чате. Слот `sprint-lead` должен удовлетворять контракту: no code write/fix; no LGTM; no procedural judgment by default; holds owner gates; writes journal ask/answer. Ангелина **подходит по контракту** 27.07. Альтернатива обязана показать то же соответствие, иначе это смена вывески без конструкции. Рекомендация формы: принять proposal, зафиксировать контракт слота отдельно от имени — имя сменяемо, контракт нет.

[Teamlead]: Вердикт по носителю: **принимаю Ангелину как appointed_lead** на контур спринт-формата с явным контрактом слота; комната не обязана была — но оснований против нет, за — канон 27.07 и «не советующая». Заместителя не назначаю молча. Если владелец потом назовёт иного — та же форма accept/counter. Планка: имя в протоколе + ссылка на предикаты, не «ну она и так».

[Математик]: Зафиксирую функцию `roleBoundary(utterance)`:  
`facilitation` если illocution ∈ {queue, halt, ask_owner, record_answer, mark_gate_open_closed};  
`supervision` если illocution ∈ {sufficient_evidence, lgtm_block, procedure_ok, override_finding}.  
Ведущая: домен только facilitation. Любой supervision-act от lead → `wrong_mouth` (класс 29.07). Машинно потом: линтер протокола может ловить глаголы; сегодня — норма формата, не код.

[Структурщик]: Home журнала ведущей — не PR исполнителя и не memory советующего. Отдельная лемма: `LeadJournal` = append-only акты (gate_id, ask, owner_answer|pending, ts). Исполнитель туда не пишет; ведущая не пишет в evidence performer. Слабая связанность: три ленты на окно — lead journal / performer evidence / auditor findings. Склейка только на close под предикатами.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Перечень актов, где ведущая **обязана** остановиться и спросить владельца | Закрытый список `mustAskOwner`: (1) установка/смена primary focus окна; (2) исключение из кодекса 27.07 (код write/fix ведущей и т.п.); (3) необратимый ops-риск; (4) смена двери приёмки / DoD окна; (5) назначение или снятие аудитора; (6) закрытие окна без performer-evidence (M1); (7) override нахождения аудитора; (8) совмещение lead+performer (и попытка lead=auditor). Расширение списка — только явным словом владельца / новой комнатой, не молча. |
| Предикат несовместимости ведущий × исполнитель и **почему** | `invalid(S) ⇐ lead(S)=performer(S)`. Дополнительно: `lead(S)≠auditor(S)`. **Почему:** control plane (открыто/закрыто, гейты) не может быть тем же субъектом, что data plane (evidence исполнения) и независимый надзор — иначе ложный close и класс «рот не тот». Это слабая связанность ролей окна, не этика. |
| Граница ведение / надзор (урок 29.07) | По illocution: **ведение** = queue, halt, ask_owner, record_answer, mark gates; **надзор** = sufficient_evidence, LGTM/BLOCK, procedure_ok, override. Supervision от ведущей → `wrong_mouth`. LGTM/процедура — Teamlead / аудитор / владелец по типу спора. |
| Что при **отсутствии** ведущей | Default: **halt-on-gate** для всех `mustAskOwner`; `close(S)` и смена аудитора невозможны. Опционально `owner_proxy` — только явным словом владельца. Rehearsal (подготовка без close) допустим под бейджем `unguarded` / `lead_absent`, не выдаётся за матч. Deputy-lead не назначается молча. |
| Кандидатура Ангелины | **Принята** комнатой как `appointed_lead` **под контракт слота** (не «навечно по имени»). Основание: канон 27.07 — секретарь контура исполнения, не советующая, кода не пишет/не фиксит, держит гейты. Контракт слота сменяем по имени; альтернатива обязана удовлетворять тому же контракту.
