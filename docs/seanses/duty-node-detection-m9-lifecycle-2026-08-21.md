# Консилиум: M9 — жизненный цикл материала дежурства

**Повестка:** O1 — Что происходит с материалом дежурства, когда места больше нет: что вытесняется, что хранится нерушимо, и на чьей стороне это решается?

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Математик (Dynin), Структурщик (Ozhegov), Музыкант (Kuryokhin), Верстальщик (Rodchenko).

**Порядок реплик:** Teamlead → Архитектор → Математик → Структурщик → Музыкант → Верстальщик

---

[Teamlead]: Комната одна, вопрос один — жизненный цикл и приоритеты хранения. Предикат события и паспорт не трогаем: M7 и M8 закрыты. Живой материал дня жёсткий: 1 ГиБ, час = 304 МБ, 116 чужих треков без правил, сеанс пишет тишину наравне с полезным. Нужен единый вердикт: что вытесняется первым, что нерушимо, где квота, что с неуехавшим, остаётся ли 413. Планка — без «зависит» без ветвления.

[Архитектор]: Конструкция из Т12 уже задана: отказ сервера при переполнении — честная граница контракта, не дефект; лечится кольцевым буфером на узле с приоритетом события над фоном; квота на узел; ротация по признаку судьбы, не по времени. Форма решения: два контура хранения — узел (живая лента duty) и сервер (принятый материал). Владелец вытеснения на живой ленте — узел. Сервер не ротирует чужое молча: говорит 413 и стоит.

[Математик]: Формализую предикат вытеснения. Пусть каждая запись несёт судьбу `fate ∈ {background, soft_event, hard_event}` и размер `s`. Квота узла `Q`. При `Σ s > Q` вытеснение — детерминированный порядок: сначала `background` (сжатый или сырой фон), затем при необходимости `soft_event` с меньшей уверенностью; `hard_event` и паспорт записи в порядке вытеснения не участвуют. Ротация не по `age(t)`, а по `fate` — иначе трёхчасовое дежурство сомнёт вчерашний hard ради сегодняшней тишины.

[Структурщик]: Леммы, чтобы не разъехались слова. «Квота узла» — лимит локального кольцевого буфера duty-ленты, сторож — процесс на узле. «Квота сервера» — лимит принятого объёма на стороне приёма; сторож — сервер, ответ 413 без silently-delete. «Судьба» — признак из решения M7 (`none/soft/hard` + confidence), записанный в паспорт M8; без паспорта запись в выборку окна не идёт и, следовательно, не получает защиту событийного класса. Публичный API вытеснения не торчит в UI-пакеты напрямую.

[Музыкант]: Слышу боль дня: писали всё подряд — тишина заняла столько же, сколько событие. Т3 уже сказал: фон сжимается или выбрасывается по квоте; событийные окна — целиком; хранить не сырой поток целиком, а отпечаток + окно вокруг события + метаданные. На узле при давлении первым уходит сырой фон и быт без soft/hard; hard-окно и его отпечаток — нерушимы локально, пока не уехали или пока оператор явно не снёс.

[Верстальщик]: С витрины оператору нужны три честных индикатора, без метафор: заполненность квоты узла (число и полоса), счётчик «не уехало / ждать 413», класс судьбы у фрагментов ленты. Когда сервер ответил 413 — не «ошибка связи», а состояние «квота сервера, материал остаётся на узле». Пустые обещания «всё сохранится» при 1 ГиБ — нарушение конструкции экрана.

[Teamlead]: Фиксирую конфликт, который нельзя оставить размытым: сервер отказывает, узел продолжает (M4). Значит вытеснение неуехавшего — обязанность узла, не сервера. Связка на вердикт: Архитектор — границы; Математик — порядок судьбы; Музыкант — что считается фоном в звуке; Структурщик — где живёт сторож квоты. Верстальщик — только отображение состояний, не политика.

[Архитектор]: Варианты с ценой. (A) Только сервер ротирует — цена: при офлайне (M4) лента взрывает диск узла; 116 треков уже доказали. (B) Только узел, сервер безлимитен — цена: сервер становится свалкой, контракт приёма лжёт. (C) Оба сторожат свою квоту: узел — кольцо по судьбе; сервер — 413 без вытеснения принятого чужим запросом. Беру (C). Модули: duty-буфер узла, passport/fate в записи, endpoint приёма с квотой.

[Математик]: Численно по живому материалу: 304 МБ/ч → ~912 МБ / 3 ч при текущем «писать всё». При Q = 1 ГиБ потолок наступает внутри трёхчасового дежурства. Если фон компактифицировать до отпечатка (грубо: метаданные + fingerprint ≪ raw), а сырой оставлять только на soft/hard-окнах фиксированной длины W, то `Σ s` растёт с числом событий, не с длительностью тишины. Это единственная устойчивая асимптотика.

[Структурщик]: Граница пакетов: политика `evictByFate(quota, entries) → evicted[]` — чистый модуль рядом с лентой узла, без импорта из UI. Серверный приём: `accept(payload) → 201 | 413`; при 413 тело не писать, уже принятое не трогать. Не смешивать «квоту узла» и «квоту сервера» в одном конфигурационном ключе — два словаря, два сторожа. M5 («слать или не слать») — компактификация исходящего; вытеснение локального — отдельный метод, не тот же фасад.

[Музыкант]: Уточняю нерушимое с слуховой стороны. Нерушимо на узле: (1) паспорт записи; (2) hard-окно целиком; (3) отпечаток, по которому hard опознан. Soft — защищён сильнее фона, но при критическом давлении после исчерпания фона может сжаться до отпечатка + укороченного окна, если confidence ниже порога. Фон / `none` — первый кандидат: drop raw, оставить редкий fingerprint или ноль. Сырой «всё подряд» как режим duty — вне контракта жизненного цикла.

[Верстальщик]: Тогда в ленте UI три визуальных веса: hard — полный контраст и замок «не вытесняется»; soft — средний; background — приглушён, может нести метку «будет сброшен при квоте». При 413 — баннер-факт на базе `base-content`, не red-alarm аварии: это граница контракта, Т12. Кнопка «повторить отправку» уместна; кнопки «удалить на сервере чужое» в этом экране нет.

[Teamlead]: Проверяю полноту покрытия O1. Вытесняется первым — фон/`none`. Не вытесняется — hard + паспорт + отпечаток события. Квота — на обеих сторонах, сторожа разные. Неуехавшее при вытеснении — уничтожается по политике узла, сервер его не видел; это не скрытое «потом дошлём из могилы». 413 остаётся. Если кто-то хочет «сервер сам подчистит старое» — в этой комнате нет: это другая повестка.

[Архитектор]: Согласен. Добавлю: материал, не уехавший до вытеснения, считается потерянным для сервера осознанно; узел не обещает infinite retry queue больше квоты. Очередь исходящего — тоже под `Q_out ≤ Q`, иначе retry съест кольцо. Судьба при ротации важнее timestamp: вчерашний hard старше сегодняшнего background и побеждает. Это прямое следствие Т12 «по признаку судьбы, не по времени».

[Математик]: Порядок ключа сортировки вытеснения (возрастание Survivability):  
`none/background → soft ∧ conf < θ → soft ∧ conf ≥ θ → hard`.  
Внутри одного класса — FIFO по времени только как tie-break, не как главный ключ. Паспорт и soft/hard-метаданные имеют вес в квоте, но `evict` их не выбирает, пока жив хотя бы один background. Инвариант: `∀ e ∈ hard: e ∈ store` пока `Σ s_background > 0` или есть что сжать.

[Структурщик]: Термин «кольцевой буфер» в Т12 — не обязательно byte-ring без индекса; это политика фиксированной ёмкости с вытеснением. Индекс по `fate` обязателен, иначе каждый overrun = полный scan. Словарь статусов исходящего: `pending | accepted | rejected_413 | dropped_local`. `dropped_local` — терминальный, не маскировать под `pending`. Это закрывает дыру «116 треков копятся вечно»: orphan без паспорта и без duty-сессии текущей — вне защищённых классов, эвакуируются как background/unknown.

[Музыкант]: Про «чужие 116 треков»: это не событийная лента текущего duty, это свалка. Жизненный цикл обязан различать `dutySessionId` текущего дежурства и архивный шум без паспорта. Архивный шум без паспорта (M8: в выборку окна не идут) — не получает hard-защиты; при давлении квоты уходит первым вместе с фоном. Иначе дежурство трёх часов проиграет полутора месяцам мусора — абсурд на слух и по диску.

[Верстальщик]: Покажу оператору раздельно: «текущее дежурство» и «прочее на устройстве». Второе — список с объёмом и действием очистки по правилам lifecycle, не смешанный timeline. Иначе конструкция экрана врёт, что все 116 — равноценны hard-событию. Для a11y: статус квоты — текст + `aria-valuenow`, не только цвет полосы.

[Teamlead]: Спор по soft при критическом давлении: Музыкант допустил ужатие soft. Математик поставил soft ниже hard, но выше background. Принимаю: soft не «никогда», soft — «после фона, до hard». Hard — никогда политикой авто-вытеснения. Снять hard — только явная команда оператора вне этой политики. Это комбинация, не соло.

[Архитектор]: Серверная сторона ещё раз одной фразой: 413 сохраняем; сервер не вытесняет уже принятое, чтобы принять новое, в рамках этого вердикта. Если когда-нибудь понадобится серверная GC — отдельный ADR и комната, не M9. Узел при 413: продолжает duty (M4), применяет компактификацию/не-слать (M5), при `Σ s → Q` — `evictByFate`. Нет пинг-понга «сервер удали → я дошлю».

[Математик]: Порог θ для soft не назначаю численно в этом вердикте — это параметр политики, не новая комната предиката (M7 закрыт). В контракте lifecycle достаточно: существует θ, и comparator использует confidence. Размер окна W для soft/hard — константа конфигурации узла; сырой фон вне окон в store не удерживается дольше горизонта компактификации `T_compact`.

[Структурщик]: Владение конфигурацией: `Q_node`, `W`, `T_compact`, θ — манифест/конфиг узла; `Q_server` — конфиг сервиса приёма. Клиент UI читает оба статуса через фасады, не пишет квоту сервера «на глаз». Нарушение связанности: UI, дергающий fs-unlink ленты в обход duty-lifecycle сервиса — BLOCK на ревью.

[Музыкант]: Режим записи duty по умолчанию после этого вердикта: не «wav на всё», а непрерывный анализ + удержание raw только в скользящем pre-roll, из которого при soft/hard вырезается окно. Иначе математика Дынина (912 МБ/3ч) бьёт 1 ГиБ независимо от красивой eviction. Lifecycle без смены режима записи — дырявое ведро с хорошим краном.

[Верстальщик]: Тогда empty-state после вытеснения фона честный: «фон снят по квоте, N событий на узле, M ждут приёма». Не пустой экран «нет данных». Это и есть сообщение конструкции: место кончилось предсказуемо, ценность осталась.

[Teamlead]: Сводим к принятию. Есть возражения по (C) двум квотам, hard-нерушимости, 413, dropped_local для неуехавшего? Молчание после круга = принять. DoD — только M9: политика судьбы, сторожа квот, поведение при 413, судьба неуехавшего. Не тащить сюда API паспорта и предикат события.

[Архитектор]: Возражений нет. Форма: узел — владелец кольца и eviction; сервер — владелец отказа при переполнении; судьба из паспорта — ключ Survivability; неуехавшее + evict = terminal drop на узле. Рекомендация — фиксировать вердиктом без ADR-развилки: посылки Т12/Т3/M4/M5/M7/M8 уже несут конструкцию.

[Математик]: Принимаю. Инварианты численные: hard ⊂ store при наличии вытесняемого меньшего класса; ключ не time-primary; 413 не меняет Σ на сервере. Порог θ и W — параметры, не дыры вердикта.

[Структурщик]: Принимаю. Словарь: fate, Q_node, Q_server, evictByFate, dropped_local, rejected_413. Два сторожа, два конфига, один паспорт как носитель судьбы (M8 дан).

[Музыкант]: Принимаю. Фон режется первым, hard-окно и отпечаток святы для авто-политики, запись duty больше не равна «писать всё сырьём».

[Верстальщик]: Принимаю. UI: квота, судьба, 413 как граница, split «дежурство / прочее». Политику не изобретаю в JSX.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| O1. Жизненный цикл при нехватке места | **Две квоты, два сторожа; вытеснение на узле по судьбе; 413 на сервере сохраняется** |
| Что вытесняется первым | Материал класса `none`/фон (в т.ч. сырой быт и тишина вне окон); затем orphans без паспорта и вне текущей duty-сессии; затем `soft` с меньшей уверенностью (допустимо сжатие до отпечатка + укороченного окна) |
| Что не вытесняется никогда (авто-политикой) | `hard`-окна целиком; паспорт записи; отпечаток, связанный с hard/soft-событием. Снятие hard — только явная команда оператора, не eviction |
| Где квота и кто сторожит | **Оба:** `Q_node` сторожит узел (кольцо / `evictByFate`); `Q_server` сторожит сервер (приём или 413). Ключи конфига раздельные |
| Ключ ротации | Признак судьбы (`fate` + confidence), не время; FIFO только как tie-break внутри класса |
| Материал, не уехавший до вытеснения | Терминально сбрасывается на узле (`dropped_local`); сервер его не имел; infinite retry queue сверх квоты не обещается; исходящая очередь входит в бюджет `Q_node` |
| Отказ сервера при переполнении | **Остаётся 413**; сервер не вытесняет уже принятое, чтобы принять новое (серверная GC — вне M9). Узел при 413: duty продолжает (M4), компактифицирует/не шлёт (M5), при давлении `Q_node` — `evictByFate` |
| Режим записи как условие жизнеспособности | Duty по умолчанию: анализ + pre-roll, raw удерживается в событийных окнах; «писать всё сырьём» несовместим с квотой 1 ГиБ на многочасовом дежурстве |
| UI (следствия, не отдельная политика) | Честные индикаторы `Q_node` / pending / 413-как-граница; визуальный вес hard > soft > background; разделение «текущее дежурство» / «прочее на устройстве» |

**Definition of Done (M9):**

1. Зафиксирована политика `evictByFate` с порядком Survivability: `background/none → soft(low conf) → soft(high conf) → hard` (hard авто-evict не подлежит).
2. Конфиг разделяет `Q_node` и `Q_server`; на узле есть сторож переполнения; на сервере приём при переполнении даёт 413 без delete accepted.
3. Статус исходящего включает терминальный `dropped_local` для неуехавшего, вытесненного локально; не маскируется под `pending`.
4. Записи без паспорта и чужой архивный шум не получают hard-защиты и уходят не позже фона.
5. Тест/прогон: при забитом фоне hard-окно трёхчасового сценария сохраняется в пределах `Q_node ≈ 1 GiB`; при 413 узел не теряет duty и не требует серверной ротации.
6. UI-контракт состояний квоты и 413 описан как отображение политики (без бизнес-логики eviction в JSX).
