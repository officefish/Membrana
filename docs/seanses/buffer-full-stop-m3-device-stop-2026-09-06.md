## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| **(а) Что гасится / что живёт** | **Гасится** при `overflowPolicy=stop`: складирование и отправка **новых** проб (T2); **активная запись** (допись медиа); **новый старт** записи/медиа-ветки. Сценарий не «убивается» целиком, а переводится в **permanent hold** на медиа (без авто-resume после освобождения места). **Живёт:** связь/сессия с сервером (T16); детекция и наблюдение потока **без** записи; рантайм доски/плагина. **Запрещено** гасить телеметрию/канал «вместо» отправки (анти-паттерн ночи 05→06.09). |
| **(б) Источник вердикта** | **Оба:** (1) **главный** — ответ сервера на пробу по контракту M2 (`ok:false` + `reason` + `overflowId`); (2) **вторичный** — собственное чтение квоты до отправки (ранний guard). При расхождении **сервер главнее**; local hold без id **promote** в серверный `overflowId` без второго эпизода/окна. |
| **(в) Память «уже остановлен»** | Один device-level носитель эпизода (**OverflowHold**): факт hold + **`overflowId`** (+ reason/policy snapshot). Один `overflowId` → один сигнал окна (T9); любой новый запуск сценария/записи при активном hold отбивается тем же фактом и снова может поднять окно по правилам T5 (не обходимо). Hold переживает смену/рестарт сценария; сброс — действием человека/очисткой (не специфицировать в M3). |
| **(г) Проводка на два входа** | **Общий носитель вердикта** + две тонкие проводки (адаптеры): доска устройства и модуль микрофона. **Не** две независимые реализации контракта (T6). |
| **Строить** | `DeviceOverflowHold` (activate from server / local guard, isHeld, getEpisode, subscribe); разбор M2 на send-path; local quota guard; quench active record; block new media; адаптеры board + mic. |
| **НЕ строить** | Stop канала/телеметрии как суррогат; kill сценария целиком; дубль state-machine stop в board и mic; авто-resume после free space; ретраи sample POST при hold; поля/коды M2 заново; каналы M4; UI M5; smart_cleanup/T12; тарифы #2297. |

### Definition of Done (только M3)

1. При активном hold и `policy=stop` исходящие POST/отправки **новых** проб = 0 (без ретраев в закрытую дверь).  
2. Канал к серверу и возможность детекции без записи **не** обязательны к остановке; нет логики «buffer full → rвать линк/телеметрию вместо склада».  
3. Отказ M2 с `device_buffer_full` / `user_storage_full` активирует hold с данным `overflowId`; 100 отказов одного id → **один** episode activate для окна.  
4. Local guard и server path пишут в **один** hold; promote id без второго window-event.  
5. Повторный старт сценария/записи при hold отбивается (`isHeld`), без обхода.  
6. Доска и mic-plugin не содержат второй полной копии stop-политики — только вызовы hold.  
7. Нет авто-resume медиа после появления места (permanent hold до человека).  
8. В протоколе есть секция **«Список посылок»**; границы M4/M5/T12/#2297 не колонизированы в DoD.

### Повестка (docs/meeting/buffer-full-stop/M3_AGENDA.md) — полное эхо

# Заседание «Полный буфер: контракт остановки» — M3 (S) Что именно останавливается на приборе и как один раз

**Объединяющее задание (одно на всё заседание):** превратить тезисы шторма 06.09 в исполнимый
контракт остановки при полном буфере — сервер, прибор, оператор, — чтобы ночь 05→06.09 не
повторилась и вещдоки в буфере не пострадали.

**Порядок M0 (ратифицирован владельцем 06.09):** M1 (P) политика → M2 (C) код отказа →
**M3 (S) остановка на приборе** → M4 (L) жизнь после → M5 (W) окно оператора. Предшественники —
M1 и M2; их вердикты — посылки этой комнаты.

## Данности (закрыто штормом, НЕ переоткрывать)

- При переполнении прибор сам прекращает отправку проб — без повторов в закрытую дверь (T2).
- Окно закрываемо, но не обходимо: повторный запуск сценария при полном буфере снова останавливает сценарий и снова поднимает окно (T5).
- Одно поведение в двух местах: в сценариях доски устройства и в модуле микрофона при активации плагина записи (T6).
- Событию «полон» нужна однократность: один факт переполнения — одно окно, не окно на каждую отвергнутую пробу (T9).
- Связь при полном буфере не рвётся; ограничение только на складирование новых медиафайлов (T16).

## Вердикт M1 (посылка)

- Политика — поле в записи прибора на сервере записей, разносится из кабинета; клиентская настройка — зеркало; умолчание и любая дыра — `stop`.

## Вердикт M2 (посылка)

- Отказ «полон» — доменный: HTTP 200 + `{ ok:false, reason }`; 413 больше не сигнал квоты.
- `reason` из закрытого списка: `device_buffer_full` (буфер прибора), `user_storage_full` (хранилище коллекций); прочие — позже (T15).
- В ответе обязательны: `buffer{usedBytes,limitBytes}`, `userStorage{usedBytes,limitBytes}`, `overflowPolicy` (stop | smart_cleanup), `overflowId` — идентификатор эпизода переполнения, один на все отказы эпизода.
- Словарь — один shared-пакет монорепо; сервер чеканит, прибор и кабинет импортируют.
- Следствие для этой комнаты: у прибора есть машинный код и идентификатор эпизода — есть чем остановиться один раз и чем помнить.

## Фактура (сверено в стволе da051639)

- Плагин записи микрофона несёт вердикт остановки «порог → стоп → сигнал» с политикой; при `stop` активная запись гасится по вердикту, новый старт отбивается тем же вердиктом, после освобождения места сценарий сам не возобновляется (permanent hold до действия человека). При `auto-cleanup` вердикт остановки не наступает — ночью так и было.
- Вердикт сегодня считается из ЧТЕНИЯ квоты прибором (числа занято/лимит), не из ответа сервера на пробу; ответ 413 плагином не разбирается.
- Доска устройства запускает сценарии со своими узлами захвата; проводка остановки по буферу в них отдельная от плагина микрофона или отсутствует — предмет проверки комнаты.
- Ночью: телеметрия узла оборвалась в минуту заполнения, при этом пробы продолжали уходить 11 часов — то есть «что-то остановилось», но не отправка.
