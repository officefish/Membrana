# Консилиум: путь тревоги сторожа диска (G1)

**Повестка:** G1 — каким коротким путём тревога сторожа диска уходит в телеграм (офис сам транзиентно таймаутит — тревога через офис умирает вместе с ним), где живёт сам сторож, и кто сторожит сторожа — чем обнаруживается его тишина?

**Участники:** Teamlead (Tarasov), Архитектор (Vesnin), Структурщик (Ozhegov), Математик (Dynin), Музыкант (Kuryokhin), Верстальщик (Rodchenko).

**Порядок реплик:** Архитектор → Структурщик → Математик → Музыкант → Teamlead → Верстальщик

---

[Архитектор]: Конструкция узкая: сторож — локальный контур на машине с диском, не модуль офиса. Диск media/кабинета — предмет измерения; офис — транзиентный посредник, который по данности таймаутит. Тревога «через офис» как единственный путь — форма, которая не выдерживает отказ носителя канала. Первичный путь — прямой Bot API с машины диска; офис — только запасной, не несущий. Недобыто: достигает ли media/кабинет `api.telegram.org` — зависимость, не допущение.

[Структурщик]: Лемма: `DiskSpaceWatchdog` ≠ `TelegramClient` офиса. Сторож — отдельный процесс/юнит на хосте диска; публичный контракт — «измерил → решил → отправил», без импорта office-кода. Секрет токена не просачивается из env офиса в media через общий пакет: раскладка — свой env/secret на хосте сторожа. Запасной путь «через офис» — отдельный адаптер с явным именем, не общий фасад «просто telegram».

[Математик]: Формализую. Пусть `free_bytes(t)` — свободное место в момент t, `write_rate` — байт/с записи (медиана за окно, не пик одной ночи). Остаток минут: `T_remain = free_bytes / max(write_rate, ε)`. Порог тревоги — по `T_remain`, не по «круглым ГБ»: так есть физический смысл. Ночь 23.08: ~0,5 ГБ — калибр цены, не сам порог. Расписание проверки: период `τ_check ≪ T_remain_alarm`, иначе промах между тиками.

[Музыкант]: С края поля: на дежурстве буфер — это лента, не «диск сервера». Когда место кончилось — записи нет, материал невозвратен. Сторож обязан жить там же, где пишется звук: media/кабинет, до сборщиков, как в Д1. Офис может спать или таймаутить — микрофонный контур от этого не становится тише. Прямой сигнал в телегу с хоста диска — единственный путь, который слышен при мёртвом офисе.

[Teamlead]: Положение: Д1 не пересматриваем; сторож — P0 в исполнении. Решение формы: живёт на машине диска; путь — прямой Bot API + запасной через офис. Связка на кусок: Математик — пороги и предикат тишины; Структурщик — границы модуля и секрет; Музыкант — смысл write_rate для ленты. Вердикт комнаты держим до закрытия DoD-предикатов. Прод не трогаем — только план раскладки.

[Верстальщик]: UI этой комнаты нет — и не надо. Но оператору в телеге нужна честная конструкция сообщения: хост, том, `free` числом, `T_remain` в минутах, порог. Без метафор «диск болеет». Тишина сторожа на витрине офиса — соседняя комната; здесь только чтобы текст тревоги читался без легенды, `tabular-nums` в голове автора шаблона.

[Архитектор]: Запасной путь через офис оправдан только при отказе прямого (сеть/фильтр до Bot API). Не наоборот: офис-first снова убивает тревогу вместе с офисом. Два канала — не украшение: цена — второй адаптер и секрет на двух концах. Рекомендация: primary = direct; secondary = office HTTP/event только если direct вернул транспортный отказ. Зависимость reachability — в DoD как добыча до включения primary в проде.

[Структурщик]: Словарь исходов отправки: `sent_direct | sent_via_office | failed_both | skipped_no_token`. Не смешивать с health офиса. Секрет: bot token + chat id — **отдельный** read-only secret хоста media/кабинета (plan: кладёт ops/Математик-контур секретов при выкладке юнита; прод сейчас не трогаем). Офисный токен не копируем «на всякий» из running prod — план выдачи/ротации, тот же bot или dedicated alert-bot — решение владельца секретов, не этой комнаты по деплою.

[Математик]: Предикат тревоги места: `alarm_space ⇔ T_remain < T_crit ∨ free_bytes < B_floor`. `B_floor` — жёсткий пол (inode/служебный запас), `T_crit` — минуты ленты. Предлагаю порядок величины для старта (норма комнаты, калибруется замером write_rate): `T_crit = 60 мин` записи; предупреждение (warn, не flood) при `T_remain < 180 мин`. Период check: 5 мин — при 60 мин запаса это ≥12 точек до нуля. Антишторм: повтор alarm не чаще 1 раз / 30 мин, пока условие истинно.

[Музыкант]: Write_rate брать с живой записи, не из «теоретических 48k/16 mono». Сеанс 21.08 давал сотни МБ/час при нарезке; duty-лента может быть иной по судьбе фона. Для сторожа достаточно: скользящая медиана прироста занятого места на томе записи за 15–30 мин, либо консервативный потолок «худший наблюдаемый байт/с». Лучше слегка рано заорать, чем опоздать на невозврат.

[Teamlead]: Нагрузка ясная: без добычи «media → api.telegram.org» primary не считаем включённым в проде — это не блокатор проектирования, это ворота DoD. Кто сторожит сторожа — не откладываем: тишина = неотличимо от «место есть» — провал матча. Назначаю в решение: presence-сигнал сторожа и встречный контроль с отдельным порогом тишины.

[Верстальщик]: В тексте Telegram для тишины сторожа — отдельный шаблон: «сторож N не отметился с T», не путать с «диск полный». Два разных сообщения — два разных действия человека. Иерархия: space-alarm важнее stale-watchdog по цвету/префиксу только если оба живы; если сторож молчит — сначала «нет глаз на диск».

[Архитектор]: Кто сторожит сторожа. Конструкция: сторож пишет heartbeat (presence) локально и/или шлёт периодический ok-ping в тот же Telegram-канал реже alarm (например раз в H часов — но это шум). Чище: presence-файл/метрика на хосте + **внешний** наблюдатель, который не живёт в том же процессе. Внешний — не офис-единственный: при мёртвом офисе тишина сторожа снова невидима. Значит: (1) cron/systemd timer sibling «watch the watchdog»; (2) optional secondary notice в Telegram при stale presence — тоже direct path.

[Структурщик]: Лемма `WatchdogPresence`: артефакт `last_ok_ts` на диске хоста (или user-unit state), обновляется каждым успешным циклом check. Sibling-юнит `disk-watchdog-stale.timer` читает `now - last_ok_ts > T_silence →` тревога «тишина сторожа». Не импортировать код сторожа — только контракт файла/пути. Офис может позже читать presence для витрины — соседняя комната; здесь офис не единственный сторож сторожа.

[Математик]: `T_silence`: если `τ_check = 5 мин`, то `T_silence = 3 · τ_check = 15 мин` — три пропущенных цикла, не один (ложные от jitter/stop-start). Предикат: `stale ⇔ (now - last_ok_ts) > T_silence`. DoD-предикат куска: `office_down ∧ space_below → ∃ delivery direct`; `watchdog_stopped → stale_detectable within T_silence + ε`. ε — лаг sibling timer (≤ τ_check).

[Музыкант]: Sibling на той же машине — да: если сгорела вся машина, ни диск, ни сторож, ни sibling не пишут — и это уже другой класс («хост мёртв»), не «сторож молчит при живом диске». Для дежурства важно отличить: процесс сторожа упал, а запись ещё идёт и жрёт место. Sibling-timer под systemd как раз ловит «запись жива, сторож нет». Полный death host — вне G1, не раздуваем.

[Teamlead]: Принимаю различение host-dead vs watchdog-dead. В кусок G1 входит только watchdog-silence на живом хосте. Связка исполнения потом: unit + timer + secret plan. Сейчас закрываем путь и пороги. Верстальщик — шаблоны текстов в решении; код UI не открываем.

[Верстальщик]: Шаблоны (содержание, не вёрстка):  
1) `[disk-alarm] host=… vol=… free=… GiB T_remain≈… min`  
2) `[disk-watchdog-stale] host=… last_ok=… age=… min`  
Без markdown-каши и без panics. Префиксы стабильные — чтобы человек фильтровал в клиенте.

[Архитектор]: Итоговая форма пути: **короткий primary** — процесс на хосте диска → HTTPS Bot API (`sendMessage`) fire-and-forget с минимальным retry (1–2) на транспорт; **secondary** — POST в офис (если жив) как best-effort дубль или fallback после failure direct. Офис не ставит в очередь ради этой тревоги в G1 (у офиса нет ретрая сегодня — факт); secondary не создаёт иллюзии надёжности. Надёжность — в direct + local sibling.

[Структурщик]: Пакет/скрипт: ops-утилита в зоне Математика (`scripts/` или unit-обвязка), не плагин кабинета и не Nest-модуль офиса. Кабинет/media не тянут `@office/telegram`. Слабая связанность: сторож зависит от (fs stat, env secret, fetch к Bot API), опционально от URL office fallback. Циклов office↔media не появляется.

[Математик]: Калибровка write_rate — явная процедура DoD, не магия: после установки снять `df`+занятость тома на интервале записи ≥30 мин; зафиксировать `write_rate_ref` в конфиге сторожа. Пока замера нет — консервативный default из известного пика (ночь 0,5 ГБ как нижняя оценка ущерба; rate default завысить). Формула `T_remain` одна, чистая: вход bytes+rate → минуты.

[Музыкант]: «Первым в исполнении, до сборщиков» — это порядок unit/service dependencies на хосте: `disk-space-watchdog` Before/Wants от цепочек, что пишут ленту, или просто отдельный always-on timer, не ждущий batch. Мне важно: сборщик не должен стартовать «nocheck» и добить диск, пока сторож молчит час. Timer каждые 5 мин + once-on-boot.

[Teamlead]: Порядок исполнения — в DoD куска как проверяемое: watchdog timer active independent of collectors. BLOCK буду ставить, если притащат в этот PR `/health/deep` или номер происшествия — чужие комнаты. Здесь только space + silence.

[Верстальщик]: Для человека в чате важно не спамить. Антишторм Математика (30 мин) — согласую: одно сообщение alarm, затем редкие reminders с тем же префиксом. Stale — отдельный антишторм, ещё реже (раз в T_silence или 30 мин), пока presence не оживёт.

[Архитектор]: Секрет — план без трогания прода: (1) завести/выделить bot token + chat_id для disk-alert (или reuse product bot — решение владельца); (2) положить в secret storage хоста media/кабинета при выкладке unit; (3) office token остаётся в office; (4) не коммитить токен. До reachability-probe direct path в проде не активируем — флаг `DIRECT_TG=off` допустим, тогда честный degraded: только secondary+local log, с явной меткой «direct disabled».

[Структурщик]: Имя конфига: `DISK_WATCHDOG_TG_TOKEN`, `DISK_WATCHDOG_TG_CHAT_ID`, `DISK_WATCHDOG_OFFICE_FALLBACK_URL?`, пороги `T_crit_min`, `B_floor_bytes`, `τ_check`, `T_silence`. Словарь env — статья контракта, не «как получится». Presence path: `/var/lib/disk-watchdog/last_ok` (или аналог под user-unit) — один писатель, один читатель-stale.

[Математик]: Сводка чисел-норм комнаты (калибруемые):

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Где живёт сторож | **На машине с диском** (media / кабинет — хост тома записи). Локальный `stat`/`df` тома; не в процессе офиса. Основание: предмет измерения локален; офис транзиентно таймаутит. |
| Порядок относительно сборщиков | Отдельный always-on timer/unit, **до/независимо** от сборщиков (Д1): boot + период, не «после batch». |
| Путь тревоги (primary) | **Прямой HTTPS → Telegram Bot API** с хоста диска (короткий путь, 1–2 транспортных retry, без очереди). |
| Путь тревоги (secondary) | **Fallback/best-effort через офис** только после отказа direct (или дубль best-effort, если офис жив). Офис-first **запрещён** как единственный путь. |
| Отказ офиса | Тревога места **не зависит** от офиса при работающем direct. |
| Отказ прямого пути | Fallback office + локальный лог; **не маскировать** как успех. |
| Недобытая фактура | **Зависимость:** достигает ли media/кабинет `api.telegram.org`. Домысливать нельзя. До успешной добычи — direct в проде не включать (флаг/degraded: log + optional office only). |
| Раскладка секрета | Отдельные `DISK_WATCHDOG_TG_TOKEN` + `DISK_WATCHDOG_TG_CHAT_ID` на хосте сторожа (plan выкладки ops; **прод этим вердиктом не трогаем**). Токен офиса остаётся в env офиса; не импортировать office client. Commit секретов — запрет. |
| Кто сторожит сторожа | Sibling timer/unit на **том же хосте**: читает `last_ok_ts` (presence), пишет/шлёт stale-тревогу. Офис **не** единственный наблюдатель тишины. Host-dead целиком — вне G1. |
| Пороги и расписание (норма комнаты, калибруемые) | `τ_check = 5 мин`; `T_crit = 60 мин` остатка записи → alarm; optional warn `T_warn = 180 мин`; `T_silence = 15 мин` (3·τ); re-alarm ≤1/30 мин; `B_floor = max(1 GiB, ~10 мин·write_rate_ref)`. `T_remain = free_bytes / max(write_rate, ε)`. |
| Write rate | Скользящая оценка по тому записи или консервативный `write_rate_ref` после замера ≥30 мин; до замера — завышенный default. |
| Тексты Telegram | Префиксы: `[disk-alarm]`, `[disk-watchdog-stale]`; поля host, vol, free, T_remain / last_ok, age. |
| Граница модуля | Ops-скрипт/unit (зона Математика/ops), **не** Nest-модуль офиса, **не** плагин кабинета. Исходы: `sent_direct \| sent_via_office \| failed_both \| skipped_no_token`. |

## Вопрос заседания

**G1 — каким коротким путём тревога сторожа диска уходит в телеграм (офис сам
транзиентно таймаутит — тревога через офис умирает вместе с ним), где живёт сам сторож,
и кто сторожит сторожа — чем обнаруживается его тишина?**

## Данности (не предмет спора)

- Д1 (директива, две подписи): свободное место media/кабинета проверяется по расписанию,
  сигнал в телеграм; сторож — **первым в исполнении**, до всех сборщиков. Основание:
  единственная мера, где цена промедления — невозвратная потеря материала (ночь 23.08
  съела ~0,5 ГБ; заполненный буфер на дежурстве = потерянные записи).
- Факт: телеграм сегодня шлёт только офис — `TelegramClient` fire-and-forget в Bot API,
  токен и chat id в env офиса, без очереди и ретрая; офис транзиентно таймаутит
  (норма ласточки: «повторить, проверить health»).
- Факт: на машинах media/кабинета токена сегодня нет.
- НЕ добыто: достаёт ли машина media/кабинета до `api.telegram.org` напрямую
  (география/фильтры провайдера). Домысливать нельзя — если путь на это опирается,
  назвать зависимостью и внести добычу в DoD.

## Что комната должна выдать

- Где живёт сторож (на самой машине с диском / рядом) и почему.
- Путь тревоги: прямой в Bot API / через офис / оба с падением на запасной — с
  обоснованием от отказа офиса И отказа прямого пути.
- Раскладку секрета: чей токен, где лежит, кто его кладёт (прод не трогать — план).
- Кто сторожит сторожа: чем видна тишина сторожа (сигнал присутствия, встречный
  контроль, порог тишины) — тишина не должна быть неотличима от «всё хорошо».
- Пороги места и расписание — с физическим смыслом (сколько минут записи остаётся).
- **DoD куска**: проверяемый предикат (тревога доходит при лежащем офисе; тишина
  сторожа обнаружима).
