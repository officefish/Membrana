Без displayForm страница не знает, рисовать ли гистограмму или строку тиков. Поле обязательное — иначе страница вынуждена угадывать или падать. description — необязательное; используется для человекочитаемого пояснения на витрине, но отсутствие не ломает поток.

[Математик]: Формализую предикат: ShowcaseManifest вводит поля тогда и только тогда, когда страница не может вывести их значение из базовых пяти полей детерминированно. kind уже говорит «showcase» — но не говорит, какую форму показа выбрать внутри рода. Значит displayForm — необходимое дополнение. description не выводится из базы; при наличии — полезен. Лишних полей вводить не стоит: каждое лишнее поле — нарушение минимальности контракта.

[Верстальщик]: С витрины читателя: страница получает манифест и должна без угадывания знать, какой компонент рендерить. displayForm — это типографика смысла: явный тег формы, не скрытая конвенция в slug. Если displayForm не задан — страница либо рисует дефолт (что нечестно), либо падает. Обязательность поля защищает пользователя от пустого слота. description даёт подпись под витриной — полезно, но не блокирует рендер при отсутствии.

[Архитектор]: Конструкция ShowcaseManifest ясна: два добавочных поля поверх базы. Первое — displayForm: DisplayForm, обязательное — это несущая конструкция витринного рода. Второе — description?: string, необязательное — декор с функцией. Прежний вердикт M5 предлагал то же самое; переподтверждаю на честной базе. Никаких label, enabled — они в базу не входили и в расширение не входят. Архитектурно чисто.

[Структурщик]: Теперь словарь DisplayForm. Прежний вердикт: row · table · zone-map · histogram · time-series плюс лазейка x-${string}. Все четыре примера покрыты пятью значениями без остатка. Лазейка x-${string} нужна для экспериментальных форм без поломки типа. Словарь переподтверждаю.

[Teamlead]: Лазейка — это предохранительный клапан, не приглашение к хаосу. Страница обязана иметь fallback-ветку при получении x-${string}: либо generic-заглушка, либо «форма не поддерживается». Без обязательного fallback лазейка опасна — страница упадёт на неизвестном значении. Это условие переподтверждаю из прежнего вердикта; оно остаётся в силе.

[Музыкант]: Соглашусь с fallback-веткой. Три смысловых кластера. Это помогает писать narrowing по кластерам, если страница захочет группировать.

[Математик]: Проверяю полноту словаря против посылки. Т2 даёт четыре конкретных примера витрин; все четыре отображаются в пять форм без добавления. Расширение словаря первой волны не обосновано посылками — лишнее. Лазейка x-${string} нужна именно потому, что посылки не исчерпывают будущих форм: это честная открытость при закрытом первом-волновом списке. Математически: закрытое перечисление с явным escape-клапаном — наилучшая форма для версионируемого контракта.

[Верстальщик]: Для рендера важно: пять конкретных значений + x-${string} — это discriminated union, не string. TypeScript сужает тип в switch; fallback — ветка default. Если сделать DisplayForm просто string — теряем проверку на этапе компиляции. Union с литералами + шаблонный литерал — правильная конструкция. Переподтверждаю.

[Архитектор]: Словарь закрыт для первой волны, open через x-${string} для экспериментов. Контракт: тип DisplayForm = 'row' | 'table' | 'zone-map' | 'histogram' | 'time-series' | `x-${string}`. Страница обязана обрабатывать неизвестный x-префикс без исключения. Это архитектурно честно: плагин декларирует намерение, страница решает, умеет ли она его исполнить. Переподтверждено.

[Структурщик]: Переходим к каналу чтения. Посылка M2: IPluginHost.getRegisteredPlugins() возвращает ReadonlyArray<PluginManifest>. Единственный канал: getRegisteredPlugins(). Альтернатива — отдельный getShowcasePlugins() — создаёт дублирование API без выигрыша; отклоняем.

[Teamlead]: Канал один — это дисциплина. Два метода на одно и то же — прямой путь к рассинхрону. Narrowing по kind — стандартный TypeScript; достаточно. [Музыкант]: Канал чтения — pull, не push. Страница запрашивает список, не подписывается на поток. Это важно: реестр не гонит события при изменении набора плагинов — страница сама решает, когда перечитать. Это упрощает реализацию и снижает связанность. Для первой волны pull достаточен.

Типы: HandlerManifest { kind: 'handler' }, ReportManifest { kind: 'report' }, ShowcaseManifest { kind: 'showcase' }. ## Итоговое решение консилиума

| Грань | Решение |
|-------|---------|
| **Состав ShowcaseManifest** | `interface ShowcaseManifest extends PluginManifest { displayForm: DisplayForm; description?: string }` — два поля поверх базы; третьего нет; enabled/label не вводятся |

| **Канал включения** | Отдельный метод `IPluginHost.setPluginEnabled(id: PluginId, enabled: boolean): void`; не канал request; PluginId branded; авторизация вне предмета собрания |

# Повестка M5′ — заседание server-plugin-foundation (переигрывание по вердикту аудита)

**Q5′ — Какова форма самоописания плагина для витрины, при том что базовый `PluginManifest` несёт РОВНО пять полей — `id` · `version` · `kind` · `mountTarget` · `triggers` — шестого нет, `enabled`/`label` в манифесте НЕ существуют (включённость — операция реестра, не поле манифеста), а расширять состав вправе только расширяющие типы родов (`ShowcaseManifest` и т.п.)?**

Единственный вопрос комнаты. Это переигрывание M5 по вердикту аудита 17.08: прежний вердикт стоял на сочинённом составе базового манифеста («предположу рабочий состав»: id, version, enabled, kind, label — находки A5-1/A5-2/A5-3). Состав базы дан в строке вопроса поимённо и НЕ обсуждается; своя база не вводится.

Что комната обязана решить (грани одного вопроса):

- Состав `ShowcaseManifest`: какие поля добавляются ПОВЕРХ пяти базовых (со шторма Т3.6: форма показа объявлена в самоописании; прежний вердикт предлагал `displayForm: DisplayForm` обязательным и `description?: string` — переподтвердить или изменить, теперь на честной базе).
- Словарь форм показа `DisplayForm`: закрытый список первой волны (прежний вердикт: row · table · zone-map · histogram · time-series с лазейкой `x-${string}` и обязательной fallback-веткой страницы) — переподтвердить или изменить.
- Канал чтения: как страница узнаёт список плагинов дома и самоописания (прежний вердикт: единственный канал `IPluginHost.getRegisteredPlugins()`, narrowing по kind).
- Канал включения: прежний вердикт — отдельный метод `setPluginEnabled(id: PluginId, enabled: boolean)`, не канал request; границы авторизации — вне предмета.
- Самоописание не-витринных родов: видимы ли handler/report странице для Т1-переключения, и чем их манифесты беднее витринного (прежний вердикт: витринных полей у них физически нет в типе — переподтвердить или изменить).

Посылки комнаты (даны, не обсуждаются): M1_VERDICT.md — АВТОРИТЕТ словаря (пять полей поимённо как в строке вопроса; PluginId branded `<org>.<kind>.<slug>`; включённость — операции реестра enable/disable, НЕ поле манифеста; расширения — только через HandlerManifest/ReportManifest/ShowcaseManifest; владелец словаря и гейты классов); M2_VERDICT.md (два дома; IPluginHost.getRegisteredPlugins(): ReadonlyArray\<PluginManifest\>); M4_VERDICT.md (канал request для постфактум; PLUGIN_TRIGGERS закрыт; сигнатуры с PluginId, не сырыми строками); Т1 шторма (переключаемость на уровне модуля — норма); Т3.6 шторма (данные для картины, не картина; форма показа в самоописании — норма); Т2 шторма (примеры витрин владельца: сортировка по громкости, пиковые зоны, аномалии, тренды — факт); вердикт аудита 17.08 (A5-1…A5-5); границы MEETING_BRIEF.md (клиентский UI вне предмета; код после вердиктов).

Требование к вердикту: назвать форму самоописания по всем граням с обоснованием против альтернатив И полный список посылок вердикта (факт/норма) в том же прогоне. Список посылок обязателен; лишняя посылка — тоже нарушение. Базовый состав манифеста НЕ переоткрывать — он в строке вопроса; `enabled`/`label` не вводить; вопросы прав вызова в чужие комнаты не передавать (находка A5-5 — границы авторизации просто вне предмета собрания).
