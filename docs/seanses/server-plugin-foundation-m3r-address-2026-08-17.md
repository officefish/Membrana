# Консилиум: Узкое переигрывание M3 — RunAddress и окно накопления

**Повестка:** Где в адресе прогона дом крепления (`mountTarget: HomeName`) и где объявляется окно накопления, при PluginId вида `<org>.<kind>.<slug>` и `mountTarget` манифеста как `HomeName` длинной формы.

**Участники:** Музыкант (Kuryo­khin), Структурщик (Ozhegov), Математик (Dynin), Верстальщик (Rodchenko), Архитектор (Vesnin), Teamlead (Tarasov).

**Порядок реплик:** Музыкант → Структурщик → Математик → Верстальщик → Архитектор → Teamlead (циклически, ≥30 реплик)

---

[Музыкант]: Открываю с практики. Плагин `membrana.handler.mfcc` монтируется в `background-media/collections`. Когда runtime запускает прогон, ему нужно знать: в каком доме этот плагин живёт — чтобы маршрутизировать результат в правильный офис. Из `pluginId` дом не читается: `handler` — это род, не адрес. Значит дом должен явно лежать в `RunAddress`. Иначе runtime слепой.

[Структурщик]: Фиксирую лемму. `RunAddress` — это адрес одного конкретного прогона в системе. По Т3.3 цепочка: `модуль → плагин → версия → коллекция → прогон`. Из этих звеньев `pluginId` даёт «плагин» (`org.kind.slug`), `version` — версию, `collectionId` — коллекцию, `runId` — прогон. Звено «модуль» в цепочке — это дом крепления. Если `pluginId` его не кодирует, значит `mountTarget` должен быть явным полем `RunAddress`. Альтернатива — восстанавливать дом из реестра по `pluginId` — это скрытая зависимость: `RunAddress` перестаёт быть самодостаточным адресом.

[Математик]: Поставлю предикат строго. Пусть `A = RunAddress`. Функция `home(A)` должна быть детерминированной и не требовать обращения к внешнему реестру в момент адресации. Если `home(A) = lookup(A.pluginId, HOME_REGISTRY)` — это не функция адреса, это запрос. Адрес — замкнутая структура. Значит `home` должен быть полем `A` напрямую: `A.mountTarget: HomeName`. Второй момент: уникальный индекс `{pluginId, version, collectionId, runId}` — он не включает `mountTarget`. Является ли `mountTarget` частью уникальности? Нет: `(pluginId, version, collectionId, runId)` уже уникально идентифицирует прогон — `mountTarget` функционально зависит от `pluginId` через манифест. Индекс менять не нужно.

[Верстальщик]: Смотрю с витрины: когда оператор открывает журнал прогонов, он фильтрует по дому — `background-office/journal` или `background-media/collections`. Если `mountTarget` нет в `RunAddress`, фильтр требует join с манифестом плагина. Это разрыв между данными и их отображением. Для честного UI `mountTarget` в `RunAddress` обязателен — не как вычислимое поле, а как явное. Иначе любой список прогонов по дому — это агрегат поверх скрытой связи.

[Архитектор]: Конструкция прояснилась. Три альтернативы адресации дома: (1) восстанавливать из HOME_REGISTRY по `pluginId` — скрытая зависимость, нарушает замкнутость адреса; (2) кодировать в `pluginId` — M1 прямо запрещает, второй сегмент есть род, не модуль; (3) явное поле `mountTarget: HomeName` в `RunAddress`. Третий вариант — единственный, не нарушающий ни M1, ни M2, ни замкнутости адреса. Цена: одно добавленное поле в структуру `RunAddress` и в схему Mongo-документа. Принимаю вариант 3.

[Teamlead]: Позиции сошлись на поле. Фиксирую: `RunAddress` несёт `mountTarget: HomeName` явным полем. Прежний индекс `{pluginId, version, collectionId, runId}` — не меняется, `mountTarget` в индекс не входит. Теперь второй вопрос — окно накопления. Слово Математику.

[Музыкант]: По окну: `windowSize` нужен плагину-обработчику для того, чтобы знать, сколько входных событий или тактов формируют один прогон. Это параметр поведения рода `handler`, не произвольный параметр любого плагина. Report и Showcase окно не используют — у них нет накопления. Значит `windowSize` принадлежит `HandlerManifest`, а не базовому манифесту.

[Структурщик]: Три кандидата для `windowSize`: (A) `HandlerManifest` — расширяющий тип рода `handler`; (B) `StateRecord` — запись состояния прогона; (C) конфигурация вне манифеста. По M1: базовый манифест закрыт пятью полями, расширения легальны через `HandlerManifest`. `StateRecord` — это хранимое состояние прогона, а не декларация поведения плагина. Класть декларативный параметр `windowSize` в `StateRecord` — смешение объявления и состояния. Кандидат (A) чист структурно.

[Математик]: Формализую различие. `windowSize` — константа декларации: она задаётся автором плагина при публикации и не меняется в ходе прогона. `StateRecord` — переменная исполнения: она меняется по мере накопления находок. Класть константу декларации в переменную исполнения — это нарушение инварианта неизменности `StateRecord` при заморозке (непереигрываемый M3). После заморозки `StateRecord` `windowSize` не должен меняться — но и не должен там оказаться, потому что он не менялся никогда. Место `windowSize` — `HandlerManifest`.

[Верстальщик]: С витрины: если `windowSize` в `HandlerManifest`, то карточка плагина в UI читает его из манифеста напрямую — один источник истины. Если в `StateRecord` — нужно заходить в прогон, чтобы узнать параметр декларации. Это инверсия: деталь реализации становится воротами к декларации. Поддерживаю `HandlerManifest`.

[Архитектор]: Закрываю находки A3-3/A3-4. `windowSize` объявляется в `HandlerManifest` — расширяющем типе рода `handler`. Это легально по M1 («расширения — через HandlerManifest/ReportManifest/ShowcaseManifest»). Т3.10 говорит «накопление определяется окном» — где объявлять, не говорит; мы не приписываем ему этого. Место выбрано по структурному принципу: декларация рода живёт в типе рода.

[Teamlead]: Хорошо. Теперь проверю периметр. `RunAddress` — поля: `pluginId`, `version`, `collectionId`, `runId`, `mountTarget`. Это пять полей адреса. Кто-нибудь видит лишнее или пропущенное звено в цепочке Т3.3?

[Музыкант]: Цепочка Т3.3 — «модуль → плагин → версия → коллекция → прогон». Проверяю: модуль — это `mountTarget` (дом крепления = модуль офиса); плагин — `pluginId`; версия — `version`; коллекция — `collectionId`; прогон — `runId`. Все пять звеньев покрыты. Пропущенных нет.

[Структурщик]: Согласен с покрытием. Уточню: `mountTarget` в `RunAddress` — это не дублирование поля манифеста, это перенос значения в адрес прогона. Манифест — декларация плагина; `RunAddress` — адрес конкретного исполнения. Они разные сущности, и одинаковое поле в них — не дубль, а правильная денормализация для замкнутости адреса.

[Математик]: Проверю индекс. Прежний уникальный индекс: `{pluginId, version, collectionId, runId}`. Вопрос: нужно ли добавлять `mountTarget`? Аргумент за добавление: дом — часть уникальности прогона. Контраргумент: `pluginId` функционально детерминирует `mountTarget` через манифест — два прогона с одинаковым `pluginId` всегда имеют одинаковый `mountTarget`. Добавление `mountTarget` в индекс не меняет множества уникальных документов. Индекс остаётся `{pluginId, version, collectionId, runId}`. Математически верно.

[Верстальщик]: Подтверждаю: для UI-запросов «все прогоны в доме X» будет нужен индекс по `mountTarget`. Это операционный индекс для выборки, а не уникальный. Его можно добавить отдельно: `{mountTarget, pluginId, runId}` как вспомогательный. Это за рамками переигрывания, но фиксирую как наблюдение.

[Архитектор]: Наблюдение Родченко принято к сведению, но не входит в вердикт этой комнаты — переигрывание узкое. Уточняю финальную форму: `RunAddress` = `{ pluginId: PluginId, version: string, collectionId: string, runId: string, mountTarget: HomeName }`. Уникальный индекс Mongo — без изменений: `{ pluginId, version, collectionId, runId }`. `windowSize` — поле `HandlerManifest`, не `StateRecord`, не базового манифеста.

[Teamlead]: Проверяю против посылок. M1 — базовый манифест закрыт, расширения через `HandlerManifest` — `windowSize` туда: ✓. M2 — `mountTarget: HomeName`, два дома длинной формы — поле в `RunAddress` это значение: ✓. Прежний M3 непереигрываемый — `StateRecord` не трогаем, `ConvergenceRecord` не трогаем: ✓. Т3.3 — цепочка покрыта пятью полями: ✓. Т3.10 — окно есть, место мы не приписываем Т3.10: ✓. Аудит A3-1/A3-2 — PluginId не несёт namespace модуля — `mountTarget` явное поле: ✓. A3-3/A3-4 — `windowSize` закрыт в `HandlerManifest`: ✓.

[Музыкант]: Один контрольный вопрос по замкнутости: если плагин переезжает в другой дом (меняет `mountTarget` в манифесте), старые прогоны сохраняют свой `mountTarget` в `RunAddress` — и это правильно, потому что адрес прогона фиксирует момент исполнения, а не текущее состояние манифеста. Замкнутость работает как надо.

[Структурщик]: Подтверждаю. `RunAddress` — это исторически точный адрес: `mountTarget` в нём — значение на момент прогона, не ссылка на живой манифест. Денормализация оправдана: адрес не гниёт при смене манифеста.

[Математик]: Формально: `RunAddress` — неизменяемая структура (immutable record). Все поля фиксируются в момент создания прогона. `mountTarget` берётся из манифеста плагина при старте прогона и записывается в `RunAddress`. После этого манифест может меняться — адрес не меняется. Инвариант корректен.

[Верстальщик]: Для витрины: исторические прогоны правильно показывают дом, в котором они реально выполнялись, а не текущий дом плагина. Это честные данные. Поддерживаю.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| Состав `RunAddress` | `{ pluginId: PluginId, version: string, collectionId: string, runId: string, mountTarget: HomeName }` — пять полей; покрывает цепочку Т3.3 «модуль → плагин → версия → коллекция → прогон» |
| Почему `mountTarget` — явное поле, а не восстанавливается из реестра | Восстановление через `HOME_REGISTRY(pluginId)` — скрытая зависимость; адрес перестаёт быть замкнутым; PluginId дом не кодирует (второй сегмент — род, M1/A3-1/A3-2). Явное поле — единственный вариант, не нарушающий M1 и M2 |
| Денормализация `mountTarget` в `RunAddress` | Оправдана: `RunAddress` — неизменяемая запись момента прогона; при смене манифеста исторические прогоны сохраняют точный адрес исполнения |
| Уникальный индекс Mongo (`plugin-results`) | Остаётся без изменений: `{ pluginId, version, collectionId, runId }`. `mountTarget` функционально определяется `pluginId` через манифест, добавление его в уникальный индекс не меняет множества уникальных документов |
| Где объявляется `windowSize` (окно накопления) | В `HandlerManifest` — расширяющем типе рода `handler`. Легально по M1 («расширения — через HandlerManifest/ReportManifest/ShowcaseManifest»). `StateRecord` отклонён: смешивает константу декларации с переменной исполнения; нарушает инвариант заморозки непереигрываемого M3 |
| Т3.10 и место окна | Т3.10 говорит только «накопление определяется окном» — где объявлять, не говорит. Приписывать ему выбор места запрещено повесткой |
