# Консилиум: K1 — Умолчание срока ключа-предъявителя, отзыв выданной ссылки, масштаб выключателя

**Повестка:** Где живёт умолчание срока ключа-предъявителя, чем отзывается уже выданная ссылка при снятом сроке, и на что распространяется выключатель?

**Участники:** Teamlead (Тарасов), Архитектор (Веснин), Структурщик (Ожегов), Математик (Дынин), Музыкант (Курёхин), Верстальщик (Родченко).

**Порядок реплик:** Верстальщик → Математик → Архитектор → Teamlead → Структурщик → Музыкант

---

[Верстальщик]: Смотрю на страницу ключей кабинета — два блока: «Новый ключ доступа» и «Ключи узла». Блока настроек срока для ключей треков нет физически. Это не баг вёрстки — это отсутствие контракта. Значит человек не может открыть блок, которого нет. Умолчание нигде не отображается и нигде не редактируется пользователем. Где оно тогда живёт — только в коде.

[Математик]: Сформулирую точнее. Есть два различных объекта: `NodeAccessKey` с полями `duration`, `expiresAt`, `revokedAt` — это модель узлового ключа. И есть ключ-предъявитель трека, который лежит в JSON-списке и по фактуре не имеет собственного блока настроек. Это разные сущности. Следствие: словарь `hours_4 / days_3 / weeks_2 / month_1 / months_3` относится к узловому ключу, не к ключу трека. Смешивать нельзя — контракты разные.

[Архитектор]: Из конструкции следует однозначно: умолчание срока ключа-предъявителя живёт не в UI и не в блоке настроек кабинета (его нет), а в серверном коде — в том месте, где ключ генерируется при выдаче ссылки. Носитель умолчания — код генератора ключа на сервере. Исполнитель — серверный слой, выполняющий выдачу. Если генератор не получает явного значения срока — он применяет жёстко вшитый дефолт или, при его отсутствии, выдаёт бессрочный ключ. Это две разные ситуации, и их надо различать.

[Teamlead]: Стоп. Это ключевое расхождение, и его надо назвать прямо. Штормом закрыто: «защита стоит по умолчанию, снятие — явным движением человека». Это утверждение о коде — не пожелание. Значит вердикт обязан сказать, чем оно держится. Держится оно ровно одним: жёстким дефолтом в генераторе ключа, который применяется тогда, когда явного значения нет — блок не открывали, хранилище пусто, запись повреждена. Если такого дефолта в коде нет — «защита по умолчанию» это надежда, а не факт. Нам нужно зафиксировать это различие в вердикте, а не обходить его.

[Структурщик]: Уточняю словарную статью. «Носитель умолчания» — это конкретная константа или ветка кода в генераторе ключа: либо `DEFAULT_TRACK_KEY_TTL` как именованная константа, либо `expiresAt = null` как явный выбор «бессрочно по умолчанию». Одно из двух. Третьего нет. Фактура говорит: блока нет, значит человек не задаёт срок вручную — его задаёт генератор. Если генератор молчит, то молчание — это тоже значение, и оно означает бессрочность. «По умолчанию защита есть» держится только если генератор явно ставит конечный `expiresAt` при отсутствии входного параметра.

[Музыкант]: Меня интересует другое — что происходит с уже выданной ссылкой. Ключ лежит в самом JSON-списке. Ссылка предъявительская: кто предъявил ключ — тот и получил файл, без дополнительной проверки личности. Это означает: если срок снят (бессрочная ссылка), то уже выданный ключ продолжает работать, пока сервер его принимает. Отозвать конкретную ссылку — значит либо инвалидировать ключ на сервере поштучно, либо сменить «замок» целиком. Вопрос: есть ли механизм поштучного отзыва?

[Верстальщик]: В модели `NodeAccessKey` есть поле `revokedAt`. Но это узловой ключ. У ключа трека (предъявительского, в JSON) аналогичного поля в фактуре не описано. Значит поштучного отзыва выданной ссылки трека через кабинет нет — по крайней мере как видимого контракта. Надо называть это прямо.

[Математик]: Формализую ситуацию с отзывом. Пусть ключ `k` выдан в момент `t₀`. Если срок снят, `expiresAt = null`. Сервер при проверке ключа выполняет: `valid ⟺ ключ найден AND (expiresAt IS NULL OR now < expiresAt) AND revokedAt IS NULL`. Если у ключа трека нет поля `revokedAt` в модели — то инвалидировать его поштучно без смены хранилища невозможно. Единственный способ «закрыть» уже выданные ссылки — сменить ключ в JSON-списке целиком, после чего старые ссылки перестают работать. Это не поштучный отзыв — это ротация ключа.

[Архитектор]: Ротация ключа — это правильное имя механизма. Смена ключа в JSON-списке инвалидирует все ранее выданные ссылки разом, поскольку они предъявляют уже несуществующий ключ. Это единица отзыва — не ссылка, а ключ. Поштучного отзыва одной ссылки при этой конструкции нет и быть не может: ключ один на весь период, все ссылки, выданные с ним, равнозначны.

[Teamlead]: Фиксирую: поштучный отзыв невозможен — это надо назвать в вердикте прямо, не обойти. Теперь масштаб выключателя. «Выключатель» — это то движение, которым человек снимает срок. Снятие срока действует на уровне чего? Пользователь может менять настройку для всей мембраны? Для конкретного набора? Для трека?

[Структурщик]: По фактуре: наборы трёх родов, в приёмном лотке — сырой материал двора владельца. Блока настроек срока нет вообще — значит выключатель (когда он появится) должен иметь чёткий масштаб. Сейчас из фактуры масштаб не задан явно. Но логика конструкции такая: ключ-предъявитель генерируется на запрос конкретного трека из конкретного набора. Значит настройка срока, если она живёт на сервере как дефолт, действует на уровне владельца (мембраны) — одна настройка для всех треков этого владельца. Если её можно переопределить на уровне набора — это отдельный контракт, которого сейчас нет.

[Музыкант]: Приёмный лоток — это сырой материал двора владельца. Лоток принадлежит мембране. Если выключатель действует на уровне мембраны — приёмный лоток попадает под него автоматически. Но если выключатель — это настройка набора, лоток попадает только если он явно включён в область действия. Сейчас это не определено, и это надо зафиксировать как открытый вопрос или принять решение.

[Верстальщик]: С точки зрения UI: если выключатель появится — он должен быть виден именно там, где человек выдаёт ссылку, а не в отдельном дальнем разделе. Иначе явное движение снятия защиты станет неявным. Конструктивизм: форма должна показывать масштаб действия — «срок для всех треков мембраны» или «срок для этого набора». Но сейчас это проектирование, а не фактура.

[Математик]: Возвращаюсь к вопросу о незаписанном значении. Три случая: (1) человек не открывал блок — блока нет, значит это нормальное состояние; (2) хранилище пусто — генератор не получает параметра; (3) запись повреждена — генератор получает невалидный параметр. Во всех трёх случаях генератор должен иметь детерминированное поведение. «По умолчанию защита есть» означает: в случаях 1, 2, 3 генератор ОБЯЗАН выдать конечный срок, а не null. Это детерминированный инвариант, и он должен быть в коде как явная ветка `if (ttl == null || ttl invalid) → ttl = DEFAULT`.

[Архитектор]: Именно. Утверждение «по умолчанию защита есть» держится единственным механизмом: fail-closed генератор. То есть генератор, который при любом отсутствии или повреждении входного параметра применяет жёсткий дефолт конечного срока. Если генератор fail-open (null → бессрочно), то утверждение ложно. Вердикт обязан это назвать.

[Teamlead]: Хорошо, конструкция собирается. Носитель умолчания — константа жёсткого дефолта в серверном генераторе ключа. Исполнитель — серверный слой выдачи ссылки. Держится это полем `expiresAt`, которое генератор обязан заполнить конечным значением при отсутствии явного входа. Если поле не заполняется — защиты нет. Это утверждение о коде, а не о намерении.

[Структурщик]: Масштаб выключателя по имеющейся фактуре: настройка срока не привязана к конкретному набору — блока на уровне набора нет. Значит умолчание действует на уровне мембраны (владельца). Выключатель — если он будет реализован — меняет дефолт для всей мембраны. Приёмный лоток как часть двора владельца попадает под этот выключатель, поскольку принадлежит той же мембране.

[Музыкант]: Резюмирую со своей стороны: уже выданная ссылка при снятом сроке продолжает работать бессрочно, пока ключ не сменён. Поштучный отзыв одной ссылки невозможен — это архитектурное следствие предъявительской конструкции с единым ключом. Единственный механизм закрытия выданных ссылок — ротация ключа, которая инвалидирует все ссылки с этим ключом разом.

[Верстальщик]: Добавлю про визуальный контракт: если на странице кабинета нет блока настроек срока для ключей треков — человек не видит, какой срок действует сейчас. Это асимметрия: настройка есть (в коде), а её видимость — нет. Вердикт должен это зафиксировать как состояние фактуры, не как задачу для этой комнаты.

[Математик]: Уточняю инвариант повреждённой записи. Если `expiresAt` при чтении даёт `NaN`, `undefined`, отрицательное число или дату в прошлом — генератор должен трактовать это как «нет явного значения» и применить дефолт. Альтернатива — считать такой ключ уже истёкшим, что тоже является fail-closed поведением. Оба варианта защищены. Единственный незащищённый вариант: повреждённое значение пропускается как валидное — этот случай вердикт должен исключить явно.

[Архитектор]: Формулирую итоговую конструкцию для вердикта. Три позиции: (А) носитель умолчания — жёсткий дефолт TTL в генераторе, исполнитель — серверный слой выдачи; (Б) при снятом сроке уже выданная ссылка продолжает работать, поштучный отзыв невозможен, механизм закрытия — только ротация ключа; (В) масштаб выключателя — мембрана владельца, приёмный лоток попадает под него.

[Teamlead]: Принимаю конструкцию. Добавлю одно: вердикт должен явно назвать, что «по умолчанию защита есть» — это требование к коду, не описание текущего состояния. Текущее состояние неизвестно без аудита генератора. Вердикт фиксирует контракт, который должен держать код, и называет, чем он должен держаться. Идём к итогу.

[Структурщик]: Согласен. Одно уточнение по словарю: «выключатель» в вопросе — это механизм снятия срока. Масштаб выключателя — мембрана. Это значит: одно движение владельца меняет поведение для всех треков его мембраны, включая все наборы и приёмный лоток. Нет механизма снять срок только для одного набора, не затронув остальные — такого блока нет.

## Итоговое решение консилиума

| Вопрос | Решение |
|--------|---------|
| **Носитель умолчания** | Жёстко вшитый дефолт TTL в серверном генераторе ключа-предъявителя. Блока настроек в UI нет — человек не может задать срок вручную ни при каком сценарии работы с кабинетом. |
| **Исполнитель** | Серверный слой выдачи ссылки: код, который при запросе генерирует ключ и записывает `expiresAt`. |
| **Что происходит, когда значение не записано** | Генератор не получает явного параметра в трёх случаях: человек не открывал блок (блока нет — это штатно), хранилище пусто, запись повреждена. Во всех трёх случаях «по умолчанию защита есть» держится единственным механизмом: **fail-closed ветка** в генераторе — `if (ttl == null \|\| ttl невалиден) → expiresAt = now + DEFAULT_TTL`. Если эта ветка отсутствует и генератор при null выдаёт `expiresAt = null` — утверждение «защита по умолчанию» является надеждой, а не фактом о коде. Повреждённое значение (`NaN`, `undefined`, дата в прошлом) обязано трактоваться генератором как отсутствующее и приводить к применению дефолта или немедленному истечению — оба варианта fail-closed; пропуск повреждённого значения как валидного — незащищённый случай. |
| **Чем отзывается уже выданная ссылка при снятом сроке** | Ссылка продолжает работать бессрочно — пока ключ в JSON-списке не сменён. **Поштучный отзыв одной выданной ссылки невозможен** — это прямое архитектурное следствие предъявительской конструкции: ключ один, все ссылки с ним равнозначны. Единственный механизм закрытия выданных ссылок — **ротация ключа**: смена ключа в JSON-списке инвалидирует разом все ссылки, выданные со старым ключом. |
| **Масштаб выключателя** | **Мембрана (владелец).** Одно движение владельца меняет дефолт срока для всей мембраны — для всех наборов и для всех треков во всех наборах. Механизма снять срок только для одного набора, не затронув остальные, в фактуре нет — такого блока не существует. **Приёмный лоток попадает под выключатель**: он принадлежит той же мембране и не выделен в отдельную область управления сроком. |
