## Problem (общая разработка)

Ночью 05→06.09 прибор упёрся в полный буфер: сервер одиннадцать часов отвечал 413, прибор
стучал пробами, телеметрия оборвалась, кабинет показал «нет телеметрии» — и никто не знал,
что прибор жив и просто не пишет. Заседание решило контракт остановки между тремя сторонами:
**сервер отказывает доменным кодом** (не HTTP), **прибор удерживается по этому отказу, не рвя
связь**, **оператор видит причину и три дороги из неё**. Политика переполнения живёт на сервере
у прибора; умолчание — `stop`; буфер — архив вещдоков, а не мусорная корзина.

Сквозная нить, общая для трёх блоков: **`overflowId` — один эпизод переполнения от чеканки на
сервере до одного окна у оператора.** Сервер чеканит (A) → прибор хранит зеркало в удержании
(C) → узел публикует в состоянии (C) → окно одно на id (4/4).

## Известные швы — намеренно НЕ согласованы заранее

Заседание зафиксировало **поля** ответа отказа и **имена** двух сущностей (`overflowId`,
`DeviceOverflowHold`) — это данности, их не обсуждают. Ниже то, чего ни одна комната не
назначала. Каждый блок пишет своё ожидание в `EXPECTATIONS.md` односторонне; сводим на
вскрытии. Расхождение — ожидаемый исход формата, не сбой.

1. **Где живёт словарь причин** (пакет и путь импорта). A выбирает пакет по замеру выше; C
   заявляет, откуда ему удобно импортировать; B — нужен ли ему словарь вовсе (его отказы
   «неполный набор параметров» — другой закрытый список или тот же union?).
2. **Как A читает политику прибора у B.** Имя колонки, enum и способ чтения (сервис
   `devices`? прямое поле `Device`?) — B называет, что отдаёт; A называет, что ждёт. До
   интеграции у A — временная константа `stop`.
3. **Как C читает эффективную политику у B.** B говорит «через контекст прибора/квоту»; каким
   полем и по какому каналу (ответ `/quota`? контекст при привязке? node-realtime?) — B
   предлагает, C ждёт своего. До интеграции у C — стаб-провайдер политики.
4. **Форма и путь разбора ответа A на клиенте.** Поля даны заседанием; TypeScript-тип, его
   импорт и место разбора (бэкенд `media-library` или плагин) — C решает у себя, A —
   в спецификации; стаб C держит копию полей у себя и **умирает на интеграции** (третья копия
   строк запрещена — стаб не в счёт до Phase 4, после — дефект).
5. **Носитель эпизода на сервере** (память процесса, колонка `Device`, отдельная таблица) и
   **время факта `overflowAt`** — кандидат эпика: чеканить вместе с `overflowId` при первом
   отказе эпизода. A реализует по кандидату и **называет носитель в CONCEPT**, не решает молча.
   Если носитель — колонка `Device`, это пересечение с зоной B (`prisma/**`) — тогда A
   объявляет ожидание, а миграцию вносит интеграция.
6. **Имя и форма значения состояния узла** «остановлен: буфер полон» — C один на обоих концах
   (клиент и кабинет), шва между блоками нет; 4/4 читает готовое.

- Имена: `bufferPolicy` (поле политики, B) ≠ `overflowPolicy` (поле ответа, A) — не сливать.
- «Умер» ⇔ молчание heartbeat/link-state дольше существующего окна присутствия; новый порог
  «от телеметрии» не вводится.
- Выкатка кабинета/media — по слову владельца, метки отката до сборки; в коворк не входит.
- Перед докладом «чисто» каждый блок называет, чем проверено и сколько файлов взяла проверка.

## Что строит координатор (Phase 4, ветка `integration`)

Названо заранее, чтобы сборка не стала сюрпризом (урок 02.09):

| Адаптер | Шов | Что делает |
|---|---|---|
| `overflowPolicy ← bufferPolicy` | A↔B | Временная константа `stop` в A заменяется чтением поля B; константа удаляется (порча: осталась → красный) |
| Эффективная политика на приборе | B↔C | Стаб-провайдер C заменяется читателем B; плагин перестаёт быть хозяином `bufferPolicy` (зеркало) |
| Разбор отказа | A↔C | Стаб-тип C заменяется импортом словаря A; копия строк у C удаляется; структурный зуб «одна копия» проходит по всему монорепо |
| Строки зависимостей и модулей | — | `package.json` workspace'ов (если A выбрал `core`, media получает зависимость), барели, `app.module.ts` |

собранной ветке; ни одного стаба в ветке; ни одной константы «временно».

## Интеграционный smoke (набросок — уточняется контрактом Phase 3)

Один сценарий через все швы:

1. Прибор с политикой по умолчанию (B: backfill → `stop`) заполняет буфер → загрузка пробы →
   **`200 {ok:false, reason:'device_buffer_full', overflowPolicy:'stop', overflowId, overflowAt, buffer, userStorage}`** (A);
   413 не участвует.
2. Прибор получает отказ → удержание активно с тем же `overflowId`/`overflowAt` (C); исходящих
   проб 0; активная запись погашена; heartbeat живёт, квота читается раз в минуту.
3. Узел публикует состояние «остановлен: буфер полон» → кабинет показывает «жив · не пишет ·
   буфер полон», не «нет телеметрии»; предикат `stopped_buffer_full` истинен, `dead` ложен.
4. 100 повторных отказов → тот же `overflowId`, один сигнал окна; перезапуск сценария при
   удержании → отбит, сигнал окна повторён тем же фактом.
5. Место освобождено ниже лимита → новый эпизод, новый `overflowId`; удержание НЕ снимается
   само (сброс — действие человека или очистка).
6. Кабинет: мембрана переводится в `smart_cleanup` без параметров → `ok:false`, режим не
   записан; с полным набором и галочкой «применить ко всем» → разноска `{updated: N, failed: 0}`;
   `/quota` (или назначенный канал) отдаёт прибору `smart_cleanup`; отказ A теперь несёт
   `overflowPolicy:'smart_cleanup'`.
7. Репро гипотезы обрыва: стоп записи без переполнения → `telemetry-track/v1` молчит при живом
   heartbeat — зафиксировано зубом, не словами.
