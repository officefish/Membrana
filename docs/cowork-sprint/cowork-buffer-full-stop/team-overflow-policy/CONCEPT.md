# Concept — Block `overflow-policy`

Блок исполняет вердикт **M1 заседания `buffer-full-stop`** («политика на сервере и её место»,
протокол `docs/seanses/buffer-full-stop-m1-policy-2026-09-06.md`, билет #2308) и только его.
Код отказа (M2, блок A), удержание на приборе (M3/M4, блок C) и окно оператора (M5, 4/4) блок
не решает: он оставляет для них швы и закрывает их стабами в своей зоне.

Данности T1, T7, T12, T13, T17 и слово владельца «умолчание — стоп; умная очистка — только после
настройки её параметров» — не переоткрываются.

## Граница блока

Блок отвечает за **одну политику в трёх носителях** и за то, чтобы в каждой дыре между ними
лежал `stop`:

| Носитель | Роль (словарь M1) | Где живёт | Что делает |
|---|---|---|---|
| Кабинет | **origin** — команда оператора | `background-cabinet`: таблица `MembraneBufferPolicy` (одна строка на мембрану: `mode`, `params`, `binding`), `Device.bufferPolicy*` | принимает выбор человека, проверяет гейт параметров, считает эффективную политику прибора, разносит |
| Сервер записей | **carrier** — рантайм | `background-media`: `Device.bufferPolicy`, `Device.bufferPolicyParams` | принимает разноску тем же PATCH, что квоты; повторно проверяет гейт; отдаёт прибору эффективную политику в ответе `/quota` |
| Клиент | **mirror** — зеркало | `apps/client/src/lib/buffer-policy/**` | читает эффективную политику с сервера записей; `effective(⊥) = stop`; локальной автоочистки как источника истины больше нет |

Блок **не** отвечает за: алгоритм умной очистки (T12), форму отказа `ok:false` при полном
буфере (A), то, что именно гаснет на приборе (C), плагин `mic-buffer-recorder` (зона C —
его подключение к моему читателю есть адаптер интеграции), окно и кнопки (4/4), тарифы (#2297).

## Имена — два разных слова

- **`bufferPolicy`** — поле политики (это мой блок): что оператор выбрал и что прибор обязан
  исполнять.
- **`overflowPolicy`** — поле *ответа отказа* блока A: снимок политики, при которой случился
  отказ. A читает моё поле и кладёт его значение под своим именем. Сливать нельзя: одно —
  настройка, второе — свидетельство в эпизоде.

## Значение политики — одна форма на всех трёх носителях

```ts
type BufferPolicyMode = 'stop' | 'smart_cleanup';

interface SmartCleanupParams {
  /** Порог срабатывания: процент занятости буфера, 1..100. */
  thresholdPercent: number;
  /** Критерий отбора жертв — слот под T12; закрытый список, расширяемый T12. */
  selection: 'oldest_first' | 'largest_first';
  /** Защита вещдоков: не трогать размеченное. Обязан быть указан явно (true | false). */
  protectLabeled: boolean;
}

type BufferPolicy =
  | { mode: 'stop'; params: null }
  | { mode: 'smart_cleanup'; params: SmartCleanupParams };
```

Три слота S — ровно каркас M1 («порог срабатывания, критерий отбора, защита вещдоков»).
Никакой семантики удаления в них нет: `selection` — имя-закладка под будущий T12, и никакой
код в этом блоке по нему ничего не выбирает и не удаляет.

**Гейт `paramsComplete(S)`**: все три поля присутствуют и валидны. `smart_cleanup` без
полного S — режим **не записывается**, ответ `200 { ok:false, reason }` (конвенция 12.08).
Закрытый список причин:

| reason | Когда |
|---|---|
| `unknown_mode` | режим вне `{stop, smart_cleanup}` — в том числе легаси `auto-cleanup` |
| `params_incomplete` | `smart_cleanup`, но хотя бы одного слота нет |
| `params_invalid` | слот есть, но значение вне домена (порог вне 1..100, чужой критерий, не-булево) |
| `binding_active` | (кабинет) правка режима прибора, пока стоит галочка-привязка |
| `binding_not_confirmed` | (кабинет) включение привязки без явного подтверждения |
| `node_not_paired` | (кабинет) у узла нет прибора — политику некуда записать |

Первые три причины — общие для обоих серверов; последние три — только у origin.

## Fail-closed: тройная скоба (Математик, M1)

Одной миграции недостаточно — старые бинарники клиента и порченые строки живут дольше миграции.
Поэтому `stop` держат три независимых скобы, и каждую сторожит свой зуб:

1. **Backfill.** SQL-миграция руками: колонка добавляется nullable → `UPDATE … SET 'stop' WHERE
   NULL` → `SET DEFAULT 'stop'` → `SET NOT NULL`. Все существующие приборы = `stop`. Зуб читает
   текст миграции: backfill стоит **до** `NOT NULL`, значение `stop`, слова `auto` нет.
2. **Enum БД.** `BufferPolicyMode { stop, smart_cleanup }` — Postgres отвергает неизвестное
   значение на уровне типа; `auto-cleanup` в базу не попадёт ни при каком коде.
3. **`effective()` на пути чтения.** На media, в кабинете и на клиенте: `⊥ | null | чужая
   строка | smart_cleanup без полного S | порченый JSON` → `stop`. Зуб-порча на каждом
   носителе: вернуть дефолт автоочистки → красный.

## Семантика галочки-привязки (T13/T17)

Галочка «применить ко всем» на странице мембраны — **привязка, не снимок**:

- **Стоит** → источник истины для *каждого* прибора мембраны — политика мембраны, **включая
  будущие приборы**: при привязке нового узла кабинет отдаёт media политику мембраны, а не
  умолчание прибора. Правка режима отдельного прибора при стоящей галочке отбивается
  (`binding_active`) — иначе она была бы молчаливым no-op.
- **Снята** → приборам **возвращаются их собственные настройки**. Это работает потому, что
  per-device значения при включённой галочке **не перезаписываются** — они лежат в кабинетной
  строке `Device` нетронутыми, а эффективное значение считается функцией
  `effective = binding ? membrane : device`. Снятие = пересчёт + разноска.
- **Включение — с явным подтверждением.** UI показывает окно «все узлы и будущие будут
  слушаться политики мембраны»; сервер требует `confirmed: true` в теле — галочка без
  подтверждения красна и на сервере, не только в форме.
- Умолчание галочки — снята. Снятая галочка при пустых per-device значениях всё равно даёт
  `stop` везде (скоба 1–3).

Носитель политики мембраны и привязки — таблица `MembraneBufferPolicy` (`membraneId` unique,
`mode`, `params`, `binding`), **не колонки `Membrane`**. Замер при постройке (06.09): любая новая
скалярная колонка на `Membrane` рушит перегрузку `requireOwnedMembrane` в
`sample-library.service.ts` (TS2394 — перегрузка задаёт ровную форму строки); чужой модуль коворк
не правит, а образец «настройка мембраны отдельной таблицей» уже есть в media
(`TrackKeyTtlSetting`). Отсутствие строки = `stop`, привязка снята; миграция заводит строку
каждой существующей мембране явно. Media о привязке **не знает**: до carrier доезжает только
эффективное значение прибора. Это намеренно: у прибора один вопрос — «что мне исполнять», а не
«почему».

## Разноска — тем же классом, что квоты (#2281)

`MembraneContextFanoutService.syncAllNodes(membraneId)` уже прогоняет контекст мембраны по
всем приборам со счётом `{updated, failed}`. Политика едет **в том же контексте**, полем
`bufferPolicy` рядом с квотами, — второго класса разноски нет. Отличие от квот одно: квоты
одинаковы для всех приборов мембраны, а политика — **per-device** (при снятой галочке), поэтому
разноска считает контекст **на каждый прибор**, а не один на всех.

Триггеры разноски:

| Событие | Кто зовёт | Объём |
|---|---|---|
| привязка узла (`PairService.pair`) | контекст при регистрации / ре-пейринге | этот прибор |
| смена политики мембраны | `PUT /v1/membranes/me/buffer-policy` | все приборы |
| смена галочки | `PUT /v1/membranes/me/buffer-policy/binding` | все приборы |
| смена политики прибора | `PUT /v1/nodes/:nodeId/buffer-policy` | этот прибор |

Ответ каждой ручки записи несёт `contextSync: {updated, failed}` — «политика не доехала» не
молчит, как и у тарифов. Частичный успех — законный исход. Порядок несущий: сначала запись в
кабинете, потом приборы (как у тарифа).

**Гейт проверяется дважды**: кабинет при записи (origin) и media при разноске (carrier). Media
на `ok:false` отвечает `200 { ok:false, reason }`, и мост кабинета обязан читать тело, а не
только `res.ok` — иначе отказ media считался бы «обновлено». Это правка `MediaBridgeService`
(моя зона `pair/**`).

## Страница мембраны — одна витрина

Блок «Переполнение буфера» на `MembranePage` рядом с тарифом:

1. режим `stop | smart_cleanup` — select; `smart_cleanup` **disabled, пока S неполон**, с
   текстом причины рядом (не серая магия);
2. область параметров S — скрыта/disabled при `stop`;
3. галочка «применить ко всем приборам» с окном подтверждения при включении;
4. при снятой галочке — список узлов мембраны с select режима **на строку** (та же витрина;
   отдельной страницы прибора нет по вердикту).

Кнопки «локальная автоочистка» как управляющей нет нигде. Счёт разноски показывается после
каждой записи, как у тарифа.

## Клиент — зеркало, не хозяин

`apps/client/src/lib/buffer-policy/**`:

- `effectiveBufferPolicy(raw: unknown): EffectiveBufferPolicy` — чистый разбор ответа сервера;
  любая порча → `{ mode: 'stop', source: 'fallback', reason }`. Тип результата **не содержит**
  `'auto-cleanup'` — откат к старой автоочистке невозможен на уровне типа, а не договорённости.
- `createBufferPolicyReader(source)` — держит последнее значение; до первого успешного чтения
  и после **любого** неудачного — `stop` (вердикт M1: `effective(sync-fail) = stop`).
  Источник — абстракция `BufferPolicySource = () => Promise<unknown>`; в моей зоне — стаб,
  отдающий ответ формы `/quota`. Подключение к живому `getQuota` и к плагину — адаптер
  интеграции (B↔C).
- Структурный зуб: в каталоге читателя строки `auto-cleanup` нет ни в одном исходнике.

## Чего блок сознательно не строит

Алгоритм очистки; автозаполнение S «для удобства»; чтение политики прибором через кабинет
(только media); галочку-снимок; отдельную страницу настроек прибора; мастер-политику в
плагине; дефолт автоочистки; форму отказа A; машину удержания C; окно 4/4.

## Известное ограничение — копии словаря

`{stop, smart_cleanup}` и три причины гейта живут копиями: media, кабинет (сервер), кабинет
(UI-follower), клиент. Общего пакета у media и клиента нет (`background-media` не зависит от
`core`), а пакет словаря выбирает блок A. На вскрытии предлагаю переселить мой словарь в тот
же каталог `buffer-overflow/`, что выберет A, — одним адаптером; до тех пор копии сторожат
зубы полноты на каждом носителе.
