## Четыре вещдока приёмки

**1. Перевыдача — ключ не служебный.** `POST /v1/devices/1c04f0bc-…/client-key?rotate=true` →
`201`; выданный `raw` **≠ `API_INTERNAL_TOKEN`** (сверено сравнением, значение не печаталось),
длина 43 символа.

**2. Строка `audience='client'` в таблице.** До деплоя колонки `audience` не существовало вовсе;
после миграции `20260820111700_node_key_audience` и перевыдачи:

```
client | active=f | used=t     ← ключ приёмки: использован, затем отозван
client | active=f | used=f     ← ключ первой проверки, отозван ротацией
node   | active=t | used=t     ← ключ полевого узла Firebat, не тронут
```

**3. Запись принята этим ключом.** Чтение коллекций client-ключом — `ok, 2`; загрузка WAV
(0,2 с, 48 кГц, PCM16 моно) — **`201`**, проба `cac7be7e-1f3c-45ba-805a-74ae8887f37c`,
в БД `sampleRate = 48000`, `createdAt 2026-08-21 12:57:55`. Устройство — `1c04f0bc-…`,
то самое из задания.

**4. Отзыв гасит ключ.** `DELETE /v1/devices/…/client-key` → `200`; повторная загрузка тем же
ключом — **`401 {"message":"client media key revoked"}`**, в таблице у строки `revokedAt`
проставлен (`active=f`). Отбой **именованный**, не общий «Invalid token».

## Обратная совместимость

Ключ узла Firebat (`audience='node'`) остался активным и использованным — выкатка его не тронула;
служебный токен продолжает приниматься стражем (`media-device-access.guard.ts`), поэтому уже
связанная Studio владельца работает без перепарринга.

## Что приёмка НЕ покрывает (названо честно)

- Живой прогон **из самой Studio** (а не HTTP-вызовом от имени клиента) — Studio на узле в этот
  прогон не поднималась; клиентский код Р4 (шифрование кредов) в стволе, но **не раздан**.
- Перевыдача **через кабинет** (кнопка связки в UI) — проверялся серверный тракт, который кабинет
  зовёт (`/client-key`); сам UI-путь владелец проходит своей рукой.
- Ротация `MEDIA_API_TOKEN` (Р3) — вне спринта по границе.
