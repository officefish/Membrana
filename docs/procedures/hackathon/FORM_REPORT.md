# Hackathon procedure form report

**Предмет.** Этот отчёт отвечает не "как запускать хакатон", а какой формы
оказалась процедура `hackathon` после переноса из матрицы в контейнер
`docs/procedures/`. Он является входом в будущее заседание об
`EXECUTION_PROCEDURE`.

## Какая форма получилась

`hackathon` получился процедурой-эстафетой:

```
owner brief -> interview -> open -> H1 -> H2 -> H3 -> H4 -> closure
```

Главный объект не "день" и не "эпик", а **передача между этапами**. Поэтому
минимальный проверяемый артефакт этапа — `stage-completion-checklist`:

| Поле чеклиста | Зачем |
|---|---|
| changed artifact | что реально изменилось и может быть принято следующим этапом |
| verification command/result | чем проверено, не пересказано |
| known gaps | что не закрыто и не должно потеряться |
| next-stage input | что именно получает следующий держатель |

## Какие поля манифеста понадобились

| Поле | Решение |
|---|---|
| `id`, `leadPersona`, `kitVersion` | нужны как общий паспорт процедуры |
| `engines` | нужны, но честно показывают неполноту: open/day-close не реализованы, close есть |
| `precedents` | обязательны для этой процедуры: форма выводится из прожитого `device-board-hackathon-1` |
| `preflight` | нужны для brief/interview до открытия |
| `frames` | несущие: H1-H4 и closure именно фреймы, а не свободный список задач |
| `post` | нужен возврат к ритму и архив задач |
| `trigger` | captain-word; машинного `hackathon:open` пока нет |
| `steps` | inline, потому что отдельного машинного steps-файла ещё нет |
| `gates` | нужны три: brief, handoff, final audit |
| `portfolio` | нужно, чтобы мастерская честно показывала, что у маршрута уже есть носители |
| `mode`, `home` | `mode: local`; `home.kind: none`, потому что живого дома формы пока нет |

## Что оказалось лишним или преждевременным

- `kitVersion` пока `null`: кита хакатона нет.
- `home.kind: path` преждевременен: `docs/HACKATHON_ACTIVE.md` и
  `docs/archive/hackathon/**` — носители прогонов, но форма живого дома не
  закреплена.
- Отдельный `steps.ref` преждевременен: нет файла, аналогичного
  `docs/tasks/evening-ritual-steps.json`.
- `EXECUTION_PROCEDURE` не вводится: этот отчёт даёт материал для интерфейса,
  но не назначает его.

## Где форма `day-sprint` не подошла

`day-sprint` устроен как эпик с фазами и owner closure gate. Для хакатона этого
мало:

- фазы внутри H-этапа могут быть несколькими задачами (`H2a-H2d`), а передача
  остаётся одной;
- закрытие отдельной карточки не равно передаче этапа;
- календарь 3-5 дней не выражает структурное правило H1-H4;
- нужен gate между этапами, а не только финальный `closure-accept`.

Из `day-sprint` взяты паспорт, `preflight` / `frames` / `post`, inline steps и
owner gate. Не взята идея, что список фаз сам по себе является формой маршрута.

## Где форма `ritual-evening` не подошла

`ritual-evening` хорошо показывает внешний `steps.ref` и owner gate после
основного потока. Но хакатон не ритуал:

- у него нет расписанного машинного steps-файла;
- он не повторяется ежедневно по одному и тому же треку;
- главный стоп находится между H-этапами, а не только в конце;
- выходом является осевая фича и handoff-аудит, а не закрытие дня.

Из `ritual-evening` взята честная очередь кадров и явный post. Не взята модель
единого повторяемого run engine.

## Что есть у хакатона, чего нет у соседей

| Сосед | Отличие хакатона |
|---|---|
| `one-shot` | не один review-атом, а цепочка передач |
| `membrana-local-sprint` | не локальная нарезка accountable-блоков, а контейнерная топология |
| `cowork` | не параллельные изолированные части, а последовательная эстафета |
| `challenge` / `competition` | нет победителя и scorecard; ценность не в выборе альтернативы |
| `marathon` | не долгий уступающий ритм; требуется непрерывная передача |
| `night build` | не автономная ночь и не hardening; нужен owner brief |

## Разрешение двух расхождений 01.08

### Число этапов

Решение: несущей мерой считать **ровно четыре передачи H1-H4**. Старое
`3-5 дней` остаётся ориентиром календаря первого кейса, но не классификатором
маршрута.

Родословная:

- `docs/HACKATHON_REGULATION.md` v0.1 назвал 3-5 дней по первому опыту;
- `device-board-hackathon-1` в реестре прошёл H1-H4, где H4 назывался закрытием;
- `DEVELOPMENT_MATRIX` зафиксировала обобщение: strict relay of four stages.

### `local-sprint` / `honest-sprint`

Prompt #1601 зафиксировал разъезд, но ствол уже разрешил его PR #1598:
живой скилл и процедура называются `membrana-local-sprint`; старое
`honest-sprint` остаётся историческим словом и нормализуется на входе. Хакатон
не должен ссылаться на старое имя как на живой маршрут.

## Кандидаты в поля `EXECUTION_PROCEDURE`

Обязательными для любого маршрута разработки выглядят:

- `id`;
- `leadPersona`;
- `trigger`;
- `steps`;
- `gates`;
- `frames` с holder;
- `mode`;
- `home` или честное `home.none`;
- `portfolio` или честное отсутствие портфолио;
- `precedents`, если маршрут выводится из прожитого образца.

Частные для эстафеты поля:

- список H-этапов;
- `stage-completion-checklist`;
- gate передачи между этапами;
- final checklist audit;
- правило "ровно четыре естественные передачи".

## Вывод

Форма хакатона подтвердила, что будущий `EXECUTION_PROCEDURE` нельзя свести к
`trigger · steps · gates`: для маршрутов разработки обязательна ещё карта
держателей, портфолио, режим исполнения и честный ответ о доме. Но топология
маршрута должна оставаться частной: иначе интерфейс начнёт навязывать всем
процедурам форму эстафеты.
