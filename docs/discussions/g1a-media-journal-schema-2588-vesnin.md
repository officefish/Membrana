**Конструкция.** g1a — это два фундамента: снятие немого каскада (Т3) и журнал-след (вердикт 1). Фундамент не описывает поведение исполнителя — только форму, в которой поведение будет доказано. По этой мерке и смотрю.

**По пунктам:**

1. **Restrict на обеих связях — верно, в т.ч. для `deleted`/`restored`.** Партия — вечный след (комментарий в схеме и ADR это закрепили); состояние партии БД не различает, FK срабатывает на существование строки. Отказ держит и прибор с одними только `deleted`-партиями — это и есть замысел: глагола удаления прибора в media нет, появится — обязан пройти через явное решение об архиве. Ничего существующего не ломает: путей удаления `Device` в media сейчас нет, в office удаление идёт через свой слой и упрётся в 409 (g8 плана). Форма выдерживает нагрузку.

2. **Уникальность `(runId, batchId)` при NULL — дыра на будущее, но не для g1a.** Postgres действительно считает NULL различными, значит ограничение «одна партия — одно задание в прогоне» живо, а `orphan_blob` его не трогает — это по замыслу (у сироты нет партии). Для verify g4 различать два `orphan_blob` одного прогона нужно по `storageRefs` или суррогатному ключу долга, не по `batchId`: класть сироте фиктивный `batchId` — декор, который сломает FK NoAction к партии. **Правка:** в g1a достаточно одной строки в комментарии модели — «`orphan_blob` различается по `storageRefs`, не по batchId»; механизм дедупликации сирот — зуб g3b (долг), не g1a.

3. **Job→Batch NoAction, Job→Run Restrict, `deviceId` без FK — верно для журнала-следа.** Run — корень доказательства, его нельзя снести, пока есть задания (Restrict). Batch — NoAction потому, что партии не удаляются в принципе (переходят в `deleted`); Restrict здесь был бы декором того же смысла. `deviceId`-снимок без FK — правильно: журнал переживает прибор, иначе след исчезнет вместе с ним (а Restrict на Device мы как раз для этого и ставим на уровне архива, не журнала). Согласованно.

4. **«Один активный live-прогон» — НЕ в g1a.** Prisma частичный уникальный индекс не выражает (`WHERE status='running' AND mode='live'`), и это не повод тащить сырой SQL в g1a. Инвариант — поведенческий, его место в g3b (advisory lock на старте прогона) + зуб runner'а. Схема обязана допускать такое ограничение в будущем — она допускает (есть индекс `(status, finishedAt)` для быстрой проверки). **Оставить g1b/g3b.** Иначе g1a переползёт черту: прецеденты 579/668 начинались ровно с «ещё одного маленького свойства».

5. **Чего не хватает g1b (не g1a).** Захват по лизу — чисто поведенческий (UPDATE … WHERE leaseUntil < now RETURNING), это g3b. Пустой прогон — тоже поведение runner'а (вердикт 5: пишем `succeeded` с нулями), не схема. В g1b жду: `purge-journal.store.ts` с методами `openRun/closeRun/addJob/claimJob/completeJob`, идемпотентность по `(runId, batchId)` через P2002, и зуб словаря ↔ схемы ↔ миграции (у тебя заявлен — хорошо).

**Затронутые модули:** `packages/background-media/prisma/schema.prisma`, две миграции, `src/modules/downgrade-archive/purge-journal.vocabulary.ts`. Границ пакетов не нарушено, core не трогается.

**Рекомендация — форма.** DoD g1a выполнен: модели есть, две миграции разделены корректно (смена поведения ≠ создание), Restrict на обеих связях, Run/Job присутствуют, словарь-чеканщик на месте, зуб схемы 15/15. **Сдан** с одной косметической правкой по п.2 (комментарий о различении `orphan_blob` по `storageRefs`).
