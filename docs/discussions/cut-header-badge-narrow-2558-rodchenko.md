**Ответ:**

## Вердикт по корню
Верен. Два ребёнка с `flex-shrink:1 min-w-0` делят отрицательное место пропорционально базе, доходят до нуля одновременно; остальные `shrink-0`; `overflow-x-clip` режет правый хвост; бейдж в DOM правее «Сохранить» → клип съедает бейдж раньше. Это механика flex, а не догадка.

## Механика A
Годится как основной путь. Перестановка бейджа первым ребёнком + пол `min-w-[5.5rem]` + внутренний `truncate` + крошке `shrink-[4]` — честная конструкция в рамках Tailwind 3.4 без контейнерных запросов. Оговорки:
- Строгого «крошка в ноль, потом бейдж» flex не даёт — только весом и полом. Это и надо честно сказать владельцу.
- Пол 5.5rem подтверждён прикидкой и приёмкой; оставить в `BOARD_HOLD_BADGE_MIN_WIDTH_CLASS` рядом с константой левой группы.
- Альтернативы: (б) сжимаемая «Сохранить» арифметически не вывозит при 1065 px, плюс «Сохр…» — не слово; (в) иконка требует прибор ширины — другой спринт; (г) CSS `order` ломает таб-порядок — не брать.
