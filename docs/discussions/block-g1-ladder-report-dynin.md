**Вопрос:** Ты держатель блока g1-ladder-report спринта scoreboard-spectral-ladder (Ф2 эпика витрины, ратифицирован владельцем 06.08 09:12Z). Зона: scripts/lab-learning-curve.mjs, scripts/lab-learning-curve.test.mjs (новый). ~130 строк. Замеры и чистые метрики — твой предмет.

ПОЛОЖЕНИЕ (проверено кодом): scripts/lab-learning-curve.mjs гоняет лестницу и ПЕЧАТАЕТ таблицу в stdout; версионируемого JSON-отчёта не пишет, а витрина Ф1 по канону читает «версионируемый JSON в репозитории» и требует ШТУКИ (detected/dronesTotal, falseAlarms/cleanTotal), 95%-интервал, rocAuc, provenance. Библиотека уже даёт всё: detectorMetrics возвращает {tp,fp,fn,tn,precision,recall,pd,pfa,pdCI,pfaCI,rocAuc}, есть wilsonInterval.

РЕШЕНИЕ РЕЗЧИКА (ратифицировано): ступени лестницы считать в записях МЕНЬШЕГО класса — дронов (при 63 дронах ступень 80 недостижима без искажения баланса; счёт по сумме классов молча смещал бы состав). Ступени 20/40/60 + full. В отчёт кладутся фактические знаменатели ОБОИХ классов на каждой ступени.

МОЯ ФОРМА ОТЧЁТА, подтверди или поправь:
{ schema: "spectral-ladder-report@1", generatedAt, corpus: {path, droneCount, cleanCount, sha256OfManifest?}, test: {size, drones, groups}, steps: [ { nTrainDrones, nTrainTotal, method: "envelope"|"percentile", params: {minConfidence, withCompetitors}, test: { detected, dronesTotal, falseAlarms, cleanTotal, pdInterval: [lo,hi], pfaInterval: [lo,hi], rocAuc } } ] }

ВОПРОСЫ: 1) верна ли форма — что в ней врёт или чего не хватает для честного чтения витриной? 2) на каждой ступени два метода сборки (envelope/percentile) — класть оба в отчёт или отбирать лучший на train и класть один (и не будет ли отбор лучшего по test подгонкой)? 3) провенанс: чем идентифицировать корпус, чтобы «числа от какого корпуса» читалось машинно — хеш манифеста, список имён файлов, что? 4) что первым покрыть зубом при новом файле тестов? Коротко по пунктам, кода не пиши.

**Ответ:**

По пунктам.

**1) Форма отчёта — что поправить/добавить.**
- Добавить `seed` и версию сплиттера/детектора (`splitter@ver`, `detector@ver`) — без этого числа невоспроизводимы.
- `test.drones` и `test.clean` (оба знаменателя) на верхнем уровне явно; `groups` — если group-aware сплит, зафиксировать список групп.
- В `steps[]` не хватает `nTrainClean` (симметрично `nTrainDrones`) и явного `seedStep` (если ступени рандомизируются).
- `pdInterval`/`pfaInterval` — указать метод (`wilson@0.95`) и уровень; интервал без метода — половина смысла.
- `rocAuc` — добавить `rocAuc.ci` тем же протоколом (bootstrap, N, seed), иначе AUC без ошибки читается как точка.
- `params.threshold` (рабочая точка, на которой считаются detected/falseAlarms) — обязательно; иначе pd/pfa не восстановимы.
- `schema` версионируй с `@1.0.0`, не `@1` — витрина потом различит minor.

**2) Envelope vs percentile.** Клади **оба** метода на каждой ступени как параллельные записи (`method` уже в ключе). Отбор «лучшего по test» — классическая подгонка на тесте, запрещено. Если нужен единственный winner — выбирай по **train/val метрике**, фиксируй правило отбора в `selection: {by, split}` и всё равно оставляй проигравшего в отчёте для честности.

**3) Провенанс корпуса.** Минимум: `manifest.sha256` (канонизированный JSON: сортировка ключей, LF, без пробелов) + `manifest.path` + `corpus.count`. Список имён — избыточен и хрупок к переименованиям; хеш решает. Дополнительно полезно `sha256` по конкатенации `(relpath, size, contentSha)` каждого сэмпла — тогда переименование ловится, а перекодировка нет. Одной строкой: **hash-of-manifest обязателен, hash-of-content-index — желателен**.

**4) Первый зуб.** Инвариант формы и знаменателей: на синтетическом мини-корпусе (например, 6 дронов / 10 clean, ступени 2/4/6) проверить, что `steps[i].test.dronesTotal === test.drones` и `cleanTotal === test.clean` на **всех** ступенях, `nTrainDrones` монотонно растёт, `pdInterval` — валидный Wilson (`lo ≤ pd ≤ hi`, `0 ≤ lo, hi ≤ 1`), `schema` совпадает. Это ловит именно тот класс ошибок, из-за которого мы и переходим на JSON: молчаливое смещение знаменателя.
