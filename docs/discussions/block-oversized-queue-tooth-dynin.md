**Вопрос:** Блок oversized-queue-tooth спринта review-oversized-queue: 24 зуба на ядро очереди, прогон зелёный. Покрыты: порог импортирован а не переобъявлен; граница ровно порог против порога плюс один; три природы; риск по строкам кода; пустой дифф не делит на ноль; порядок по риску а не по объёму; вторичный ключ доля кода; детерминизм при равенстве; снятие только по артефакту ревью; три причины отбрасывания раздельными числами; пустая очередь как утверждение; урезание с остатком при полном счётчике; исполняемое вне кодовых корней (docs/prompts, .github/workflows, .githooks, docs/procedures, Dockerfile, turbo.json) — код; markdown внутри packages — не код; номера PR сравниваются числом а не строкой; коммиты без номера не схлопываются, порядок задаёт sha. Ответь как математик коротко: 1) какой зуб пройдёт на сломанной реализации; 2) зубы про исполняемость перечисляют пути списком — не подгонка ли это под текущий состав дерева; 3) чего в зубах нет, но по природе дефекта обязано быть.

**Ответ:**

По существу, три ответа.

**1) Какой зуб пройдёт на сломанной реализации.**
«Порядок детерминирован при полном равенстве» — единственный зуб, который зелёный на реализации, всегда возвращающей пустую очередь: `[] === []`. Аналогично «пустая очередь — утверждение» проходит на функции `formatQueue`, возвращающей константу с нужным словом. Это не тавтологии, но одиночно они ничего не держат — оба сцеплены с соседями и без них слепые. Формально «зуб на сломанной реализации» — «детерминизм при равенстве»: у него нет ни одного предиката про содержимое очереди.

**2) Списки путей — не подгонка ли под дерево.**
Частично да, и это стоит назвать. `CODE_ROOTS` проверяется циклом (замкнутость списка на себе — хорошо), а вот `docs/prompts/*`, `.github/workflows/*`, `.githooks/*`, `docs/procedures/*/MANIFEST.json`, `Dockerfile`, `turbo.json` — enumerated allow-list. Пока классификатор работает по «списку исключений», зуб проверяет **тот же список**, а не правило. Правильнее: предикат вида «исполняемое = не-markdown вне `docs/archive|seanses` **или** явно перечисленный манифест», и тест на инвариант — «добавление пути в новый workflow не требует правки классификатора». Сейчас требует — и тест этого не поймает.

**3) Чего в зубах нет, но по природе дефекта (168 из 185) обязано быть.**

- **Монотонность знаменателя.** `denominator = queue.length + dropped.reviewed`? или `+ notOversized`? Ровно этот вопрос — сердце замера «непроревьюированных». Ни один зуб не фиксирует, из чего складывается 185 и что такое 168.
- **Идемпотентность снятия.** `reviewed` дважды тот же PR — знаменатель не должен раздуться.
- **Устойчивость к дубликатам входа** (один sha дважды).
- **Численный инвариант доли:** `code + docs ≤ total`, `codeShare ∈ [0,1]`, отсутствие NaN при `total>0, code=0`.
- **Смешанный PR наверху** — заявлен в шапке файла («поправка резчика»), но проверен только на равном риске. Нет зуба «малый код + большая дока обгоняет чистую большую доку, если та вернулась флагом `includeDocs`».
- **Порог импорта строгий:** сейчас проверено `> порог` и `= порог`, но не то, что смена на `≥` в реализации будет поймана где-то ещё, кроме одной строки.
- **Стабильность сортировки при частичном равенстве** (равен риск, равна доля — что дальше? sha? тест есть только для полного равенства).

Первое из этого списка — про знаменатель — я бы добавил сегодня же: без него метрика «168/185» невоспроизводима, а именно она и была поводом к этим зубам.
