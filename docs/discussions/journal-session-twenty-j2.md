**Вопрос:** Блок j2 ратифицированной нарезки. Ответь Q1–Q6: имена, род, повод, окно, порт, payload, место регистрации. Границы держим: контракты не трогаем, дом назначен комнатой.

**Ответ:**

Принимаю постановку: контракты не трогаем, дом — `background-media/collections`, выход — адреса в `plugin-results`.

**Q1.** Род — `report`, не `handler`. Определение через функцию: `handler` возвращает поток артефактов по событию; `report` — односвязный свод по завершённому контексту. Разбор сеанса даёт свод, не поток.

**Q2.** Повод — `collections.sample_added`. Лемма: сеанс существует, когда в коллекции есть адресуемые сэмплы; `sample_added` — единственный из трёх, после которого окно (from/to) определено. `collection_created` — до данных, `journal.entry_created` — вне нашего дома.

**Q3.** `windowSize` для `report` — число треков окна, не секунды. M3′ не спорит: там окно накопления (вход), здесь — объём разбора (выход). Один термин — два смысла в разных родах; закрепить в манифесте комментарием.

**Q4.** Расширять существующий `CollectionSampleReader` методом `createdAt(sampleId)` — НЕ ломает mfcc: добавляем, не меняем сигнатуры. Отдельный порт — избыточный фасад, отклоняю.

**Q5.** Окно передаётся через `ctx.payload` как `SampleAdded` с границами коллекции: `from` — первый `sampleId` в окне, `to` — последний; диапазон восстанавливается через `createdAt` из Q4. Новый payload-тип не нужен.

**Q6.** Отдельная функция `registerReportWave`, не в `registerFirstWave`. Первая волна — детекторы с общим контрактом; report — другой род, общий контейнер смешает словари.

Затронутые пути: `packages/plugin-handlers/src/session-metrics/`, порт `CollectionSampleReader`, регистратор в `background-media/collections`. Риск: `ctx.payload` как `SampleAdded` — проверьте, что поле `sampleIds` в интерфейсе допускает диапазон, иначе передаём первый/последний id.
