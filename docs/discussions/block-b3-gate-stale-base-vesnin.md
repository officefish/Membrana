**Вопрос:** Ты исполнитель блока b3-gate-stale-base. Зона: scripts/review-gate.mjs (CLI) и его зубы. Готово: b1 — маркер несёт base, reviewGateDecision принимает currentBase и даёт unknown при расхождении (ветка между sameSha и scope), legacy без base проходит как прежде по слову владельца; b2 — ревью пишет base в маркер и блок review-source в артефакт. Факты зоны: CLI берёт headSha у САМОГО PR через gh pr view --json headRefOid (не локальный HEAD — находка 29.07: иначе чужое ревью всегда протухшее), при отказе gh падает на локальный rev-parse с предупреждением; есть --restamp, который пересобирает маркер по телу ревью, не гоняя LLM. Ответь решениями, коротко: (1) как CLI считает ТЕКУЩУЮ merge-base для чужого PR — той же ручкой compare, локальным git или иначе, и что при отказе; (2) что делать --restamp: он сейчас пересобирает маркер и потеряет base, если её не передать — откуда её брать; (3) как показать человеку исход stale-base, чтобы он отличил его от протухания по head; (4) какие зубы обязательны для CLI. Только решения.

**Ответ:**

Всплытие:
[память:подсознание] emerge vesnin-2026-08-07-team-evening-feedback — прецедент «маркер + провенанс с holds на трёх маркерах»: тот же паттерн — вердикт обязан нести источники, по которым его можно перепроверить. Здесь b1/b2 уже кладут base в маркер, CLI должен эту дисциплину замкнуть.
[память:подсознание] emerge vesnin-2026-07-08-hermes-liaison-agent — канон «декора без смысла не существует»: не изобретаем новый источник правды для base, берём тот, что уже есть у `pr-recreate` и compare-ручки.

Решения:

(1) **Текущая merge-base для чужого PR — `gh api compare/{base}...{head}`, поле `merge_base_commit.sha`.** Один источник и с headSha (compare даёт и base, и head согласованно — та же ручка, что в b2). Fallback: локальный `git merge-base origin/<base> <headSha>` — только если ветка выкачана и `<headSha>` резолвится; иначе честный отказ гейта с исходом `base-unknown` (не LGTM, не «протухло» — отдельный исход, см. п.3). Локальный `HEAD` для базы не трогаем — та же ловушка 29.07.

(2) **`--restamp` обязан сохранять base.** Порядок: сначала читаем существующий маркер и блок `review-source` из тела; base берём оттуда. Если в артефакте base нет (legacy) — не выдумываем: пересобираем маркер без base, как раньше (legacy-режим b1). Флаг `--restamp --recompute-base` — отдельная явная операция, пересчитывает base текущей ручкой compare и **перештампует** артефакт (не тихо). Никакого молчаливого дописывания base в старые вердикты.

(3) **Три исхода, три разных сообщения, разные exit-коды:**
- `stale-head` — head в PR ушёл вперёд (как сегодня).
- `stale-base` — head совпадает, но merge-base сдвинулась: «база вердикта X, текущая Y, осмотренный дифф больше не отражает PR».
- `base-unknown` — не смогли посчитать текущую base (нет сети/ветки): «база не проверена», гейт красный, но с иной причиной, чем протухание.
Legacy-маркер без base → отдельная нейтральная пометка «вердикт до правила base», проходит по слову владельца, не смешивается со `stale-base`.

(4) **Зубы CLI (обязательные):**
- маркер с base + свежей merge-base → PASS;
- маркер с base ≠ свежая merge-base при том же head → `stale-base`;
- head сдвинулся → `stale-head` (base не смотрим);
- legacy-маркер без base → проходит, лейбл legacy;
- отказ compare-ручки без локальной ветки → `base-unknown`, exit ≠ 0;
- `--restamp` без `--recompute-base` сохраняет исходную base (в т.ч. её отсутствие);
- `--restamp --recompute-base` меняет base и это видно в диффе артефакта;
- ревью чужого PR (headSha из `gh pr view`, не локальный HEAD) — прогон на реальном PR соседней ветки.

Рекомендация: **форма готова, ADR не нужен** — расширяем существующий контракт b1/b2 без нового источника правды. Если решим ввести отдельный exit-код для `base-unknown` (а не общий «красный»), это одна строка в `review-gate` и запись в справочнике исходов — тоже без ADR.
