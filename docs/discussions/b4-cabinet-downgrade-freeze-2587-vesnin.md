## 2026-10-06 15:57 UTC · vesnin

**Контекст:** packages/background-cabinet/src/modules/tariff/tariff-downgrade.service.ts
**Вопрос:** Блок b4 спринта tariff-downgrade-freeze-2587 (план v3, ADR-0031 р.5), ветка feat/cabinet-downgrade-freeze-2587. Состав: таблица MembraneDowngradePolicy (отдельно, без backfill, CHECK на три режима) + домен downgrade-policy.ts (зеркало словаря media; isDowngrade по рангу сетки) + сервис/контроллер GET/PUT /v1/membranes/me/downgrade-policy; порт MediaDowngradeArchiveClient (preview/freeze дверей media b3b; 200/201 по телу, иное — ServiceUnavailable); оркестратор TariffDowngradeService (файл в билете): preview по всем узлам мембраны (bufferLimitBytes из строки Tariff цели, criterion из политики, retentionDays из ARCHIVE_RETENTION_READER), select: избытка нет → обычный selectTariff + разноска; избыток → нужны planDigest по каждому узлу с избытком (preview_required с предпросмотром), freeze по узлам по очереди, первый сбой останавливает (freeze_failed с batchId failed-партии, setTariff 0 вызовов), все ok → selectTariff → syncAllNodes; ответ несёт frozen[]. Новые причины в SERVICE_DENY_REASONS: preview_required, freeze_failed, media_unavailable. Контроллер: previewDigests в теле, дверь POST membranes/me/tariff/preview; разноска из контроллера ушла в оркестратор. Зубы: порядок preview×N→freeze→setTariff→sync, media отказ → setTariff 0, идемпотентный повтор после обрыва, preview_required; 85 зубов зелёные, typecheck/lint 0. Объём +1068 строк — точка перерезки. Проверь: (1) порядок freeze-first и остановка на первом сбое — верно ли не морозить остальные узлы? (2) preview в select пересчитывается заново и хеши сверяются с ним — а не с тем, что показали человеку: не даёт ли это ложный preview_required при безобидном изменении (новая запись на узле без избытка)? (3) где зона ответственности за сверку digest — кабинет или media (plan_stale)? (4) select при частичной заморозке и падении commit — повтор идемпотентен, но что с узлами, у которых избыток исчез между запросами? (5) как резать на ≤400: предложи b4a/b4b по файлам. Вердикт сдан/не сдан по BLOCK-условиям b4 плана (порядок не freeze→commit→fanout; понижение при избытке без предпросмотра проходит; отказ media → смена тарифа; retentionDays не из daysFor; промо вниз открылось).

**Ответ:**

**Конструкция.** Порядок в `select` собран верно: preview-гейт → freeze по узлам → только затем `commitAndFanout`. Это и есть freeze-first; альтернативу (тариф → мораторий) отработали в ADR-0031 р.5, повторять не буду.

**По вопросам.**

1. **Обрыв на первом сбое — правильно.** Морозить остальные под тариф, который не сменится, значит плодить партии без причины; узлы в `frozen[]` честно названы. Один нюанс: первый сбой — цепочка стоит, но уже замороженные узлы остаются замороженными до повтора того же `planDigest`. Это записано в комментарии и лечится идемпотентностью media — форма выдержит.

2. **Главная дыра.** `select` зовёт `this.preview(...)` заново и сверяет digests с **этим** свежим предпросмотром, а не с тем, что видел человек. Если между `POST preview` и `select` на узле без избытка появилась новая запись — `preview`-снимок по этому узлу не меняется (`excess` по-прежнему `false`), сетка пересчёта не даст; но если изменился **freeze-набор** хоть на байт — `planDigest` уедет, и человек получит `preview_required` на хеш, которого не видел. Формально это не ложь (сервер прав), функционально — тупик «предпросмотр не сходится сам с собой». Сверять надо с теми digest'ами, что ушли в ответе preview; media — второй барьер (`plan_stale`), не первый. Это BLOCK-смежное: без правки сценарий «подтвердил → повторил → снова подтверди» реален.

3. **Зона сверки — media.** `plan_stale` живёт там, где живут данные буфера; кабинет несёт только хеш, который показали человеку. Кабинет не перепроверяет хеш, он его **передаёт**. Если `select` пересчитывает preview — это уже вторая сверка, лишняя и вредная (см. п.2). Правильно: `select` не делает preview заново, а берёт `previewDigests` из входного запроса как факт подтверждения и шлёт их в media. Предварительная проверка нужна ровно одна — «есть ли вообще избыток по данным на момент commit», и её источник — не свежий preview, а факт `requiresConfirmation` из подтверждённого плана.

4. **Узел, где избыток исчез.** Сейчас он просто не попадёт в `excessNodes` при пересчёте — но мы пересчитываем, значит опять п.2. После правки п.2: узел из `previewDigests` без соответствующего excess-узла в свежих данных — это уже media решает через `plan_stale`; если media вернёт `ok` с пустым freeze — принимаем как «нечего морозить», идём дальше. Отдельной новой причины не заводить.

5. **Резка на ≤400.** По файлам: **b4a** = `downgrade-policy.ts` + таблица + контроллер GET/PUT политики (домен и его дверь); **b4b** = порт `MediaDowngradeArchiveClient` + `TariffDowngradeService` + контроллер `POST membranes/me/tariff/preview` + select с `previewDigests`. Зубы бьются по той же линии: b4a — словарь и CHECK; b4b — порядок, отказы, идемпотентность.

**Затронуто:** `tariff-downgrade.service.ts` (п.2), `SERVICE_DENY_REASONS` — без новых причин, тесты порядка — не трогаем.

**Рекомендация — форма: доработать п.2/п.3 внутри b4b перед сдачей; после правки резать b4a/b4b.**

**Вердикт по BLOCK-условиям плана b4:** порядок freeze→commit→fanout — **соблюдён**; понижение при избытке без предпросмотра — **не проходит** (`preview_required`); отказ media → смена тарифа — **не проходит** (стоям на `freeze_failed`, `setTariff` 0); `retentionDays` из `daysFor` — **да**; промо вниз — **не открылось**. По букве блока — **не сдан** из-за п.2 (вторичный preview ломает сходимость подтверждения); после правки п.2/п.3 — сдан.
