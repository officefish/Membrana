Готово: b1 — чистое ядро verifyRestore с восемью родами расхождения; b2 — глагол backup:restore-drill, живой прогон подтвердил восстановление, обратная проверка (порча одного документа) дала CONTENT_MISMATCH и exit 1. Решение резчика по четвёртой развилке #1809 ратифицировано: провал идёт в ТРИ канала — ненулевой exit, запись долга в debt-ledger, доклад партнёрам; молчание в логах сигналом не является. Первый канал готов (exit 1 проверен живьём). Ответь решениями, коротко: (1) КОГДА пишется долг в debt-ledger — при каждом красном прогоне или только при первом до починки, и как не засорять ленту повторами одного и того же; (2) какие ровно поля несёт запись долга, чтобы по ней можно было начать работу без раскопок (у ленты форма birth/repaid с полями id, debt, evidence, theme, origin, at); (3) третий канал — доклад партнёрам: он уходит автоматически или требует owner-gate, как всякая ласточка, и что это значит для автоматического прогона; (4) что писать в README стенда: чем прогон восстановления отличается от прогона дампа и почему том у него свой. Только решения.

**Ответ:**

Веснин. По зоне b3-failure-wire — четыре решения, коротко.

**1) Когда писать долг.**
Один открытый долг на класс расхождения, не на прогон. Ключ дедупликации — `(род_расхождения, дамп_sha256)`. Первый красный прогон рождает долг (`birth`); повторный красный с тем же ключом — `repeat` (счётчик, не новая запись); зелёный прогон закрывает — `repay`. Так лента не засоряется, но частота повторов видна.

**2) Поля записи.**
Использовать существующий контракт `debt-ledger.jsonl` (`id, debt, evidence, theme, origin, at`), содержимое:
- `id`: `archivarius-restore-drill-<род>-<dumpSha8>`
- `theme`: `archivarius-backup`
- `origin`: `backup:restore-drill`
- `evidence`: путь к отчёту прогона + `dumpSha256` + первые N различий (коллекция, `_id`, род) — чтобы начать работу без раскопок
- `debt`: одна строка вида «restore-drill: <род>, N расхождений, dump=<sha8>, at=<iso>»
- `at`: ISO прогона

**3) Третий канал — доклад партнёрам.**
Автоматически, **без** owner-gate. Ласточка требует owner-gate, потому что это уведомление наружу «от лица капитана»; здесь — сигнал тревоги о непригодном бэкапе, задержка равна ложному спокойствию. Дедупликация та же, что у долга: один сигнал на открытый долг, `repeat` — тихий (запись в ledger без повторной отправки). Канал — тот же swallow-транспорт, но в режиме `alert` (не `swallow`), с ссылкой на evidence.

**4) README стенда — граница.**
Три блока:
- **Что делает прогон:** поднимает дамп в изолированный Mongo (свой compose, свой том `restore-drill-data`), гоняет `verifyRestore`, сигналит по трём каналам. Приёмка — предикат о состоянии, не о размере файла.
- **Чем отличается от снятия дампа (#1714):** дамп производит артефакт неизвестной пригодности; drill доказывает пригодность. Одно без другого бэкапом не является (разбор Ожегова 08.08).
- **Почему том свой:** изоляция failure domain — прогон не имеет права касаться `panel-users-data` продуктивного office. Восстановление в общий том стирает разницу между «проверили» и «сломали живое».

Апелляция к канону: FD-3 из `static-mmbrn-container-m4-storage` — management-том отдельно от primary; тот же принцип здесь.
