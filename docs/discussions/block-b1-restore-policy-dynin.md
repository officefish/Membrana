Решения.

**(1) Форма записи об одной коллекции.** Кортеж `{ name: string, count: number (int ≥ 0), sha256: string (hex64, over BSON dump отсортированного по `_id` asc), invariants: { schemaVersion: enum(KNOWN_SCHEMA_VERSIONS), requiredIndexes: string[] (sorted), pkField: string, extras?: Record<string, string|number|boolean> } }`. Опись — `{ subject: enum(SHA256_SUBJECTS), source: enum(INVENTORY_SOURCES), takenAt: number, collections: Inventory[] (sorted by name asc, unique) }`. Почему именно так: три слоя обязательны и независимы (count — грубая арифметика, sha — побитовое равенство содержимого, invariants — семантика ключевых сущностей); сортировка имени и `_id` делает sha детерминированным без «примерно равно»; `subject`/`source` — закрытые списки, чтобы ядро не мигрировало на строках.

**(2) Вердикт сравнения.** `verify(source, restored) → { ok: true } | { ok: false, reason: MismatchReason, at: { collection: string, layer: 'count'|'sha'|'invariant', field?: string }, expected, actual }`. Первое расхождение, а не все, — сознательно: (а) сравнение — предикат тождества, не отчёт аудитора; ok/¬ok достаточно для гейта; (б) детерминированный порядок обхода (коллекции по имени, слои `count → sha → invariants`) даёт воспроизводимую точку отказа без зависимости от того, дошли ли до дальних слоёв; (в) полный дифф — работа отдельной функции над тем же входом, ядро её не совмещает.

**(3) Закрытый список `MismatchReason`.** `COLLECTION_MISSING`, `COLLECTION_EXTRA`, `COUNT_MISMATCH`, `CONTENT_MISMATCH` (равный count, разный sha), `SCHEMA_VERSION_MISMATCH`, `REQUIRED_INDEX_MISSING`, `PK_FIELD_MISMATCH`, `EXTRA_INVARIANT_MISMATCH`. `COUNT_MISMATCH` ≠ `CONTENT_MISMATCH`: первое — арифметика мощности множества (документ пропал или лишний), второе — мощность совпала, но хотя бы один документ отличается побитово (порча поля, реордер значений массива, потерянное поле). Разделение обязательно: восстановление с равным count и разным sha — самый опасный случай («тихая порча»), его нельзя маскировать под «всё сошлось по числу».

**(4) Отсутствие слоя во входе.** Отказ входа: `throw InvalidInventoryError({ collection, missingLayer })`. Ни `unknown`, ни расхождение. Обоснование: ратификация резчика — «все три слоя обязательны»; если `sha` не посчитан на восстановленной стороне, это дефект пайплайна снятия описи, а не свойство состояния БД. Ядро — чистый предикат тождества, оно не имеет права молча возвращать `ok=false` при неполном входе (это ложный минус) и не имеет права возвращать `ok=true` (ложный плюс). Только отказ входа с явным кодом.

**(5) Обязательные зубы.**
- Равные непустые описи → `ok: true`.
- `COLLECTION_MISSING` / `COLLECTION_EXTRA` детектируются раньше count.
- `COUNT_MISMATCH`: одинаковые sha по формуле, но разный count (синтетический вход) — reason именно count, не sha (порядок слоёв).
- **Частичная порча при равном count**: одна коллекция, count равен, один документ с изменённым не-`_id` полем → `CONTENT_MISMATCH` с `at.collection` и `layer:'sha'`. Это ключевой зуб — без него трёхслойность декоративна.
- Реордер массива внутри документа при равном count → `CONTENT_MISMATCH` (sha чувствителен к порядку BSON, что и требуется).
- `SCHEMA_VERSION_MISMATCH`, `REQUIRED_INDEX_MISSING`, `PK_FIELD_MISMATCH` — по одному зубу с ожидаемым `expected`/`actual`.
- Неотсортированная опись на входе → отказ входа, не «толерантная сортировка внутри».
- Отсутствие любого из трёх слоёв → `InvalidInventoryError`, зуб проверяет код и `missingLayer`.
- Детерминизм: два прогона одинакового входа дают побитово равный вердикт (без `Date.now()`, без `Math.random()`, без обхода `Object.keys` без сортировки).
