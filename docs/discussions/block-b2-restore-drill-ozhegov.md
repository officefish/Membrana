## Решения по b2-restore-drill

**(1) Опись источника — пересчёт на живой базе перед восстановлением, не из манифеста дампа.**
Манифест дампа несёт `sha256` тела архива (артефакта), а не описи коллекций в трёхслойной мерке `verifyRestore`. `parseDbInventory` из stderr `mongodump` даёт только `{db, collection, count}` — этого хватит на первый слой мерки, но не на второй (sha256 сортированного дампа документов) и не на инварианты. Значит, перед `mongorestore` снимаем **описи источника и цели одним и тем же конвейером** (см. п.2); только так две ветви `verifyRestore(source, restored)` сопоставимы по построению. Манифест остаётся артефактом происхождения, не мерилом.

**(2) Конвейер sha256 — `mongodump --archive` per-collection в stdout, поток в sha256, документы отсортированы по `_id` через промежуточный проход.**
`mongoexport` даёт JSON (нестабильная сериализация ключей, потеря BSON-типов) — непригоден. Прямой `mongodump` архива идёт в природном порядке (`$natural`), несопоставим между инстансами. Конвейер на коллекцию: `mongosh --eval "db.<c>.find().sort({_id:1})"` в BSON через `bsondump`/скрипт **либо** предварительный `db.<c>.aggregate([{$sort:{_id:1}},{$out:"<c>__sorted"}])` в **служебной БД прогона**, затем `mongodump --archive --db=<probe> --collection=<c>__sorted | sha256sum`. Порядок обязателен — без сортировки по `_id` sha256 плавает; сортировка по `_id` даёт канон.

**(3) Восстанавливаем во ВТОРОЙ контейнер, поднимаемый прогоном рядом со стендом.**
Тот же стенд с другой БД — грязный ход: разделяем данные общим `mongod`, любой сбой изоляции портит источник (Ожегов 08.08: «изолированное окружение»). Снос БД перед накатом на том же контейнере — прямое нарушение того же требования: мы теряем возможность после провала посмотреть источник рядом с восстановленным. Значит, `deploy/archivarius-backup/restore-drill.compose.yml`, имя проекта `archivarius-restore-drill`, сервис `archivarius-mongo-restored`, свой том `archivarius-mongo-restored-data`, порты не публикуются. Источник для описи — существующий `archivarius-mongo-proof` (или продовый, задаётся через `ARCHIVARIUS_RESTORE_SOURCE_*`); цель — новый контейнер.

**(4) После прогона — контейнер и том сносятся ВСЕГДА, независимо от исхода.**
`docker compose -p archivarius-restore-drill down -v` в `finally`. Причины: (а) том прогона несёт восстановленную копию продовых данных — держать нельзя; (б) следующий прогон обязан начинаться с пустого состояния, иначе мерка теряет смысл (может пройти на остатках прошлого раза); (в) провальный прогон **не** оставляем на разбор в томе — разбор ведётся по `verifyRestore.diff` (первое расхождение + род ошибки), это и есть артефакт. Флаг `--keep-on-failure` не вводим: соблазн отладки перевесит правило.

**(5) Зубы без docker: мокается граница «оркестратор ↔ окружение», ядро остаётся живым.**
Скрипт разбиваем на два слоя: `restore-drill-runner.mjs` (композирует, дёргает CLI-адаптеры, вызывает `verifyRestore`) и адаптеры `mongo-cli-adapter.mjs` / `docker-compose-adapter.mjs` с узким интерфейсом (`up`, `down`, `dump(db,coll) → Buffer`, `restore(archive)`, `listCollections(db)`, `countDocs`, `hashSortedDump`). Зубы:
- юнит на `runner` с fake-адаптерами, возвращающими предзаготовленные описи → проверяем ветвление на восьми родах из `verifyRestore` + happy path;
- юнит на парсер `mongodump --archive` stderr (у нас уже есть в b0);
- юнит на канонизацию описи (детерминизм сортировки, стабильность sha при повторе на тех же байтах);
- **интеграционный** зуб с docker — отдельный `it.skipIf(!process.env.DOCKER_AVAILABLE)`, не входит в основной прогон CI-этапа b2.

Зубы `verifyRestore` уже стоят в b1 — здесь не дублируем, здесь про оркестрацию.
