## 1) Форма сигнала от порта

Вариант **(а) — расширить возврат**, но **обратно совместимо**.

```ts
type RetrievalResult = 
  | Hit[]  // старая форма, пока порт не обновлён
  | { 
      hits: Hit[],
      mode?: 'full' | 'reduced',
      modeReason?: string
    };
```

Ядро нормализует:
```ts
const result = await retrieve(axis, topic);
const hits = Array.isArray(result) ? result : result.hits;
const mode = !Array.isArray(result) ? result.mode ?? 'full' : 'full';
const modeReason = !Array.isArray(result) ? result.modeReason : undefined;
```

**Признак:** старые зубы (блоки 1–2) видят `hits` как раньше; новые зубы C3 проверяют `mode` без правки старых. Ядро остаётся чистым: одна нормализация, всё детерминировано.

---

## 2) Что кладём в запись оси

**mode пишется всегда** — включая `'full'`. 

**Довод через читателя:** Без режима в записи при полном прогоне читатель (консилиум, клиент) не может ответить: «был ли порт предложен выбор и отклонил часть, или этот набор исчерпывающ?» Это не деталь реализации — это смысловой факт о полноте облака.

**Что кладём:**
```ts
{
  axis: string,
  status: 'ran' | 'failed' | 'skipped',
  count: number,
  mode: 'full' | 'reduced',      // ВСЕГДА
  modeReason?: string             // ТОЛЬКО если mode === 'reduced' или status === 'failed'
}
```

**Почему отдельный ключ:** `reason` зарезервирован за *диагностикой статуса* (failed, skipped). `modeReason` — это *объяснение режима*, ортогональное статусу. Переиспользование `reason` запутает читателя: какой отказ перед ним — статус или режим?

---

## 3) Множество значений режима

**Только `'full' | 'reduced'` — замороженное множество, с зубом.**

```ts
const MODE = Object.freeze(['full', 'reduced']);
```

Аргумент: *это не параметр*, а **диагностический флаг**, отражающий контракт с портом. Если завтра портов станет три (LLM, лексикон, гибрид) и возникнет `'partial_llm'` — это будет сигнал **расширить контракт ядра**, а не замять разницу под enum. Зуб на дословность:

```ts
assert.deepEqual(
  OP_VERBS.filter(v => v.startsWith('surface_')).length,
  0, // mode никогда не зависит от verbs
);
```

Множество замороженное как `AXIS_STATUS`, но независимое.

---

## 4) Граница с planHealth

**Режим и здоровье — ортогональные оси, не смешивать.**

| Вопрос | Отвечает |
|--------|----------|
| «Прошёл ли мультизапрос строго?» | `planHealth` → `ok | empty-archive | retrieval-broken` |
| «Покрыл ли мультизапрос предметную область в полноте?» | `mode` → `full | reduced` |

**Пример:**
- Ось `Q1 topic` прошла, вернула 5 документов, режим `'full'` → `status:'ran'` + `mode:'full'` + `planHealth:'ok'`.
- Ось `Q2 contrast` прошла (статус ran), но лексикон дал только два антонима вместо обещанного диапазона → `status:'ran'` + `mode:'reduced'` + `planHealth:'ok'`.
- Ось `Q1` упала (портал недоступен) → `status:'failed'` + `planHealth:'retrieval-broken'`.

Здоровье — об **исполнимости**; режим — об **адекватности покрытия**. Их смешивание превратит `planHealth` в свалку.

- Если `status !== 'ran'` → `mode` не пишется ✓
- Неизвестный режим → становится `reduced` с причиной ✓

Нет магических чисел, нет проверки внутреннего состояния класса. Всё через контракт.

**Оценка:** ✓ поведение.

## 4) Чего не хватает в зубах?

Три наблюдения:

### A. Тест на граничный случай: `modeReason` в форме пробелов

```js
const given = typeof result?.modeReason === 'string' ? result.modeReason.trim() : '';
```

Ты обрезаешь пробелы — умно. Но **зуб должен покрыть**:
```js
normalizeRetrieval({ hits: [1, 2], mode: 'reduced', modeReason: '   ' })
// → { ..., modeReason: 'порт не назвал причину урезания' }
```

Проверь, есть ли такой тест.

### B. Граница между `undefined` и пропущенным полем

```js
const declared = result?.mode;
if (declared !== undefined && !AXIS_MODES.includes(declared)) { ... }
const mode = declared ?? 'full';
```

Это работает корректно, но есть нюанс: если порт отправит `{ mode: null }`, ты получишь:
- `declared === null` → пройдёт первую проверку (не `undefined`)
- затем упадёт на `AXIS_MODES.includes(null)` → false → reduced

Это **правильное поведение**, но тест должен покрыть:
```js
normalizeRetrieval({ hits: [], mode: null })
// → reduced с причиной 'режим … вне закрытого списка'
```

### C. Взаимодействие с фильтром уже операционных кандидатов

В `buildSubconsciousCloud` ты используешь результат `normalizeRetrieval` прямо:
```js
const { hits: list, mode, modeReason } = normalizeRetrieval(hits);
axes.push(axisEntry(axis, 'ran', list.length, undefined, mode, modeReason));
```

Зубы должны проверить, что количество хитов в плане соответствует **после** фильтрации по `notAlreadyOperational`:

```js
for (const hit of list) {
  if (hit?.id === undefined) continue;
  if (typeof notAlreadyOperational === 'function' && !notAlreadyOperational(hit.id)) {
    continue;  // ← здесь кандидат выбрасывается
  }
  // ...
}
```

Вопрос: **должен ли hitCount в плане показывать хиты ДО фильтра или ПОСЛЕ?** Сейчас ты пишешь `list.length`, то есть ДО. Это имеет смысл (режим `reduced` указывает на урезание на уровне портала, не фильтра), но тест должен явно покрыть сценарий:

```js
// Порт вернул reduced с 10 хитами; 3 оказались уже операционны
// → hitCount в плане = 10, но в облаке их будет < 10
```
