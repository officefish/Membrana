**Вопрос:** Блок b3-dump-archive-source спринта dump-inventory-from-archive (ты держатель; b1-b2 готовы). Дом lib/archive-inventory отдаёт buildInventoryFromArchive({archivePath, adapter, keepUp})→{inventory, listing} (listing: {name,count,indexes}[]). Твой дифф: scripts/archivarius-dump.mjs + mongo-dump-policy.mjs (+ их зубы). Решения резчика уже стоят: parseDbInventory демонтировать; incompleteCollections(stderr) остаётся гардом протокола отдельным полем protocolChecks.incompleteCollections; без докера/стенда — стоп DUMP_INVENTORY_UNAVAILABLE, фолбэка нет; манифест: inventorySource='archive-contents'. Твои развилки исполнения: (а) маппинг listing→dbInventory манифеста [{db, collection, documentCount}]: db откуда — DB_NAME дома (архив режется nsInclude DB_NAME.*) или из имени коллекции? предлагаю db=DB_NAME константой дома; (б) схема манифеста: MANIFEST_SCHEMA_VERSION бампить? поле incompleteCollections переезжает в protocolChecks.incompleteCollections — политика сейчас валидирует его на верхнем уровне (строка 191) и dbInventory (195); совместимость: старые манифесты 09.08 с inventorySource='mongodump-stderr' и верхнеуровневым incompleteCollections должны оставаться валидными для isFitForRetention (ретенция читает старые!) — версионировать валидацию по schemaVersion или по inventorySource? (в) момент снятия описи: после закрытия артефакта (tmp→final до или после описи?) — опись обязана описывать ТОТ файл, который лёг на диск: снимать с финального пути и вписывать в манифест рядом с sha256 того же файла; (г) sha256 артефакта уже считается потоком при дампе — опись из артефакта читает файл второй раз, это ок? (д) зубы: fake-adapter дома + захват реального вывода несуществующего стенда невозможен до b4 — допустимы ли синтетические листинги как в зубах дома?

**Ответ:**

Положение: держу b3, дом готов, резчик отрезал parseDbInventory и фолбэк, манифест переезжает на `inventorySource='archive-contents'`. Пять развилок — по существу, отвечаю коротко.

Решения:
- **(а) db в маппинге.** `db = DB_NAME` константой дома. Мы режем архив `nsInclude DB_NAME.*` — парсить имя коллекции обратно = вводить второй источник истины на пустом месте. Одна правда — конфиг дома.
- **(б) схема манифеста.** Бампить `MANIFEST_SCHEMA_VERSION` (2). Валидация в политике — ветвление **по schemaVersion**, не по inventorySource: v1 читает `incompleteCollections` на верхнем уровне (старые 09.08 остаются валидными для ретенции), v2 — из `protocolChecks.incompleteCollections`. inventorySource — это *откуда взяли данные*, а не *какая форма манифеста*; смешивать оси нельзя.
- **(в) момент снятия описи.** После `tmp→final`. Опись обязана описывать файл, который лёг на диск, — читаем финальный путь, sha256 в манифесте — того же файла. До ротации описи быть не может.
- **(г) двойное чтение sha256.** Ок. Поток дампа считает sha256 артефакта (as-written), опись из архива — независимая проверка того же файла через adapter. Это не оптимизация, это разные назначения: один — интегритет записи, другой — содержимое архива. Совпадение хеша тут не требуется (опись не хеширует, она перечисляет).
- **(д) зубы без стенда.** Синтетические листинги через fake-adapter — допустимы и обязательны на b3. Реальный прогон против несуществующего стенда должен упасть в `DUMP_INVENTORY_UNAVAILABLE` — это отдельный зуб (гард протокола), пишется тем же fake-adapter'ом с пустым listing + флагом недоступности. Живой стенд — задача b4.

Связка: tarasov (исполнение диффа) + reznik (сверка границ по решениям резчика, если всплывёт краевой случай в политике) + arkhipov (ревью схемы манифеста v1/v2 — версионирование затрагивает канон).

## 2026-08-10 16:03 UTC · tarasov

**Вопрос:** Уточнение по твоему (в) до кода. В тракте дампа стоит ИМЕНОВАННЫЙ инвариант (докблок): «Манифест ложится РАНЬШЕ переименования: увидев финальное имя, читатель обязан уже иметь возможность прочесть, чем этот файл является» — а опись есть поле манифеста. Твоё (в) читается как «опись после tmp→final», что требует либо сломать этот инвариант (rename до манифеста), либо писать манифест дважды. Третий путь, сохраняющий оба: опись снимается с ЗАКРЫТОГО tmp-файла (поток дописан, файл закрыт, pipeline завершён) — это те же байты, которые атомарным rename получат финальное имя; порядок: закрыть tmp → опись из tmp (read-back с диска, не из состояния потока) → манифест → rename. Существо твоего (в) — «опись описывает файл на диске, а не поток» — соблюдено read-back'ом; sha256 в манифесте и так считан с тех же байт. Подтверждаешь третий путь, или ломаем инвариант порядка манифест/rename?

**Ответ:**

Положение: инвариант «манифест раньше rename» — именной, назван в докблоке; ломать его ради описи — потеря сильнее, чем выигрыш. Двойной манифест — гниль (два источника правды об одном файле, повод для расхождения). Третий путь снимает противоречие без цены.

Решение: **подтверждаю третий путь**. Порядок жёсткий:
1. закрыть tmp (поток дописан, fsync);
2. read-back с диска tmp → опись + sha256 (те же байты, что уедут под финальное имя);
3. манифест (с описью и sha256) кладётся рядом;
4. атомарный rename tmp→final.

Условия приёма:
- опись и sha256 считаются **из одного прохода** read-back'а — не двумя чтениями;
- в докблоке инварианта добавить строку: «опись — read-back с закрытого tmp, до rename»; это не новый инвариант, это разъяснение существа (в);
- крэш между (3) и (4) — сирота tmp+manifest под tmp-именем; уборщик обязан их снести парой. Зафиксировать в тесте.

Связка: структурщик пишет докблок и порядок в коде, математик — тест на «манифест ссылается на те же байты, что и final после rename» (sha256 совпадает до и после).

Вердикт: **LGTM** на третий путь. Ломать порядок манифест/rename — BLOCK.
