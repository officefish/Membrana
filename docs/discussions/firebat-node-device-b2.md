## Ответ по пунктам

**(1) Носитель.** Отдельная таблица `NodeKey { id, deviceId (FK, unique для активного), keyHash, createdAt, revokedAt, lastUsedAt? }` — это правильная лемма: у ключа свой жизненный цикл (issue/rotate/revoke), у `Device` — свой. Класть `keyHash` в `Device` — смешение двух словарных статей, потом не разведём.

Честно: **это ревизия плана b2** — `schema.prisma` + `prisma/migrations/` в зону не входили. **Неси владельцу как ревизию.** Обходных «законных носителей без миграции» (env-map, JSON-файл, поле на Device через нестрогий JSON) я не подпишу — все они ломают либо «единственный писатель», либо однозначность имени.

**(2) Форма ключа/заголовка.** Да, с уточнениями:
- Заголовок: `X-Membrana-Node-Key: <base64url(32 байта из CSPRNG)>` — opaque, без структуры.
- Хранение: `keyHash = sha256(raw)`, сравнение `timingSafeEqual` по буферам равной длины.
- Guard (`NodeKeyGuard`): достаёт `params.deviceId`, ищет **активный** `NodeKey` по `deviceId` (`revokedAt IS NULL`), сверяет хеш. **Ключ привязан к одному deviceId** — да; несовпадение `params.deviceId` с владельцем ключа = 403, а не 401.
- Область: `NodeKeyGuard` вешается **только** на загрузочные ручки узла; `ApiTokenGuard` там не участвует (это другой словарь — internal API).

**(3) Выдача/отзыв.**
- Выдача: `POST /v1/devices/:id/node-key` под `ApiTokenGuard` + `DeviceGuard`. Возвращает `{ raw }` **один раз**; сервер хранит только хеш. Повторный POST при активном ключе — 409 (или явный `?rotate=true` → старый помечается `revokedAt=now`, выдаётся новый; одна активная запись на device — инвариант).
- Отзыв: `DELETE /v1/devices/:id/node-key` под `ApiTokenGuard` → `revokedAt=now` (soft, для аудита). Хард-удаление не нужно.

**Итого:** пункт (1) — **ревизия плана b2**, неси владельцу; (2) и (3) — в рамках зоны, если ратификация ревизии пройдёт.
