**Контекст:** docs/adr/ADR-0028-pair-media-token-per-device.md
**Вопрос:** Блок b5 — твой: ADR-0028 записана (в ticket) по твоей форме из нарезки: долг служебного mediaToken назван кодом и строкой; сверка словарей NodeKey vs ключ парринга таблицей (вывод: два лица устройства, не дубль; per-device право на media — только у NodeKey сегодня); Р1 per-device ключ через мост (носитель — та же таблица NodeKey или audience-поле, решит резчик реализации), Р2 отзыв связки отзывает media-ключ, Р3 ротация служебного после раскатки, Р4 включение safeStorage с миграцией и без размывания sync-порта. Реализация — отдельный спринт media-per-device-token. Подписываешь b5? «подписываю» или недостающее.

**Ответ:**

Подписываю.

Три уточнения на полях — не блокирующие подпись, а для резчика спринта `media-per-device-token`, чтобы не переоткрывать форму:

- **Носитель ключа.** Моя рекомендация — расширить `NodeKey` полем `audience: 'node' | 'client'`, а не заводить вторую таблицу. Один словарь ключей устройства, один guard с проверкой audience на ручке. Но это решает резчик реализации на своём консилиуме — форма ADR не диктует.
- **Р4 и порт b2.** Три sync-глагола (`get/set/clear`) остаются контрактом. `AsyncPairingCredentialsStore` — отдельным именем в web-адаптере, либо кэш-при-старте; смешивать в один порт запрещено (наблюдение Ожегова из b2 держим).
- **Порядок раскатки жёсткий:** Р1+Р2 → Р4 → Р3. Р3 до Р4 = положит клиентов, которые ещё носят служебный токен; это в «Последствия» уже сказано, повторяю здесь для приёмки.

Форма выдержит: два лица устройства = два применения одного словаря ключей, отзыв — одно действие пользователя, служебный токен уходит из клиентских носителей до ротации. Дальше — резчик.
