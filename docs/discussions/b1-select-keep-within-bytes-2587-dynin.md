**Ответ:**

[память:подсознание] emerge dynin-2026-08-01-evening-review-predicate-m4-memoization — там я уже разбирал пару несовместимых предикатов на одном органе; тут та же техника: pinned и «влезает в бюджет» задают два разных отбора, и важно формально показать, что они сведены в один линейный порядок без противоречия.
[память:подсознание] emerge dynin-2026-07-28-memory-subconscious-m2-priority — ровно задача «pinned ⊈ бюджетного конкурса»: pinned-неизмеримая не участвует в knapsack, остаётся по инварианту. Здесь та же структура, перенесённая на байты.

По существу:

1. **Компаратор.** Ключ `(¬pinned, modeRank ?? +∞, −createdAt, sampleId)` в лексикографическом порядке над полностью упорядоченными доменами — автоматически строгий тотальный порядок: антисимметричен и транзитивен. Проверь зубом: `cmp(a,b) = −cmp(b,a)` для всех пар на фикстуре из 6–8 элементов со всеми коллизиями по каждому ключу, и `cmp(a,b)<0 ∧ cmp(b,c)<0 ⇒ cmp(a,c)<0` на тройках. Тонкое место — `null` в `modeRank`: эквивалент `+∞` только если **и** `a` **и** `b` неизмеримы — тогда они равны по этому ключу и спор уходит на `createdAt`/`sampleId`. Без явной нормализации `null→+∞` рискуешь получить `NaN`-подобное поведение.

2. **Инвариант байт.** Knapsack-greedy с пропуском сохраняет `sum(keep) ≤ limit` строго: добавление в `keep` обусловлено `keepBytes + c.bytes ≤ limit`, иначе `freeze`. Инвариант не ломается, потому что мы не откатываем ранее принятые — монотонность `keepBytes` вверх. **Но:** это не оптимальный knapsack, а greedy по приоритету; это осознанный выбор (приоритет важнее плотности) — зафиксируй это в README как «priority-greedy, не 0/1-optimum», иначе кто-то «починит».

3. **Pinned.** Да, разделение верное и согласуется с принципом «целое управляет частями»:
   - pinned + измеримая → остаётся (участвует в учёте байт);
   - pinned + неизмеримая → остаётся **вне** бюджета (байты неизвестны, но воля владельца сильнее);
   - ¬pinned + неизмеримая → freeze (нет данных для решения);
   - ¬pinned + не влезла → freeze.
   
   Однако есть щель: **pinned-неизмеримая не входит в `keepBytes`**, значит `sum(keep.bytes) ≤ limit` остаётся, но **фактическое** потребление может превышать лимит. Это нужно либо явно задокументировать как «лимит = бюджет измеримого keep», либо вернуть отдельное поле `unmeasuredPinnedCount` в результате.

4. **Чего не хватает зубам (7 штук):**
   - антисимметрия и транзитивность компаратора на сгенерированной выборке (property-based, 100+ случаев);
   - стабильность при `modeRank=null` у обоих кандидатов → решает `createdAt`, затем `sampleId`;
   - pinned-неизмеримая **не** увеличивает `keepBytes` (отдельный зуб на равенство);
   - pinned с `bytes > limit` — остаётся или freeze? Сейчас, судя по описанию, остаётся — это надо зафиксировать зубом явно;
   - лимит = `Number.MAX_SAFE_INTEGER` и суммарные байты, близкие к переполнению;
   - `createdAt` равные **и** `sampleId` равные при разных объектах → должен сработать `duplicate-sample`, а не молчаливое слияние;
   - идемпотентность: `selectKeepWithinBytes(selectKeepWithinBytes(xs).keep ∪ freeze, L) ≡ исходный результат` при том же L.

Один уточняющий вопрос: pinned-кандидат с `bytes > limitBytes` — по контракту остаётся (воля владельца) или уходит во freeze с отдельным кодом отказа? От ответа зависит формулировка 4-го зуба и строка в README про «лимит = бюджет измеримого non-pinned+pinned-измеримого keep».
