**Вопрос:** Блок report-surfacing-render спринта memory-report-surfacing. Зона: scripts/lib/team-memory-report.mjs и его зуб scripts/team-memory-report.test.mjs. Бюджет 220 строк. Ты держатель: предмет ведут ИМЕНА состояний, они станут терминами журнала.

ЧТО ЕСТЬ. Отчёт памяти команды печатает на каждую персону три строки формы кристалла token 121: «записал в оперативку / утонуло в подсознание / всплывало сегодня». Первые две считаются по диффу журналов. Третья прибита намертво: lines.push('- всплывало сегодня: контур не поставлен (#1366 ч.2)'). Шапка отчёта говорит то же: «v1: контуры подсознания и всплытия не поставлены (#1366 ч.2, #1368) — вытеснение = потеря, поимённо».

Модуль ЧИСТЫЙ по собственному объявлению: вход — текст git-диффа, выход — структура/markdown, fs и git у CLI. Данные снаружи уже приходят опцией: opts.reasonsByPersona — Map ref→причина, собранная CLI из op-log по глаголу transfer_to_archive. Всплытие придёт тем же ходом, новой опцией; её сбор — соседний блок, здесь только приём и рендер.

ПОЧЕМУ СТРОКА ТЕПЕРЬ ЛЖЁТ. Контур всплытия поставлен сегодня, три PR влиты. Живой прогон дал журналу Веснина: cloud_query 5, surface_invoke 5, emerge 2, reject 1. Всплывшее — подлинные записи архива с объяснениями персоны.

ЧЕТЫРЕ СОСТОЯНИЯ, различимые по журналу:
(1) есть emerge — всплыло, поимённо, с объяснением персоны из поля reason;
(2) есть reject без emerge — облако показывали, персона отвергла, причина названа;
(3) ноль cloud_query — лифт сегодня не звали;
(4) cloud_query есть, surface_invoke нет — облако собрано пустым, показывать было нечего.

Ответь строго по пунктам.

1) НАЗВАНИЯ четырёх состояний в отчёте, дословно, как они будут стоять в строке. Форма кристалла — «всплывало сегодня: …». Учти, что состояние (3) «лифт не звали» и прежнее «контур не поставлен» — РАЗНЫЕ вещи, и читатель обязан их различать: первое про этот день, второе было про отсутствие механизма. И учти, что состояние (4) — про пустой архивный отбор, а не про отказ персоны.

2) Что показывать при состоянии (1): только счёт, или имена всплывшего, или имена с объяснением персоны. Довод через читателя отчёта, а не через объём. Прецедент рядом: строка вытеснения показывает поимённо и приписывает «→ архив (причина)», когда причина есть.

3) Форма опции на входе чистой функции. reasonsByPersona — это Record<persona, Map>. Что берёт всплытие: сырые события журнала за день по персоне, или уже посчитанную сводку? Кто тогда определяет состояние — чистый модуль или CLI? Обоснуй через то, что состояние есть СУЖДЕНИЕ по данным, и решить, где оно выносится, важнее удобства.

4) Шапка отчёта. Она утверждает, что контуры не поставлены. Заменить полностью, дополнить или снять? Что там должно стоять теперь, дословно.

5) Зубы. Минимальный набор, доказывающий РАЗЛИЧЕНИЕ четырёх состояний, а не рендер строк. Назови, чем зуб отличит состояние (3) от состояния (4) — оба дают ноль всплывшего.

**Ответ:**

Отвечаю по пунктам. Держу как словарные статьи: одно состояние — одно имя, одна граница.

**1) Имена четырёх состояний** (после «всплывало сегодня: …»):

- (1) `<N>: <ref> (<reason>), <ref> (<reason>)…` — поимённо, как у вытеснения.
- (2) `облако отвергнуто (<reason>)` — персона видела, отказалась.
- (3) `лифт не звали сегодня` — про день, не про механизм.
- (4) `облако пустое` — механизм звали, архив не дал кандидатов.

Границы: (3) ≠ прежнее «контур не поставлен» (то было про отсутствие кода, снимается вместе с шапкой); (4) ≠ (2) (пустой отбор ≠ отказ персоны).

**2) Состояние (1): имена с объяснением персоны.** Довод — читатель отчёта сверяет всплытие с вытеснением построчно: там `→ архив (причина)`, здесь должно быть `← архив (причина)`. Счёт без имён рвёт эту симметрию и заставляет читателя лезть в журнал, чтобы понять, что именно вернулось. Кристалл на то и кристалл, что обе стороны — поимённо.

**3) Форма опции и место суждения.**

```ts
opts.surfacingByPersona: Record<persona, {
  cloudQueries: number;
  invocations: Array<{ ref, reason, outcome: 'emerge'|'reject' }>;
}>
```

То есть **уже посчитанная сводка по глаголам journal**, не сырые события. Суждение о состоянии (выбор одной из четырёх веток) выносит **чистый модуль** — потому что состояние есть функция от данных, и его определение должно быть тестируемо без git/fs. CLI отвечает за сбор (парсинг op-log), модуль — за классификацию и рендер. Это та же граница, что уже держит `reasonsByPersona`: CLI приносит факты, модуль их именует.

**4) Шапка — снять полностью и заменить.** Прежняя фраза про «контуры не поставлены» была признанием долга; долг закрыт. Дословно:

> `v2: вытеснение и всплытие — поимённо, с причиной персоны (op-log: transfer_to_archive, surface_invoke).`

**5) Зубы на различение, не на рендер.** Четыре кейса + один граничный, вход — фиктивная сводка:

- (1) `invocations: [{outcome:'emerge', ref:'X', reason:'Y'}]` → строка содержит `X (Y)`.
- (2) `cloudQueries:1, invocations:[{outcome:'reject', reason:'Z'}]` → `облако отвергнуто (Z)`.
- (3) `cloudQueries:0, invocations:[]` → `лифт не звали сегодня`.
- (4) `cloudQueries:1, invocations:[]` → `облако пустое`.
- Граничный: emerge + reject в один день → (1) поглощает (2), reject не печатается отдельно.

Различение (3)/(4) держится на **одном поле** — `cloudQueries`: оба дают пустой `invocations`, но (4) требует ≥1 запроса. Это и есть предмет теста — не текст, а ветка классификатора.
