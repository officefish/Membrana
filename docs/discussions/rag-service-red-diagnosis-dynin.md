# Диагноз: почему `@membrana/rag-service#test` красный третий день

**Блок 1 `rag-red-diagnosis` спринта `contour-sanity-2026-08-19` (#1972). Персона: dynin.**
**Дата:** 2026-08-19. Правок кода нет — только прогоны и измерения. Машина: Windows 11,
дерево `Membrana-product`, ветка `fix/contour-sanity` от `origin/main` (`aacc1732`).

## 1. Что именно красное — и что зелёное

| Прогон | Команда | Исход |
|---|---|---|
| Изолированный, канонический | `yarn workspace @membrana/rag-service test` (= `vitest run --exclude '**/acceptance.test.ts'`) | **45/45 зелёный**, 40 с |
| Как в вечерней цепочке | `yarn turbo run test --force --concurrency=3 --continue` (rag + core + office + fft параллельно) | **1 из 45 падает**: `src/service.test.ts › keywordSearch (R2 operative) › returns operative fragments without LanceDB` — `Test timed out in 30000ms` → `@membrana/rag-service#test … exited (1)` |
| Полный `vitest run` пакета (с acceptance) | `vitest run` в `packages/services/rag` | тот же таймаут + три `acceptance.test.ts › P@5: …` с `expected 8803/14466/8102 to be less than 8000` |

Красный статус фидбека 16–18.08 рождается **ровно вторым прогоном**: `scripts/context-collector.mjs:149`
(`yarn code-review` вечером) гоняет `yarn turbo run test --concurrency=3 --continue` по всему монорепо,
и падение одного теста по времени даёт `exited (1)` всей задаче. CI (`unit-tests.yml`) гоняет
`turbo run test --continue` на Linux-раннере и отдельным шагом `test:acceptance` — там тот же тест
укладывается в порог; зелёный CI и красная вечерняя цепочка — это **две разные машины и две разные
нагрузки**, а не разный код.

## 2. Причина — замер, не мнение

Тест зовёт `keywordSearch(REPO_ROOT, 'Membrana', { days: 30, topK: 3 })` по **живому репозиторию**.
Внутри (`src/operative/recent-docs.ts`) на каждый вызов:

| Фаза | Что делает | Замер 19.08 (в одиночку) |
|---|---|---|
| `gitChangedPaths` | `git log --since=30 days ago --pretty=format:%cI --name-only -- docs/ *.md AGENTS.md .cursorrules` | **6 862 мс**; 868 коммитов за 30 дней, 7 694 строки вывода, 4 061 уникальный путь |
| glob P1 | `docs/archive/daily-day/**/*.md`, `docs/archive/night-build/**/*.md` + `stat` каждого | 277 файлов, 170 в окне 30 дней |
| сборка refs | `stat`/`access` на каждый путь | `getRecentDocs(30)` целиком: **4 860 мс, 2 543 документа** |
| чтение и скоринг | читает каждый документ, режет на чанки, считает BM25-lite | `keywordSearch`: **8 385 мс** (повтор 6 965 мс) |

Итого один вызов — ~7–8 с на ненагруженной машине при таймауте 30 с. Под `turbo --concurrency=3`
три пакета запускают по своему пулу vitest-воркеров, и `git log` + 2,5 тысячи `stat`/`readFile`
на Windows растягиваются в 4× и больше — 30 с пробиты. Тот же механизм у `acceptance.test.ts`:
порог `elapsedMs < 8000` на один запрос, который в одиночку стоит 7–8 с — запас нулевой.

**Корень:** тест утверждает **стеночные часы** (wall-clock) на операции, цена которой растёт с
репозиторием — числом коммитов за 30 дней и числом документов в `docs/archive/*` — и зависит от
машины и соседей по CPU/диску. Это не регрессия кода `rag-service`: за месяц сам `recent-docs.ts`
не менялся (последняя правка 22.06), выросли корпус и история.

## 3. История того же класса

- 24.06 `aad189e5` — порог acceptance поднят 5000 → 8000 мс «timing on CI».
- 29.06 `26ca2779` — срез операций ограничен, таймаут acceptance.
- cg1 (ci-gate-stabilization) — `testTimeout: 30_000` в `vitest.config.ts` с комментарием «на нагруженном
  раннере спайкало за 5 s → флейк».

Трижды лечили подъёмом порога; корпус растёт быстрее порогов. Четвёртый подъём даст четвёртый
рецидив.

## 4. Что НЕ причина

- Не поиск: все 45 функциональных утверждений проходят, падают только часы.
- Не песочница: воспроизводится обычным `turbo run test --force --concurrency=3` в терминале.
- Не `media#test` и не плагины: зоны не пересекаются.

## 5. Варианты решения (для блока 2)

1. **Отделить часы от функции.** В `service.test.ts` утверждение о времени у keywordSearch'а нет —
   красный даёт только `testTimeout`; дать этому тесту корпус-фикстуру (маленькое дерево во
   временном каталоге с `git init`/без git) вместо живого репозитория → проверяется функция
   (`operative`, `length > 0`), а не скорость диска. Acceptance оставить живым, но перенести
   утверждение `< 8000 мс` из `expect` в **репортируемую метрику** (логируется, не валит), либо
   вынести его под флаг `RAG_ACCEPTANCE_TIMING=1`.
2. **Архивировать** timing-утверждения как известный флейк (`it.skip` с причиной) — честно, но
   теряется сигнал о деградации.
3. **Оставить** — статус тестов дня остаётся недостоверным; отвергается.

Рекомендация Дынина — **вариант 1**: красное снимается по существу (тест перестаёт измерять
чужую машину), сигнал о времени сохраняется как число в отчёте, а не как падение.
