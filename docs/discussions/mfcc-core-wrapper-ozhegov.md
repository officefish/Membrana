## 2026-07-30 15:49 UTC · ozhegov

**Вопрос:** Прими или отклони реализацию как структурщик. Конкретно: 1) Границы соблюдены — процессор stateless, состояние только в движке, meyda за периметром? 2) Термины совпали с назначенными тобой, или где я их исказил? 3) Что в этой реализации ты считаешь дефектом, который проявится при подключении второго потребителя?

**Ответ:**

**Оценка как Структурщика: ПРИНЯТО с одним замечанием** (отклоню позже при нарушении).

1. **Границы соблюдены?**  
   Да. `mfcc-processor.ts` — чистый stateless поток: библиотека `meyda` передаётся параметром, модуль не импортирует её глобально. Состояние — только в `mfcc-engine.ts`. Это корректное разделение: процессор = лемма «преобразование», движок = лемма «жизненный цикл/конфигурация».

2. **Термины совпали?**  
   Да. `AudioWindow`, `MfccVector`, `MfccConfig`, `MfccExtractor` — названы как в твоём контракте. Конфиг-хэш (`configHash`) — сознательное расширение против коллизий конфига; приемлю, так как предсказуемо.

3. **Дефект при second consumer:**  
   `mfcc-engine` экспортирует **экземпляр как singleton**:  
   ```ts
   export const mfccEngine = new MfccEngine(…)
   ```  
   Если второй независимый потребитель хочет другой `bufferSize` или свой `onResult`, он **не получит** отдельного инстанса; получит тот же, с уже вызванным constructor. Решение: публиковать только класс `MfccEngine`, а синглтон оставить факультативным в самом потребителе (или выпилить из `index.ts`). **Исправьте: `export { MfccEngine }` — без предсозданного экземпляра.**
