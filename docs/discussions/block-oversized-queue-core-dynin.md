## 2026-08-02 12:03 UTC · dynin

**Контекст:** scripts/lib/review-oversized-queue.mjs
**Вопрос:** Блок oversized-queue-core спринта review-oversized-queue. Ядро очереди: describeCommit считает total и code (код — префиксы packages/, apps/, scripts/), природу code|docs|mixed и долю кода; buildQueue отбрасывает не-oversized, уже проревьюированные (по наличию артефакта, список приходит значением) и чистые доки, отдавая разбивку отброшенного по причинам с числами; порядок — риск по строкам КОДА, затем доля кода, затем номер PR. Порог импортируется из day-work-diff, не переобъявляется. Живой прогон: рассмотрено 589 коммитов, отброшено 404 не oversized, 23 с артефактом, 49 чистых доков; в очереди 113. Ответь как математик коротко: 1) три ключа сортировки — достаточно ли для полного порядка, и есть ли вход где очередь всё ещё недетерминирована; 2) доля кода как ВТОРОЙ ключ при равном риске — не вырождается ли она, ведь при равном code бОльшая доля означает просто меньший total; 3) отбрасывание чистых доков по умолчанию — не прячет ли оно случай, когда в docs лежит исполняемое (скрипт с расширением .md, конфиг, промпт-задание, которое читает движок).

**Ответ:**

Коротко и по делу — три предиката, три ответа.

**1) Полнота порядка по трём ключам.**
Ключи: `code ↓`, `codeShare ↓`, `pr ↑` (лексикографически как строка). Порядок полный тогда и только тогда, когда третий ключ инъективен на входе. Контрпримеры, где детерминизм ломается:
- `pr === null` у нескольких коммитов (прямые пуши, локальные ветки без PR) — все схлопываются в пустую строку. У тебя в живом прогоне 589 коммитов — вероятность, что хоть один без PR, близка к 1.
- Дубликаты `pr` (переоткрытие, cherry-pick с сохранением номера в subject-парсере).
- Лексикографика: `#1099 < #99` — это не баг сортировки, но читатель ждёт числового порядка.
Починка: третьим ключом `sha` (уникален по построению), а `pr` — численно; либо `(pr_num ?? +∞, sha)`.

**2) Вырождение `codeShare` при равном `code`.**
Да, вырождается ровно так, как ты описал: при равном `code` бо́льший `codeShare` ⇔ меньший `total` ⇔ меньше доки. То есть второй ключ поднимает наверх «более кодовые» PR — это защитимо как политика («меньше шума вокруг того же риска»), но это **не независимая мера риска**, а функция от `total` при фиксированном `code`. Если цель именно такая — оставь и назови честно в комментарии («при равном коде — сначала те, где меньше docs-обвязки»). Если хотелось второй оси риска — нужен другой предикат: плотность правок на файл, число тронутых кодовых файлов, или `code`-энтропия по путям.

**3) Docs-фильтр и исполняемое под `.md`.**
Тут дыра. `CODE_ROOTS` — префиксы каталогов, а не суждение о «исполняемости». Под фильтр `docs` тихо уедут:
- `scripts/**/*.md` — не уедут (префикс `scripts/` ловит), ок.
- `docs/prompts/*.md`, читаемые движком как задание — уедут.
- корневые `*.yml`, `*.yaml`, `Dockerfile`, `.github/workflows/**` — не в `CODE_ROOTS`, попадут в `docs`/`mixed` некорректно.
- `packages/**/README.md` — попадут в `code` (префикс), хотя это чистая дока. Симметричная ошибка.
Мерка риска смешивает «где лежит» и «что делает». Минимальная поправка: классифицировать файл по паре (корень, расширение/имя), с явным списком исполняемых вне `CODE_ROOTS` (`.github/workflows/`, корневые `*.y?ml`, `Dockerfile`, `docs/prompts/`) и явным списком не-кода внутри `CODE_ROOTS` (`**/README.md`, `**/*.md` в `packages/`). Список закрытый, читается глазом — как и сейчас.

Ложный минус здесь дороже ложного плюса: пропущенный исполняемый промпт хуже, чем лишний архивный PR в очереди. Значит по умолчанию — `includeDocs: true` для файлов из «исполняемого» списка, независимо от корня.
