## Зачем

Магистраль дня 09.08 — owner-choice владельца. Разбор Ожегова 08.08 дословно: «бэкап =
дамп + верифицированное восстановление на изолированном окружении; без второго это
`mongo-dump-artifact`, а не `backup`».

Дамп влит утром 09.08 (PR #1815) — и ровно с этого момента у нас появился артефакт, **о
котором никто не знал, восстановится он или нет**. Инструмент дампа сам говорил об этом
вслух: «backup:dump — это ДАМП, не страховка: откат не проверялся (см. #1809)».

## Итог: страховка стала полной

**Живой прогон 09.08 подтвердил восстановление.** Стенд засеян синтетикой (5000 спанов +
1 прогон), снят дамп (48.4 КиБ, 5002 документа), накат в изолированную цель дал
«восстановление подтверждено» — три слоя сошлись, том снесён за собой.

**Обратная проверка — мерка умеет краснеть.** Один документ из 5000 изменён при неизменном
счёте: прогон дал `CONTENT_MISMATCH` на слое `sha`, оба хеша в выводе, код возврата 1, долг
заведён. Зелёный прогон после отката порчи записей не добавил.

Это и есть разница между «файл создан, размер ненулевой» и проверкой: первая такого случая
не видит вовсе.

## Итог блоков

- **b1** — [`mongo-restore-policy.mjs`](../../../scripts/lib/mongo-restore-policy.mjs): чистое
  ядро по образцу соседа-политики дампа. Трёхслойная мерка предикатом тождества, порядок
  обхода фиксирован (`count → sha → invariant`), возвращается **первое** расхождение —
  предикат для гейта, а не отчёт аудитора. Восемь родов; `COUNT_MISMATCH` и
  `CONTENT_MISMATCH` разведены намеренно: второй — тихая порча при совпавшем счёте.
  Отсутствие любого слоя — `InvalidInventoryError`, а не тихий вердикт.
- **b2** — [`archivarius-restore-drill.mjs`](../../../scripts/archivarius-restore-drill.mjs),
  глагол `yarn backup:restore-drill`. Оркестрация без единого правила сравнения: обе описи
  снимаются **одним конвейером**, вердикт приходит из ядра.
- **b3** — провал уходит долгом попугая; README стенда объясняет разницу между дампом и
  откатом, три слоя таблицей и почему том свой.

Зубов: **23** на две семьи, все зелёные.

## Три решения исполнителей, отклонённые по факту

1. **Второй compose-файл для цели** — работы там нет. Изоляция достигается **именем
   проекта**: `docker compose -p archivarius-restore-drill config` даёт том
   `archivarius-restore-drill_…`, у источника `archivarius-dump-proof_…`. Проверено до кода.
2. **Хеш через `$out` во временную коллекцию** — `$out` **пишет** в базу, которую мы меряем.
   Мерка не имеет права менять предмет. Взят канонический EJSON документов, отсортированных
   по `_id`.
3. **Автоматический доклад партнёрам без owner-gate** — прямо против CLAUDE.md: всякая
   ласточка требует явного «ок» владельца, и инструмент не вправе обходить гейт сам.
   Третий канал вынесен развилкой владельца и назван в README.

## Шероховатости

1. **Лента долгов отказала на первой попытке — по делу.** Норма M6: рождение только с родом
   происхождения из закрытого списка. Я передал `backup:restore-drill`, лента потребовала
   один из пяти. Исправлено на `detector`: прогон меряет состояние, а не высказывает мнение.
2. **Времена в следах я ставил «на глаз» трижды за два дня** — и трижды они оказывались из
   будущего либо мимо факта. Каждый раз правил по `op-log` и часам. Закономерность признаю:
   отметку следа надо брать из источника (op-log, `date -u`), а не из головы — как и всё
   остальное в этом контуре.
3. **Выход за зону b3**: запись долга живёт в скрипте прогона (зона b2) — иначе провод не
   подключить. Объявлено в следе заранее.
4. **Точность нарезки 66.7%**: b2 переполнил оценку, b3 оказался вдвое меньше — снятый
   compose-файл.

## Что вне границ

- Врезка прогона в цепочку дампа («каждый дамп зовёт откат») — решение резчика принято, но
  вынесено: сначала прогон должен быть зелёным сам по себе, иначе цепочка дампа встанет на
  первом же красном.
- Прод-прогон на живом томе: спринт доводит до зелёного на синтетике, живой жест — по
  чек-листу владельца.
- Замена источника описи (`mongodump-stderr` → `archive-contents`) — [#1814](https://github.com/officefish/Membrana/issues/1814).
- Аутентификация Mongo (#1753), соседние тома — свои карточки.
