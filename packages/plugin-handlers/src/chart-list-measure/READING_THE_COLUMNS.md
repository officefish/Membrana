# Как читать «превышение над фоном» и «пик»

> Написано 23.08 после того, как я истолковал разность двух столбцов ЗАДОМ НАПЕРЁД и был поправлен
> координатором по одной арифметике, без доступа к коду. Толкование, которое не выводится из формул
> явно, — догадка; поэтому формулы теперь лежат рядом с колонками.

## Две формулы дословно

**Превышение над фоном** — [`session-metrics/index.ts`](../session-metrics/index.ts), `dbOverFloor`:

```
превышение = 20·log10(L / фон),   L = loudest.peak
```

`L` — НЕ пик, несмотря на имя поля. Это `frameLoudness` самого громкого кадра события:
`max(RMS_кадра, пик_кадра × 0.45)` ([`metrics.ts`](../../../services/fft-analyzer/src/math/metrics.ts)).

**Пик** — [`executor.ts`](./executor.ts), `peakDbFs(truePeakOf(...))`:

```
пик = 20·log10(P),   P = max|отсчёт| по всему окну события
```

## Разность двух столбцов

```
D = превышение − пик = 20·log10(L/P) − 20·log10(фон)
```

Фон у выборки ОДИН на все строки, значит `20·log10(фон)` — общее слагаемое, и **D меняется только
вместе с отношением L/P**.

**Верхняя граница.** `RMS ≤ пик_кадра` и `0.45·пик_кадра ≤ пик_кадра`, а окно события содержит этот
кадр целиком, поэтому `L ≤ P` всегда. Отсюда `20·log10(L/P) ≤ 0` и `D ≤ −20·log10(фон)`.

## Что показал прогон 23.08

Восемнадцать строк из двадцати дали **ровно 39.1** (#15 — 39.0, округление). Одинаковость означает,
что у всех восемнадцати L/P одно и то же: победила ветвь `пик × 0.45`, а пик громчайшего кадра
совпал с истинным пиком окна. Тогда `L/P = 0.45` точно, `20·log10(0.45) = −6.94`, и

```
−20·log10(фон) = 39.1 + 6.94 = 46.04   →   фон ≈ 0.00499
```

Совпадение отношения с литералом `peakWeight = 0.45` до двух знаков — само по себе проверка: столбцы
считаются теми формулами, что записаны выше, а не какими-то другими.

Побочно: 0.005 НИЖЕ литерала-заглушки `estimateNoiseFloor` (0.01), то есть фон здесь измерен, а не
подставлен по умолчанию.

## #14 — почему это НЕ транзиент

`#14` дал `D = 41.5` — на 2.4 дБ БОЛЬШЕ обычного. Фон общий, значит у него `L/P` ВЫШЕ:

```
20·log10(L/P) = 41.5 − 46.04 = −4.54   →   L/P = 0.593 = 0.45 × 1.32
```

`L/P > 0.45` возможно ровно одним способом: в `max(RMS, пик×0.45)` **победил RMS**. То есть
`RMS/P = 0.593`, крест-фактор `P/RMS = 1.69` (4.54 дБ) — при том, что весу 0.45 отвечает крест 6.94 дБ,
а чистой синусоиде 3.01 дБ.

**Значит #14 — самый ПЛОТНЫЙ и наполненный звук выборки, а не самый резкий.** Из двадцати он один
настолько сплошной, что среднеквадратичное обошло пиковую оценку. Это ближе всего к дрону, и критерий
«похожесть на дрон» взял его не вопреки замеру, а в согласии с ним — крест-фактор подтверждает отбор
независимой величиной.

**Ошибочное толкование, ради которого написан файл.** Я прочёл 2.4 дБ как «истинный пик оказался выше
покадровой оценки, значит резкий удар». Направление не сходится: транзиент увеличивает `P`, то есть
УМЕНЬШАЕТ `L/P` и уводит `D` НИЖЕ 39.1. Ни одна из двадцати строк ниже 39.1 не ушла — **транзиентов в
этой выборке нет вовсе**.

**И #14 же опровергает фон 0.0111.** Такое значение выводится из 39.1, если считать `L = P`, то есть
забыв про вес 0.45. Но при `фон = 0.0111` граница `D ≤ −20·log10(0.0111) = 39.09` запрещает строке
41.5 существовать. Строка существует — значит фон меньше.

## Правило чтения

| D | что это значит |
|---|---|
| ровно 39.1 | обычный крест: громкость взята как `пик × 0.45` |
| **больше** 39.1 | звук ПЛОТНЫЙ, RMS обошёл пиковую оценку — тем плотнее, чем больше отклонение |
| **меньше** 39.1 | резкая атака: истинный пик выше того, что видит кадр |

Сам по себе столбец пика для восемнадцати строк из двадцати **выводится** из превышения вычитанием
константы. Смысл в нём ровно там, где отклонение есть.

## Долг: фон измеряется, но до человека не доезжает

Измеритель возвращает `floor: { value, measured }` — фон ЕСТЬ числом. В кабинет он не передаётся и
нигде не показан, поэтому его приходится восстанавливать арифметикой из двух столбцов, как сделано
выше. Показанный фон снял бы и этот разбор, и спор о 0.0111. **Названо, не чинится.**
